# 00.13 — Spec Claim Verification and Research Delegation

**Set:** 00-dev-loop · **Queue:** 13 · **Depends on:** 00.01, 00.06, 00.07, 00.08
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-claims`

## Summary

Coordinates the pre-implementation claim verification stage of the development loop. Before test authoring or code implementation begins on an approved piece, this service extracts and checks all load-bearing claims (repository facts, pinned dependency APIs, external behaviours, performance/quota numbers, and negative existence claims) by delegating verification briefs to a read-only Research preset. Verified findings are recorded into the piece's `## Resources and proof` table, keeping direct inspection distinguishable from reported research and unverified claims. When verification contradicts the specification, execution halts immediately: neither silent correction nor building on false claims is permitted; the piece is amended first before work resumes.

## Behaviour

- **Given** an approved piece with a load-bearing claim regarding a pinned dependency API **When** claim verification delegates the brief to the Research preset and valid source citation is returned **Then** the claim is marked verified and recorded in `## Resources and proof` with citation and `reported by Research`.
- **Given** a piece claiming an export or framework seam exists **When** the Research preset verifies the codebase and proves the symbol does not exist **Then** verification detects a contradiction, halts work immediately, transitions status to `blocked`, and emits `piece/contradicted`.
- **Given** a claim whose veracity cannot be established against available sources or hardware **When** verification finishes without definitive proof **Then** the claim is marked `UNVERIFIED` in `## Resources and proof`, execution proceeds, and dependent implementation is flagged to disclose this in its completion report.
- **Given** a Research preset returning verified evidence with file and symbol citations **When** the orchestrating agent records the finding in the piece **Then** the provenance records `reported by <role, preset>` rather than `direct inspection`, keeping specialist findings distinct from direct orchestrator inspection.
- **Given** a piece containing a negative existence claim asserting a capability does not exist **When** verified **Then** the Research preset executes an exhaustive symbol search across repo and dependency exports before certifying absence, preventing redundant code creation.
- **Given** a contradicted claim where an agent attempts silent correction during implementation **When** evaluated **Then** the loop rejects execution, enforcing that the piece specification itself must be amended and re-approved before work resumes.

## Harness fit

This is a `Service Provider` mounted on the host plane (`ctx.devLoopClaims`) extending `@deepseek-ai/cordis.Service`. It consumes `ctx.devLoopRoles` (`00.06`) to dispatch read-only-scoped Research subagents under `ctx.devLoopResearchGuard` (`00.07`), updates piece markdown via `ctx.fs`, and emits serial lifecycle veto events (`'piece/claims-verified'`, `'piece/contradicted'`).

## Contracts

```typescript
export type ClaimKind =
  | 'repository_fact'
  | 'dependency_api'
  | 'external_behavior'
  | 'performance_quota'
  | 'negative_existence'

export type ClaimStatus = 'verified' | 'contradicted' | 'unverified'

export interface VerificationBrief {
  claimId: string
  pieceId: string
  claim: string
  kind: ClaimKind
  decisionRestingOnClaim: string
  permittedSources: readonly string[]
  readOnlyScope: true
  budget: { maxTokens?: number; maxToolCalls?: number; timeoutMs?: number }
  requiredEvidence: { file?: boolean; symbol?: boolean; docSection?: boolean; pinnedVersion?: boolean }
}

export interface VerificationFinding {
  claimId: string
  claim: string
  status: ClaimStatus
  citation: string
  howEstablished: 'direct inspection' | `reported by ${string}` | 'measured' | 'UNVERIFIED'
  checkedAgainst: string
  evidenceSummary: string
  contradictionReason?: string
}

export interface ClaimVerificationReport {
  pieceId: string
  allPassed: boolean
  hasContradictions: boolean
  findings: readonly VerificationFinding[]
}

export interface DevLoopClaims {
  verifyPieceClaims(pieceId: string): Promise<ClaimVerificationReport>
  recordProofTable(pieceId: string, findings: readonly VerificationFinding[]): Promise<void>
}

declare module '@deepseek-ai/cordis' {
  interface Events {
    'piece/claims-verified': (event: { pieceId: string; report: ClaimVerificationReport }) => void
    'piece/contradicted': (event: { pieceId: string; finding: VerificationFinding }) => void
  }
}
```

## Teach me while you build

- **Background**: Specifications are hypotheses, not infallible truth. Spec authors hallucinate APIs, cite drifting line numbers, and assume packages export features they do not. Implementing a wrong spec faithfully produces defects. Claim verification is an upfront gate that tests factual claims before tests or code are authored.
- **How it works here**: Mounted as `ctx.devLoopClaims`, the service extracts claims from approved pieces (`00.03`). For each claim, it compiles a `VerificationBrief` defining the claim, the dependent architectural decision, permitted sources, and required citations. It invokes the `Research` role via `ctx.devLoopRoles.delegate`, enforced read-only by `00.07`. If verification succeeds, findings are written to `## Resources and proof`. If a contradiction occurs, the loop halts immediately: the piece transitions to `blocked` (`00.02`), `piece/contradicted` fires, and neither test authoring nor implementation begins until the specification is amended. Open `packages/dev-loop/claims/src/index.ts`.
- **Why this approach**: Upfront claim verification via delegated read-only research. The simplest alternative is letting implementers discover errors while coding, but implementers frequently hack around discrepancies or build broken assumptions into tests. Halting at spec contradiction preserves architectural integrity.
- **Approaches considered**: (1) *Delegated Research subagent with structured brief (chosen)*: Decouples verification from orchestrator context; enforces read-only safety. (2) *Orchestrator inlines all checks*: Fast for trivial files but pollutes orchestrator context and invites hallucinated confirmations. (3) *Post-implementation verification*: Discovers contradictions only after code is written, wasting work and tainting git history. (4) *External static analyzer (cargo-vet / osv-scanner pattern)*: Excellent for known vulnerability CVEs, but incapable of verifying semantic repo facts or negative existence.
- **Prior art inspected**: `cargo-vet` (Mozilla/Rust, MIT) separates code auditing into explicit cryptographic supply-chain criteria; adapted its distinction between verified, unverified, and trusted assertions. RFC 2119 (IETF) strictness conventions for conformance verification.
- **What we get for free**: `ctx.devLoopRoles` handles subagent lifecycle; `00.07` guarantees the verifier cannot mutate files.
- **From the docs**: `plans/AGENTS.md`: "When verification contradicts the piece: STOP and report the contradiction with its evidence... Neither silently implementing the corrected version nor implementing the wrong version is acceptable."
- **What to notice**: Negative existence claims ("feature X does not exist") require broad search across symbols and exports, because an erroneous negative claim justifies writing redundant duplicate code.
- **Concepts to own**: *Epistemic provenance* (tracking evidence origin), *Precondition verification* (proving spec assumptions before execution), *Fail-stop semantics* (immediate halt upon contradiction), *Negative proof burden* (exhaustive search for non-existence).
- **Interview angle**: *"How do you prevent autonomous agents from implementing hallucinated designs?"* Gate implementation behind factual claim verification: extract load-bearing claims, delegate verification to a sandboxed read-only agent, require exact file:line or pinned version evidence, and fail-stop on contradiction.
- **Decisions you can now make alone**: Adding new claim categories to `ClaimKind`; tuning budget limits in `VerificationBrief`; formatting markdown table rows. **Escalate:** altering the contradiction fail-stop policy; bypassing read-only guards.
- **Lesson**: Never let an agent build on an unverified assumption; verifying the specification first is ten times cheaper than debugging a faithful implementation of a lie.
