# 00.03 — Approval Junction and User Clarification

**Set:** 00-dev-loop · **Queue:** 3 · **Depends on:** 00.01, 00.02
**Status:** todo
**Harness primitive:** model-facing tool · **Package:** `@deepseek-ai/dsh-dev-loop-approval`

## Summary

Presents one specification piece to the human before work starts and returns an explicit Accept, Question, or Change decision. Acceptance invokes the lifecycle's compare-and-set transition from todo to pending. Questions and revision instructions return to the orchestrator without queuing work.

The owner sees the full source, including teaching, alternatives, References, and Resources and proof. Approval is not inferred from prose. This package is not implemented yet, and no dev-loop preset is mounted; the behavior below is the proposed test contract.

## Behaviour

- **Given** a valid todo piece and a live root caller **When** the tool executes **Then** it displays the piece markdown in a generic two-question batch: decision, then optional feedback.
- **Given** the teaching section lacks `Approaches considered` or `Prior art inspected` **When** it is displayed **Then** a warning names each missing subsection without removing the original source.
- **Given** exactly one Accept selection with no custom text in the decision answer **When** cancellation and file freshness checks succeed **Then** the tool invokes `transition(pieceId, 'todo', 'pending')` and returns `accept` only after that transition succeeds.
- **Given** Question or Change **When** the human submits **Then** the corresponding decision and optional feedback return without a lifecycle write.
- **Given** a skipped, duplicate, unknown, custom-only, or multi-label decision **When** it is received **Then** execution fails with `APPROVAL_DECISION_REQUIRED` and does not transition. Optional feedback alone never authorizes work.
- **Given** an absent piece **When** lookup runs **Then** `PIECE_NOT_FOUND` is reported before prompting. A malformed existing piece preserves `PieceParseError` rather than being reported as absent.
- **Given** the piece is not todo **When** execution begins **Then** it fails with `PIECE_NOT_APPROVABLE` before prompting. If the status changes during review, the lifecycle compare-and-set still rejects stale acceptance.
- **Given** the source changes while the human reviews it **When** acceptance arrives **Then** execution fails with `PIECE_REVIEW_STALE` and requests a fresh presentation; acceptance is not applied to a different document.
- **Given** no calling agent **When** execution begins **Then** `CALLER_NOT_LIVE` is reported. A supplied agent must pass the existing question service's exact-live-root checks; owned children fail with `DELEGATED_CALLER`.
- **Given** cancellation, provider failure, or plugin disposal while waiting **When** the wait settles **Then** no lifecycle write occurs and owned work is awaited. Replacing the plugin must not allow an old unanswered call to approve later.
- **Given** the process restarts during review **When** session repair runs **Then** it records an interrupted tool result, not an automatic re-presentation. A new model call may present the piece again if its lifecycle status is still todo.

## Harness fit

A function plugin exports `name`, `inject`, and `apply`, registers through `ctx.tools.register(defineTool(...))`, and publishes no service. Inject `tools`, `userQuestions`, `devLoopDirectory`, `devLoopLifecycle`, and `fs`. Shared providers belong in the host composition; this consumer may be mounted in a session preset.

`PieceRecord` has metadata, summary, scenarios, and warnings, but not teaching or References bodies. Resolve its path with `fs.resolve(record.path, { signal })`, then use `fs.readText(target, signal)`. Observe the file version before reading and reject a changing read. Revalidate the actual text through `devLoopDirectory.validate(record.path, content)` before presentation rather than trusting the earlier scan's line count. That public method uses the directory's resolved parsing options, so no new validation API or copied defaults are needed. Require the newly validated id to equal the requested id; otherwise report `PIECE_REVIEW_STALE`.

`UserQuestionService.ask` validates requests and dispatches an answerer waterfall. The browser provider renders markdown detail in a scrollable viewport without truncating the transferred source. The currently shipped browser answerer is not a promise that every deployment has an answerer: unclaimed requests fail with `NO_PROVIDER`.

The generic composer always offers custom text for an optioned question. In single-select mode, custom text clears the selected label. Two questions preserve the separation of decision and feedback but cannot disable custom text on the first question. The tool must reject invalid decision answers explicitly. Do not use `plan-review` intent: its specialized UI requires one binary question, whereas this junction has three choices and a feedback question.

`exit_plan_mode` is a useful example of markdown detail and cancellation handling, not a three-way feedback implementation. Its specialized card's Discuss action cancels the request so the human can speak separately.

Approval is currently a lifecycle memory update plus an announcement, not a durable approval record. 00.12 must bind accepted evidence to the reviewed content and preserve it before the full loop is restart-safe. A final file-version check narrows the review race but does not make filesystem content and an in-memory lifecycle update one transaction; durable revision-bound approval remains an integration requirement.

## Contracts

```typescript
export type ApprovalDecision = 'accept' | 'question' | 'change'
export interface PresentPieceResult {
  pieceId: string
  decision: ApprovalDecision
  feedback?: string
}
```

Tool name: `present_piece_for_approval`. Parameters: one required string `pieceId`. Output: a strict object with required `pieceId`, required decision enum, and optional feedback string. Use `defineTool` for typed arguments, JSON validation, and pure `output.render`; the renderer returns the canonical JSON value as text. A complete raw definition can also register, but partial objects without output schema/render are rejected. `execute` is required by the typed definition, not checked by `ToolRuntime.register` at runtime.

Question ids: `decision` and `feedback`. Decision labels are exactly `Accept`, `Question`, and `Change`, with single-select semantics. Require exactly one answer for `decision`, exactly one matching selected label, and no custom decision text. Allow an absent/skipped feedback answer; if present, trim its custom text and omit an empty result. Duplicate feedback answers fail with `APPROVAL_DECISION_REQUIRED` rather than choosing arbitrarily.

Pass the caller and the operation signal to `ask`; never omit the agent to bypass liveness validation. Check cancellation immediately before committing the lifecycle transition. A stale lifecycle rejection must not be rendered as a successful acceptance.

Missing-teaching detection applies only inside `## Teach me while you build`, outside code fences. Recognize either a markdown subheading or a bold list label named `Approaches considered` or `Prior art inspected`. Append `Review warning: missing teaching subsection: <name>.` for each absent subsection to the displayed detail. This is consumer behavior, not validation the directory already provides.

## Teach me while you build

- **What it does:** puts a human decision before an automated work queue rather than guessing approval from conversational text.
- **Background:** a structured result records explicit fields. A human-in-the-loop wait suspends one tool call; it is not itself a durable checkpoint. A compare-and-set checks that the state observed before the wait still permits the write afterward.
- **How it works here:** the tool reads and validates a piece, asks the root session's answerer, validates the exact selected label, checks freshness, and calls the lifecycle writer. Provider errors, questions, and changes do not approve anything.
- **Why this approach:** reuse the existing answerer rather than build a new browser panel. A custom panel is preferable only if required interactions cannot be expressed by the question API; its maintenance and localization costs are otherwise unnecessary.
- **Approaches considered:** existing generic question batch (minimal integration); a dedicated review UI (better constrained decision/feedback controls, more client work); LangGraph checkpointed interrupts (durable resumability but a different orchestration/persistence stack). Plain chat remains suitable for nonbinding clarification, not for inferring authorization.
- **Prior art inspected:** the orchestrator read the official LangGraph interrupt guide at `https://docs.langchain.com/oss/python/langgraph/interrupts.md`, not its implementation. It requires a checkpointer and thread id for resumability. No external code was copied.
- **What we get for free:** `defineTool` supplies argument/output validation and schema projection, Cordis owns registration cleanup, and the browser provider owns rendering and pending-question lifetime. We own piece lookup, warning text, exact decision validation, and the lifecycle write.
- **From the docs:** LangGraph's interrupt guide says “The function accepts any JSON-serializable value which is surfaced to the caller.” This supports separating display data from execution, but does not confer LangGraph's persistence guarantees on a DSH question promise.
- **What to notice:** an optional UI field can change the answer encoding. Validate the answer actually returned, not the interaction you hoped the user would choose.
- **Concepts to own:** authorization (explicit acceptance); optimistic concurrency (status/content checks after a long wait); separation of concerns (presentation versus state mutation); replay safety (interrupted tools are not automatically re-executed).
- **Interview angle:** “What if the document changes while approval is pending?” Reject the stale review and present again; do not approve unseen content. Follow-up: how do you close the final check/write race? Use revision-bound durable authority, which remains required in 00.12.
- **Decisions you can now make alone:** improve question descriptions or add validation tests without weakening exact acceptance. Escalate changes to approval meaning, restart behavior, or new UI controls to the owner.
- **What you should learn from this:** a structured UI is useful only when the executor validates its returned decision and binds it to the work being authorized.

## Acceptance

1. Tests validate source display, teaching warnings, exact Accept/Question/Change answers, optional feedback, and rejected ambiguous decisions.
2. Only an explicit valid Accept can invoke todo → pending, and only after source freshness and cancellation checks. Lifecycle races surface as errors, not accepted results.
3. Missing/malformed files, non-todo state, missing/non-root caller, provider failure, and cancellation cause no approval mutation.
4. Plugin disposal removes the tool and settles owned waits without later approval; a real Loader composition and model-visible result snapshot demonstrate the integration.
5. Full-loop acceptance additionally requires durable revision-bound approval and an observed UI demo through the mounted 00.14 preset; neither is claimed by isolated unit tests.
