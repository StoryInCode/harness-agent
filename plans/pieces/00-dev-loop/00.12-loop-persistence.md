# 00.12 — Dev Loop Storage Domain Persistence

**Set:** 00-dev-loop · **Queue:** 12 · **Depends on:** 00.02, 00.04, 00.06
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-persistence`

## Summary

Defines and manages the durable `dev_loop` storage domain via `ctx.storageDomain`. It declares schema-validated tables for piece execution states, approval junction records, queue entries, and delegation logs, so development-loop state survives host reboots, session drops, and worker restarts without inventing a private database or ad-hoc JSON files. For completed pieces the durable record carries the relocated file path (`<set>/done/<id>-<slug>.md`). On startup the service reconciles against the physical filesystem: where record and disk disagree, the filesystem location governs — a `done` record whose file is still in the set root reverts to `pending`, and a file already in `done/` promotes a stale record.

The domain is **key/value, not relational**. `domainTable(schema)` yields `{ valueSchema }`, and `open` loads each table into a `Map<string, unknown>` behind a handle with `get`, `entries`, `keys`, `put`, `update`, and `delete`. There is no query builder and no migration runner. Every read is a synchronous in-memory read, and every ordering this piece needs — `queue.position`, the per-piece history — is **derived in memory from `entries()`**, never queried. Changing a stored schema is a hand-written migration, not a framework feature.

## Behaviour

- **Given** an updated piece status or new delegation record **When** persisted **Then** records are written to `ctx.storageDomain` under domain `dev_loop`.
- **Given** a piece completing to `done` **When** persisted to `dev_loop` **Then** the `pieces` table updates `status` to `done` and stores the relocated path under `<set>/done/<id>-<slug>.md`.
- **Given** a host process restart **When** the `dev_loop` domain opens **Then** all piece states, approval logs, and active queue positions are restored.
- **Given** a host restart where a piece record claims `done` but the physical file remains in the set root **When** startup reconciliation executes **Then** the record status reverts to `pending`, preventing phantom completion and ensuring state and filesystem never diverge.
- **Given** a host restart where a piece file is physically in `<set>/done/` but the database record is stale **When** startup reconciliation executes **Then** the record status is updated to `done` with its new path in `done/`.
- **Given** a stored record that fails its zod schema **When** the domain opens **Then** the open rejects with `DomainError` code `invalid-record`, naming the table and key, and no handle is returned.
- **Given** a piece id **When** its history is assembled **Then** approvals, delegations, and queue entries are collected by iterating each table's `entries()` and filtering in memory, because the domain exposes no query language.
- **Given** several queued pieces **When** dispatch order is needed **Then** `queue.position` is sorted in memory from `entries()`; positions are values in a key/value table, not an index.
- **Given** a backend that rejects a write **When** the mutation is attempted **Then** the in-memory state is left untouched and the write rejects, so a read never reflects a value the medium refused.

## Harness fit

This is a `Service Provider` extending `@deepseek-ai/cordis.Service` on the host plane (`ctx.devLoopPersistence`). It opens the `dev_loop` domain via `ctx.storageDomain.open(devLoopDomainSpec)` (`DomainFacility.open`, `packages/storage/storage-domain/src/index.ts`), obeying META AXIOM item 6 rather than inventing private persistence. The **caller owns the handle**: this service closes it on disposal, and the name frees for reopening only after that teardown completes.

The durability contract this piece builds on, from `packages/storage/storage-domain/README.md`: *"Memory is authoritative; the medium is the durable projection."* Every write queues on **one per-domain write chain** in the order **backend durability first, then the memory mutation, then `domain/changed`**. A rejected backend write leaves memory untouched, so reads never diverge from the medium. `put`, `delete`, `update`, and `global.set` share that chain, and `update`'s transform runs at its chain slot, so concurrent updates cannot interleave. `domain/changed` is *"a notification, not a transaction participant: a throwing listener is contained with a logged warning rather than rejecting the already-durable write"* — so nothing this piece does may treat that event as a commit vote, and a consumer that must not miss a change reads the table rather than counting events.

Reconciliation is **observe-and-correct-the-record only**. `ctx.fs` has no rename, move, or delete, so startup may `resolve`, `stat`, and `listDir` to find where a piece file really is and then fix the record; it may not move a file to match a record. Moving files belongs to 00.02's `git mv`.

## Contracts

```typescript
import { defineDomain, domainTable } from '@deepseek-ai/dsh-storage-domain'
import { z } from 'zod'

/**
 * `defineDomain(spec)` takes ONE argument and requires `name` AND `version`;
 * both are validated at module load, so a malformed spec fails the mount.
 * Table keys are the `Map` keys: `pieces` is keyed by piece id, `approvals`
 * and `delegations` by a minted event id, `queue` by piece id.
 */
export const devLoopDomainSpec = defineDomain({
  name: 'dev_loop',
  version: 1,
  tables: {
    pieces: domainTable(z.object({
      id: z.string(),
      status: z.enum(['todo', 'pending', 'done', 'blocked']),
      path: z.string(),
      updatedAt: z.number(),
    })),
    approvals: domainTable(z.object({
      pieceId: z.string(),
      decision: z.enum(['accept', 'question', 'change']),
      feedback: z.string().optional(),
      timestamp: z.number(),
    })),
    queue: domainTable(z.object({
      pieceId: z.string(),
      position: z.number(),
      status: z.enum(['queued', 'dispatched', 'blocked']),
    })),
    delegations: domainTable(z.object({
      pieceId: z.string(),
      role: z.string(),
      preset: z.string(),
      rationale: z.string(),
      outcome: z.string().optional(),
      timestamp: z.number(),
    })),
  },
})

export interface DevLoopPersistenceService {
  /**
   * Compare each record's `path` against the filesystem and correct the
   * RECORD. Never moves a file: `ctx.fs` has no rename, move, or delete.
   * @returns the corrections applied, for the startup log.
   */
  reconcileWithFilesystem(): Promise<readonly { pieceId: string; from: string; to: string }[]>
  /**
   * Queue entries in dispatch order, sorted in memory from the table's
   * `entries()`. The domain has no ORDER BY; ordering is ours.
   */
  queueInOrder(): readonly QueueRow[]
}
```

`version: 1` is the format stamp reads enforce. A later schema change bumps it and either lists the old number in `compatibleVersions` — which the current record schemas must genuinely accept, typically by declaring new fields optional — or migrates the stored data by hand. `invalidRecords` is deliberately left absent: these records are authoritative, so a record that fails its schema must reject the whole open rather than be skipped.

## Teach me while you build

- **Background**: A *storage domain* here is a named, schema-validated key/value store: tables of records, each table a `Map` from a string key to a zod-validated value. A *write chain* is a queue that serialises writes so two callers cannot interleave. *Durable before resolve* means a write's promise settles only after the backend has acknowledged the data, so a resolved write survives a crash. None of this is SQL: there is no query planner, no index, and no join.
- **How it works here**: Mounted on `ctx.devLoopPersistence`, the service calls `ctx.storageDomain.open(devLoopDomainSpec)` once and keeps the handle, closing it on disposal. Four tables load into memory, every record validated against its zod schema — a bad record rejects the open with `invalid-record` naming the table and key. Reads are synchronous `get`/`entries` calls against that memory. A write goes on the domain's single chain: the backend makes it durable, then memory changes, then `domain/changed` announces it. On startup, `reconcileWithFilesystem()` resolves each record's `path` through `ctx.fs` and corrects the RECORD in whichever direction disk dictates. Open `packages/dev-loop/persistence/src/index.ts` next to `packages/storage/storage-domain/src/domain.ts`.
- **Why this approach**: The filesystem is ground truth for completion because 00.02 makes the `git mv` the commit point; the record is a projection of it. The simplest alternative — trusting the record — reports pieces done whose files never moved.
- **Approaches considered**: (1) *One storage domain, chosen* — the axiom's sanctioned mechanism, validated at open, durable per write, and free of migration machinery we would have to operate. (2) *Session events plus a projection*, which is the neighbouring durable mechanism in this repository; correct when the facts belong to one conversation's history, wrong here because loop state outlives any session and is queried across sessions. (3) *A hand-rolled JSON file*, which META AXIOM item 6 forbids outright and which would re-derive atomic write, validation, and crash-safety badly. (4) *An embedded SQL database* — real ordering and indexes, and it would win if the loop ever needed multi-table queries over thousands of pieces; today the corpus is around 120 records, so an in-memory sort costs nothing and a dependency would buy an operational burden.
- **Prior art inspected**: None external; no outside project was opened for this piece. The in-repository authorities read were `storage-domain`'s `spec.ts`, `domain.ts`, and README.
- **What we get for free**: Named-unit routing to a configured backend, load-time validation of every stored record, durable-before-resolve writes on one serialised chain, contained `domain/changed` notification, and facility-owned teardown. Explicitly NOT provided, contrary to this piece's first draft: **connection pooling, a query builder, and a migration runner**. `version`/`compatibleVersions` declare which stored versions are ACCEPTED; they do not transform data. Ordering, filtering, history assembly, and any future migration are ours.
- **What to notice**: `queue.position` cannot be selected in order — sort it from `entries()` in `queueInOrder()`, in one place, so no caller invents a second ordering. And read the write chain's order once: durability, then memory, then event. That is why a failed write cannot leave a phantom value in a reader's hands.
- **Lesson**: "Durable storage" and "a database" are not the same promise. Check which operations a store actually offers before designing against SELECT, ORDER BY, or automatic migration — a key/value domain gives strong durability and no query power, and a design that assumes otherwise fails at the first sort.

## Reuse capture

- **Reuse candidate**: Startup reconciliation of a durable record against the filesystem it describes · Reads where an artifact really is and corrects the record, never the file, in whichever direction disk dictates · Used in `reconcileWithFilesystem` · Reusable wherever a durable index tracks files a separate commit point moves — build outputs, uploads, archived artifacts · Would need the path derivation and the correction policy lifted into parameters · Evidence: the reconciliation cases in `packages/dev-loop/persistence/tests/persistence.spec.ts` · Confidence: medium
- **Anti-pattern worth keeping**: Assuming "storage domain" means "database". This piece claimed connection pooling, query building, and schema migrations from a store that has none, and wrote a two-argument `defineDomain` that does not exist. A store's README `Known Limitations` section is the cheapest place to find out what you are not getting.
- **Known limitations**: Requires `ctx.storageDomain` on the host plane. No query language: every filter and ordering is an in-memory pass over `entries()`, which is fine at corpus scale and would not be at millions of records. No migration: a schema change is hand-written. `domain/changed` is in-process only, so a second host process or a reconnecting GUI sees no change notification.

## Acceptance

1. Unit tests in `packages/dev-loop/persistence/tests/persistence.spec.ts` pass, covering `open`, `put`/`update`/`delete`, and `get`/`entries` on all four tables.
2. `devLoopDomainSpec` is constructed by a single-argument `defineDomain` carrying `name: 'dev_loop'` and `version: 1`; a spec omitting `version` or passing two arguments fails to compile, and a spec with a negative version throws at module load.
3. State survives closing and reopening the domain, and the reopened handle returns the same records.
4. Completed pieces persist their relocated `<set>/done/` path in the `pieces` table.
5. Startup reconciliation reverts a `done` record to `pending` when the file is still in the set root, and promotes a stale record when the file is already in `<set>/done/`; it performs no filesystem mutation in either case.
6. A stored record failing its zod schema rejects `open` with `invalid-record` naming the table and key.
7. `queueInOrder()` returns entries sorted by `position` from an unordered table, and is the only place that sort appears.
8. A rejected backend write leaves the in-memory value unchanged, asserted by reading the table after the rejection.
9. A listener that throws on `domain/changed` does not fail the write that emitted it.
