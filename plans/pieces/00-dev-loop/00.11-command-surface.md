# 00.11 — Human Command Surface `/dev-loop`

**Set:** 00-dev-loop · **Queue:** 11 · **Depends on:** 00.01, 00.02, 00.04
**Status:** todo
**Harness primitive:** command · **Package:** `@deepseek-ai/dsh-dev-loop-command`

## Summary

Registers the command named `dev-loop` on `ctx.commands`, giving the human operator an out-of-turn control surface for the development loop. Supports subcommands to inspect piece statuses (`list`, `show`), check the dispatch queue and running workers (`queue`, `status`), and approve or reject pieces (`approve`, `reject`), without waiting for an agent turn or spending model tokens.

Two facts about the real command seam shape this piece. The registered name has **no leading slash**: `COMMAND_NAME = /^[a-z][a-z0-9_-]*$/u`, so the registration is `dev-loop`, and `/dev-loop` is only how a user types it — `parseCommand` strips the slash before dispatch. And the runtime supplies **no argument parser and no completion**: the handler receives `rawInput`, the exact text following the command name, and **returns** a `CommandResult` rather than printing. Parsing `approve 00.03` into a subcommand and a piece id is therefore this piece's own work, and is specified here as such.

## Behaviour

- **Given** an active session **When** the user submits `/dev-loop status` **Then** the handler receives `rawInput` `" status"` and returns `{ kind: 'success', text }` reporting active workers against the configured ceiling, queue length, and piece counts by status.
- **Given** an approved piece waiting in the queue **When** the user submits `/dev-loop queue` **Then** the returned success text lists every queued piece with its position and dependency state.
- **Given** a piece in `todo` status **When** the user submits `/dev-loop approve 00.03` **Then** this piece's own parser splits `rawInput` into subcommand `approve` and argument `00.03`, the lifecycle transition to `pending` is recorded, and a success result names the new status.
- **Given** a piece identifier **When** the user submits `/dev-loop show 00.03` **Then** the returned success text carries the piece's summary and its Given/When/Then scenarios.
- **Given** an unknown subcommand, a missing argument, or an unknown piece id **When** the handler runs **Then** it returns `{ kind: 'error', text }` whose non-empty text names the fault and the accepted subcommands — it does not throw, and it does not print.
- **Given** `/dev-loop` submitted with no input at all **When** the handler runs **Then** it returns the usage text as a success result, because listing what a command accepts is not an error.

## Harness fit

This is a `command` registered on `ctx.commands` (`CommandRuntime.register`, `packages/interaction/commands/src/index.ts`). It runs on the host plane outside model turns, giving the operator visibility and authority without consuming model tokens.

`register(definition)` returns the exact disposer, and `normalizeDefinition` validates the definition at registration: the name against `COMMAND_NAME`, a non-empty string `description`, a function `handler`, and — when present — an `input` descriptor carrying a non-empty `hint` string and an optional `attachments` boolean. That descriptor is the ONLY input metadata the seam has: a `hint` is placeholder text for a composer, not a grammar the runtime enforces. This piece declares `input: { hint: 'status | list | queue | show <id> | approve <id> | reject <id> <reason>' }` and parses `rawInput` itself.

The handler returns; it never prints. `normalizeResult` accepts `{ kind: 'success', text?, sourceEventSeq? }` or `{ kind: 'error', text }` with non-empty text, freezes it, and rejects anything else with a `TypeError` — so a handler that returned nothing would fail at the registry boundary. Because output is a returned value, every operator action is reconstructable from the `command/run` / `command/done` session records rather than from terminal scrollback.

## How to see it

In an active CLI or chat session, type the command with its leading slash (the registration itself carries none):
```text
/dev-loop status
```
The returned success text renders as:
```text
Dev Loop Status:
  Active workers: 2 / 4 (configured ceiling)
  Queue: 3 queued [00.03, 00.04, 00.05]
  Pieces: 13 total (1 done, 2 pending, 10 todo)
```
The worker ceiling is whatever `dev-loop-queue` is configured with (00.04), not a constant this command knows. To see the same behaviour without a session:

## Teach me while you build

- **Background**: A *human command* is an operator control executed on the host plane, outside any model turn. A *registry seam* is a service you contribute to with `register()`, receiving a disposer back. `rawInput` is the exact text after the command name: "free-form" means the runtime performs no tokenising, quoting, or type coercion on it.
- **How it works here**: `apply(ctx)` registers one definition named `dev-loop`. A submitted line reaches `parseCommand`, whose regular expression `/^\/([a-z][a-z0-9_-]*)(?=$|[\t\n\r ])/u` peels off the name and hands the remainder over as `rawInput`; the runtime then resolves the registration and invokes the handler with a `CommandInvocation`. `parseDevLoopInput` splits that text into a subcommand and arguments, the router queries `ctx.devLoopDirectory`, `ctx.devLoopLifecycle`, and `ctx.devLoopQueue`, and the handler returns a `CommandResult`. `normalizeResult` validates and freezes it; the dispatching UI renders `text`. Open `packages/dev-loop/command/src/index.ts` and read `normalizeDefinition`/`normalizeResult` in `packages/interaction/commands/src/index.ts` alongside it.
- **Why this approach**: Asking the model for status costs tokens, waits for a turn, and invites a confident wrong number. A command reads the host services directly, so the report is the system's own state.
- **Approaches considered**: (1) *One command with self-parsed subcommands, chosen* — one registration, one help surface, and the parser is about fifteen lines; the cost is owning the grammar. (2) *One registration per subcommand* (`dev-loop-status`, `dev-loop-approve`), which the name regular expression permits — discovery lists each separately and no parsing is needed, but six registrations must stay consistent and the operator loses a single usage line. This would win if the client offered per-command argument UI. (3) *A model-facing tool instead* — rejected outright: the operator is not the model, and an approval gate the model could call would not be an approval gate. (4) *Taking an argument-parser dependency* such as a `yargs`-style library — rejected because `rawInput` here is at most a verb and two words, and a parser would add a dependency to delete nothing.
- **Prior art inspected**: None external. The in-repository sibling is the `command-kanban` design in `plans/00-architecture-mapping.md`, which was read; no other project was opened for this piece.
- **What we get for free**: Name validation, definition normalisation, result validation and freezing, agent-scoped shadowing of global registrations, discovery metadata for UI clients, the `command/run` and `command/done` session records, and the disposer. Explicitly NOT provided: argument parsing, tab completion, terminal printing, and any notion of subcommands. Those were claimed by the first draft of this piece and do not exist.
- **What to notice**: The `input.hint` string is advertisement, not grammar — nothing validates `rawInput` against it. Keep the hint and the parser in one file so they cannot drift.
- **Lesson**: Read the seam before designing against it. "The framework parses arguments for me" is the kind of assumption that survives an entire design document and dies on the first line of implementation.

## Reuse capture

- **Reuse candidate**: Subcommand parser over `rawInput` for a human command · Splits the free text the commands seam hands a handler into a verb and arguments, returning a usage/error result instead of throwing · Used in `parseDevLoopInput` · Reusable by every future `dsh` command with more than one operation, since the runtime will never supply this · Would need the verb table and usage text lifted into parameters · Evidence: the parser cases in `packages/dev-loop/command/tests/command.spec.ts` · Confidence: medium — one implementation, but the gap it fills is a property of the seam rather than of this command
- **Anti-pattern worth keeping**: Designing a command surface around `argv`, `print()`, and tab completion because every other CLI framework has them. This seam has none: the handler gets one string and returns one result. The correction cost a Contracts block and an acceptance list — noticing it during implementation would have cost the package.
- **Known limitations**: Only available where `ctx.commands` is mounted. The `input.hint` is advisory, so a client may submit any text; the parser is the only validation. Output is a single text blob — there is no structured rendering, and `sourceEventSeq` only points a UI at a richer event some other plugin already logged.
