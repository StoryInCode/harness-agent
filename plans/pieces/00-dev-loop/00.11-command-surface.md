# 00.11 — Human Command Surface `/dev-loop`

**Set:** 00-dev-loop · **Queue:** 11 · **Depends on:** 00.01, 00.02, 00.04
**Status:** todo
**Harness primitive:** command · **Package:** `@deepseek-ai/dsh-dev-loop-command`

## Summary

Inspect pieces and live Queue state, review a source revision, and explicitly approve or block work without a model turn. This proposed command registers as `dev-loop`, not `/dev-loop`. Its handler parses rawInput and returns CommandResult. It uses existing Directory/Lifecycle/Queue APIs; durable acceptance integration belongs to 00.12, not a nonexistent approval service.

## Behaviour

- **Given** an active session **When** `/dev-loop status` runs **Then** it returns live worker count, Queue ceiling, queued count and current Lifecycle counts, with malformed-source diagnostics.
- **Given** queued work **When** `/dev-loop queue` runs **Then** it lists actual entries in Queue order and derives each dependency status from Directory and Lifecycle.
- **Given** a piece **When** `/dev-loop show 00.03` runs **Then** it returns the full reviewed source and exact SHA-256 needed for approval, plus current status and declared metadata.
- **Given** the shown current digest **When** the root human submits `/dev-loop approve 00.03 <sha256>` **Then** it rechecks the source and requests todo-to-pending with actual command identity; stale digest refuses approval.
- **Given** pending work **When** `/dev-loop reject 00.03 reason with spaces` runs **Then** it requests pending-to-blocked with that full reason, not an illegal todo-to-blocked edge.
- **Given** unknown verbs, extra arguments, missing arguments or invalid ids **When** the handler runs **Then** it returns a specific error and usage without silently ignoring input; unsupported attachments are refused earlier by CommandRuntime with its own diagnostic.
- **Given** empty input or help **When** submitted **Then** it returns complete usage; disposal removes the registration.

## Harness fit

The **command** function plugin injects `commands`, `agents`, `devLoopDirectory`, `devLoopLifecycle`, `devLoopQueue` and `fs`, and effect-owns `commands.register({name:'dev-loop',description,input:{hint},handler})`. No model-facing approval tool is added. Existing `present_piece_for_approval` remains the separate question-based Consumer; its private presentPiece is not a public service.

`CommandInvocation` carries commandId, exact receiving agent, rawInput, attachments and signal. Registration supplies no subcommand parser or completion engine. CommandResult is returned, not printed. Existing command runtime logs command/run and command/done; output is human UI state, not automatically injected model context. The command does not launch an app, server or bin.

## Contracts

### Complete grammar

Whitespace separates the verb and fixed arguments. No quoting, flags, aliases or shell evaluation are supported. `reject` consumes the nonempty remaining text verbatim except leading/trailing whitespace. All other routes reject trailing tokens. Dotted ids follow the Directory’s canonical NN.MM grammar. Digests require 64 hexadecimal SHA-256 characters; normalize case only.

| Input after /dev-loop | Operation and result |
|---|---|
| empty or `help` | Success with the complete grammar; help takes no arguments. |
| `status` | `getActiveWorkers`, `getQueuedEntries`, public Queue.maxConcurrency; scan all sets and use Lifecycle.getStatus for logical counts. |
| `list` | Directory.listSets then scanSet; deterministic set/queue/id order, current Lifecycle status, title, path and rejected-source diagnostics. |
| `queue` | Queue.getQueuedEntries in returned order, numbered display positions, queueOrder/enqueuedAt and per-dependency status. |
| `show <id>` | Directory.getPiece and fs source read/stat/recheck; full source, current Lifecycle status and content SHA-256. No clipped review is represented as complete. |
| `approve <id> <sha256>` | Require exact live runtime root; read/validate source and match digest, then Lifecycle.transition(id,'todo','pending',reason,signal,authorization) under the 00.12 amendment. |
| `reject <id> <reason...>` | Require exact live runtime root; require pending and call Lifecycle.transition(id,'pending','blocked',reason,signal). Other statuses return a legal-state diagnostic. |

Before 00.12 exists, command tests use the existing five-argument transition and prove revision checking; those tests must not claim durable approval. 00.12 extends both human consumers with authorization forwarding and direct Lifecycle durable checks. Final composition requires that integration. Do not introduce a command dependency on Persistence or duplicate its domain to make standalone tests pass.

Authorization is built from actual invocation.commandId, receiving Session id and observed source digest/version, not caller JSON. The explicit digest in the human command declares which revision they accept. It does not prove they read every line. Require `agents.get(agent.id) === agent` and `agents.roots().includes(agent)` before mutations; a delegated child cannot manufacture a root interaction. The direct human command is the authority path, not a model-generated string.

Dependency display looks up the queued piece via Directory.getPiece, reads its dependsOn, then calls Lifecycle.getStatus for each id. QueueEntry has no dependency field. Missing/malformed dependencies display specific diagnostics and never count as done. Counts distinguish logical Lifecycle state from disk header state; rejected sources remain visible. These independent reads are a timestamped observation, not a transactional cross-service snapshot or restored activity after restart.

The handler returns `{kind:'success',text}` or `{kind:'error',text}` for expected input/domain failures. CommandRuntime owns pre-admission attachment refusal and cancellation: a pre-aborted execution or its withAbort race may reject rather than return CommandResult, so cancellation is not promised as a handler-formatted error. Runtime defects likewise follow the command runtime’s error path; do not promise that no exception can ever occur or swallow defects into success. Empty results are explicit, for example `Queue: empty`. Unknown ids, stale review, illegal/stale status and missing referents have nonempty corrective text. The input descriptor does not enable attachments.

Require Config.maxOutputBytes and maxInputBytes as positive safe integers. Derive the minimum valid output budget from the UTF-8 size of the actual fixed refusal text plus its complete owned CommandResult wrapper; reject smaller configuration rather than emitting an oversized or empty error. Test tiny-invalid, exact-minimum and multibyte boundaries. Bound complete UTF-8 text including usage and wrappers. Oversized show returns explicit refusal, never a truncated source plus an approval digest. The owner may read the file by another approved route, but this command cannot assert a completed review. Overflowing list/queue/status returns a named error rather than a silent partial count; no ignored pagination flags. Propagate invocation.signal through source/transition calls and check it between synchronous scans.

## How to see it

Proposed command sequence in a root session: `/dev-loop help`, `/dev-loop list`, `/dev-loop show 00.03`, then `/dev-loop approve 00.03 <digest returned by show>`. Expect full source and digest, then a success naming pending only if the source still matches. `/dev-loop queue` can remain empty: approval changes eligibility and does not itself enqueue a role callback.

Proposed test command: `pnpm exec vitest run packages/dev-loop/command/tests`. Required named observations include raw-input grammar, full source review, stale-digest rejection, multiword reason preservation, logical status counts and dependency diagnostics. ## Teach me while you build

- **What it does:** Lets the human inspect real state and authorize one exact revision.
- **Background:** A command is a human control outside model turns. Compare-and-set uses the expected current status to reject concurrent stale changes. A digest identifies source bytes, not human comprehension.
- **How it works here:** CommandRuntime supplies rawInput and commandId; the parser routes to Directory/Queue reads or Lifecycle.transition. Read QueueEntry to see why dependency display must look elsewhere.
- **Why this approach:** One command keeps discovery and usage together. Separate registered commands would win if each needed a distinct client form; they add registrations without eliminating source-review logic here.
- **Approaches considered:** One raw-input command is chosen; independent command registrations are supported by this same runtime; a model tool is appropriate for model requests but not independent human authorization. This is a narrow Harness-specific interface; no external parser or prior-art implementation was inspected, and no library comparison is asserted.
- **Prior art inspected:** Only in-repository command and user-question owners. No external project or code reuse is claimed.
- **What we get for free:** The command runtime validates registration/results, logs invocation/settlement and owns dispatch. Application code owns grammar, source review, bounds and status composition.
- **From the docs:** CommandInvocation describes rawInput as “Exact text following the registered command name, including separator whitespace.” The parser must consume and validate all of it.
- **What to notice:** Approval does not create a Queue callback. A disk todo header may coexist with logical pending until durable Lifecycle integration reconciles its own facts.
- **Concepts to own:** Optimistic concurrency binds approval to observed bytes; complete input validation rejects trailing tokens; separation of concerns keeps display derivation outside Queue.
- **Interview angle:** “How do you stop approving a changed specification?” Require the reviewed digest and recheck source before the sole writer accepts. Follow-up: durable acceptance must occur inside Lifecycle, not a command-only wrapper.
- **Decisions you can now make alone:** Improve diagnostics and strict grammar fixtures. Escalate new state transitions, reopening done or automatic dispatch to their owners.
- **What you should learn from this:** Returned text, human authority and durable state are separate responsibilities.
