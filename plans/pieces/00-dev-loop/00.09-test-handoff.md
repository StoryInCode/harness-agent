# 00.09 — BDD Scenario Extractor and Test Handoff

**Set:** 00-dev-loop · **Queue:** 9 · **Depends on:** 00.01, 00.06, 00.13
**Status:** todo
**Harness primitive:** workflow capability · **Package:** `@deepseek-ai/dsh-dev-loop-test-handoff`

## Summary

Extracts the 3-8 Given/When/Then scenarios from a piece's `## Behaviour` section and formats them into an authoritative test specification for the Test Writer subagent. The Test Writer receives VERIFIED claims established by claim verification (00.13). If claim verification is outstanding, incomplete, or contradicted, test handoff is blocked, so no test is authored against an ungrounded assumption. It sequences the handoff: validating that scenarios are discrete and testable, dispatching the Test Writer in the allocated worktree, and asserting that the newly authored tests FAIL against the baseline codebase (RED) before implementation begins.

The sequencing is **this piece's own code**. `WorkflowEngine` is an abstract Service with exactly one method, `start(request): WorkflowRun`, and the `workflow/*` events are `@mode emit` progress narration. The engine offers no execution graph, no state checkpoints, no rollback, and no retry — searching `packages/workflow/workflow/src/` for `rollback`, `checkpoint`, or `retry` returns nothing. Every abort code, every ordering guarantee, and any recovery from a half-finished handoff below is written here.

## Behaviour

- **Given** a parsed piece with 5 Given/When/Then scenarios and verified claims **When** extraction runs **Then** a structured `TestBrief` with 5 scenarios and verified claim citations is produced.
- **Given** a piece with outstanding or unverified claim verification **When** test handoff is attempted **Then** handoff is aborted with `CLAIM_VERIFICATION_OUTSTANDING`.
- **Given** a piece with fewer than 3 or more than 8 scenarios **When** extraction runs **Then** validation fails with `INVALID_SCENARIO_COUNT`.
- **Given** a scenario not following the Given/When/Then pattern **When** extraction runs **Then** validation fails with `MALFORMED_BDD_SCENARIO`.
- **Given** a valid `TestBrief` with verified claims **When** handed off to the Test Writer subagent **Then** the Test Writer receives the scenarios and target test file paths.
- **Given** tests authored by the Test Writer **When** executed against the baseline codebase **Then** the test runner reports failure, proving a discriminating RED test state.

## Harness fit

This capability is a `workflow capability` consuming `ctx.workflowEngine` (`packages/workflow/workflow/src/index.ts`, `abstract class WorkflowEngine extends Service` with `super(ctx, 'workflowEngine')`). It sequences the handoff pipeline: scenario extraction → validation → Test Writer delegation → RED gate verification.

What the engine actually provides is narrow, and the piece is built for that: `start(request)` parses and executes one script and returns a `WorkflowRun` whose `result` resolves when the script settles, while `workflow/start`, `workflow/phase`, `workflow/log`, `workflow/agent-start`, `workflow/agent-end`, and `workflow/end` announce progress at `@mode emit`. Emit-mode events are announcements: nothing awaits a listener, and a listener cannot veto or alter a step. They are therefore usable for operator visibility and useless as control flow.

Consequences this piece owns outright:

- **Ordering** is the script's own sequencing; there is no engine-level graph to declare.
- **Failure handling** is explicit: each step either produces the next input or throws one of this piece's abort codes. There is no checkpoint to resume from, so a handoff that dies mid-flight is re-run from the start, which is safe because extraction and validation are pure and the RED run is read-only.
- **The only non-idempotent step is the Test Writer's file authoring.** Re-running it over an existing test file is the piece's own concern; it re-reads what is on disk in the worktree and treats already-authored files as its starting point rather than overwriting them blindly. No framework undo exists.

The RED-before-GREEN requirement is unaffected by any of this: the engine never promised to enforce it, and the gate is a real test run whose non-zero exit is the evidence.

  executeHandoff(brief: TestBrief): Promise<TestHandoffOutcome>

## Teach me while you build

- **Background**: Test-Driven Development (TDD) mandates writing tests that fail before the implementation exists. The RED state proves the suite discriminates between missing and completed behaviour rather than passing trivially. Tests written against unverified spec claims merely encode a falsehood in executable form. An *emit-mode event* is a fire-and-forget announcement: the emitter does not await listeners and a listener cannot change the outcome — which is why the `workflow/*` events can report progress but cannot gate it.
- **How it works here**: The workflow capability extracts Given/When/Then scenarios from `## Behaviour` using markdown AST parsing, validating between 3 and 8 scenarios. Before dispatching the Test Writer, it asserts that claim verification (`00.13`) has completed and no contradictions are unresolved. If claims are outstanding, handoff aborts with `CLAIM_VERIFICATION_OUTSTANDING`. It compiles a `TestBrief` with verified claims and scenarios, dispatches the `Test Writer` subagent via `ctx.devLoopRoles`, and asserts that authored tests fail against the baseline codebase. Open `packages/dev-loop/test-handoff/src/index.ts`.
- **Why this approach**: Separating the author of the tests from the author of the code is what stops a tautological suite. The simplest alternative — letting the Implementer write both — reliably produces tests that assert what the code happens to do.
- **Approaches considered**: (1) *A workflow script sequencing the four steps, chosen* — one run, one settled result, progress visible through `workflow/*` for the operator; the cost is owning all failure handling. (2) *Four separate service calls orchestrated by 00.06's delegation path* — fewer moving parts and no engine dependency at all, and genuinely better if the operator never needs to watch the handoff progress; rejected mainly for the visibility. (3) *A durable state machine over 00.12*, checkpointing after each step so a crashed handoff resumes — the right answer IF resuming ever becomes expensive, which it is not while only the authoring step writes anything. (4) *Trusting the Test Writer to self-report RED* — rejected outright: the gate exists precisely because a self-report is what it is checking.
- **Prior art inspected**: None external; no outside project was opened for this piece. The RED-before-GREEN discipline here is taken from `docs/testing.md`, which was read.
- **What we get for free**: From `WorkflowEngine`: script parsing, one `start(request)` entry, a `WorkflowRun` whose `result` settles once, cancellation through the request signal, and six `@mode emit` progress events with contained listener dispatch. That is the complete list. **Explicitly NOT provided — and claimed by this piece's first draft — are multi-step execution graphs, state checkpoints, rollback, and retry.** Grepping the engine's source for those three words returns nothing. Every one of them, if wanted, is code written here.
- **What to notice**: The RED gate's evidence is a real test run's non-zero exit and its captured output, stored on `TestHandoffOutcome.failureOutput`. A gate that inferred RED from the absence of an implementation file would pass for a test that asserts nothing.
- **Lesson**: Read what a framework's service actually exposes before deciding what it handles for you. One abstract method and six announcement events is a narrow surface, and a design that assumed checkpoints and rollback would have discovered the gap only after the orchestration was supposedly done.

## Reuse capture

- **Reuse candidate**: RED-gate verification step · Runs the newly authored tests against the unmodified baseline and treats a non-zero exit plus captured output as the evidence that the suite discriminates · Used in `executeHandoff` · Reusable by any agent pipeline that authors tests before code · Would need the runner command and the failure-parsing lifted into parameters · Evidence: the RED-baseline case in `packages/dev-loop/test-handoff/tests/test-handoff.spec.ts` · Confidence: medium
- **Anti-pattern worth keeping**: Listing a dependency's facilities in "What we get for free" without opening it. This piece credited the workflow engine with execution graphs, checkpoints, and rollback; the engine has one abstract method and six emit-mode events. The failure mode is specific and expensive — the orchestration is designed as if recovery were handled, and the gap appears only when something has already half-run.
- **Known limitations**: Requires Given/When/Then syntax. No resumable state: a handoff interrupted mid-flight re-runs from extraction, which is safe only because the sole file-writing step is the Test Writer's and it re-reads the worktree first. The `workflow/*` events cannot gate anything, so operator visibility and control are separate problems here.

## Acceptance

1. Unit tests in `packages/dev-loop/test-handoff/tests/test-handoff.spec.ts` pass verifying scenario parsing from markdown.
2. Rejection of pieces with <3 or >8 scenarios with `INVALID_SCENARIO_COUNT`.
3. Rejection of malformed scenarios lacking Given, When, or Then clauses.
4. Test handoff aborts with `CLAIM_VERIFICATION_OUTSTANDING` if claim verification is incomplete or contradicted.
5. The Test Writer receives the verified claims table alongside the BDD scenarios.
6. A successful run records `redBaselineConfirmed: true` only after a real test execution exits non-zero, with its output captured in `failureOutput`; a suite that PASSES against the baseline fails the gate and blocks the handoff.
7. Every abort code is raised by this package's own step sequencing, asserted directly — no test asserts that the workflow engine rolled anything back, because it cannot.
8. An interrupted handoff re-run from the start reaches the same outcome, proving the pipeline is safe to repeat without checkpoints.
