# 00.04 — Dev Loop Dispatch Queue and Concurrency Guard

**Set:** 00-dev-loop · **Queue:** 4 · **Depends on:** 00.02, 00.03
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-queue`

## Summary

Maintains the dispatch queue of approved pieces and enforces a concurrency ceiling on running subagents. When an approved piece is queued it dispatches immediately if active workers are below the ceiling; otherwise it parks in FIFO order. As active subagents settle, the queue dispatches the next eligible piece in queue order.

The ceiling is a **validated `Config` field**, `maxConcurrency`, changeable from `cordis.yml` — not a constant. Root `AGENTS.md` is explicit: *"No hardcoded tunables in plugins: deployment-varying choices are validated `Config` fields changeable from cordis.yml; a `DEFAULT_*` constant or test hook is not configurability."* How many agents a machine can run is exactly such a choice: it depends on host memory and on the provider's rate limits, neither of which this package knows.

**The default is 4**, matching `plans/15-orchestrator-vision-and-control.md`, whose `maxConcurrentChildren` is schema'd `z.number().int().min(1).max(32).default(4)`. This piece previously specified a hardcoded 6 while citing that same plan, which says neither 6 nor hardcoded. The reconciliation is to follow the cited source rather than the number: one ceiling concept, one default, and a deployment that wants 6 sets 6. The bounds are adopted with the default — at least 1, because 0 would park every piece forever, and at most 32 as an obvious-mistake guard rather than a measured capacity. No measurement of this machine's real capacity exists; the number is a convention, not a benchmark.

## Behaviour

- **Given** a configured ceiling of 4 and 3 active subagents **When** an approved piece is enqueued **Then** it dispatches immediately and the active count becomes 4.
- **Given** active subagents equal to the configured ceiling **When** another approved piece is enqueued **Then** it parks in the queue and no subagent is spawned.
- **Given** a full ceiling and 2 queued pieces **When** a `subagent/end` arrives for a run this queue started **Then** the first eligible queued piece dispatches and the active count returns to the ceiling.
- **Given** a `cordis.yml` row setting `maxConcurrency: 8` **When** the service mounts **Then** eight workers may run concurrently, with no code change; a row setting `0` or `33` fails the mount at load with a schema error.
- **Given** multiple queued pieces **When** dispatch eligibility is evaluated **Then** pieces dispatch strictly in queue order among those whose dependencies are satisfied.
- **Given** a queued piece whose dependency failed or is `blocked` **When** a slot opens **Then** the queue skips it, marks it blocked, and dispatches the next unblocked piece.

## Harness fit

This capability is a `Service Provider` mounted on the host plane (`ctx.devLoopQueue`) extending `@deepseek-ai/cordis.Service`, with a `static Config` schema carrying `maxConcurrency`.

It tracks running children through the `subagent/start` and `subagent/end` events, which are **declared** in `packages/subagent/subagent/src/index.ts` (declaration merging on `Events`, both `@mode emit`) and **emitted** in `packages/subagent/subagent/src/lifecycle.ts`. A listener receives one argument: `subagent/start` carries `SubagentRunInfo { runId, provider, id, local }` and `subagent/end` carries `SubagentRunEndInfo { runId, provider, id, local, stopReason, lastAssistantMessage? }`. The delegating parent is **not** a payload argument — the emitter passes it as the scoped dispatch carrier, so a parent-scoped listener observes only its own delegations. Slots are reclaimed by matching `runId`, not by counting events, because this queue must ignore children other code delegates.

`subagent/end` fires for every settlement including errors (`stopReason: 'error'`), and each listener is independently contained: a throw or rejection is logged and cannot starve peers or alter the run. A slot must therefore be released in the listener itself, not in a promise chain the emitter awaits — nothing awaits it.

No ceiling exists upstream to consume today. `maxConcurrentChildren` and `spawnPaused` appear nowhere in `packages/`; Plan 15 proposes them for `tool-subagent`. If that lands, this queue's ceiling becomes the loop-level WIP limit above the process-level one, and the two remain separate concerns — this one bounds pieces in flight, that one bounds children per parent.

## Contracts

```typescript
export interface QueueEntry {
  pieceId: string
  enqueuedAt: number
  priority: number
  status: 'queued' | 'dispatched' | 'blocked'
}

export interface ActiveWorker {
  pieceId: string
  subagentId: string
  startedAt: number
}

/** Every field optional so a cordis.yml row may set one and inherit the rest. */
export interface Config {
  /**
   * Concurrent dispatch ceiling. Integer, 1–32, default 4 — the bounds and
   * default of `maxConcurrentChildren` in
   * `plans/15-orchestrator-vision-and-control.md`. Deployment-varying, so it
   * is a validated field and never a constant.
   */
  maxConcurrency?: number
}

export interface DevLoopQueue {
  /** The resolved ceiling for this mount, for operator surfaces such as 00.11. */
  readonly maxConcurrency: number
  enqueue(pieceId: string): Promise<QueueEntry>
  dequeue(): Promise<string | undefined>
  getActiveWorkers(): ActiveWorker[]
  getQueuedEntries(): QueueEntry[]
}
```

`ActiveWorker.subagentId` is the `SubagentRunInfo.runId` observed at `subagent/start`, which is what the paired `subagent/end` carries. Matching on the child `SessionId` instead would confuse a continuable child's successive residency epochs.

## Teach me while you build

- **Background**: A *WIP (work-in-progress) limit* caps how many units run at once, protecting memory, CPU, and provider rate limits. A *`Config` schema* is a schemastery declaration validated when the plugin mounts, so a bad value in `cordis.yml` fails the mount loudly instead of surfacing later as strange behaviour. *Scoped dispatch* means an event's listeners are selected by a carrier — here the delegating parent — so a listener can observe only its own children.
- **How it works here**: Mounted as `ctx.devLoopQueue` with `static Config`, the service resolves `maxConcurrency` once at construction. It listens for `piece/approved`; an arriving piece dispatches if `getActiveWorkers().length < maxConcurrency`, else parks in FIFO order. `ctx.on('subagent/start', …)` records `runId`, and `ctx.on('subagent/end', …)` releases the slot whose `runId` matches and dispatches the next piece with satisfied dependencies. Both subscriptions return disposers that unwind with the fiber. Open `packages/dev-loop/queue/src/index.ts` next to `packages/subagent/subagent/src/lifecycle.ts`.
- **Why this approach**: Events arrive when a child actually settles, so there is no polling interval to tune and no window where a freed slot sits unused. The simplest alternative — spawning unboundedly — exhausts memory and trips rate limits.
- **Approaches considered**: (1) *Event-driven slot accounting, chosen* — exact, no timers, and disposal-safe. (2) *A semaphore around the spawn call*, which is simpler still and is how most task pools do it; it would win if this package also owned the spawn, but the settlement signal here is an event from another package, so the semaphore would need releasing from that listener anyway. (3) *Polling `ctx.subagents` for live children* — no event coupling, but it re-derives state the seam already publishes and adds latency exactly when a slot frees. (4) *Delegating the ceiling entirely to `tool-subagent`'s proposed `maxConcurrentChildren`* — attractive because one limit is easier to reason about, rejected because it does not exist, and because a per-parent child limit is not a loop-wide piece limit even once it does.
- **Prior art inspected**: None external; no outside project was opened for this piece. Plan 15's Hermes comparison table cites `tools/delegate_tool.py` for `max_concurrent_children`, and that file was NOT opened here — it is Plan 15's citation, not this piece's.
- **What we get for free**: Typed event declarations with documented payloads, contained listener dispatch (a throwing listener cannot break a run), scoped dispatch keyed by the delegating parent, disposers from `ctx.on`, and schemastery validation of `maxConcurrency` at mount. We write the queue, the dependency check, and the slot accounting.
- **What to notice**: Release the slot inside the `subagent/end` listener. The emitter dispatches `emit`-mode and awaits nothing, so any cleanup deferred to a promise the emitter might await simply never runs. And match on `runId`: a continuable child can start and end several times under one `SessionId`.
- **Lesson**: A tunable with a number in the source is a decision taken away from whoever deploys the system. Put it in `Config` with bounds and a default, and say which source the default follows — then the number is reviewable and the choice is still theirs.

## Reuse capture

- **Reuse candidate**: Event-driven slot accounting over a lifecycle event pair · Bounds concurrent work by matching a start event's run id against its paired end event, with no polling and no timers · Used in `DevLoopQueue` · Reusable for any bounded dispatcher over a start/end event pair — background processors, test runners, batch fetchers · Would need the event names and the id accessor lifted into parameters · Evidence: the ceiling and slot-release cases in `packages/dev-loop/queue/tests/queue.spec.ts` · Confidence: medium
- **Anti-pattern worth keeping**: A tunable written as a literal in a type (`readonly maxConcurrency: 6`), justified by a citation that actually specified a configurable field with a different default. Two defects in one line: the number was unsupported by its own evidence, and the form was forbidden by root `AGENTS.md`. When a piece cites a source for a number, open the source and read the number.
- **Known limitations**: In-flight workers are tracked in memory and must be reconstituted from 00.12 on restart. The ceiling counts pieces this queue dispatched, not all subagents in the process: children delegated elsewhere consume real capacity this counter cannot see. The `min(1).max(32)` bounds are inherited convention, not a measured capacity for any particular machine.

## Acceptance

1. Unit tests in `packages/dev-loop/queue/tests/queue.spec.ts` pass, never pinning a literal ceiling: each case configures `maxConcurrency` and asserts against that value.
2. With the ceiling reached, the next piece stays queued until a worker settles, then dispatches in queue order.
3. `maxConcurrency` is read from configuration: a real-composition test mounts the package from a test-only `cordis.yml` with a non-default value and observes that many concurrent workers. No source file contains the ceiling as a literal.
4. A configured `0`, `33`, or non-integer fails the mount with a schema error; the default when the field is absent is 4.
5. A slot is released by the `subagent/end` listener for every `stopReason`, including `error`, and a `subagent/end` carrying an unknown `runId` changes nothing.
6. Pieces with unmet dependencies are not dispatched ahead of prerequisites, and a blocked dependency causes the queue to skip and continue rather than stall.
7. Disposing the fiber removes both event subscriptions, proven by a disposal test.
