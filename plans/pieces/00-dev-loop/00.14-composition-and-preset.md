# 00.14 — Dev Loop Host Composition and Agent Preset

**Set:** 00-dev-loop · **Queue:** 14 · **Depends on:** 00.01, 00.02, 00.03, 00.04, 00.06, 00.10, 00.11, 00.12
**Status:** todo
**Harness primitive:** agent-preset composition · **Package:** `@deepseek-ai/dsh-dev-loop-preset`

## Summary

Makes the development loop mountable. The loop's services are host-plane rows added to the deployment's `cordis.patch.yml`; the session-facing tools, persona and prompt sections are an agent preset directory the operator selects. Together they let a fresh session run the loop against the piece corpus without the operator composing anything by hand.

The split is not stylistic. A service row inside a preset must sit in an `isolate` realm, which gives every session its own private copy — and the loop's state is explicitly shared: the `/dev-loop` operator command reads it out of turn, and the storage domain is meant to survive restarts. A per-session loop would give each session its own queue and its own idea of what is done. Host services, preset tools: the same division `plans/14-presets-profiles-and-bundle.md` records for the Hermes presets, where `ctx.ledger`, `ctx.axioms`, `ctx.kanban` and `ctx.memory` all live host-side while the preset carries only their tools.

## Behaviour

- **Given** a deployment whose `cordis.patch.yml` carries the loop's service rows **When** the process starts **Then** `ctx.devLoopDirectory`, `ctx.devLoopLifecycle`, `ctx.devLoopQueue` and `ctx.devLoopPersistence` are published once for the process, not once per session.
- **Given** the preset directory is present under the authored-preset root **When** the operator lists presets **Then** `dev-loop` appears with its display name and description from `preset.yml`, not as a bare directory name.
- **Given** a session mounted on the `dev-loop` preset **When** the agent takes its first turn **Then** the approval-junction tool, the delegation tools and the loop's prompt sections are available, and the persona states the loop's obligations: approval before work, roles before implementation, RED before GREEN, evidence before done.
- **Given** the preset is mounted twice, in two concurrent sessions **When** both run **Then** neither collides on a service name and neither sees the other's tool registrations, because the preset publishes no service of its own.
- **Given** a preset row that publishes a service without an `isolate` realm **When** the preset is mounted **Then** the mount fails loudly with the leaked-service diagnostic rather than silently publishing into the process-global realm.
- **Given** the loop's host rows are absent but the preset is mounted **When** a loop tool is called **Then** the failure names the missing service and the composition file that should provide it, rather than surfacing as an undefined-property error.
- **Given** an operator who has never used the loop **When** they follow this piece's `## How to see it` **Then** they reach a session that can present a piece for approval, with no hand-editing of any composition.

## Harness fit

This is an `agent-preset composition`: one preset directory holding `agent.cordis.yml` and `preset.yml`, plus the host rows that preset depends on. Authored presets live one directory per preset under `${DSH_HOME:-$HOME/.dsh}/.agent-presets/`, which is where this one is installed; the shipped set beside the deployment's own config is never edited, because an upgrade overwrites it.

Per `PRESET-RULE 4`, rows that register into host registries — `ctx.tools`, `ctx.systemPrompt` — publish no service and sit at preset root with no realm. Per `PRESET-RULE 5` and META AXIOM item 5, any row that does publish a service must sit in a `cordis:group` carrying an `isolate` realm, and `verify-cordis-config` statically rejects a preset row that repeats a row already active in the host composition.

## How to see it

```bash
ls ${DSH_HOME:-$HOME/.dsh}/.agent-presets/dev-loop/
# agent.cordis.yml  preset.yml
```

Then start a session and select the `dev-loop` preset. Correct result: the preset appears in the picker as **Dev Loop** with its description, the session starts, and asking the agent to begin a piece produces an approval junction rather than immediate work. `/dev-loop status` answers out of turn with the queue and worker counts, which proves the host rows mounted; if that command is missing, the preset mounted but the host patch did not.

## Teach me while you build

- **Background** — A *composition* is a list of plugin rows; there is no separate configuration language. A *realm* (`isolate`) scopes a published service so it is visible only inside that group. The *host plane* is the process: one instance, shared by every session. The *agent plane* is one session, mounted and unwound with it.
- **How it works here** — The operator selects a preset; the roster mounts that preset's rows under the session's scope. Rows registering tools and prompt sections attach to the host registries and disappear when the session ends. The loop's services were mounted once at process start from the host patch, so every session sees the same queue and the same completion record.
- **Why this approach** — The alternative is a self-contained preset carrying its own service rows in isolate realms, which looks tidier and is wrong here: each session would get a private loop. The tell is `/dev-loop`, an out-of-turn operator surface that must see the same state the agent does.
- **Approaches considered** — (1) *Host services + preset tools, chosen*, matching the Hermes split. (2) *Everything in the preset behind isolate realms* — correct for genuinely private state like an orchestrator's own workflow engine, wrong for shared state, and it collides on the second session because a provider name registers once. (3) *A bundle* (`packages/bundle/*/cordis.patch.yml`) rather than a hand-edited host patch — the right end state for distribution, since a bundle is installable and versioned, and worth taking once the rows stop changing. (4) *No preset at all*, with the operator composing rows by hand — what is happening today, and the reason this piece exists.
- **Prior art inspected** — `packages/preset/agent-presets/presets/cordis/` (read in full): a shipped preset that carries a persona, a toolset and skills, publishing no service of its own; its persona states the plane rule this piece follows. No external project was inspected for this piece; the composition rules are specific to this harness, and inventing an outside comparison would be worse than saying so.
- **What we get for free** — The roster owns discovery, display metadata, mounting and unmounting. `verify-cordis-config` statically rejects a preset row duplicating a host row. The mount-time leaked-service check catches a missing realm. We write two YAML files and a persona.
- **What to notice** — The preset has no `isolate` realm at root, and that is correct rather than an omission: it publishes no service. If a future row does publish one, it needs a realm or it must move to the host patch.
- **Concepts to own** — *Composition over configuration*: capability is a row, not a flag. *Scope and lifetime*: per-process versus per-session ownership. *Service locator with realms*: name resolution bounded by a realm. *Shared mutable state*: the reason the loop's services cannot be per-session.
- **Interview angle** — *"Two sessions of the same agent must share a work queue but not share tools. How do you arrange that?"* Publish the queue once per process and let each session contribute only its own registrations; the test is whether an out-of-turn operator surface sees the same state the agent does. Follow-up: *"What breaks if you put the queue in the per-session scope?"* — each session gets a private queue, the operator command reports one session's view as the truth, and the second session collides on the provider name.
- **Decisions you can now make alone** — Adding a tool row, a prompt section, or persona wording to the preset; changing the display name or description. **Escalate:** moving any row between the two planes, adding a service row to the preset, or editing the shipped preset install. **Open:** whether the host rows should become an installable bundle rather than a hand-applied patch, which is the right end state but not yet worth the versioning overhead.
- **Lesson** — Decide where a capability lives by asking who else must see it, not by how closely it belongs to the agent.

## Reuse capture

- **Reuse candidate:** host-rows-plus-preset split for a stateful subsystem · Puts shared services on the host plane and their tools in a preset · Used by this composition · Reusable for any subsystem with both an agent-facing tool and an out-of-turn operator surface · Would need the row list parameterised · Evidence: the Hermes split recorded in `plans/14` reaching the same shape independently · Confidence: medium
- **Known limitations** — A hand-applied host patch is not versioned and is lost if the profile is recreated; a bundle solves that and is not done here. The preset assumes the loop's packages are resolvable from the deployment's `node_modules`, which holds for a source checkout and is untested for an installed deployment.

1. The preset directory exists under the authored-preset root with both files, and appears in the picker with its display name.
2. A session mounted on it exposes the approval-junction and delegation tools, and the persona states the loop's obligations.
3. The host patch publishes the loop's services once per process; two concurrent sessions share one queue, proven by `/dev-loop status` reporting the same state from either.
4. `verify-cordis-config` passes, and no preset row duplicates a host row.
5. A preset row publishing a service without a realm fails the mount with the leaked-service diagnostic, proven by a deliberately broken fixture.
6. With the host patch absent, a loop tool fails naming the missing service and the file that should provide it.
7. The shipped preset install is unmodified, proven by comparing it against a clean checkout.
