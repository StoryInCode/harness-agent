# 00.14 — Opt-In Host Assembly and Authored Brain Preset

**Set:** 00-dev-loop · **Queue:** 14 · **Depends on:** 00.01, 00.02, 00.03, 00.04, 00.05, 00.06, 00.07, 00.08, 00.09, 00.10, 00.11, 00.12, 00.13

## Summary

Assemble the existing and proposed pieces into an opt-in development loop with shared Host state and scoped Brain tools. Publish a tested local authored integration, not a new launch bin or edits to shipped presets. This specification defines required wiring; it is not an executable composition or a claim that unbuilt rows already mount.

The first supported scenario uses a fresh todo corpus and records genuine completion. An existing corpus with unjournaled done pieces is not immediately dispatchable: 00.12 quarantines those observations, and inspect/acknowledge cannot authorize them. Legacy bootstrap, repair execution and reopening done require a separate accepted product decision before using this assembly for that corpus.

## Behaviour

- **Given** the complete configured Host assembly **When** a fresh todo corpus loads **Then** each shared service opens once and Lifecycle requires durable persistence before admitting transitions.
- **Given** two Brain sessions **When** both mount the authored preset **Then** they share Queue/evidence services while each owns its scoped tool registrations.
- **Given** the actual Brain tool list **When** a piece begins **Then** approval, claim verification, role delegation and test handoff use their real Consumers, not persona-only service names.
- **Given** missing Host rows, required config or provider capabilities **When** the assembly is validated **Then** it fails explicitly instead of silently using memory mode or unrestricted Research.
- **Given** a complete frozen-test lifecycle **When** code is transferred and actual post-transfer checks succeed **Then** only the existing Lifecycle completion path may move the piece to done.
- **Given** unjournaled done or interrupted durable state **When** startup runs **Then** recovery commands display anomalies, never fabricated completion or restored workers.
- **Given** installation and teardown **When** the authored integration is removed **Then** shipped presets remain unchanged, scoped registrations disappear and retained worktrees/evidence are not deleted by preset disposal.

## Harness fit

This is an **agent-preset composition** with an opt-in Host patch and copied local authored preset. Host rows own cross-session registries, policy, storage, model routes, subprocess/filesystem providers and dev-loop services. The preset contributes only tools and persona/prompt registrations into those Host registries. It does not publish dev-loop services behind private realms or duplicate providers.

Load editing-cordis-compositions before implementation. Use `agentPresets.list/resolve` to find actual source and destination paths; `copy(from,'dev-loop',name)` creates an authored copy and returns void, so resolve the result afterward. The default authored root is `${DSH_HOME:-$HOME/.dsh}/.agent-presets`, but roster-reported paths govern. Never edit or overwrite the deployment’s shipped agent-presets directory. Source a full coding preset through the roster; do not assume an internal checkout preset path exists.

No new application bin, demo server or SDK argv escape is added. Existing `dsh` profiles remain the launch owner. Deliver the Host patch and local authored preset through an explicitly authorized opt-in installation, with a real test-only Loader composition as proof. Do not change shipped defaults or modify this running deployment merely because a plan names a patch file.

### Scoped Brain Consumers

Keep the copied coding toolset only where policy permits; configure explicit role restrictions rather than assuming the parent toolset is safe for Research. Required scoped additions are:

- `@deepseek-ai/dsh-dev-loop-approval`: existing present_piece_for_approval Consumer, with 00.12’s actual answer/source authorization forwarding.
- `@deepseek-ai/dsh-dev-loop-roles/tool`: dev_loop_delegate and dev_loop_delegations, with maxToolOutputBytes/maxHistoryRecords from 00.06. Generic tool-subagent is not its substitute.
- `@deepseek-ai/dsh-dev-loop-claims/tool`: dev_loop_verify_claims, with complete output bound owned by this Consumer.
- `@deepseek-ai/dsh-dev-loop-test-handoff/tool`: dev_loop_test_handoff, with complete output bound owned by this Consumer.
- `@deepseek-ai/dsh-dev-loop-gates/tool`: required 00.10 execution/report/completion Consumer, dev_loop_check `{pieceId,stage:'worktree'|'post-transfer'}`, dev_loop_gate_report `{pieceId}` and dev_loop_complete `{pieceId}`. It calls runChecks/getReport or actual Lifecycle.transition under the evidence hook, never taking passed/evidence/revision/command arguments. No persona can call its Host methods directly.
- Persona/prompt registration: approval before work, fail-closed load-bearing Claims, canonical four roles, frozen Test Writer tests, independent RED, Implementer production-only edits, explicit transfer and post-transfer checks, no automatic worktree retirement, no fifth Reviewer, no unrequested push.

Consumers declare their own complete model-output byte limits, pure renderers and real tool schemas; they do not read a Host service’s private config. Existing tool runtime records model-visible results. No new Session event is needed merely to display a tool-owned report. Preserve generic tool presentation unless a separately justified pure presenter is tested.

This assembly does not supply a magic autonomous transfer operation. The Brain uses its configured existing execution tools under explicit user authorization to transfer exact files without overwriting unrelated mainline changes, requests actual Gates execution and asks the existing lifecycle-owning orchestration path for completion. The required 00.10 `dev_loop_complete {pieceId}` Consumer calls Lifecycle.transition(pending,done) and reports failure only after awaited veto release; it never asserts evidence or auto-blocks. Lifecycle injection belongs on that Consumer, not on Persistence. Assembly acceptance exercises this exact model/tool path.

### Installation and validation

The implementation provides a concrete opt-in Host patch based on the selected existing profile’s actual patch mechanism, authored preset agent.cordis.yml and preset.yml with name/description, and a manifest of exact installed rows/configuration. It records the chosen profile, roster source/destination paths and repository association. No fictional universal deployment defaults, absolute machine-specific patch claim or incomplete snippet is labeled runnable.

Run `agentPresets.standingKeyFor('dev-loop')` after authoring; roster list’s broken flag is not mount proof. Validate both Host patch and actual preset activation through the Loader and a real session. Missing-service diagnostics must name the absent service/row; a deployment-specific patch location can be named only by an owner that actually knows it. No unconditional promise that the runtime invents that path in every error.

## Teach me while you build

- **What it does:** Makes all the pieces usable together without giving each session a private queue or imaginary tools.
- **Background:** Host scope lasts across sessions. Agent scope contributes tools for one session. A provider publishes a capability; a Consumer gives a human or model an actual way to invoke it.
- **How it works here:** Read Roles’ Host/tool split, then the table above. Persistence initializes before Lifecycle; model tools call the shared owners, and the preset only contributes those tools/persona.
- **Why this approach:** Shared state belongs to the Host. A wholly isolated preset is appropriate when every consumer belongs to that one agent; it cannot satisfy cross-session command/state consumers here.
- **Approaches considered:** Local Host patch plus copied preset is chosen for opt-in testing; an installable bundle would suit distribution after actual package/config ownership is accepted. Private preset service realms suit genuinely private state, not this loop. These rules are Harness-specific; no external composition project was inspected.
- **Prior art inspected:** The editing skill and AgentPresets source, plus current dev-loop configuration owners. No external code reuse or uninspected shipped preset source claim.
- **What we get for free:** Roster owns copy/discovery/mount, Loader resolves declared dependencies, existing providers own execution worlds and storage routing. Application assembly owns complete values, Consumers, policy and end-to-end proof.
- **From the docs:** The editing skill states “A service with a consumer outside the agent plane cannot move into a preset.” That decides the shared queue’s placement.
- **What to notice:** A service row without its tool Consumer can mount yet remain unreachable to the model. A done filename without a durable record remains an anomaly, not bootstrap evidence.
- **Concepts to own:** Dependency direction prevents initialization cycles; separation of policy and mechanism puts Research allowlists in Roles while ToolRuntime enforces them; scope/lifetime determines which session can see a contribution.
- **Interview angle:** “How do two agents share a queue but not tool registrations?” Mount one Host queue and two scoped Consumers. Follow-up: prove actual calls and teardown, not just object identity.
- **Decisions you can now make alone:** Adjust documented local config values with validation fixtures. Escalate new providers, plane changes, legacy bootstrap or automatic repair; never edit a shipped preset.
- **What you should learn from this:** Complete wiring includes the caller, provider, configuration and lifetime—not just a service name.
