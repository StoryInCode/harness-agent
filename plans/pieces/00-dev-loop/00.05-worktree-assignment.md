# 00.05 — Per-Piece Git Worktree Allocation

**Set:** 00-dev-loop · **Queue:** 5 · **Depends on:** 00.04
**Status:** todo
**Harness primitive:** Consumer · **Package:** `@deepseek-ai/dsh-dev-loop-worktree`

## Summary

Allocates a dedicated Git worktree for each dispatched piece before the subagent is spawned, by consuming the host `worktrees` service. It provisions `.worktrees/<piece-id>` on branch `piece/<piece-id>`, records the immutable base commit, and passes the worktree path as the child session's `SessionHeader.cwd`.

**This piece is dormant.** `packages/worktree/worktree` does not exist, so `inject: ['worktrees']` cannot resolve today and nothing here can be built until set 05 ships that seam. No replacement mechanism is invented here.

The confinement this piece relies on is real but narrower than "isolation", and the exact promise matters to 00.06, which builds on it. Setting the child's `cwd` does move the write boundary: `SandboxPolicyService.resolve({ session })` derives `workspaceRoot` from `session.header.cwd`, and the filesystem fence tests containment against `writableRoots(policy)`. The guarantee, stated completely: **a `write` or `edit` by an agent whose session carries `cwd`, under effective mode `workspace-write`, in a composition that mounts `@deepseek-ai/dsh-fs-sandbox` together with `ctx.sandboxPolicy`, is confined to that `cwd` — plus `/tmp` and the OS temp dir, which are always writable.** Outside those conditions there is no fence: `danger-full-access` returns the target unchecked, `read-only` denies every write, an approved `sandbox_permissions` escalation widens the mode for one call, and a composition without the sandboxing backend has no check at all. It is an in-process path check in TypeScript, not a kernel mechanism.

## Behaviour

- **Given** an approved piece dispatched from the queue **When** worktree assignment runs **Then** `ctx.worktrees.allocate(pieceId)` creates `.worktrees/<piece-id>` on branch `piece/<piece-id>`.
- **Given** an allocated worktree **When** the subagent session is initialized **Then** its `meta.cwd` is the worktree path and is durably recorded as `SessionHeader.cwd`.
- **Given** a child session whose `cwd` is the worktree, a composition mounting `dsh-fs-sandbox` with `ctx.sandboxPolicy`, and effective mode `workspace-write` **When** the child's `write` targets a path outside the worktree and outside the temp areas **Then** `checkedTarget` throws `FS_SANDBOX_DENIED` and the tool reports the `[sandbox: …]` denial marker.
- **Given** the same child **When** it writes under `/tmp` or the OS temp dir **Then** the write SUCCEEDS, because those roots are always writable under `workspace-write`; the worktree is not an exclusive boundary.
- **Given** a child whose effective mode is `danger-full-access` **When** it writes outside the worktree **Then** the write succeeds unfenced, because `checkedTarget` returns the target before any containment test — the fence is a property of the mode, not of the `cwd`.
- **Given** an existing branch or path collision **When** worktree allocation runs **Then** allocation resolves a non-conflicting path without crashing.
- **Given** a subagent finishing with uncommitted or dirty files **When** cleanup is attempted **Then** the preservation guard refuses deletion.

## Harness fit

This is a `Consumer` injecting `['worktrees', 'subagents']`, and it stays dormant until the `worktrees` seam exists: `inject` holds a plugin in waiting until its services appear, so the correct behaviour today is an unresolved dependency, not a stub. `WorktreeManager` is specified in `plans/07-worktree-management.md` and owned by set 05; this piece invents no filesystem interception of its own.

How the confinement actually composes, so nobody builds on a stronger promise than exists:

1. `SessionHeader.cwd` (`packages/core/session/src/types.ts`) carries the worktree path on the child's durable header.
2. `SandboxPolicyService.resolve({ session })` returns `workspaceRoot: resolveWorkspaceRoot(session?.header.cwd ?? this.workspaceRoot)`. Its JSDoc states it plainly: "A session cwd is its workspace-write boundary; the configured root is the fallback for agentless calls and sessions without a cwd." So `cwd` is not an alternative to `workspaceRoot` — it is what derives it.
3. `FsSandboxController.resolvePolicy` (`packages/fs/tool-fs/src/sandbox.ts`) stamps that policy on every `write`/`edit`, resolving it from the calling agent's session.
4. `SandboxedFileSystem.checkedTarget` re-canonicalises the target and requires containment under `writableRoots(policy)`, which is `[policy.workspaceRoot, '/tmp', tmpdir()]` canonicalised and deduplicated.

Two honest limits follow. The check is **user-space**: `checkedTarget` is TypeScript running in this process, defending against a confused agent rather than a hostile one, and only for calls that route through the filesystem seam. And `/tmp` is **always** writable, so two concurrent workers can still reach each other's files there — worktree isolation is isolation of the repository, not of the machine.

## Teach me while you build

- **Background**: A *Git worktree* checks a second branch out into its own directory from one repository, so parallel workers do not fight over one index or working tree. A *sandbox policy* is a per-call record of a mode (`read-only`, `workspace-write`, `danger-full-access`) and a workspace root. A *writable root* is a directory the mode permits writing under; containment means the canonical target path lies beneath one of them.
- **How it works here**: On dispatch, `assignWorktree(pieceId)` calls `ctx.worktrees.allocate(pieceId)`, yielding `.worktrees/<piece-id>` on `piece/<piece-id>`, and the child session starts with that path as `cwd`. When the child calls `write`, `FsSandboxController.resolvePolicy` resolves a policy from its session — `workspaceRoot` comes from `session.header.cwd` — and `SandboxedFileSystem.checkedTarget` re-resolves the target NOW (catching a symlink ancestor swapped since the tool resolved it) and requires it under a writable root, throwing `FS_SANDBOX_DENIED` otherwise. Read `packages/sandbox/sandbox/src/roots.ts` first; it is four lines and it defines what "inside the workspace" means.
- **Why this approach**: Worktrees give each worker its own index and branch, which is what actually prevents concurrent edits from corrupting each other. The sandbox is a second, weaker layer that catches a stray path. The simplest alternative — one shared working directory — loses the git-level isolation that is the real point.
- **Approaches considered**: (1) *Worktree plus session `cwd`, chosen* — git owns isolation, the sandbox narrows accidental reach, and both already exist as seams. (2) *A process-level sandbox* (`@deepseek-ai/dsh-sandbox-local`, whose Seatbelt profile derives its allow-list from the same `writableRoots`) — genuinely stronger because it binds shell commands too, and worth adding for a child that runs `bash`; it does not remove the need for a worktree. (3) *Separate clones per worker* — complete isolation including `.git`, at the cost of disk and fetch time, and the right choice if workers ever ran on different machines. (4) *No isolation, serialised execution* — the honest fallback if worktree allocation proves fragile; it costs all the parallelism this set exists to provide.
- **Prior art inspected**: None external; no outside project was opened for this piece.
- **What we get for free**: `WorktreeManager` (once set 05 ships it) owns `git worktree add`/`prune`, classification, and the preservation guard. The filesystem fence supplies canonical-path containment, TOCTOU-resistant re-resolution, and the `FS_SANDBOX_DENIED` denial marker. Explicitly NOT free: kernel-level confinement, confinement of anything that does not route through the fs seam, and any protection at all under `danger-full-access` or without the sandboxing backend mounted.
- **What to notice**: `checkedTarget`'s first branch returns the target unchecked under `danger-full-access`. A test asserting denial will pass or fail on the session's mode alone — so a fencing test must pin the mode explicitly, or it proves nothing about the fence.
- **Lesson**: State a security guarantee with its preconditions or do not state it. "Writes are fenced to the worktree" and "writes are fenced to the worktree plus `/tmp`, under `workspace-write`, when the sandboxing backend is mounted, by an in-process check" describe the same code and lead to different systems being built on top.

## Reuse capture

- **Reuse candidate**: Per-task worktree paired with a session-scoped write boundary · Allocates a branch-isolated directory and sets it as the child session's `cwd`, which the sandbox policy turns into that session's workspace root · Used in `DevLoopWorktree` · Reusable for multi-agent test execution, automated fix agents, and parallel PR generation · Would need the directory template and branch prefix parameterised · Evidence: pending — the seam it consumes does not exist, so there is no working implementation · Confidence: **low**, and it stays low until something runs
- **Anti-pattern worth keeping**: Describing a user-space policy check as "kernel-level" and an allow-list containing `/tmp` as "restricted to the worktree". Both overstatements pointed the same direction — toward trusting the boundary more than the code earns — and a piece downstream would have inherited that trust without re-reading the sandbox.
- **Known limitations**: Requires a local git repository with a working tree; bare repositories are unsupported. **`/tmp` and the OS temp dir are writable by every worker under `workspace-write`, so two concurrent workers can still interfere through shared temp files — worktree allocation isolates the repository, not the machine.** The fence covers only mutations routed through the filesystem seam; a child with a shell tool needs the separate process sandbox. Under `danger-full-access`, or without `dsh-fs-sandbox` mounted, there is no fence at all.
