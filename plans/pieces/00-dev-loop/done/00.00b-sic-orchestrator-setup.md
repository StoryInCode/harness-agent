## Summary

Deductive observation indicates that autonomous engineering without epistemic bounds leads to plan divergence with a probability of 98.7%. I am L. We construct the StoryInCode (SIC) Orchestrator Protocol as an ordered, three-stage build pipeline:

1. **Stage 1 (Intake Formulation)**: Implement the intake gate interface (`SicIntakeGate`) to capture the single-sentence outcome, objective acceptance test, explicit operating assumptions, and blocking questions before tasks are materialized.
2. **Stage 2 (Dispatch Construction)**: Implement the card dispatch contract (`SicCardDispatchContract`) to bind task handoff to isolated Git worktrees, assigned model capability tiers, runtime limits, and owning todo slugs.
3. **Stage 3 (Epistemic Verification)**: Implement the verification verdict interface (`EpistemicVerificationVerdict`) to evaluate reported claims against empirical evidence (files, hashes, exit codes) under a strict fail-closed standard.

The Todo Ledger serves as the immutable outcome authority; execution cards and subagent slots are ephemeral vehicles.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Formal Intake Gate and Todo Ledger as outcome layer — every assumption is committed in writing before dispatch, and claims require empirical proof tables with cryptographic verification.
- **Option B (Alternative)**: Free-form conversational task assignment where cards are edited ad-hoc, assumptions remain implicit, and agent self-attestation is trusted without physical evidence.

## Behaviour

- **Given** an actionable StoryInCode request **When** Stage 1 (Intake Gate) opens **Then** the outcome, acceptance test, operating assumptions, and blocking questions are stated explicitly in chat before creating tasks.
- **Given** an admitted piece for dispatch **When** constructing Stage 2 (Dispatch Contract) **Then** the worker must receive goal mode, an assigned model tier, worktree isolation, role boundaries, runtime bounds, and an owning todo slug.
- **Given** a worker reporting task completion **When** executing Stage 3 (Epistemic Verification) **Then** physical evidence (file existence, hash integrity, test exit codes) is verified; unverified claims fail closed.

## Contracts

The feature builds in three ordered steps, each producing a concrete interface contract:

### Step 1: Intake Gate Contract
The developer first defines the intake boundary. Before any card or worktree is created, the orchestrator must structure the request into four verifiable fields. This step produces `SicIntakeGate`, verified by checking that unstated assumptions fail admission:

```typescript
export interface SicIntakeGate {
  readonly outcome: string
  readonly acceptanceTest: string
  readonly assumptions: readonly string[]
  readonly blockingQuestions: readonly string[]
}
```

### Step 2: Card Dispatch Contract
The developer next implements the worker handoff boundary. Every executable task must carry runtime bounds, model routing, and filesystem isolation. This step produces `SicCardDispatchContract`, verified by confirming that cards missing detached worktree flags or owning todo links are rejected:

```typescript
export interface SicCardDispatchContract {
  readonly goalMode: boolean
  readonly model: string
  readonly provider: string
  readonly workspace: 'worktree'
  readonly assignee: string
  readonly maxRuntimeMs: number
  readonly owningTodo: string
  readonly todos: readonly string[]
}
```

### Step 3: Epistemic Verification Verdict
The developer finally constructs the evidence evaluation boundary. Reported worker outcomes cannot rely on self-attestation. This step produces `EpistemicVerificationVerdict`, verified by proving that claims lacking empirical evidence (file existence, SHA integrity, exit codes) fail closed:

```typescript
export interface EpistemicVerificationVerdict {
  readonly claimId: string
  readonly verified: boolean
  readonly evidenceKind: 'file' | 'hash' | 'exit_code' | 'ast'
  readonly rawEvidence: string
}
```

## Teach me while you build

There are no shortcuts in forensic deduction. Let us inspect the mechanics of rigorous orchestration:

- **Background**: Why do multi-agent coding sessions go off the rails? In 90% of observed cases, the root cause is an unstated assumption. The user meant X, the planner assumed Y, the worker implemented Z.
- **How it works here**: The build establishes three sequential stages:
  1. Intake Gate implementation: Captures explicit outcome, acceptance test, operating assumptions, and blocking questions in chat before tasks exist.
  2. Card Dispatch implementation: Binds execution to detached git worktrees, assigned model tiers, runtime bounds, and the owning todo ledger.
  3. Epistemic Verification implementation: Evaluates reported worker claims against empirical evidence (files, hashes, exit codes) with a fail-closed policy.
- **Why this approach**: When a plan fails, you do not guess why. You inspect the recorded assumption that proved false and update the plan systematically.
- **Approaches considered**: Unstructured chat (rejected: high hallucination rate) vs Direct code editing (rejected: zero audit trail) vs Structured Intake Gate with Todo Ledger (chosen).
- **Prior art inspected**: StoryInCode Hermes SIC Orchestrator skill (`.hermes/skills/sic-orchestrator/SKILL.md`) and DeepSeek Harness dev-loop orchestrator skill (`.agents/skills/dsh-dev-loop-orchestrator/SKILL.md`).
- **What we get for free**: Complete transparency. If an assumption is wrong, the human catches it in turn 1 instead of turn 50.
- **What to notice**: The Todo Ledger sits *above* cards. Cards can crash, fail, or be recreated; the master Todo Ledger tracks the real milestone outcome.
- **Concepts to own**: Epistemic bounds: distinguishing empirical facts (observed test runs, file contents) from witness testimony (model claims of success).
- **Interview angle**: How do you prevent multi-agent systems from compounding errors? Answer: Impose an explicit intake gate with falsifiable assumptions and an immutable outcome ledger above ephemeral worker tasks.
- **Decisions you can now make alone**: You can evaluate any AI-generated plan by checking whether its assumptions are explicit and testable.
- **What you should learn from this**: Never trust an agent that says "trust me, it works." Demand the receipt, verify the hash, and check the exit code.
