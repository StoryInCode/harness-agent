## Summary

Listen up. Git has an annoying habit: if you try to create two worktrees with the same path or touch the same worktree from two processes, git locks blow up with `.git/worktrees/<name>/locked`. Daru built a collision detector and single-writer concurrency controller. If an allocation is already in-flight for a piece ID, concurrent callers coalesce onto that attempt. If an unmanaged directory or git inventory entry already occupies the path, we fail-closed immediately instead of corrupting the git index. Clean and orderly.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: In-memory promise chain serialization and request coalescing preventing simultaneous allocations of the same piece worktree.
- **Option B (Alternative)**: Relying on Git's internal lock files alone, which leaves stale locks behind if a process crashes.

## Behaviour

- **Given** an active in-flight worktree assignment attempt **When** a concurrent caller requests the same piece ID **Then** it coalesces onto the owner attempt, and a waiter cancellation does not abort the owner.
- **Given** an existing unmanaged directory or git inventory entry at the target path **When** `assignWorktree` executes **Then** it refuses collision fail-closed and preserves disk residue for explicit recovery.
- **Given** sequential allocation requests for distinct piece assignments **When** `assignWorktree` is called **Then** each mutating action is serialized through a promise tail queue without racing Git CLI processes.

## Teach me while you build

Two writers on one directory equals corrupted code. Let's talk mutual exclusion and request coalescing on disk.

- **What it does**: Prevents two workers or processes from accessing the same worktree directory simultaneously while coalescing duplicate requests.
- **Background**: Git index operations are not re-entrant. Concurrent writes corrupt the index and cause fatal lock errors.
- **How it works here**: Maintains an active `attempts` map for in-flight piece allocations and chains mutating operations onto `this.tail`. Callers for the same piece coalesce on the in-flight promise. If an unmanaged directory or inventory entry already exists, allocation refuses fail-closed.
- **Why this approach**: Catching collisions and coalescing requests in process memory before invoking Git CLI prevents messy `.git/index.lock` collisions and race conditions.
- **Approaches considered**: Relying on `git.lock` (flaky on crash) vs PID lock files (stale on SIGKILL) vs In-process promise serialization with pre-check validation (chosen).
- **Prior art inspected**: Database row locks, promise memoization queues, and SQLite `SQLITE_BUSY` contention handling.
- **What we get for free**: Promise chaining in Node guarantees deterministic FIFO execution order across asynchronous operations.
- **From the docs**: docs/defensive-patterns.md: 'Lifecycle and concurrency: serialize state mutations and preserve diagnostic residue on failure.'
- **What to notice**: Notice how an aborting waiter in `wait()` detaches its cancellation listener without rejecting the owner's promise!
- **Concepts to own**: Single-writer principle and request coalescing: ensuring mutable shared resources execute through one serial queue while deduplicating in-flight work.
- **Interview angle**: How do you prevent index corruption when orchestrating concurrent Git operations? Answer: Pre-empt Git with in-process promise serialization and request coalescing per target path.
- **Decisions you can now make alone**: You can safely handle high-frequency worker requests knowing identical attempts collapse into a single execution.
- **What you should learn from this**: Never let two workers write to the same directory. Serialize mutations, coalesce in-flight requests, and fail-closed on collision.
