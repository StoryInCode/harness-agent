# 00.04 — Dev Loop Dispatch Queue and Concurrency Guard

**Set:** 00-dev-loop · **Queue:** 4 · **Depends on:** 00.01, 00.02, 00.03
**Status:** done
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-queue`

## Summary

Bounds concurrent one-shot delegations for approved pieces. A role consumer submits the piece id, its own start callback, and its cancellation signal. The queue captures the current live initiator, reads canonical dependencies and queue order from the directory, and reserves capacity before invoking the callback. It does not invent a parent, provider, assignment, role, or worktree from an approval event.

`maxConcurrency` is a validated integer Config field, 1–32, default 4. This is the loop-owned dispatch limit, not a process-wide or provider-internal subagent limit. The default and bounds are inherited conventions from Plan 15, not measured machine capacity. A deployment can choose 6 without changing code.

## Behaviour

- **Given** a pending piece, a live initiator, and spare capacity **When** its request is admitted **Then** capacity is reserved before its start callback runs.
- **Given** reservations at the configured ceiling **When** another request arrives **Then** its callback remains uncalled until a reservation is released.
- **Given** several eligible requests **When** capacity opens **Then** lower canonical queue numbers run first, with FIFO admission order breaking ties.
- **Given** an incomplete dependency **When** scheduling runs **Then** the dependent parks; a later completion notification wakes it.
- **Given** a blocked dependency **When** scheduling runs **Then** the dependent piece transitions from pending to blocked, its request rejects, and unrelated eligible requests continue.
- **Given** an approval notification without a submitted request **When** the listener runs **Then** no callback or subagent is created.
- **Given** absent or stale initiator identity **When** admission or dispatch checks run **Then** the request rejects without starting a child.
- **Given** a start callback that rejects **When** it settles **Then** its reservation is released without waiting for a subagent event that might never occur.
- **Given** a returned run whose result settles **When** cleanup remains pending **Then** the reservation stays occupied until `dispose()` and result observation settle.
- **Given** queued cancellation **When** its signal aborts **Then** no callback runs and the request settles cancelled.
- **Given** starting or running cancellation **When** its signal aborts **Then** the queue awaits startup settlement, disposes any returned run, and joins it before releasing capacity.
- **Given** disposal of the queue **When** teardown begins **Then** admission and wakeups stop, every operation is aborted, and teardown awaits startup and run cleanup.
- **Given** run cleanup failure **When** quiescence cannot be established **Then** the queue closes admission, cancels remaining requests, and surfaces the failure rather than claiming free capacity.

## Harness fit

A host Service Provider exposes `ctx.devLoopQueue`. Hard dependencies are `agents`, `devLoopDirectory`, and `devLoopLifecycle`; the subagent package supplies the existing run/result types, not a new dispatch method. The role consumer (00.06) constructs the real `SubagentStartRequest` and calls `ctx.subagents.start(provider, request)` inside the supplied callback.

The queue captures `ctx.agents.currentInitiator()` before its first await, checks `ctx.agents.get(agent.id) === agent`, and rechecks before invoking a callback under `ctx.agents.withInitiator(agent, ...)`. Scheduling itself runs without an inherited arbitrary initiator. Live Agent objects, callbacks, and run handles remain private; status queries return owned scalar records.

The returned one-shot `SubagentRun` already has `id`, `result`, and `dispose()`. Its result and cleanup promises own settlement, so the queue does not infer identity or reclaim capacity by counting global `subagent/start` or `subagent/end` announcements. `id` is a child SessionId, not a run epoch; this package does not support continuable residency epochs. An unrelated event cannot release a reservation.

`piece/approved`, `piece/completed`, and `piece/blocked` only wake existing requests. They do not provide dispatch context. The queue reads dependencies through Directory and authoritative logical status through Lifecycle; it does not treat a disk todo header as a replacement for pending memory.

## Contracts

```typescript
import type { Agent } from '@deepseek-ai/dsh-agent'
import type { SessionId } from '@deepseek-ai/dsh-session'
import type { SubagentRun, SubagentResult } from '@deepseek-ai/dsh-subagent'

export interface Config {
  maxConcurrency?: number // integer 1–32, default 4
}

export interface QueueRequest {
  pieceId: string
  signal: AbortSignal
  dispatch(agent: Agent, signal: AbortSignal): Promise<SubagentRun>
}

export interface QueueTicket {
  readonly pieceId: string
  readonly result: Promise<SubagentResult>
  cancel(reason?: unknown): Promise<void> // idempotent; awaits owned cleanup
}

export interface QueueEntry {
  pieceId: string
  queueOrder: number
  enqueuedAt: number
  status: 'queued' | 'starting' | 'running'
  subagentId?: SessionId // available only after the one-shot start returns
}

export interface DevLoopQueue {
  readonly maxConcurrency: number
  enqueue(request: QueueRequest): Promise<QueueTicket>
  getActiveWorkers(): QueueEntry[] // includes starting reservations
  getQueuedEntries(): QueueEntry[]
}
```

Admission validates the piece and dependencies, requires lifecycle pending, and rejects a duplicate outstanding piece id. It returns a ticket without waiting for capacity or worker completion. Cancellation rejects the ticket result; `cancel()` resolves only after cleanup, or rejects with its cleanup failure. A settled request permits a later role request for the same still-pending piece. Public records contain no live Agent or run references.

There is no separate dispatcher registry or public `dequeue()`: the current consumer already owns a per-invocation callback and signal, so another registration lifetime would duplicate that ownership. A role fiber aborts its invocation signal when it unloads. A late callback return after cancellation is joined and disposed, never admitted as fresh work.

## Teach me while you build

**Background:** A semaphore reserves a limited number of permits. Here a reservation covers startup, execution, and cleanup, because each can still consume resources. Releasing at leader completion alone can exceed the intended limit while old work remains alive.

**How it works here:** The role consumer supplies an executable callback; the queue supplies admission, ordering, dependencies, captured initiator identity, and cancellation. Existing Cordis and subagent APIs provide scoped calls, removable listeners, a result promise, and a disposal promise. We do not build another subagent backend.

**Approaches considered:** A per-request callback using the existing run handle is chosen because 00.06 already owns the provider and assignment. A dispatcher registry would be useful for multiple independently selected dispatcher implementations, but no current consumer needs that extra lifetime. Direct queue-owned spawning would require it to absorb role/worktree policy and introduce a dependency cycle. Counting global events loses startup-rejection and cleanup information already available from the owned promises.

**Prior art inspected:** Parent directly read the [p-queue README](https://raw.githubusercontent.com/sindresorhus/p-queue/main/readme.md), API `add`/`signal`, `onIdle`, `clear`, and Custom QueueClass, during round 38. This was documentation inspection of the moving main branch, not a pinned implementation or benchmark; no code was reused. p-queue is a real alternative for priority/concurrency scheduling, but piece dependencies, captured Agent identity, and resource joining would remain our responsibility.

**From the docs:** Its cancellation FAQ says “it does not automatically stop the async work inside your function.” Rejecting a task promise is therefore not evidence that its resource stopped. A library-backed implementation would still need the owned cleanup promise and tests used here.

**What to notice:** Reserve before awaiting startup, and do not free the reservation until disposal settles. Capture the initiating Agent before parking; a later lifecycle event's ambient caller is not the original delegator.

**Concepts to own:** Structured concurrency joins child work before its owner exits. Backpressure parks work instead of spawning without a bound. Stable priority scheduling uses queue number first and FIFO order for ties. These appear in dispatch lifetime, capacity reservation, and eligible-request selection respectively.

**Interview angle:** “Why can a concurrency limiter exceed its limit?” Because it counts only returned handles or releases before cleanup. Reserve before calling the asynchronous factory and join the returned resource before releasing. The follow-up is how to handle a factory that returns a resource after cancellation; this queue disposes and joins that late resource.

**Decisions you can make:** Change the configured limit within the documented bounds after measuring the deployment. Do not add continuable runs without a real cancellation/join owner, or infer an assignment from a status event. The provider and role owners must resolve those changes together.

**Lesson:** A lifecycle announcement reports an event; an owned handle provides the cancellation and settlement needed to manage capacity.

## Reuse capture

**Reusable implementation pattern:** Hold a reservation around an asynchronous resource factory, its result, and its cleanup. Potential reuse includes subprocess admission and bounded background operations. Generalization requires another consumer with equivalent ownership; this is not a new generic task-pool library. Confidence is medium for these one-shot operations, supported by the named tests; generic reuse remains unproven.

**Anti-pattern:** An event payload with no caller or assignment cannot become an executable request by naming an `enqueue(pieceId)` method. The missing information belongs to the dispatching consumer, not an inferred default.

**Known limitations:** State is process-local. Restart recovery and durable revision-bound approval belong to 00.12. The limit counts only submitted one-shot operations, not every subagent or provider-internal child in the process.
