## Summary

If any specification parameter is ambiguous, an autonomous agent must never assume or guess. To guess is to introduce a 91% error rate into the case. We provide the `present_piece_for_approval` tool consuming the user-questions service. When a decision is required, execution suspends until the human operator responds. Every response is verified fail-closed: answers must match an explicit decision option, and only live root agents may query the user. Evidence must be corroborated by the authority.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Suspend execution and query the human via typed prompt schema, recording the response in the session log.
- **Option B (Alternative)**: Make an autonomous probabilistic guess and proceed without human confirmation.

## Behaviour

- **Given** a specification piece presented for approval **When** the human provides an ambiguous, skipped, or multiple-choice answer **Then** it rejects with `APPROVAL_DECISION_REQUIRED` without authorizing work.
- **Given** a delegated child agent attempting to invoke approval **When** `present_piece_for_approval` runs **Then** it rejects with `CALLER_NOT_LIVE` or `DELEGATED_CALLER` because human interaction requires a live root agent.
- **Given** an unanswered question or failed question provider **When** the request settles without a human claim **Then** it propagates `NO_PROVIDER` or provider error fail-closed without mutating piece lifecycle state.

## Teach me while you build

When deduction reaches an epistemic boundary, the detective consults the commissioner. Never extrapolate beyond known facts.

- **What it does**: Suspends execution to obtain an explicit, unambiguous decision from the human operator via the user-questions service.
- **Background**: DSH provides native interaction services (`userQuestions`). The approval consumer binds that capability to the development loop with strict fail-closed validation.
- **How it works here**: The model invokes `present_piece_for_approval`. The tool delegates to `ctx.userQuestions.ask` and awaits the human answer, enforcing that exactly one decision (`Accept`, `Question`, or `Change`) is selected.
- **Why this approach**: Suspending cleanly preserves the agent's turn budget and prevents hallucinated decisions from contaminating git worktrees.
- **Approaches considered**: Agent guessing (rejected: causes unreviewed bugs) vs Free-form text parsing (rejected: affirmative words in feedback could be misread as accept) vs Strict single-select validation (chosen: fail-closed).
- **Prior art inspected**: Elixir/Erlang GenServer calls with timeout and human-in-the-loop workflow approvals.
- **What we get for free**: `ctx.userQuestions` handles live-root verification, answerer waterfall dispatch, and cancellation propagation.
- **From the docs**: `packages/dev-loop/approval/README.md`: 'Only one exact decision selection with no custom decision text is accepted. Skipped, duplicate, unrecognized, or multiple choices fail with APPROVAL_DECISION_REQUIRED.'
- **What to notice**: Notice how delegated subagents are rejected with `DELEGATED_CALLER`: only the live root agent is permitted to prompt the human directly!
- **Concepts to own**: Epistemic bounds: recognizing when information is absent and suspending rather than fabricating.
- **Interview angle**: How do you prevent hallucinated approvals in multi-agent architectures? Answer: Require live root agent provenance and enforce strict single-select validation over structured prompts.
- **Decisions you can now make alone**: You can distinguish whether an approval failure stemmed from caller invalidity, provider absence, or human malformed input.
- **Lesson**: Never guess when you can verify. A single unambiguous clarification prevents days of forensic debugging.
