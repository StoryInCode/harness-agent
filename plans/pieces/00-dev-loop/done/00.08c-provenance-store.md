## Summary

Let us complete the provenance circuit. A reference is not merely a path; it is an evidentiary claim. The `DevLoopReferences` service verifies all citations in a piece via `verifyReferences`, cross-referencing source file hashes, line ranges, and role delegations against live storage. It records an authoritative `ProvenanceObservation` in the durable storage domain. If a citation points to phantom lines or a missing file, the observation flags it without fabricating claims of inspection.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Persist durable, detached `ProvenanceObservation` records in the `dev_loop_references` storage domain, recording explicit error codes and source fingerprints.
- **Option B (Alternative)**: Return ephemeral in-memory validation summaries without durable persistence, losing auditability across service restarts.

## Behaviour

- **Given** a valid piece with existing source citations **When** `verifyReferences(pieceId, signal)` is invoked **Then** it parses references, checks source existence and line ranges, links delegation records, and persists a `valid` `ProvenanceObservation`.
- **Given** a piece with a citation whose line range exceeds the decoded line count **When** `verifyReferences` executes **Then** it records an `INVALID_RANGE` error and marks `structuralStatus` as `invalid`.
- **Given** a piece that was previously verified **When** `getProvenance(pieceId)` is called **Then** it returns the detached durable observation without re-reading the filesystem.

## Harness fit

Host service in `packages/dev-loop/references/src/index.ts` injecting `devLoopDirectory`, `devLoopRoles`, `fs`, and `storageDomain`. Publishes `ctx.devLoopReferences` with durable storage backed by `referencesDomain` in `packages/dev-loop/references/src/records.ts`.

## Teach me while you build

In court, every exhibit must be verified against original source evidence. Let us inspect the verification engine.

- **Background**: Documentation and plan drift occur when code changes but references remain pointing to stale line numbers or deleted files.
- **How it works here**: `verifyReferences` retrieves piece content via `devLoopDirectory`, parses GFM table locators, validates sources and ranges with `fs`, attaches role delegations via `devLoopRoles`, and persists the validated `ProvenanceObservation` into `storageDomain`.
- **Why this approach**: Persisting observations into an authoritative key-value domain ensures reproducibility and query detachment without re-scanning.
- **Approaches considered**: In-memory caching (lost on restarts) vs live re-parsing on every query (slow and non-deterministic) vs durable domain persistence (chosen: durable and detached).
- **Prior art inspected**: Content-addressable storage (CAS) and Cordis key-value storage domains in `@deepseek-ai/dsh-storage-domain`.
- **What we get for free**: `storageDomain` handles transaction boundaries, persistence, and isolation across restarts.
- **From the docs**: AGENTS.md: 'No document may claim an agent was invoked, a source was inspected... unless it actually happened.'
- **What to notice**: Notice that `inspectionStatus` strictly remains `'unverified'`: source existence and report attribution never prove an agent actually inspected the source.
- **Concepts to own**: Evidentiary provenance: distinguishing structural citation validity from claims of human or agent verification.
- **Interview angle**: How do you design an audit log for code citations? Answer: Compute cryptographic digests of referenced files and separate mechanical existence checks from assertions of semantic inspection.
- **Decisions you can now make alone**: You can retrieve cached provenance with `getProvenance` or trigger a live re-verification with `verifyReferences`.
- **Lesson**: Trust only what can be verified against physical evidence, and never conflate source existence with source inspection.
