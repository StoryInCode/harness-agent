# 00.02 — Piece Lifecycle State Machine

**Set:** 00-dev-loop · **Queue:** 2 · **Depends on:** 00.01
**Status:** done
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-lifecycle`

## Summary

Owns the compare-and-set writer for specification status (`todo`, `pending`, `done`, `blocked`) and the staged Git move into `<set>/done/`. The local operation is implemented, and its post-merge test suite passes. The built-export smoke also passes through the actual Loader and local providers, proving exact header/rename/index results, unchanged HEAD, and awaited disposal. Full-loop mounting remains owned by 00.14.

The full loop must enforce human approval (00.03), verification gates (00.10), durable records and crash reconciliation (00.12), and claim checks before implementation (00.13). These remain integration obligations, not features supplied by an in-memory status table or an event with no listeners. This package supplies the lifecycle operation and pre-completion hook; the composition must install its policy consumers before autonomous completion is enabled.

## Behaviour

- **Given** `todo` **When** the approval consumer requests `todo → pending` **Then** the service records the in-memory status and emits `piece/approved`; the caller owns the human decision.
- **Given** an illegal edge, including `todo → done` or any outgoing edge from `done` **When** transition is requested **Then** it rejects with `INVALID_STATE_TRANSITION`.
- **Given** two concurrent calls with the same expected status **When** they compete **Then** the claim is taken before the first await, only one call proceeds, and the other rejects with `PIECE_STALE_STATUS`.
- **Given** a pending completion **When** `piece/pre-complete` listeners run **Then** they are awaited serially before any file or Git mutation. A rejection releases the claim and leaves the piece pending without a completion announcement.
- **Given** a tracked piece and an accepted pre-completion hook **When** completion succeeds **Then** the source header declares `done`, Git stages that change and moves the file into `done/`, memory adopts the new path/status, and `piece/completed` carries `newPath`.
- **Given** an untracked source **When** completion is attempted **Then** tracking fails before the file is edited, with `PIECE_MOVE_NOT_TRACKED`.
- **Given** a concurrent file edit **When** the lifecycle attempts its header edit **Then** the version-guarded edit rejects instead of overwriting that edit.
- **Given** a failed staging, directory-creation, or move command **When** completion handles it **Then** the exact failed argv and stderr are reported, later forward commands do not run, and the logical status remains pending.
- **Given** an ordinary failure after this operation rewrote the header **When** recovery runs **Then** it restores the actual pre-edit disk header through a version-guarded edit; the logical status stays pending. If recovery fails or detects another writer, it reports both failures as `PIECE_RECOVERY_FAILED` rather than overwriting someone else's changes or claiming recovery.
- **Given** a file initially declaring todo **When** memory transitions through todo → pending → done **Then** completion rewrites the actual disk header to done even though the pending transition did not edit the file. The logical expected status is not assumed to be the disk's current header.
- **Given** a header already declaring `done` from an abandoned attempt while the live status is pending **When** the call is retried **Then** it can complete without requiring a missing pending substring. Restart reconciliation is separately owned by 00.12.
- **Given** a cancelled call or a disposed lifecycle fiber **When** work is in flight **Then** its signal reaches filesystem and subprocess operations, owned work is awaited to quiescence, and no new forward work or completion announcement is started after cancellation is observed.
- **Given** disposal during initial directory hydration **When** the loading fiber is disposed **Then** cancellation reaches the active listing/scan before Cordis waits for initialization; no subsequent scan or cache publication begins. Both listing and scan use the lifecycle signal.
- **Given** a command leader has exited but its managed descendants remain **When** command cleanup runs **Then** the handle's managed range is terminated and `waitForExit()` is awaited without the cancelled forward signal before another command or transition settlement. Waiting on `done` alone is insufficient.
- **Given** cancellation after a successful Git move but before memory publication **When** completion observes it **Then** the same guarded recovery path is attempted. An absent source raises `PIECE_RECOVERY_FAILED` retaining the original cancellation and actual recovery failure, not a raw cancellation falsely suggesting retry is sufficient.
- **Given** the source disappears or its status header becomes invalid after hydration **When** completion reads it **Then** it rejects without publishing completion and releases its claim. Without a format listener, lifecycle validates only the status header; it does not validate the remainder of the updated document.
- **Given** a synchronous announcement listener throws **When** the operation reports that error **Then** the already-published state is not rolled back. Cordis `emit` does not contain synchronous exceptions or await asynchronous listeners.
- **Given** a blocked piece **When** it returns to todo **Then** the status changes without an announcement; no reopen event is declared here.
- **Given** malformed and valid files in the same set **When** hydration runs **Then** valid pieces are available and malformed ids retain their `PieceParseError`, distinct from `PieceNotFoundError` for absent ids.

## Harness fit

A host `Service Provider` extends Cordis `Service` and injects `devLoopDirectory`, `fs`, and `subprocess`. It hydrates all statuses with `listSets`/`scanSet` during `Service.init`, not with the queue filter that excludes blocked/done pieces.

The filesystem capability has no rename or mkdir. The operation uses `git ls-files --error-unmatch -- <file>`, a version-guarded `fs.editText`, `git add -u -- <file>`, `mkdir -p done`, and `git mv -- <file> done/<file>`. Every nonzero command outcome is checked. `git mv` stages a rename; it creates no commit. The current directory command assumes a POSIX execution world; portable directory creation remains an explicit gap.

Header edit, Git index update, filesystem move, and memory publication are not one atomic transaction. Recovery may restore the header after an ordinary failure, but must not reset unrelated staged content. A staged change may remain after failure and must be reported as such; no Git reset/clean is authorized. A process crash can prevent recovery entirely. 00.12 must reconcile location, header, and persisted status before enabling restart-safe operation.

`piece/pre-complete` uses serial dispatch. Its listeners return void and reject to veto. No listeners means no policy has run; this package alone is not a verification enforcer. Announcements retain `emit` semantics. Durable records cannot be written reliably from an unawaited completion announcement; the 00.12 integration must define an awaited persistence operation before notification.

An operation has one cancellation lifetime combining the caller signal and the plugin lifetime. Teardown aborts and awaits all active operations, including startup hydration. Cordis emits `internal/plugin` with the exact fiber's `uid === null` before it waits for loading to finish; an effect-owned listener can signal cancellation at that point without modifying vendor code. The ordinary disposer remains responsible for joining work. Recovery is awaited even when the forward signal is cancelled. A process killed during `git mv` can have an uncertain filesystem outcome, which must not be represented as a proven rollback.

Command cleanup terminates and awaits the provider-managed range even when the leader's `done` has already settled. It does not pass an aborted signal to the quiescence wait. Ordinary command failures retain argv/stderr; caller cancellation takes precedence and preserves the original reason. A cleanup failure must be surfaced rather than reported as a proven empty range. This API does not return every command outcome concurrently with cancellation.

Validated optional `Config` fields make process budgets deployable: `terminationGraceMs` defaults to 5,000, is a positive integer no larger than 2,147,483,647 (Node timer limit); `outputMaxBytes` defaults to 65,536 and is a positive integer. Both are supplied to every subprocess request. Invalid values reject at mount. These replace private budget constants, not the fixed piece status vocabulary.

## Contracts

```typescript
export type PieceStatus = 'todo' | 'pending' | 'done' | 'blocked'
export interface StateTransitionEvent {
  pieceId: string
  from: PieceStatus
  to: PieceStatus
  reason?: string
  timestamp: number
  newPath?: string
}
export interface PieceCompletedEvent extends StateTransitionEvent {
  to: 'done'
  newPath: string
}
export interface PiecePreCompleteEvent {
  pieceId: string
  from: 'pending'
  to: 'done'
  reason?: string
  signal: AbortSignal
}
export interface DevLoopLifecycle {
  getStatus(pieceId: string): PieceStatus
  canTransition(from: PieceStatus, to: PieceStatus): boolean
  transition(pieceId: string, expected: PieceStatus, to: PieceStatus, reason?: string, signal?: AbortSignal): Promise<void>
}
```

Legal edges: `todo → pending`, `pending → done`, `pending → blocked`, `blocked → todo`. `done` is absorbing until the conflicting reopen requirements in 02.04 and the supervisor plan are resolved.

Host events: `piece/pre-complete(PiecePreCompleteEvent)` is serial; `piece/approved(StateTransitionEvent)`, `piece/blocked(StateTransitionEvent)`, and `piece/completed(PieceCompletedEvent)` are emit announcements. All registrations and operation cleanup belong to the lifecycle fiber.

Error codes: `INVALID_STATE_TRANSITION`, `PIECE_STALE_STATUS`, `PIECE_MOVE_NOT_TRACKED`, `PIECE_MOVE_FAILED`, and `PIECE_RECOVERY_FAILED`. Move errors retain `pieceId`, `argv`, and `stderr`. Recovery errors retain the initiating failure and the recovery failure. Filesystem stale-version and caller cancellation errors retain their original causes.

## Teach me while you build

- **What it does:** makes status changes through one guarded writer and archives a finished specification without creating a commit.
- **Background:** a finite-state machine enumerates permitted states and edges. Compare-and-set rejects a write unless the caller's expected state still holds. A version token identifies a filesystem observation so another writer's change can invalidate an edit.
- **How it works here:** `transition(id, 'pending', 'done')` claims the piece, awaits verification listeners, edits/stages/moves the file, then publishes state. Look at `claim`, `moveIntoDone`, and the operation disposer in the implementation.
- **Why this approach:** the owner needs progress visible in the file tree. Keeping files stationary and using only a database would simplify storage transactions, but would not meet that visibility requirement.
- **Approaches considered:** (1) checked Git operations plus compensating edits, appropriate for the required tree visibility; (2) database-only status, preferable when transactional records matter more than physical placement; (3) durable checkpointed orchestration, preferable for cross-process resumability but requiring a persistence layer and an explicit recovery protocol.
- **Prior art inspected:** the orchestrator read the official LangGraph interrupt documentation, not its source, at `https://docs.langchain.com/oss/python/langgraph/interrupts.md`. Its checkpointer requirement illustrates why an in-memory wait is not restart durability. No external implementation code was reused.
- **What we get for free:** Cordis supplies service activation and effect disposal; filesystem providers supply atomic guarded edits; subprocess providers react to cancellation. We still own ordering, compensation, attribution, and the decision of when completion is true.
- **From the docs:** LangGraph's interrupt guide lists “A **checkpointer** to persist the graph state (use a durable checkpointer in production)”. This is a contrast with the current in-memory lifecycle, not a claim that this package uses LangGraph.
- **What to notice:** `writeText(readText(...).replace(...))` can overwrite an intervening edit. A guarded `editText` must carry the observed version. A cleanup that only sends an abort can return while a process is still running; awaiting settlement is part of cleanup.
- **Concepts to own:** optimistic concurrency control (expected status/version); compensating transaction (restore an owned header change after failure); quiescence (no owned work remains when teardown resolves); time-of-check/time-of-use race (file or index changes between observations and actions).
- **Interview angle:** “How do you make a file move and state update atomic?” They are not atomic here. Explain the ordered operations, detected failures, compensating edits, and crash reconciliation. Follow-up: how do you avoid undoing another writer's work? Use version guards and report recovery conflicts rather than overwriting them.
- **Decisions you can now make alone:** add tests for a new failure point and inspect whether the claim is released. Escalate changes to approval requirements, reopen semantics, or persistence authority to the owner; those alter the loop's policy.
- **What you should learn from this:** test the promised failure and recovery behavior, not just successful statements or coverage percentages.

## Acceptance

1. Legal-edge, illegal-edge, and concurrent same-piece claim tests pass; malformed and absent ids remain distinguishable.
2. A rejecting serial pre-complete listener prevents all file/Git mutation and releases the claim for retry.
3. Completion checks tracking before editing, uses version-guarded literal edit, checks every command exit, and stages the rewritten header with the rename.
4. Ordinary failure after the edit attempts safe header recovery; recovery failure is explicit and preserves both causes. Concurrent edits are never silently overwritten.
5. Tests distinguish a retry after a real post-rewrite failure from a retry that failed before any rewrite. An already-done header is handled explicitly.
6. Caller abort and lifecycle-only disposal reach quiescence during both startup and transitions. Tests hold listing/scan and managed process-range work open; disposal must signal cancellation before waiting and remain pending until settlement. A leader's exit alone is not quiescence. Post-move cancellation enters guarded recovery and reports an absent-source recovery failure explicitly.
7. Config defaults and nondefault budgets reach subprocess requests, and invalid budgets reject at mount.
8. Events carry the committed state/new path. Synchronous listener errors do not undo that state; documentation matches emit semantics.
9. Full-loop release additionally proves approval evidence, unresolved-claim rejection, all four gates, persistence-before-notification, crash reconciliation, and README status updates through the owning integration packages. None is discharged by this package's local tests alone.
