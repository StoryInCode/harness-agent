## Summary

Tutturu~ 🌸 Mayuri is here to make sure everyone works together peacefully! When pieces are waiting to be made, we only want to pick up pieces that are actively waiting to be worked on—picking completed or blocked pieces would cause so much confusion! Candidate Selector gently gathers only `todo` and `pending` pieces in queue order so we can work happily!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Filter candidates by active lifecycle status (`todo` and `pending`) while preserving queue and set order.
- **Option B (Alternative)**: Return all pieces indiscriminately and require every downstream consumer to re-filter completed or blocked items.

## Behaviour

- **Given** a set containing completed (`done`) and pending pieces **When** getQueueCandidates is called **Then** completed pieces are excluded from the candidate list while remaining resolvable via getPiece.
- **Given** pieces in `todo`, `pending`, `blocked`, and `done` statuses **When** getQueueCandidates is called **Then** only `todo` and `pending` pieces are returned as candidates.
- **Given** multiple eligible pieces within a set **When** getQueueCandidates returns results **Then** candidates are ordered by queue position ascending, tie-broken by piece id.
- **Given** no set name is specified **When** getQueueCandidates is called **Then** candidates are grouped by set name before queue position across the corpus.

## Teach me while you build

Just like sewing a dress, you have to cut the fabric before you can sew the ribbons! Tutturu~

- **What it does**: Filters parsed pieces to find those ready for dispatch: status `todo` and `pending`, while excluding `done` and `blocked` items.
- **Background**: In a dispatch queue, completed tasks must not re-enter the queue, and blocked tasks wait for human resolution rather than automatic scheduling.
- **How it works here**: `getQueueCandidates` scans each set directory. For each valid piece, it checks whether its status is `'todo'` or `'pending'`, collecting only active pieces and sorting them deterministically.
- **Why this approach**: Filtering at the directory boundary gives callers a clean view of actionable work without requiring every consumer to know internal folder mechanics.
- **Approaches considered**: Dynamic re-scanning by every consumer (slow and duplicated) vs Centralized candidate selection query (chosen: consistent and clean).
- **Prior art inspected**: Work queue candidate filtering in priority-based schedulers (e.g. Celery and BullMQ ready queues).
- **What we get for free**: Native array filtering and sorting on parsed records.
- **From the docs**: `packages/dev-loop/directory/README.md`: 'getQueueCandidates selects from the valid pieces of every set it scans... A completed piece stays resolvable as another piece's dependency while getQueueCandidates excludes it from dispatch.'
- **What to notice**: Notice that `blocked` pieces are excluded alongside `done` pieces because blocked work requires human intervention!
- **Concepts to own**: Work pool candidacy: selecting runnable items from a broader state corpus based on lifecycle preconditions.
- **Interview angle**: How should a scheduler handle tasks in various lifecycle states? Answer: Expose explicit query methods that filter out finished and blocked items while preserving queue order.
- **Decisions you can now make alone**: You can safely add new sets to plans/pieces knowing `getQueueCandidates` will group them deterministically.
- **What you should learn from this**: Clear boundaries make happy systems! Filtering out non-runnable work early keeps workers productive and peaceful! 🌸
