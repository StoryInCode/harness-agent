# 00.01 — Piece Directory and Specification Parser

**Set:** 00-dev-loop · **Queue:** 1 · **Depends on:** none
**Status:** done
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-directory`

## Summary

This service finds, reads, and checks piece specification files. A piece is a markdown file under `plans/pieces/**/*.md` that describes one unit of work. The service scans each set directory, reads the metadata header at the top of each file, and checks the rules. It rejects a file over the line ceiling. It checks that the known sections appear in the required order. It checks that the declared Harness primitive and status are on their fixed lists of accepted values. The result is a checked record, so a broken or oversized specification cannot enter the development loop.

The parser is the executable form of the `axiom` blocks in `plans/AGENTS.md`. Those axiom checkers run their shell commands through `scripts/check-pieces.ts`, which calls this same parser. The severities match the axioms. `R-piece-size`, `R-piece-required-sections`, `R-harness-primitive-declared`, `R-piece-visible-result`, and `R-piece-teaches` are blockers. A blocker rejects the file. `R-piece-reuse-capture` is a warning. A warning is recorded on the returned record and the file still passes. The line ceiling, the discovery root, and the primitive vocabulary are validated `Config` fields. A deployment changes them from `cordis.yml`, not by editing code.

## Behaviour

- **Given** a valid piece markdown file within the configured ceiling carrying every blocker-required section **When** the directory parses it **Then** it returns a validated `PieceRecord` with status `todo`, extracted metadata, and no warnings.
- **Given** a piece file over the configured `maxLines` limit **When** validation runs **Then** parsing fails with `PIECE_SIZE_EXCEEDED`. The error reports the line count and the ceiling.
- **Given** a piece missing a blocker-required section such as `## Behaviour` **When** validation runs **Then** parsing fails with `MISSING_REQUIRED_SECTION`. The error names the missing section.
- **Given** two sections in the wrong order, so a section that belongs later appears before a section that must come first **When** validation runs **Then** parsing fails with `MISSING_REQUIRED_SECTION`. The error names the section that appeared too early.
- **Given** a piece with a `##`-prefixed line inside a fenced code block, opened by three backticks or three tildes **When** validation runs **Then** that line counts as content, not as a section heading. It does not satisfy a required section and does not break the section order. A fence left unclosed runs to the end of the file. A closing fence may be longer than its opener, as CommonMark specifies.
- **Given** a piece with a `##` heading outside the canonical list **When** validation runs **Then** the unknown heading is ignored, not reported. A piece may carry extra sections.
- **Given** a piece with every blocker-required section but no `## Reuse capture` **When** validation runs **Then** parsing succeeds. The record carries one `MISSING_RECOMMENDED_SECTION` warning.
- **Given** a piece declaring a primitive outside the accepted list, such as `Plugin` **When** validation runs **Then** parsing fails with `INVALID_HARNESS_PRIMITIVE`. The error lists the accepted values.
- **Given** a piece with a status other than `todo`, `pending`, `done`, or `blocked` **When** validation runs **Then** parsing fails with `INVALID_PIECE_STATUS`.
- **Given** a set directory with multiple pieces **When** `scanSet('00-dev-loop')` is called **Then** `pieces` comes back ordered by queue position, then by id. `rejected` is empty.
- **Given** a set with one malformed piece **When** the set is scanned **Then** the valid pieces are still returned. The malformed file appears in `rejected` with its code and findings. One bad file never blocks the rest of the set. A malformed sibling is data about the corpus, not an exception for an unrelated caller.
- **Given** a malformed piece elsewhere in the corpus **When** `getPiece` or `getQueueCandidates` runs **Then** the failure never names a file the caller did not ask about. `getPiece` raises a parse error only when the requested id's own file is the rejected one. `getQueueCandidates` selects from the valid pieces of every set it scans.
- **Given** a set whose completed pieces moved to `<set>/done/` per `R-done-pieces-moved` **When** `scanSet` runs **Then** the set directory and its `done/` subdirectory merge into one queue-ordered list.
- **Given** a completed piece in `<set>/done/` **When** dependencies are resolved or queue candidates are queried **Then** it resolves as a dependency. It is excluded from `getQueueCandidates`. Completed work is never offered for dispatch.
- **Given** a piece with status `blocked` **When** `getQueueCandidates` runs **Then** it is excluded too. A blocked piece waits on a human decision, not on a dispatch slot. Candidates are the `todo` and `pending` pieces only.
- **Given** no set name **When** `getQueueCandidates()` runs across every set **Then** results are ordered by set, then queue, then id. Queue numbers are local to one set. Mixing independent sets would offer a later set's first piece before an earlier set finished.
- **Given** a set name that no directory matches **When** `scanSet` or `getQueueCandidates` runs **Then** it rejects with `SET_NOT_FOUND` instead of returning an empty list. A mistyped set must never look like a finished one. A missing `done/` stays optional. A set whose pieces all moved into `done/` scans successfully and yields no candidates.
- **Given** the same piece id in both `<set>/` and `<set>/done/`, as a half-finished move leaves it **When** the set is scanned **Then** it rejects with `DUPLICATE_PIECE_ID`. The error names both paths.
- **Given** a consumer that must list the whole corpus, including `done` and `blocked` pieces **When** `listSets()` is called **Then** it returns every set directory name under the root, sorted by name. `getQueueCandidates` filters to `todo` and `pending`, so `listSets()` is the only public way to reach the other states.
- **Given** a root with no set directories **When** `listSets()` is called **Then** it returns an empty list. Nothing was named, so nothing is missing. **Given** a configured root that does not exist **When** it is called **Then** it rejects. Reading a misconfiguration as "no work" would idle every consumer silently.
- **Given** an unknown piece id **When** `getPiece('99.99')` is called **Then** it rejects with `PIECE_NOT_FOUND`.

## Harness fit

This capability is a `Service Provider` on the host plane. Consumers reach it as `ctx.devLoopDirectory`. It extends `@deepseek-ai/cordis.Service`, following the service-plus-`static Config` shape of `packages/skill/skill/src/index.ts:356-377`. It reads files through the existing filesystem seam `ctx.fs` (`packages/fs/fs/src/index.ts:116-236`), not through `node:fs`. A sandboxed or remote backend therefore governs every read. Parsing is a pure function over file text. A pure function gives the same output for the same input and touches nothing else. That makes the validator testable without a filesystem and reusable by the format gate in 00.10. `Directory` is the role word `docs/cookbook/adding-a-package.md:54` defines for a service that "exposes entries and metadata for discovery or selection". Nothing registers pieces, so `Registry` would be dishonest.

## Contracts

```typescript
export type PieceStatus = 'todo' | 'pending' | 'done' | 'blocked'

export type PieceFindingCode =
  | 'PIECE_SIZE_EXCEEDED'
  | 'MISSING_REQUIRED_SECTION'
  | 'MISSING_RECOMMENDED_SECTION'
  | 'INVALID_HARNESS_PRIMITIVE'
  | 'INVALID_PIECE_STATUS'
  | 'MALFORMED_PIECE_HEADER'

export interface PieceFinding {
  code: PieceFindingCode
  severity: 'blocker' | 'warning'
  message: string
}

export interface PieceMetadata {
  id: string
  title: string
  set: string
  queue: number
  dependsOn: readonly string[]
  status: PieceStatus
  primitive: string
  pkg: string
}

export interface PieceRecord extends PieceMetadata {
  path: string
  lineCount: number
  summary: string
  scenarios: readonly { given: string; when: string; then: string }[]
  warnings: readonly PieceFinding[]
}

/** Every field is optional so a cordis.yml row may set one and inherit the rest. Defaults and meanings are in the package README. */
export interface Config {
  root?: string
  maxLines?: number
  primitives?: string[]
}

/** One file the scan could not parse. A malformed sibling is data, not an exception. */
export interface PieceRejection {
  path: string
  code: PieceFindingCode
  findings: readonly PieceFinding[]
}

/** Valid records and rejected files, reported together so neither hides the other. */
export interface SetScan {
  pieces: readonly PieceRecord[]
  rejected: readonly PieceRejection[]
}

export class DevLoopDirectory extends Service {
  /** Set directory names under the configured root, so a consumer can enumerate the corpus. */
  listSets(signal?: AbortSignal): Promise<string[]>
  getPiece(id: string, signal?: AbortSignal): Promise<PieceRecord>
  scanSet(setName: string, signal?: AbortSignal): Promise<SetScan>
  getQueueCandidates(setName?: string, signal?: AbortSignal): Promise<PieceRecord[]>
  validate(filePath: string, content: string): PieceRecord
}
```

`PieceParseError extends Error` takes `(path, code, findings)` and exposes all three. The explicit code keeps the class total, with no unreachable fallback branch. Scan-level corpus defects are separate errors, because they belong to no single file. `SetNotFoundError` carries `code: 'SET_NOT_FOUND'` and `setName`. `DuplicatePieceError` carries `code: 'DUPLICATE_PIECE_ID'`, `pieceId`, and both `paths`. `PieceNotFoundError` carries `code: 'PIECE_NOT_FOUND'` and `pieceId`.

## Dependencies

None among pieces. This piece is the root entry point for discovery and validation of all specification pieces. It consumes the already-shipped `fs` service and declares it through `inject`.

## Teach me while you build

- **Background** — A *Cordis Service* is a class whose instance is published on the shared `Context` under one key. Consumers reach it as `ctx.<key>`. A *Service Provider* is the package that publishes one. *Dependency injection* here means a plugin lists in `inject` the services it cannot run without. Cordis delays starting the plugin until those services exist, and restarts it if they vanish. A *closed vocabulary* is a fixed set of accepted strings. Anything outside it is an error, not a new case.
- **How it works here** — `ctx.devLoopDirectory.scanSet('00-dev-loop')` resolves `<root>/00-dev-loop` through `ctx.fs.resolve()`. It lists the directory and its `done/` subdirectory with `ctx.fs.listDir()`. It keeps basenames matching `NN.MM-<kebab-slug>.md`. It reads each file with `ctx.fs.readText()` and hands the text to the pure `validate(path, content)`. `validate` splits lines, parses the header region before the first heading, walks `##` headings once against the canonical order while toggling a fenced-code flag, and collects findings. A blocker throws `PieceParseError`. Warnings ride on the record. Open `packages/dev-loop/directory/src/parse.ts` and `src/index.ts`.
- **Why this approach** — Parsing is split from I/O because two callers need it. This service calls it after `readText`. The 00.10 format gate already holds the text. A pure function also needs no temp directory to test. That is what makes 100% per-file coverage affordable.
- **Approaches considered** — (1) *Fence-aware line scan, chosen.* The idiom in `scripts/verify-agent-note-format.ts:44-70`. Zero dependencies, about 3 lines for the fence toggle. It wins because the piece format is ATX-`##`-only by construction. (2) *`mdast-util-from-markdown`,* already a root devDependency and a runtime dependency of `packages/client/ui-primitives`. The Research role recommended it. It would win the moment the format admits setext or HTML headings. Measured today: zero such occurrences across 117 pieces. (3) *`remark` + `unified-lint-rule` + `vfile-message`,* used by remark-lint, MDX and Gatsby. A real plugin architecture, correct if third parties must contribute rules. Rejected as about 6 packages and an inversion of control nothing here needs. (4) *YAML frontmatter validated by schemastery,* already mounted for `Config`. Rejected because `PIECE-FORMAT.md:11-13` fixes a `**Bold:** value ·` prose header instead.
- **Prior art inspected** — `markdownlint`'s `lib/md043.mjs` (source read, MIT) solves exactly this problem with a single monotone cursor over a required-heading array plus `addErrorDetailIf(expected, actual)`. Its walk is adopted. Its stop-at-first-error is not. `vfile-message`'s readme (API docs only, MIT) models severity as `fatal: true|false|undefined` on one message type. That is evidence for one `PieceFinding` carrying `severity`, rather than Danger JS's four parallel arrays (`source/dsl/DangerResults.ts`, source read, MIT), which force every consumer to know all four names. Cucumber Gherkin's `javascript/src/Errors.ts` (source read) accumulates into `CompositeParserException` instead of throwing first. That is why `findings` is a list. Conftest encodes severity in rule names (`deny`/`warn`). Rejected because a naming convention is invisible to TypeScript. No code was copied from any of them.
- **What we get for free** — Cordis supplies service publication, `inject` gating, and disposal on unload. `@deepseek-ai/schemastery` validates `Config` at load, so a bad `maxLines` in `cordis.yml` fails the mount instead of surfacing as a strange parse result. The `fs` seam supplies path resolution, listing, UTF-8 decoding, and binary rejection. We write the markdown grammar and the severity model. Nothing else.
- **From the docs** — `plans/AGENTS.md` `R-piece-size` states the ceiling and narrates its own history. 160 originally. 220 when the visibility, teaching and reuse-capture sections became mandatory. 280 once `Resources and proof` became required. `Config.maxLines` tracks whatever that axiom currently says. That is why this piece quotes the axiom by name instead of pinning a number in prose. A quoted number goes stale the moment the axiom moves, as this very bullet did twice.
- **What to notice** — The section walk is one forward pass with a monotone cursor. A cursor is a finger moving forward through a checklist and never moving back. So a missing section and a transposed section fall out of the same loop. And `validate` never reads the filesystem. `path` exists only for messages.
- **Concepts to own** — *Pure function / referential transparency* (`validate`). *Functional core, imperative shell*, meaning computation separated from I/O (`parse.ts` vs `index.ts`). *Total vs partial function*: `validate` returns findings, while `getPiece` rejects with `PIECE_NOT_FOUND`. *Tagged union / closed vocabulary* (`PieceStatus`, `PieceFindingCode`). *Single-pass algorithm with a monotone cursor* (the section walk). *Severity-based policy evaluation*: a blocker rejects, a warning rides along. *Error accumulation versus fail-fast* (`findings` as a list). *Schema validation at a trust boundary*: schemastery over `cordis.yml`, because file text is untrusted input.
- **Interview angle** — *"How would you validate that a document follows a required structure?"* Answer: one forward pass with a cursor over the required list. A heading found before the cursor is reported with expected/actual. Required headings never reached are reported at the end. Missing and misordered are the same defect in a sequence check. Follow-up: *"How do you report every problem instead of stopping at the first, and why does markdownlint choose to stop?"* Then: *"When do you take a dependency instead of writing forty lines?"* mdast was already in the lockfile and would delete real edge cases, but this corpus measured zero of them, and `unified` would add a plugin pipeline while deleting no owned code. Follow-up: *"What is your rollback plan when the dependency changes its AST in a major version?"*
- **Decisions you can now make alone** — Adding, reordering, or re-severity-ing a canonical section. The list and severity map are data, so change the constant and add the rejected/accepted-with-warning tests. Finding message wording, following the `path:line: quoted-text` form the other gates print. Whether the section walk stops after the first ordering violation. **Escalate:** any dependency not already in the lockfile. Adding a `PieceFindingCode` member, because 00.04 and 00.10 will branch on it. Changing the `maxLines` default, which tracks `R-piece-size` and must move with it. Any use of `node:fs`, which the `ctx.fs` seam forbids. **Still open for your judgment:** whether `validate` should return `{ record, findings }` uniformly instead of throwing for blockers and returning warnings. That is two channels for one concept, with no repository precedent either way.
- **Lesson** — When a written rule already names a checker, implement the rule where it can return structured, severity-carrying findings. A document citing a script that does not exist enforces nothing.

## Reuse capture

- **Reuse candidate:** ordered-section markdown validator · Walks a fixed heading sequence once, fence-aware, reporting missing versus out-of-order sections with per-section severity · Used by `validate()` in `DevLoopDirectory` · Reusable for Agent Note templates, postmortem templates, and README structure gates, several of which hand-roll their own scan in `scripts/` · Would need the section list and severity map lifted into parameters instead of module constants · Evidence: the ordering and severity cases in `packages/dev-loop/directory/tests/directory.spec.ts` · Confidence: medium
- **Known limitations** — Only ATX `##` headings participate. Setext headings are not recognised, which is safe only while the corpus contains none. Line ranges inside a References table are not verified against the cited file. 00.08 owns that. Do NOT reuse this to judge prose quality. It checks structure only.
- **Failure worth keeping** — The first implementation was written before any test existed. It scanned `##` headings with a regex over every line and silently treated a `##` line inside a fenced code block as a section heading. The Research role found it by comparing against `markdownlint`. The trigger is *not* `PIECE-FORMAT.md`, which `isPieceFilename` rejects so `scanSet` never reads it. The trigger is a piece that embeds a markdown template inside `## Contracts` — this piece already embeds a fenced `typescript` block — plus the 00.10 gate calling `validate()` on text it holds directly. The Test Writer role caught that misattribution while writing the case for it. Transferable lesson: a structure check over markdown must know where code fences are. Writing the implementation before the tests hides exactly this class of defect. And a justification can be wrong even when the rule it argues for is right.
- **Anti-pattern worth keeping** — This piece twice pinned a ceiling number in prose and twice went stale. It first specified 160 while the axiom said 220. It later quoted the 220 text verbatim after the axiom moved to 280. The Implementer role caught the second instance. A specification's own citation is not evidence until the cited lines are reopened. A number copied out of an axiom is a fact with a decay rate. Name the axiom instead.

## Acceptance

1. Unit tests in `packages/dev-loop/directory/tests/directory.spec.ts` pass, covering valid parsing, metadata extraction, and scenario extraction.
2. The parser rejects files over the configured ceiling with `PIECE_SIZE_EXCEEDED`, and accepts a file of exactly the ceiling.
3. The parser rejects pieces with missing or out-of-order blocker sections with `MISSING_REQUIRED_SECTION`, ignores unknown headings, and ignores `##` lines inside fenced code blocks.
4. The parser rejects primitives outside `Config.primitives` with `INVALID_HARNESS_PRIMITIVE`, and statuses outside the four states with `INVALID_PIECE_STATUS`.
5. A piece lacking only `## Reuse capture` validates successfully and carries exactly one warning.
6. `listSets()` returns the corpus's set directories sorted by name, excluding files and each set's own `done/`, returning `[]` for an empty root and rejecting for a missing one. `getQueueCandidates` enumerates through it, proven by a case asserting candidate set order agrees with the reported order rather than restating the sort.
7. `scanSet('00-dev-loop')` over the real `plans/pieces` corpus returns every piece of the set in queue order, whether it sits in the set directory or in its `done/` subdirectory. The assertion checks the invariants the parser does **not** already guarantee. These are strictly increasing queue positions, unique ids, each record's declared `**Set:**` agreeing with the directory holding it, and a file under `done/` if and only if it declares `done`. Plus one anchor id proving the scan reached the right tree. It never pins an id list, because the set grows.
