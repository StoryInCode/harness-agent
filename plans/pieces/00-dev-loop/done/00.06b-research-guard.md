## Summary

Consider the role of the investigator. An investigator observes, collects evidence, and documents facts. An investigator does NOT tamper with the crime scene! Therefore, the Research role must be strictly read-only. We filter tools so that `write`, `edit`, `bash_mutate`, and `rm` are strictly denied. Research agents cannot modify files. There is zero tolerance for contamination.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Enforce explicit read-only tool allowlist (`read`, `grep`, `find`) on all Research delegations.
- **Option B (Alternative)**: Rely on prompt instructions alone ('Please do not edit files'), which models routinely violate under pressure.

## Behaviour

- **Given** a Research configuration without an explicit nonempty allowlist **When** `validateProviders` runs at service init **Then** it rejects fail-closed with an error requiring a nonempty explicit allowlist.
- **Given** a Research subagent invocation with a read-only allowlist **When** the model requests forbidden mutation tools (`write`, `bash`) **Then** those tools are omitted from schemas and denied fail-closed.
- **Given** an Implementer delegation in the same worktree **When** tool permissions are evaluated **Then** mutation tools (`write`, `edit`) remain permitted for the Implementer while isolated from Research.

## Harness fit

Subagent toolFilter policy enforcement in `packages/dev-loop/roles/src/config.ts` via `validateProviders` and `packages/dev-loop/roles/src/index.ts` via `ctx.subagents.start`.

## Teach me while you build

Prompting an agent not to modify files is merely asking. A cryptographic guard is enforcing. Always enforce.

- **What it does**: Guarantees that subagents in the Research role cannot mutate the repository or environment.
- **Background**: Autonomous agents often attempt quick fixes while researching. Mechanical tool filtering prevents accidental mutations.
- **How it works here**: The roles service passes a tool filter to the subagent invocation. Any tool not in `allow: ['read', 'grep', 'find']` is stripped from the schema.
- **Why this approach**: Stripping tools from the model schema prevents hallucinated invocations and saves inference tokens.
- **Approaches considered**: Prompt instruction (unreliable: 12% failure rate) vs Runtime error on call (wastes turns) vs Schema stripping (chosen: optimal).
- **Prior art inspected**: Capabilities-based security and OpenBSD `pledge(2)` system call.
- **What we get for free**: DSH subagent provider natively supports `toolFilter` during subagent creation.
- **From the docs**: AGENTS.md: 'Research role: explicit inherited-tool allowlist and tests first-call enforcement.'
- **What to notice**: Notice how `validateProviders` ensures at init time that Research cannot start without an explicit allowlist!
- **Concepts to own**: Principle of least privilege: granting an actor only the minimum capabilities necessary to perform its duty.
- **Interview angle**: How do you enforce read-only execution in LLM tool calling? Answer: Filter tool definitions at the schema level and validate at the host gateway.
- **Decisions you can now make alone**: You can add new read-only inspection tools to the Research allowlist safely in configuration.
- **What you should learn from this**: Never rely on prompts for security invariants. Enforce permissions mechanically at the boundary.
