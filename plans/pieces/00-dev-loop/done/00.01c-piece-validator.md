## Teach me while you build

Listen up! A validator's job is to protect the system boundary by enforcing structural invariants without imposing artificial limits where they don't belong.

- **What it does**: Validates that a piece file declares required header fields, uses canonical Harness primitives from the closed vocabulary, and orders sections canonically.
- **Background**: We don't mechanically cap markdown documents with arbitrary line limits. Bounding belongs on code through modularization, functional design, and separation of concerns (where ~150 lines is an informal heuristic signaling that code needs splitting). For specs, deterministic validation enforces structure: closed vocabularies, required metadata, and canonical section sequence.
- **How it works here**: The parser extracts header fields, checks them against `REQUIRED_HEADER_FIELDS`, validates the declared primitive against `primitives` (`HARNESS_PRIMITIVES`), and checks canonical section sequence with `checkSectionOrder`.
Here is the actual closed-vocabulary check from `packages/dev-loop/directory/src/parse.ts` (lines 508-513):
```typescript
  const primitive = headerField(fields, 'Harness primitive')
  checkDeclaredField(fields, 'Harness primitive', findings, value => primitives.includes(value) ? [] : [{
    code: 'INVALID_HARNESS_PRIMITIVE',
    severity: 'blocker',
    message: `Harness primitive "${value}" is not one of ${primitives.join(', ')}`,
  }])
```
Notice how `checkDeclaredField` decouples finding generation from field presence: if the field is present, the predicate checks whether `primitives.includes(value)` and returns a structured blocker finding if it fails.
- **Why this approach**: Aggregating all findings into a list before throwing gives the user complete feedback in one go rather than one error at a time.
- **Approaches considered**: Throw-on-first-error (annoying: fix one error, run, get next error) vs Collected findings error (chosen: lists everything).
- **Prior art inspected**: GCC and Rust compiler error diagnostic collectors.
- **What we get for free**: TypeScript discriminated union on `PieceFindingCode` makes error handling exhaustive.
- **From the docs**: `plans/AGENTS.md`: "Every piece file declares a Harness primitive from the closed vocabulary in its `## Harness fit` section, and names the owning package."
- **What to notice**: Notice that warnings don't block parsing unless there is at least one blocker finding!
- **Concepts to own**: Validator pattern: decoupling linting/validation rules from AST data construction.
- **Interview angle**: How do you design a compiler error reporter? Answer: Collect warnings and blockers separately, throw on first blocker threshold.
- **Decisions you can now make alone**: You can add new warnings (e.g. word count suggestions) without blocking valid piece files.
- **What you should learn from this**: Enforce strict closed vocabularies and schema boundaries where correctness is non-negotiable; let code modularity and functional design guide component size. Keep it lean, hacker style.
