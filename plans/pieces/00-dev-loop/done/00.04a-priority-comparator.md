## Summary

Yo! In an asynchronous queue, if your sort order isn't 100% deterministic, you get random race conditions depending on which millisecond an item popped in. Daru doesn't do flaky randomness. We implement a strict multi-key ordering inside `DevLoopQueue`: primary sort by numeric queue position ascending, secondary sort by monotonic admission sequence FIFO order. Same inputs = identical dispatch order every single time. No RNG.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Deterministic two-key ordering (canonical queue number, then FIFO sequence counter) with zero random tie-breakers.
- **Option B (Alternative)**: Arbitrary non-deterministic dispatch based on unsequenced wall-clock timestamps or race conditions.

## Behaviour

- **Given** two queued pieces with queue positions 1 and 2 **When** queued entries are ordered for dispatch **Then** the piece with queue position 1 is selected before the piece with queue position 2.
- **Given** two pieces with identical queue position 10 submitted sequentially **When** queued entries are ordered for dispatch **Then** the piece admitted earlier runs first using monotonic sequence FIFO tie-breaking.
- **Given** pieces submitted with diverse queue positions in arbitrary arrival order **When** capacity becomes available **Then** they dispatch in strictly deterministic sequence ordered by queue number then admission order.

## Teach me while you build

Let me teach you the golden rule of systems hacking: determinism is king. Flaky tests are born from non-deterministic queues.

- **What it does**: Orders queued pieces deterministically so agents and tests always execute tasks in the exact same sequence.
- **Background**: In distributed scheduling, priority queues must use total orders to prevent oscillating queue states.
- **How it works here**: In `DevLoopQueue`, `this.sequence++` assigns a monotonic sequence number `order` at admission. The `queued()` helper sorts entries by `a.view.queueOrder - b.view.queueOrder || a.order - b.order`.
- **Why this approach**: Monotonic sequence fallback guarantees that no two distinct queue entries ever produce undefined ordering, creating a deterministic total order.
- **Approaches considered**: Timestamp FIFO (flaky: clock jitter causes reordering) vs Random tie-breaking vs Monotonic sequential counter tie-breaking (chosen).
- **Prior art inspected**: POSIX priority queues and Linux CFS (Completely Fair Scheduler) red-black tree ordering.
- **What we get for free**: Standard JavaScript `Array.prototype.sort` runs an in-place, stable TimSort.
- **From the docs**: AGENTS.md: 'Prefer symmetry for parallel values... Explicit > implicit at package boundaries.'
- **What to notice**: Notice that wall-clock timestamps are NOT used in dispatch ordering, keeping re-runs completely replayable!
- **Concepts to own**: Total ordering: a binary relation where every pair of elements is comparable, antisymmetric, and transitive.
- **Interview angle**: How do you ensure deterministic replay in event-driven systems? Answer: Use total ordering with static sequence tie-breakers instead of wall-clock time.
- **Decisions you can now make alone**: You can add priority weight multipliers as long as the monotonic sequence fallback remains intact.
- **What you should learn from this**: Eliminate non-determinism at the source. Deterministic software is debuggable software.
