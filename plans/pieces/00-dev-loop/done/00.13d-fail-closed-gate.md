## Summary

Here is the ultimate verdict. If a piece contains even ONE unverified load-bearing claim, incomplete inventory coverage, or if any cited reference or finding was contradicted by empirical inspection, the piece is inadmissible. We enforce this through `DevLoopClaims.requireAdmissible()`. Inadmissible pieces reject fail-closed with `CLAIM_VERIFICATION_OUTSTANDING` or `CLAIM_REPORT_STALE` before worker dispatch or completion. The author must amend the piece or resolve the evidence. The detective permits no uncorroborated assertions.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Block dispatch fail-closed if any load-bearing claim remains unverified or contradicted.
- **Option B (Alternative)**: Allow pieces with unverified claims to be dispatched, risking builds based on false assumptions.

## Behaviour

- **Given** a verified piece with current source and evidence identities and supported load-bearing claims **When** `requireAdmissible(pieceId, pieceDigest, signal)` is called **Then** it returns the detached `ClaimVerificationReport` authorizing downstream dispatch.
- **Given** a piece with an unverified load-bearing claim or incomplete inventory coverage **When** `requireAdmissible(pieceId, pieceDigest, signal)` runs **Then** it throws `CLAIM_VERIFICATION_OUTSTANDING` fail-closed and blocks dispatch.
- **Given** a piece where research proved a load-bearing claim was contradicted **When** `requireAdmissible(pieceId, pieceDigest, signal)` executes **Then** it throws `CLAIM_VERIFICATION_OUTSTANDING` and leaves the piece unadmitted for revision.
- **Given** a piece whose source text or evidence has drifted since verification **When** `requireAdmissible(pieceId, pieceDigest, signal)` runs with the previous digest **Then** it throws `CLAIM_REPORT_STALE` rather than reusing stale admission.

## Contracts

```typescript
import { Service } from '@deepseek-ai/cordis'
import type { ClaimVerificationReport } from './types.ts'

export class DevLoopClaims extends Service {
  /**
   * Recheck exact piece and evidence identities; unresolved work rejects OUTSTANDING, changed identity STALE.
   * @param pieceId - Canonical piece identifier.
   * @param pieceDigest - Caller-captured raw SHA-256 of approved source.
   * @param signal - Cancellation lifetime for rechecks.
   * @returns Current admissible report only, never an exception-authorized report.
   */
  requireAdmissible(pieceId: string, pieceDigest: string, signal: AbortSignal): Promise<ClaimVerificationReport>
}

export interface ClaimVerificationReport {
  readonly reportId: ClaimReportId
  readonly pieceId: string
  readonly pieceSha256: string
  readonly inventoryDigest: string
  readonly checkedAt: number
  readonly referencesDigest: string
  references: ProvenanceObservation
  delegationIds: DelegationId[]
  inventory: InventoryClaim[]
  inventoryCoverage: { complete: boolean; limitations: string[] }
  findings: ClaimFinding[]
  additionalClaims: AdditionalClaim[]
  limitations: string[]
  state: 'completed' | 'failed' | 'aborted'
}
```

## Teach me while you build

The case cannot proceed to trial on unverified rumors. Every allegation must be corroborated or dismissed.

- **What it does**: Prevents pieces with unverified, contradicted, or stale claims from entering the execution pipeline.
- **Background**: Building software on false assumptions wastes enormous time. Gating claims before execution stops defects early.
- **How it works here**: Inspects the piece and its stored verification report in `DevLoopClaims.requireAdmissible()`. If any load-bearing claim is `unverified` or `contradicted`, or if source or evidence digests drifted, rejects fail-closed with `CLAIM_VERIFICATION_OUTSTANDING` or `CLAIM_REPORT_STALE`.
- **Why this approach**: Enforces the R-claims-verified meta axiom mechanically: false or unproven claims halt the process before code is written.
- **Approaches considered**: Warning banner (ignored by agents) vs Fail-closed dispatch block (chosen: stops execution).
- **Prior art inspected**: Formal logic premise validation and legal standards of evidence admissibility.
- **What we get for free**: Built-in integration with Cordis service injection (`ctx.devLoopClaims`) and cryptographic SHA-256 fingerprinting.
- **From the docs**: `plans/AGENTS.md`: "When verification contradicts the piece: STOP and report the contradiction with its evidence... The piece is amended first."
- **What to notice**: Notice that stopping on a contradiction is treated as a victory, not a failure!
- **Concepts to own**: Fail-closed admission: rejecting requests unless all required evidence is positively affirmed and verified against current storage.
- **Interview angle**: How do you prevent hallucinated architectural requirements from entering production? Answer: Fail-closed claim admission gates requiring verified citations and cryptographically proven evidence before allowing worker dispatch.
- **Decisions you can now make alone**: You can distinguish between load-bearing claims that require admission gating and non-load-bearing context that does not block execution.
