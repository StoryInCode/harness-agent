# 00.12 — Durable Lifecycle Integration and Reconciliation

**Set:** 00-dev-loop · **Queue:** 12 · **Depends on:** 00.02, 00.04, 00.06
**Status:** done
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-persistence`

## Summary

This piece makes lifecycle transitions durable and recoverable. It does three things:

1. Save every transition before the system announces success.
2. Rebuild the lifecycle from saved records at startup. `Hydrate` means load saved state back into memory.
3. Show interrupted operations so a human can reconcile them. `Reconcile` means compare records and decide what really happened.

This proposed Host service owns the `dev_loop` storage domain. It does not own the domains already owned by Roles, References, Claims, Handoff or Gates. Queue callbacks and live Agents cannot be restored from stored rows. A file in done/ is an observation, not completion authorization.

## Behaviour

- **Given** durable mode **When** any legal lifecycle transition resolves **Then** its committed record is durable before memory publication and notification.
- **Given** a failed intent write **When** transition is attempted **Then** no lifecycle or filesystem mutation begins.
- **Given** a completion interrupted between Git move and durable commit **When** the Host restarts **Then** it reports an unresolved intent and withholds admission rather than inventing completion or rollback.
- **Given** consistent committed records **When** Lifecycle initializes **Then** it hydrates from those records before accepting calls, including pending/blocked states not reflected in old disk headers.
- **Given** a path/header/record discrepancy **When** startup scans **Then** it records an anomaly without auto-promoting done or issuing an illegal done-to-pending transition.
- **Given** historical queued work or requested-only delegation **When** reopened **Then** it remains historical/unresolved, and no callback, Agent, lease or automatic dispatch is reconstructed.
- **Given** authoritative malformed data **When** the domain opens **Then** opening rejects, and no backup-and-skip policy hides the record.

Two terms used above: an `intent` is a record written before an operation runs. An `anomaly` is a recorded mismatch that needs a human decision.

## Harness fit

The **Service Provider** publishes `ctx.devLoopPersistence`, injecting `storageDomain`, `devLoopDirectory` and `fs`. It does not inject Lifecycle, Queue or Roles. The dependency direction has one reason:

```text
Lifecycle consumes persistence
        ↓
Queue already consumes Lifecycle
        ↓
Roles consumes Queue
```

This direction prevents a dependency cycle. Human consumers assemble history using each owner’s public reads.

Open `defineDomain({name:'dev_loop',version:1,layout:'single',tables:{...}})` with schema-validated transition records and reconciliation decisions. One record keyed by branded transition id contains intent plus optional terminal observation. Commit updates that same row on the domain write chain.

Per-piece committed status comes from the ordered sequence of records. There is no second, separately written pieces table. Concurrent transitions are serialized by Lifecycle. The domain update supplies durable-before-memory publication. It is not a transaction spanning Git and storage. A `transaction` here means one all-or-nothing operation across both systems.

### Required adjacent Lifecycle amendment

Current Lifecycle has one synchronous claim/CAS writer, asynchronous initialization from Directory, a serial pre-complete policy hook only for done, and unawaited announcements. No existing extension covers all transitions or hydration. Durable integration therefore belongs in the existing adjacent `dev-loop/lifecycle`, not Agent-loop, a wrapper that direct callers bypass, or an announcement listener.

Add explicit `Config.durability: 'memory' | 'required'`. Omission keeps the existing standalone memory behavior. Keep Lifecycle's existing static inject list. Declare the typed service through Context augmentation and resolve optional presence with `ctx.get`. Cordis has no optional Inject descriptor.

The required-mode Loader entry adds literal `inject: [devLoopPersistence]` metadata and `config.durability: required`. So provider activation precedes Lifecycle initialization. Memory-mode entries omit that dependency. Required config without an available provider rejects initialization. Missing required entry dependencies reject through app-boot's `assertEntriesActivated`, not merely `assertEntriesLoaded`. Final 00.14 always uses required config plus entry injection. Memory mode is nondurable and cannot serve final acceptance.

In required mode, Lifecycle awaits persistence hydration before it publishes its service-ready state. Every transition follows this order:

1. Keep its existing claim before the first await.
2. Await durable intent before side effects.
3. Await committed observation before publishing status, releasing claim, and emitting.
4. Join all transitions during disposal, including non-done edges.

After a side effect followed by recording failure, quarantine that piece from further transitions until explicit reconciliation. `Quarantine` means the piece is blocked from new transitions. A rejected promise must disclose whether a filesystem effect may have happened. It cannot claim unchanged disk.

Keep `piece/pre-complete` as the policy veto under the held done claim. A pre-complete veto leaves committed pending state. Release the claim before an orchestration owner may request pending-to-blocked. Do not persist a committed done row before Gates approves or before Git move succeeds. No changes to legal transitions or Agent-loop are authorized.

| Extension considered | Why insufficient |
|---|---|
| piece/approved, piece/blocked, piece/completed | Announcements occur after memory mutation, async listeners are not awaited, and blocked-to-todo has no announcement. |
| piece/pre-complete | Awaited but covers only done, runs before Git effects, and provides no hydration or post-effect durability point. |
| Command/approval wrapper | Other direct transition callers bypass it; it cannot repair Lifecycle’s initial cache. |
| Directory scan or domain/changed listener | Directory is asynchronous source observation; domain notifications are not transaction participants or a Lifecycle hydration API. |
| Separate persistence service alone | Supplies durable I/O but cannot intercept the sole writer or its private cache. The narrow explicit consumer integration above is required. |

## Contracts

The following concrete persistence operations are proposed. Test Writer freezes exact DTOs and failures before implementation. These are not an extensible journal framework.

- `loadLifecycle(signal): Promise<LifecycleHydration>` opens no second domain and returns committed per-piece status/path/revision, unresolved intent ids and anomalies. Lifecycle adopts this result once during initialization, and conflicted ids remain known but unavailable for admission.
- `beginTransition(request): Promise<TransitionId>` receives piece id, expected/from/to, canonical source and destination paths, observed source digest/version, monotonic piece sequence, reason and optional human authorization facts. It durably records intent and returns its branded id.
- `finishTransition(id, observation): Promise<void>` accepts only the Lifecycle-owned actual outcome (`committed` with observed path/content or `failed` with effect/cleanup uncertainty). No model or command exposes this method or accepts arbitrary passed/done fields.
- `getHistory(pieceId): Promise<readonly TransitionRecord[]>` and `getAnomalies(): Promise<readonly ReconciliationAnomaly[]>` return detached deterministic observations.
- `acknowledgeAnomaly(anomalyId, invocation, reason, signal): Promise<ReconciliationAcknowledgment>` rereads the anomaly’s local source observations and records actual root human commandId/Session/reason against that version. Acknowledgment does not clear quarantine, change status or certify completion. No generic reconcile/promote method is exposed.

The package’s separate `./command` Consumer injects commands, agents and devLoopPersistence and registers `dev-loop-recovery`. Grammar: `inspect <pieceId>` returns transition history and current anomalies, and `acknowledge <anomalyId> <reason...>` records the actual root human acknowledgment. Reject extra/missing arguments and non-root mutations. Return bounded CommandResult with no silent truncation. This consumer needs no Gates, Roles, Queue or subprocess injection because it neither evaluates completion nor changes admission. It is a concrete inspection/reconciliation-decision path, not a recovery execution engine.

Records include repository identity, piece id, source digest/version, expected status, target, sequence, timestamps, source/destination paths, reason, intent id and terminal effect certainty. Durable parsers validate and brand ids. Config requires repositoryRoot, maxRecordBytes and maxHistoryRecords. Complete UTF-8 records and rendered history must reject overflow explicitly. The composition selects a durable backend and storage root. Dispose after admitted terminal recording attempts, then await domain.close.

### Human acceptance and source identity

Extend `Lifecycle.transition(pieceId, expected, to, reason?, signal?, authorization?)` with a typed final authorization argument for human acceptance. In required mode, todo-to-pending requires four facts: actual command or tool invocation identity, receiving Session id, displayed source digest/version, and decision. Lifecycle rechecks current source identity. Stale approval rejects.

This is evidence of the human interaction. It is not a caller-supplied `approved: true` flag. Only the existing human approval and command consumers construct these facts from their actual invocation and result. No model input may manufacture them.

The existing approval Consumer already reads source before asking and checks its version after Accept, then calls transition. UserQuestions.ask returns answers, not a receipt id. Forward the actual tool invocation callId, receiving Session, displayed source identity and validated answer observed by this Consumer. Persist those facts with intent, without inventing a question receipt or changing user-questions. Command acceptance uses its actual commandId and explicit reviewed digest.

This records trusted Consumer observation of human interaction. It is not independent proof against malicious trusted plugins. Question and Change remain logged tool decisions, not todo-to-pending transitions. A reopened pending record proves historical acceptance of the recorded revision. It does not prove acceptance of subsequent edits.

### Hydration and explicit recovery

For a consistent record, restore its committed status even if a non-done disk header remains todo. Current Lifecycle only edits headers on done. Compare source identity under a documented header-only normalization for lifecycle-owned status edits. Preserve both raw digests. A substantive source change invalidates approval and evidence.

Each of the following is an anomaly, not an automatic status correction:

1. A done record missing its destination.
2. Duplicated files.
3. An unrecorded done file.
4. Changed source.
5. An unknown piece.
6. A pending intent.

No record may be promoted solely from directory location. Ordinary todo pieces can seed initial corpus observations. An unjournaled done piece is quarantined and reported. So a corpus containing completed dependencies requires a separately accepted bootstrap-evidence import before those dependencies can authorize dispatch. This piece does not invent that evidence or expose an import-pass API. Final 00.14 tests use a fresh todo corpus and journal genuine completion. Deployment of a legacy done corpus remains an explicit blocked product decision until bootstrap policy is specified and accepted.

The supported recovery operation observes and acknowledges anomalies only. It never clears quarantine or promotes interrupted intent to done. No Queue pause API or stopped-admission guarantee is invented. Executing repairs or validating Git and Gates evidence needs a separately specified orchestration consumer and a real admission-stop owner. That extension is deliberately outside this piece.

Acknowledged anomalies survive remount and remain blocked. Consistent committed records hydrate normally on remount. Hydration does not call done-to-pending or mutate Lifecycle’s private map. Repairing a confirmed done piece back to pending is not legal. Reopening policy remains outside scope.

Persisted QueueEntry observations, if displayed, have observation times and never claim current activity. A new dispatch requires a fresh live initiator and new Roles request. There is no id-to-Agent reconstruction or automatic restart replay.

## Teach me while you build

- **What it does:** Saves what actually committed and exposes what a crash left uncertain.
- **Background:** `Compare-and-set` rejects stale writers. It means write only if the status is still what you read. A `write-ahead intent` records an attempted operation before its side effect. `Reconciliation` compares independent observations rather than guessing a transaction succeeded.
- **How it works here:** Inspect Lifecycle.claim and complete for ownership, then Domain.put/update for durability. The new direct Lifecycle consumer awaits persistence at both intent and publication points. Approval forwards the actual reviewed revision.
- **Why this approach:** A post-event mirror cannot make a direct transition durable. A concrete adjacent service plus narrow sole-writer integration covers every caller without changing Agent-loop.
- **Approaches considered:** Domain-backed integration is chosen. Session-event projection suits facts owned by one conversation, unlike shared piece lifecycle. Temporal is an external orchestration alternative, but reported SDK promises alone do not establish its server replay semantics or justify adding it here.
- **Prior art inspected:** Research reported Temporal sdk-typescript v1.11.8 workflow.ts and workflow-handle.ts inspection. No external code reused, and no crash guarantee borrowed.
- **What we get for free:** storageDomain validates reopen and serializes durable writes. Lifecycle already owns legal edges and claims. This application owns intent interpretation, approval identity and crash reconciliation.
- **From the docs:** Domain.close says “reject new writes immediately, drain already-queued writes”. Stop transitions and finish recording before close.
- **What to notice:** Non-done transitions do not currently update disk headers. Blocked-to-todo has no event. Event subscription cannot cover this lifecycle.
- **Concepts to own:** `Commit-point publication` delays visible status until durable success. `Referential integrity` links authorization and evidence ids. `Distributed transaction uncertainty` appears between Git and storage.
- **Interview angle:** “How do you recover a move followed by a failed database write?” Keep the intent and inspect both systems. Never infer success from one filename. Follow-up: quarantine prevents retries from duplicating an uncertain effect.
- **Decisions you can now make alone:** Add anomaly diagnostics and bounds tests. Escalate reopening done, stronger authorization receipts, or automatic recovery to the relevant owner.
- **What you should learn from this:** Durable observation is not restoration of a live execution capability.
