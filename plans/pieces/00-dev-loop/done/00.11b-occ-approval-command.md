## Summary

Yo! When the operator runs `/dev-loop approve 00.01a <sha256>`, Daru handles the OCC validation! Optimistic Concurrency Control means we check if the piece specification changed while the operator was reviewing it. The command handler reviews the current validated piece source, compares its raw SHA256 digest against the provided hexadecimal hash, requires live root human authority, and atomically transitions the piece from `todo` to `pending` in `ctx.devLoopLifecycle` with `HumanAuthorization` metadata. It changes only memory and never enqueues work directly. If someone edited the file behind your back, or if the piece is not in `todo` status, it throws a refusal immediately. Total safety!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Validate SHA-256 digest against current reviewed source and require live root human authority before committing the `todo`-to-`pending` lifecycle transition with authorization metadata.
- **Option B (Alternative)**: Blindly transition piece state by ID alone or automatically enqueue execution tasks, risking TOCTOU races and violating lifecycle/queue separation of concerns.

## Behaviour

- **Given** a piece in `todo` state and a matching 64-character SHA256 digest **When** `/dev-loop approve <id> <sha256>` is executed by the root human agent **Then** it transitions the piece from `todo` to `pending` in `ctx.devLoopLifecycle` and returns `Piece <id>: pending.`
- **Given** a provided SHA256 digest that does not match the reviewed source content **When** `/dev-loop approve` is executed **Then** it throws a `Refusal` stating `Stale SHA256 digest; show the current source before approving.`
- **Given** a piece that is not in `todo` status (e.g. `pending`, `blocked`, or `done`) **When** `/dev-loop approve` is executed **Then** it throws a `Refusal` stating that the piece is in another state and approve requires `todo`.
- **Given** a non-root or child agent invocation **When** `/dev-loop approve` is executed **Then** it throws a `Refusal` requiring the exact live root human agent.

## Teach me while you build

OCC: Optimistic Concurrency Control. Assume no conflicts until commit time, then verify hashes. Daru's golden rule for safe hacking!

- **What it does**: Allows human operators to approve pieces securely by verifying content SHA256 hashes before transitioning state to `pending`.
- **Background**: In web and CLI workflows, operators inspect a piece, ponder, and run approve seconds later. OCC ensures nothing in the file mutated during that think time.
- **How it works here**: The command parses `<id>` and `<sha256>`, calls `review(ctx, id, signal)` to get current source and its hash, verifies hash equality, confirms root authority, and calls `ctx.devLoopLifecycle.transition(id, 'todo', 'pending', undefined, signal, authorization)`.
- **Why this approach**: Verifying exact SHA256 content hashes prevents TOCTOU tampering and ensures the operator approved the exact byte-for-byte spec currently on disk.
- **Approaches considered**: File locking during review (blocks concurrency, fragile across crashes) vs Unchecked approval by ID (vulnerable to unreviewed edits) vs Hash-verified optimistic approval (chosen: safe, non-blocking, and fail-closed).
- **Prior art inspected**: Git commit SHAs, HTTP `If-Match` with `ETag`, and database MVCC.
- **What we get for free**: `ctx.devLoopLifecycle` provides compare-and-set state validation, and `ctx.fs` handles versioned stat observation.
- **From the docs**: AGENTS.md: 'Public APIs are pre-stable... Explicit > implicit at package boundaries.'
- **What to notice**: Notice that approve only transitions lifecycle state to `pending` and does not enqueue execution work; the queue subsystem handles scheduling separately!
- **Concepts to own**: Optimistic concurrency control: validating precondition fingerprints at mutation time to guard against concurrent interference.
- **Interview angle**: Why separate lifecycle state transition from work queue submission? Answer: Decoupling state machine transitions from queue dispatch preserves modularity and avoids duplicate job scheduling.
- **Decisions you can now make alone**: You can confidently extend approval authorization metadata with command and session context.
- **Lesson**: Never approve a mutable resource without verifying its cryptographic fingerprint at commit time!
