## Summary

Let us scrutinize the citations. When a piece cites a file and line range (`packages/dev-loop/references/src/sources.ts:44-99`), does that file actually exist? Does it lie within the workspace bounds, or does it attempt path traversal (`../outside.txt`)? We enforce strict containment via `fs.contains` and verify physical existence with `checkSources`. Fabricated references will not be admitted.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Canonicalize paths and verify strict subpath containment within repository root via `fs.contains`, rejecting escapes with `OUTSIDE_ROOT`.
- **Option B (Alternative)**: Accept unvalidated paths or naive substring checks, exposing the system to directory traversal vulnerabilities.

## Behaviour

- **Given** an inline code citation pointing to an existing file within `repositoryRoot` **When** `checkSources` is called **Then** it resolves the target, verifies containment, computes `contentSha256`, and marks `sourceStatus` as `resolved`.
- **Given** a path citation attempting escape like `../outside.txt` **When** `checkSources` checks containment against `repositoryRoot` **Then** it rejects fail-closed with an `OUTSIDE_ROOT` error and sets `sourceStatus` to `invalid`.
- **Given** a cited path pointing to a nonexistent file **When** `checkSources` runs **Then** it records a `SOURCE_MISSING` error and marks `sourceStatus` as `missing` with an explicit limitation note.

## Teach me while you build

The suspect claims to have been at a specific address. We must check the map and verify the location exists.

- **Background**: Path traversal (CWE-22) occurs when untrusted path strings access files outside the intended root directory via relative navigation (`..`).
- **How it works here**: `checkSources` resolves inline code locators against `config.repositoryRoot` and markdown links against `dirname(piecePath)`. It confirms containment via `fs.contains(root, target)`.
- **Why this approach**: Explicit containment verification prevents path traversal while allowing relative links between pieces and documentation.
- **Approaches considered**: Naive substring checking (flawed if root prefix matches sibling directories) vs `fs.contains` canonical containment (chosen: secure and filesystem-native).
- **Prior art inspected**: Node.js path security practices and Cordis `FileSystem` containment semantics in `packages/fs/`.
- **What we get for free**: `FileSystem.contains` handles canonicalization and platform-specific path separators cleanly.
- **What to notice**: Notice that missing files are recorded as `SOURCE_MISSING` with an explicit limitation rather than throwing an unhandled exception.
- **Concepts to own**: Path containment verification: proving that a computed filesystem path remains strictly within a designated root boundary.
- **Interview angle**: How do you prevent path traversal attacks when resolving user- or model-provided paths? Answer: Canonicalize the path against the base directory and check that the resolved path is contained within the root boundary before accessing the filesystem.
- **Decisions you can now make alone**: You can distinguish between missing files (`SOURCE_MISSING`), non-file targets (`SOURCE_NOT_FILE`), and out-of-bounds traversal (`OUTSIDE_ROOT`).
- **Lesson**: Never trust an uncanonicalized path. Bounds checking is the first duty of forensic verification.
