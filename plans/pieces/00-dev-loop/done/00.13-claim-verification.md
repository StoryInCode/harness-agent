# 00.13 — Revision-Bound Claim Verification

**Set:** 00-dev-loop · **Queue:** 13 · **Depends on:** 00.01, 00.06, 00.07, 00.08
**Status:** done
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-dev-loop-claims`

## Summary

A specification makes claims. This piece checks whether the load-bearing claims have enough evidence before Test Writer or Implementer builds on them. A `load-bearing claim` is a claim that a later decision rests on. `Research` supplies attributed evidence, not an oracle.

This proposed service binds findings to the exact source. It marks unsupported claims UNVERIFIED. Unresolved load-bearing claims and contradictions block handoff under 00.09. There is no automatic exception and no model-supplied pass API.

## Behaviour

- **Given** an approved current piece **When** verification starts **Then** the owner reads its file, extracts a claim inventory and delegates bounded VerificationAssignments through Roles.
- **Given** a supported finding with exact evidence **When** validated **Then** it records a supported reported finding with the actual delegation id, role and optional preset, not Direct inspection by Utility.
- **Given** contradictory or insufficient evidence **When** findings settle **Then** the report is non-admissible and no tests or implementation start.
- **Given** a negative search **When** recorded **Then** it states the bounded corpus, queries, versions, exclusions and limitations rather than certifying universal absence.
- **Given** source or dependency identity drift **When** a report is consumed **Then** admission rejects as stale and requires fresh verification.
- **Given** an unresolved contradiction **When** work resumes **Then** an explicit source amendment and renewed human approval precede new verification, and no silent correction occurs.

Two terms used above: a `claim inventory` is the list of claims extracted from a piece. A `negative search` is a search that found nothing. It proves absence only inside the corpus it searched.

## Harness fit

The **Service Provider** publishes `ctx.devLoopClaims`, injecting `agents`, `devLoopDirectory`, `devLoopRoles`, `devLoopReferences`, `fs` and `storageDomain`. Its optional scoped `./tool` Consumer registers `dev_loop_verify_claims` with `{pieceId}` and a pure rendered report. The Consumer requires exact live `exec.agent`, uses `agents.withInitiator`, and forwards cancellation. Handoff calls the same Host method under its captured initiator.

Directory exposes metadata, paths and scenarios. It does not expose an AST or a claim extractor. Claims reads and parses the actual file with maintained Markdown dependencies. Roles owns the Research configuration and tool filter under 00.06/07. There is no `devLoopResearchGuard` service and no arbitrary preset selector. Research’s excluded inherited tools cannot execute. Trusted plugins, child-local contributions and allowed executable effects remain outside that guarantee. Claim verification does not promise general nonmutation.

Do not add claims-verified or contradicted serial events as imaginary control points. Return an explicit report and reject admission through `requireAdmissible`. The orchestration caller may request legal pending-to-blocked only after no Lifecycle completion claim is held. A report notification, if later needed, must be declared as an observation. It must not be used as an unawaited authorization mechanism.

## Contracts

Proposed operations:

- `verifyPieceClaims(pieceId, signal): Promise<ClaimVerificationReport>` reads current source, obtains References observation, creates the inventory, delegates Research using Roles.VerificationAssignment, validates evidence and persists the report.
- `getReport(pieceId): Promise<ClaimVerificationReport | undefined>` returns detached latest report, including non-admissible findings.
- `requireAdmissible(pieceId, pieceDigest, signal): Promise<ClaimVerificationReport>` rereads relevant source/dependency identities and returns only a current supported inventory, and otherwise rejects with `CLAIM_VERIFICATION_OUTSTANDING` or `CLAIM_REPORT_STALE`.

Raw source identity requires byte-faithful text. The current fatal UTF-8 reader strips an initial BOM. So require a known filesystem size equal to the UTF-8 byte length of the complete decoded text. Otherwise refuse the observation. Unknown size and stripped-BOM input cannot silently acquire a purported raw digest. This restriction does not change References' explicitly documented decoded-text fingerprints.

No `recordProofTable(pieceId, arbitraryFindings)` setter accepts caller truth. The service does not silently edit an approved specification. Its rendered report supplies proposed Resources-and-proof rows for the explicit amendment owner. Editing the piece invalidates the old report and approval. Fresh checks are required before handoff.

### Inventory and evidence

`ClaimVerificationReport` contains branded report id, piece id and raw SHA-256, inventory digest, checked time, References observation identity/digest, exact delegation ids, findings and limitations. Findings use branded claim id, claim text, category, dependent decision, status (`supported`, `contradicted`, `unverified`), evidence and provenance. A citation alone is not verified truth. Admission is derived by this owner. It is never stored from a caller’s `allPassed` field.

Inventory works in these steps:

1. Read the piece’s explicit Resources and proof rows.
2. Derive stable row-based claim ids and keep their exact text.
3. Ask Research to assess inventory completeness against the full piece.
4. Have Research enumerate omitted candidate claims.

Do not claim a regex can extract every factual assertion. Machine parsing cannot prove it found every semantic premise. Record inventory coverage and limitations. Unresolved load-bearing omissions block. An explicit no-load-bearing-claims inventory requires an explained assessment, not an empty parser result. Reject malformed or missing proof structure rather than treating it as empty success.

Use one full-inventory Research assignment per verification attempt. Reject overlapping verify requests for the same piece before a second intent or delegation. Queue admits only one piece claim. So any follow-up for additional claims starts sequentially after the prior Roles call settles and cleanup releases admission. Different pieces may use shared Queue concurrency.

Each assignment uses 00.06’s `verification: {claim, decisionRestingOnClaim, permittedSources, requiredEvidence}` and role Research, with claim and decision text describing the complete inventory. Put the inventory/report correlation in the assignment text and retained record. No unsupported token or tool-call budget or child context callback is promised. Timeout is an owner-configured cancellation lifetime. Cleanup still must be joined.

Roles returns free-text outcome, not a structured-output request. The brief requires exactly one JSON object: `{inventoryCoverage:{complete:boolean,limitations:string[]}, findings:[{claimId,claim,kind,loadBearing,decisionRestingOnClaim,status,evidence:[{locator,symbol?,version?,digest?,query?,corpus?,measurement?,resultSummary}],limitations:string[]}], additionalClaims:[{claim,kind,loadBearing,decisionRestingOnClaim}]}`. Test Writer freezes the complete JSON schema, category/status enums and bounds.

The JSON boundary is untrusted. Claims handles it in this order:

1. Parse the whole outcome as JSON.
2. Reject unknown or missing fields.
3. Reject duplicate, unknown or missing explicit claim ids.
4. Treat malformed output as a non-admissible failed observation.

No Markdown-fence stripping and no guessed JSON repair. Additional load-bearing claims require a new verification assignment before admission. complete:false cannot pass.

Evidence must name the exact repository file/symbol/content identity, dependency installed version/export, external pinned source, or measurement command/environment/result appropriate to the claim. A supported research finding requires those fields, a matching settled delegation with actual child identity, and no unresolved limitations that undermine the decision. It remains reported evidence. A lying cited report is not mechanically detectable merely because the cited path exists.

Measurement evidence adds optional `measurement: {command:string, environment:Record<string,string>, recordedAt:number, result:string, reportedExecution:'executed'|'not-executed'}`. Validate this object strictly: nonempty command and result, at least one nonempty environment key/value, nonnegative safe-integer epoch milliseconds and the closed execution enum. A supported measurement requires reported execution, complete metadata and an exact local log locator with its current SHA-256. Unexecuted or absent metadata stays unverified. This service neither executes the command nor proves the report truthful. Record the measurement fields in the Research brief as well as its parsed report.

References.verifyReferences checks source structure and attribution, not source use or semantic truth. Legacy prose claiming direct inspection without independent observations remains unverified attribution under 00.08. Preserve that uncertainty. Do not retroactively turn another agent’s prose into Utility inspection. A new properly linked Research report may support a claim while the legacy attribution remains unverified, provided that legacy attribution is not itself a required premise. Contradicted identities cannot be ignored.

For freshness, Claims rereads local evidence files, package manifests, lockfile and recorded export entry points through fs, and compares their exact digests. External evidence is retained at the cited immutable version. This service does not fetch it or assert current remote freshness. A mutable or unpinned external locator remains unverified when version identity is load-bearing. Measurements remain scoped to their recorded environment and time. They cannot establish current performance without remeasurement.

For negative claims, record repository commit/content manifest, dependency versions and export entry points, included directories, exclusions, exact query or tool, and result counts. Every named export entry point requires a corresponding content-manifest digest. Admission rereads these files even when they differ from the main evidence locator. Conclude only “not found in this inspected corpus with these queries.” If the design requires broader absence than that evidence supports, status stays unverified. Performance and quota claims require actual measurements or authoritative scoped limits, not guessed numbers.

### Admission, storage and bounds

The selected policy is fail-closed. `Fail-closed` means any unresolved load-bearing claim blocks before tests. There is no exception input in this API.

A human wishing to proceed must do three things in order:

1. Explicitly amend the product decision and its evidence requirements.
2. Capture renewed approval.
3. Reverify the revised piece.

A warning in the completion report is not authorization. Contradictions likewise require amendment first. Non-load-bearing contextual uncertainty can remain disclosed without pretending it was proved.

Own `dev_loop_claims`, version 1, single layout, schema-validated attempts and reports. Persist intent before delegation and owner-produced terminal report before return. Roles retains delegation history separately. References retains source observations separately. Join all admitted operations before domain.close. Restarted incomplete attempts remain unresolved. There is no automatic Research retry or work dispatch.

The scoped `./tool` Consumer requires its own `Config.maxToolOutputBytes`, validated at mount against the minimum complete error content. Bound the entire rendered content array, including the report wrapper, proposed proof rows and failure prefixes. A finalizer also bounds registered-tool errors produced before its executor runs. Host `maxReportBytes` covers the stored report, not this larger presentation. The Consumer must not read private Host configuration or clip evidence into apparent success.

Host Config requires repositoryRoot, maxPieceBytes, maxClaims, maxEvidenceBytes, maxReportBytes and verificationTimeoutMs. Validate positive integer limits and complete UTF-8 envelopes. Overflow cannot silently drop a claim, citation, report wrapper or limitation. Missing providers or filter referents fail through Roles at the earliest supported point. Report ids and evidence identities are validated before branding at JSON and durable boundaries. Store no live Agent, Session object or abort signal.

## Teach me while you build

- **What it does:** Checks whether the reasons behind a specification have enough evidence to build on.
- **Background:** `Provenance` describes origin. `Attribution` names an author. `Usage` says an activity consumed a source. Neither relation alone proves a claim true.
- **How it works here:** Read PieceRecord for input limits, Roles.VerificationAssignment for supported dispatch, and 00.08 for source and attribution observations. Claims adds the semantic inventory and admission decision.
- **Why this approach:** A cited report supplies inspectable evidence while preserving uncertainty. Automated static checks win for exact symbol and path questions. They cannot cover arbitrary semantic premises alone.
- **Approaches considered:** Delegated evidence review is chosen. Deterministic static checks supplement it for bounded locators. W3C PROV-DM’s richer relation model is useful for cross-system provenance, but importing a generic graph framework would not prove semantic claims.
- **Prior art inspected:** Research reported the W3C PROV-DM 2013-04-30 overview, including usage, delegation and attribution distinctions. Utility did not directly open it. No external code reused. No cargo-vet or RFC inspection is claimed.
- **What we get for free:** Roles supplies actual identity and joined cleanup. References checks locators. storageDomain validates durable records. Claims owns completeness assessment, evidence interpretation and fail-closed admission.
- **From the docs:** The reported W3C overview informs the relationship distinction. No verbatim external quotation or full normative conformance is claimed.
- **What to notice:** A successful file read does not validate an earlier author’s claim to have read it. A zero-match search needs an explicit search domain.
- **Concepts to own:** `Epistemic uncertainty` tracks missing knowledge in each finding. `Closed-world reasoning` limits negative findings to the recorded corpus. `Content addressing` binds reports to source bytes.
- **Interview angle:** “How do you prevent hallucinated APIs becoming tests?” Require evidence and reject unresolved load-bearing premises before authoring. Follow-up: the inventory and Research interpretation can themselves be incomplete, so retain limitations and require explicit amendment.
- **Decisions you can now make alone:** Add exact evidence and parser rejection cases and improve query coverage. Escalate admission exceptions, new executable Research capabilities or changing the approved source to their owners.
- **What you should learn from this:** State what the evidence establishes, not what a confident report implies.
