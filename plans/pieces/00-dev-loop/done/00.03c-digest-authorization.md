## Summary

Alright, listen up. Here's how hackers exploit approval systems: the user reviews version A of a spec, but right before or during human review, a rogue script swaps in version B! Classic Time-of-Check to Time-of-Use (TOCTOU) vulnerability! To stop that nonsense, our approval consumer brackets reads with filesystem stat versions and byte counts, re-verifies them upon human acceptance, and binds the exact source via `observeSource` before the lifecycle transition. If the file changes by even one byte during review, the check fails with `PIECE_REVIEW_STALE` and execution halts. Bulletproof security!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Bracket specification reads and human acceptance with filesystem stat versions and byte sizes, rejecting concurrent edits with `PIECE_REVIEW_STALE`.
- **Option B (Alternative)**: Approve by piece ID alone without version or byte checks, allowing unreviewed file edits to execute without re-authorization.

## Behaviour

- **Given** an approved piece whose file version and byte size match the reviewed observation **When** the human accepts the piece **Then** `present_piece_for_approval` binds the observed source and commits the `todo`-to-`pending` lifecycle transition.
- **Given** a piece whose file content or version was modified while under human review **When** the human submits acceptance **Then** it rejects with `PIECE_REVIEW_STALE` without queuing work.
- **Given** a piece that transitions or conflicts concurrently in lifecycle state **When** acceptance commits **Then** it surfaces the compare-and-set conflict rather than returning an invalid authorization.

## Teach me while you build

Time of Check vs Time of Use. If you don't understand TOCTOU bugs, script kiddies will own your pipeline.

- **What it does**: Guarantees that what the human reviewed is byte-for-byte identical to what gets authorized and committed to the lifecycle.
- **Background**: TOCTOU occurs when a resource changes between when permissions or specifications are inspected and when an action or state transition is committed.
- **How it works here**: Before reading the specification, `presentPiece` captures the file stat version and size. After reading, it confirms the stat version hasn't drifted and byte size matches UTF-8 length. Once the user clicks `Accept`, it checks the file stat version and size a third time. If anything drifted, it throws `PIECE_REVIEW_STALE`. On match, it binds the observed source with `observeSource` into `ctx.devLoopLifecycle.transition`.
- **Why this approach**: Bracketing reads and commits with filesystem stat versions and exact UTF-8 byte counts detects concurrent edits without requiring heavy global file locks.
- **Approaches considered**: Approve by ID alone (rejected: vulnerable to TOCTOU tampering) vs Global filesystem locks (rejected: fragile across processes and crashes) vs Version-bracketed stat observations with CAS commit (chosen: resilient and fail-closed).
- **Prior art inspected**: Linux openat2 atomic file resolution, Subresource Integrity (SRI), and HTTP `ETag`/`If-Match` conditional requests.
- **What we get for free**: `ctx.fs` provides versioned stat descriptors, and `ctx.devLoopLifecycle` provides atomic compare-and-set state transitions.
- **From the docs**: `packages/dev-loop/approval/README.md`: 'Changed source versions, a mismatched parsed id, or unknown/mismatched UTF-8 byte counts report PIECE_REVIEW_STALE and require a fresh presentation.'
- **What to notice**: Notice how `observeSource` records the exact version and text into the lifecycle transition payload, ensuring full traceability in persistence logs!
- **Concepts to own**: Optimistic concurrency control (OCC) and version-bracketed read verification.
- **Interview angle**: How do you prevent TOCTOU vulnerabilities in asynchronous approval systems without pessimistic locking? Answer: Bracket read and approval steps with monotonic version/stat observations and commit via atomic compare-and-set.
- **Decisions you can now make alone**: You know how to handle `PIECE_REVIEW_STALE` errors by triggering an automated re-presentation of current source rather than crashing.
- **Lesson**: Never authorize an object by identity alone when its underlying content can mutate. Verify versions before and after every human decision!
