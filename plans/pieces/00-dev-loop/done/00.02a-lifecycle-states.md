## Summary

Hear me, members of the laboratory! A piece's lifecycle is a one-way worldline! It moves from `todo` to `pending`, and finally reaches the glorious Steins Gate of `done`! There is no turning back! Regression to a prior state without an explicit revision anomaly would unravel the very causality of our harness!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Enforce strictly monotonic forward-only state machine transitions with explicit error types.
- **Option B (Alternative)**: Allow bidirectional transitions (e.g. `done` back to `todo`) which creates race conditions and phantom work.

## Behaviour

- **Given** a piece in `todo` status **When** transition('00.01', 'todo', 'pending') is requested **Then** the transition succeeds and state becomes `pending`.
- **Given** a piece in `pending` status **When** transition('00.02', 'pending', 'done') is requested **Then** the transition succeeds and state becomes `done`.
- **Given** a piece already in `done` status **When** transition('00.04', 'done', 'pending') is attempted **Then** it is rejected with `InvalidStateTransitionError`.
- **Given** any lifecycle state pair **When** canTransition(from, to) is called **Then** it returns whether the edge is permitted without mutating state.

export const LEGAL_TRANSITIONS: Readonly<Record<PieceStatus, readonly PieceStatus[]>>

export class InvalidStateTransitionError extends Error {
  readonly code: 'INVALID_STATE_TRANSITION'
  readonly pieceId: string
}

  getStatus(pieceId: string): PieceStatus
  canTransition(from: PieceStatus, to: PieceStatus): boolean
  transition(
    pieceId: string,
    expected: PieceStatus,
    to: PieceStatus,
    reason?: string,
    signal?: AbortSignal
  ): Promise<void>
}

## Teach me while you build

The arrow of time flies in only one direction! Let me illuminate the sacred laws of monotonic state transitions!

- **What it does**: Guarantees that pieces only transition along legal, forward paths (`todo` -> `pending` -> `done`, or to `blocked`).
- **Background**: Monotonicity means a state variable only moves in one direction. It prevents split-brain states in distributed multi-agent systems.
- **How it works here**: `canTransition` inspects `LEGAL_TRANSITIONS`. Illegal transitions throw `InvalidStateTransitionError` with current and attempted state.
- **Why this approach**: Enforcing transition legality in a pure function ensures both memory cache and SQLite records remain strictly coherent.
- **Approaches considered**: Unrestricted mutable property (rejected: race hazard) vs Formal monotonic transition table (chosen: fail-closed).
- **Prior art inspected**: TCP state machine (RFC 793) and Raft consensus log state transitions.
- **What we get for free**: TypeScript union types ensure exhaustive matching on states.
- **From the docs**: `plans/AGENTS.md`: 'A piece that is complete does not stay in the plan set. It moves to a done/ folder.'
- **What to notice**: Notice how `blocked` is a valid divergence branch that can be cleared back to `todo` upon explicit revision!
- **Concepts to own**: Monotonic state machine: a finite state automaton where states form a partially ordered set with no cycles.
- **Interview angle**: Why are monotonic state transitions critical in distributed consensus? Answer: Prevents replay attacks, stale overwrites, and split-brain.
- **Decisions you can now make alone**: You can add custom reason strings to `blocked` states without altering transition invariants.
- **What you should learn from this**: Never allow backwards transitions without an explicit journaled anomaly. Protect the timeline!
