## Summary

Yo! Here is the relational bedrock of the dev loop. We store our pieces, state transitions, intents, and anomalies in a strongly typed storage domain schema with strict row parsers and repository identity checks. We also enforce monotonic schema versioning (`version: 1`). If records ever drift or come from a foreign repository, the domain refuses to open! No messy manual SQL hacks!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Strongly typed storage domain schema with version 1 layout, monotonic migrations, and repository digest validation.
- **Option B (Alternative)**: Ad-hoc unvalidated JSON files on disk prone to corruption, race conditions, and lack of schema enforcement.

## Behaviour

- **Given** a new or existing repository root **When** DevLoopPersistence initializes **Then** it computes the repository identity digest and opens the dev_loop storage domain at monotonic version 1.
- **Given** stored authoritative records with a differing repository identity or malformed schema **When** the service starts **Then** it rejects with DEV_LOOP_REPOSITORY_MISMATCH or schema validation refusal fail-closed.
- **Given** authoritative transition and anomaly rows in durable storage **When** inspected by persistence operations **Then** it provides keyed access and sequence verification across the transitions and anomalies tables.

## Teach me while you build

Databases are the memory of your application. Design your tables cleanly, validate your schemas, and never skip monotonic versions.

- **What it does**: Maintains the authoritative storage domain tables for transitions, worker intents, and anomalies.
- **Background**: Relational integrity and schema validation guarantee that records cannot drift into illegal states or point to invalid entities.
- **How it works here**: Defines `persistenceDomain` with `transitions` and `anomalies` tables. On init, computes the SHA-256 digest of the canonical repository path and validates all rows against it.
- **Why this approach**: Guarantees deterministic relational integrity without running external database services.
- **Approaches considered**: Unvalidated JSON files (slow, prone to corrupt partial writes) vs External DBMS (requires running service) vs Typed storage domain (chosen: embedded, typed, and fail-closed).
- **Prior art inspected**: SQLite monotonic schema migration patterns and schema-validated document stores.
- **What we get for free**: `@deepseek-ai/dsh-storage-domain` provides transactional file-backed table management.
- **From the docs**: AGENTS.md: 'Public APIs are pre-stable; update every consumer. SQLite uses monotonic SCHEMA_VERSION.'
- **What to notice**: Notice how copying database records to a different repository root refuses foreign identity rather than silently adopting state!
- **Concepts to own**: Monotonic schema versioning: tracking storage schema iterations with an increasing integer version and fail-closed structural parsers.
- **Interview angle**: How do you prevent state pollution when durable stores are copied across repository locations? Answer: Bind records to canonical repository identity digests and validate on storage open.
- **Decisions you can now make alone**: You can configure history limits and maximum record byte sizes to bound resource consumption.
- **What you should learn from this**: Relational schemas protect data integrity. A clean domain with strict validation makes crash recovery trivial.
