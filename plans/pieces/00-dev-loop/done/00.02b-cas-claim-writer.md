## Summary

Sup! Imagine two orchestrators trying to transition the exact same piece at the exact same millisecond. If you don't have atomic compare-and-swap (CAS), both start racing transitions and corrupt the piece state! We implement atomic compare-and-swap on `transition` in `ctx.devLoopLifecycle` so callers pass their expected current status. A synchronous claim is taken before any asynchronous work begins: exactly one caller wins, and the racing caller gets a clean `StalePieceStatusError` rejection. Easy peasy.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Synchronous compare-and-swap claim verifying expected current status before starting asynchronous effects.
- **Option B (Alternative)**: Unsynchronized check-then-act across async ticks, creating race conditions where multiple callers mutate state simultaneously.

## Behaviour

- **Given** a piece in `todo` status **When** `transition('00.01', 'todo', 'pending')` is called **Then** the transition succeeds and moves the piece to `pending`.
- **Given** a piece currently in `pending` status **When** `transition('00.01', 'todo', 'pending')` is called with stale expected status `todo` **Then** it rejects with `StalePieceStatusError` (`code: 'PIECE_STALE_STATUS'`) and mutates nothing.
- **Given** two orchestrators racing the same transition simultaneously **When** `Promise.allSettled` runs concurrent `transition('00.02', 'pending', 'done')` calls **Then** exactly one call succeeds and the racing call is rejected with `StalePieceStatusError`.

## Teach me while you build

Time for some hardcore concurrency reality. In multi-agent land, race conditions will ruin your weekend if you don't use atomic CAS.

- **What it does**: Atomically guards piece transitions with compare-and-swap on the expected current status, preventing double-allocation and conflicting transitions.
- **Background**: Compare-And-Swap (CAS) checks if a state or memory location holds an expected value before updating it. It's the basis of non-blocking concurrency and optimistic locking.
- **How it works here**: In `DevLoopLifecycle.transition`, the service calls `this.claim(pieceId, expected, to)` synchronously before any `await`. If `piece.claim` is already set or `piece.status !== expected`, it throws `StalePieceStatusError`.
- **Why this approach**: Guarantees single-writer safety across parallel orchestrators without external distributed lock daemons.
- **Approaches considered**: File locks on disk (flaky across OSes and slow) vs In-memory synchronous CAS claim (chosen: synchronous check before first await prevents interleaving ticks).
- **Prior art inspected**: CPU `CMPXCHG` instruction and optimistic concurrency control (OCC) version fencing.
- **What we get for free**: Node's single-threaded event loop ensures synchronous statements execute without interruption before the next event loop tick.
- **From the docs**: `docs/defensive-patterns.md`: "Async state is not synchronous state".
- **What to notice**: Notice how `claim` sets `piece.claim = to` synchronously so a concurrent transition arriving in the same microtask queue sees the claim and rejects!
- **Concepts to own**: Mutual exclusion via CAS: guaranteeing single ownership of state transitions during asynchronous workflows.
- **Interview angle**: How do you prevent race conditions when two async operations attempt to update the same resource in Node.js? Answer: Synchronously inspect and set an in-flight claim before yielding execution to the microtask queue or an `await`.
- **Decisions you can now make alone**: You can safely add new transition targets knowing concurrent callers will be rejected by the synchronous CAS guard.
- **What you should learn from this**: Check-then-act across an `await` boundary without an atomic claim is always broken under concurrency! Lock it down right.
