### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Physical atomic rename moving piece file into `<set>/done/` with `git mv` and rewriting header status to `done`.
- **Option B (Alternative)**: Leave the file in place and only flip a status bit in a database, making progress invisible to directory viewers.

## Behaviour

- **Given** a verified piece in `pending` status **When** `transition(pieceId, 'pending', 'done')` is called **Then** its disk header is rewritten to `done`, staged with git, and moved to `<set>/done/` via `git mv`.
- **Given** a piece in untracked files or not in a git working tree **When** transitioning to `done` **Then** it rejects with `PieceMoveFailedError` (`code: 'PIECE_MOVE_NOT_TRACKED'`) without mutating untracked files.
- **Given** a completion in a set directory without a `done/` folder **When** `transition(pieceId, 'pending', 'done')` executes **Then** it creates `<set>/done/` with `mkdir -p` before invoking `git mv`.

## Harness fit

State transition method on `ctx.devLoopLifecycle` service in `packages/dev-loop/lifecycle/src/index.ts`. Rewrites header status, coordinates Git index and filesystem relocation via `ctx.subprocess` (`git mv`), and emits `piece/completed`.

## Teach me while you build

Time to put the finished toy in the toybox! Nya~ (=^･ω･^=)

- **What it does**: Physically moves a completed piece file into its set's `done/` subdirectory and rewrites `**Status:** done`.
- **Background**: The `R-done-pieces-moved` axiom requires completed pieces to live in `done/` so humans can inspect progress at a glance.
- **How it works here**: In `DevLoopLifecycle.complete()`, after pre-complete hooks pass, the service rewrites `**Status:** done` via `fs.editText`, stages it with `git add -u`, ensures `done/` exists, and executes `git mv` via `ctx.subprocess`.
- **Why this approach**: A filesystem move makes status visible immediately to `ls`, file tree explorers, and git status without relying on external databases.
- **Approaches considered**: Database-only status (invisible in git) vs In-place status update (clutters set folder) vs Move to `done/` with git mv (chosen: atomic tracking and visible progress).
- **Prior art inspected**: Kanban physical board movement from 'Doing' to 'Done'.
- **What we get for free**: Git index tracking ensures rename history is preserved across commits.
- **From the docs**: `plans/AGENTS.md`: "A piece that is complete does not stay in the plan set. It moves to a done/ folder".
- **What to notice**: Notice how the file is staged with `git add -u` before `git mv` so the commit contains a clean rename!
- **Concepts to own**: Information radiator: designing system state to be visible passively without querying an API.
- **Interview angle**: Why design systems where progress is physically reflected in the filesystem? Answer: Transparency, low tooling overhead, and auditable history.
- **Decisions you can now make alone**: You can add placement verification scripts knowing filenames and IDs are preserved.
- **What you should learn from this**: Make progress visible so your team can celebrate every victory! Purr~ (=^･ω･^=)
