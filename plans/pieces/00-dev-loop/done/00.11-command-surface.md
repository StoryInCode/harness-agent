# 00.11 — Human Command Surface `/dev-loop`

**Set:** 00-dev-loop · **Queue:** 11 · **Depends on:** 00.01, 00.02, 00.04
**Status:** done
**Harness primitive:** command · **Package:** `@deepseek-ai/dsh-dev-loop-command`

## Summary

The owner needs to see real state, review one exact source revision, and approve or block work. This command does that without a model turn. A `model turn` is one request to the language model.

This proposed command registers as `dev-loop`, not `/dev-loop`. Its handler parses rawInput and returns CommandResult. A `handler` is the function that runs when the command fires. `rawInput` is the exact text after the command name. `CommandResult` is the value the handler returns to the command runtime.

The command uses existing Directory, Lifecycle and Queue APIs. It does not invent an approval service. Durable acceptance integration belongs to 00.12.

## Behaviour

- **Given** an active session **When** `/dev-loop status` runs **Then** it returns live worker count, Queue ceiling, queued count and current Lifecycle counts, with malformed-source diagnostics.
- **Given** queued work **When** `/dev-loop queue` runs **Then** it lists actual entries in Queue order and derives each dependency status from Directory and Lifecycle.
- **Given** a piece **When** `/dev-loop show 00.03` runs **Then** it returns the full reviewed source and exact SHA-256 needed for approval, plus current status and declared metadata.
- **Given** the shown current digest **When** the root human submits `/dev-loop approve 00.03 <sha256>` **Then** it rechecks the source and requests todo-to-pending with actual command identity, and stale digest refuses approval.
- **Given** pending work **When** `/dev-loop reject 00.03 reason with spaces` runs **Then** it requests pending-to-blocked with that full reason, not an illegal todo-to-blocked edge.
- **Given** unknown verbs, extra arguments, missing arguments or invalid ids **When** the handler runs **Then** it returns a specific error and usage without silently ignoring input, and unsupported attachments are refused earlier by CommandRuntime with its own diagnostic.
- **Given** empty input or help **When** submitted **Then** it returns complete usage, and disposal removes the registration.

A `digest` here means the SHA-256 hash of the source bytes. A `root human` is the top-level human in the root session, not a delegated child agent.

## Harness fit

The **command** function plugin injects `commands`, `agents`, `devLoopDirectory`, `devLoopLifecycle`, `devLoopQueue` and `fs`, and effect-owns `commands.register({name:'dev-loop',description,input:{hint},handler})`. No model-facing approval tool is added. Existing `present_piece_for_approval` remains the separate question-based Consumer, and its private presentPiece is not a public service.

`CommandInvocation` carries commandId, exact receiving agent, rawInput, attachments and signal. Registration supplies no subcommand parser or completion engine. CommandResult is returned, not printed. Existing command runtime logs command/run and command/done, and output is human UI state, not automatically injected model context. The command does not launch an app, server or bin.

Read that as four small facts:

1. The Harness gives the handler the full raw input and an id.
2. The command does its own parsing.
3. The handler returns text. It does not print.
4. The command output goes to the human. The model does not see it.

## Contracts

### Complete grammar

Whitespace separates the verb and fixed arguments. No quoting, flags, aliases or shell evaluation are supported. `reject` consumes the nonempty remaining text verbatim except leading/trailing whitespace. All other routes reject trailing tokens. Dotted ids follow the Directory’s canonical NN.MM grammar. Digests require 64 hexadecimal SHA-256 characters, and normalize case only.

| Input after /dev-loop | Operation and result |
|---|---|
| empty or `help` | Success with the complete grammar; help takes no arguments. |
| `status` | `getActiveWorkers`, `getQueuedEntries`, public Queue.maxConcurrency; scan all sets and use Lifecycle.getStatus for logical counts. |
| `list` | Directory.listSets then scanSet; deterministic set/queue/id order, current Lifecycle status, title, path and rejected-source diagnostics. |
| `queue` | Queue.getQueuedEntries in returned order, numbered display positions, queueOrder/enqueuedAt and per-dependency status. |
| `show <id>` | Directory.getPiece and fs source read/stat/recheck; full source, current Lifecycle status and content SHA-256. No clipped review is represented as complete. |
| `approve <id> <sha256>` | Require exact live runtime root; read/validate source and match digest, then Lifecycle.transition(id,'todo','pending',reason,signal,authorization) under the 00.12 amendment. |
| `reject <id> <reason...>` | Require exact live runtime root; require pending and call Lifecycle.transition(id,'pending','blocked',reason,signal). Other statuses return a legal-state diagnostic. |

Before 00.12 exists, command tests use the existing five-argument transition and prove revision checking. Those tests must not claim durable approval. 00.12 extends both human consumers with authorization forwarding and direct Lifecycle durable checks. Final composition requires that integration. Do not introduce a command dependency on Persistence or duplicate its domain to make standalone tests pass.

Authorization is built from actual invocation.commandId, receiving Session id and observed source digest/version, not caller JSON. The explicit digest in the human command declares which revision they accept. It does not prove they read every line.

Before any mutation, require `agents.get(agent.id) === agent` and `agents.roots().includes(agent)`. A delegated child cannot manufacture a root interaction. The direct human command is the authority path, not a model-generated string.

Dependency display works like this:

1. Look up the queued piece via Directory.getPiece.
2. Read its dependsOn list.
3. Call Lifecycle.getStatus for each dependency id.

QueueEntry has no dependency field. That is why display looks elsewhere. Missing or malformed dependencies display specific diagnostics. They never count as done.

Counts distinguish logical Lifecycle state from disk header state. Rejected sources remain visible. These independent reads are a timestamped observation. They are not a transactional cross-service snapshot or restored activity after restart.

The handler returns `{kind:'success',text}` or `{kind:'error',text}` for expected input and domain failures.

Errors and cancellation have two owners.

```text
Problem: an attachment is refused, or execution is already aborted.
Cause: CommandRuntime owns pre-admission refusal and cancellation.
Fix: the runtime refuses or rejects before the handler. Cancellation is
not promised as a handler-formatted error.
```

Runtime defects follow the command runtime’s error path. Do not promise that no exception can ever occur. Do not swallow defects into success.

Empty results are explicit, for example `Queue: empty`. Unknown ids, stale review, illegal or stale status and missing referents have nonempty corrective text. The input descriptor does not enable attachments.

Require Config.maxOutputBytes and maxInputBytes as positive safe integers. Derive the minimum valid output budget from the UTF-8 size of the actual fixed refusal text plus its complete owned CommandResult wrapper. Reject smaller configuration rather than emitting an oversized or empty error. Test tiny-invalid, exact-minimum and multibyte boundaries. Bound complete UTF-8 text including usage and wrappers.

Oversized show returns explicit refusal. It never returns a truncated source plus an approval digest. The owner may read the file by another approved route, but this command cannot assert a completed review. Overflowing list, queue or status returns a named error rather than a silent partial count. There are no ignored pagination flags. Propagate invocation.signal through source and transition calls, and check it between synchronous scans.

## How to see it

Run in a root session: `/dev-loop help`, `/dev-loop list`, `/dev-loop show 00.03`, then `/dev-loop approve 00.03 <digest returned by show>`. Expect full source and digest, then `Piece 00.03: pending.` naming pending only if the source still matches. `/dev-loop queue` can remain empty: approval changes eligibility and does not itself enqueue a role callback. The recorded Web snapshots replay the same surface without a model turn: `pnpm run test:snapshot -t 'shipped Web dev-loop-command'`.

## Teach me while you build

- **What it does:** Lets the human inspect real state and authorize one exact revision.
- **Background:** A command is a human control outside model turns. `Compare-and-set` means write only if the status is still what you read. That rejects concurrent stale changes. A digest identifies source bytes, not human comprehension.
- **How it works here:** CommandRuntime supplies rawInput and commandId. The parser routes to Directory or Queue reads, or to Lifecycle.transition. Read QueueEntry to see why dependency display must look elsewhere.
- **Why this approach:** One command keeps discovery and usage together. Separate registered commands would win if each needed a distinct client form. They add registrations without eliminating source-review logic here.
- **Approaches considered:** One raw-input command is chosen. Independent command registrations are supported by this same runtime. A model tool is appropriate for model requests, not independent human authorization. This is a narrow Harness-specific interface. No external parser or prior-art implementation was inspected, and no library comparison is asserted.
- **Prior art inspected:** Only in-repository command and user-question owners. No external project or code reuse is claimed.
- **What we get for free:** The command runtime validates registration and results, logs invocation and settlement, and owns dispatch. Application code owns grammar, source review, bounds and status composition.
- **From the docs:** CommandInvocation describes rawInput as “Exact text following the registered command name, including separator whitespace.” The parser must consume and validate all of it.
- **What to notice:** Approval does not create a Queue callback. A disk todo header may coexist with logical pending until durable Lifecycle integration reconciles its own facts.
- **Concepts to own:** `Optimistic concurrency` binds approval to observed bytes. `Complete input validation` rejects trailing tokens. `Separation of concerns` keeps display derivation outside Queue.
- **Interview angle:** “How do you stop approving a changed specification?” Require the reviewed digest and recheck source before the sole writer accepts. Follow-up: durable acceptance must occur inside Lifecycle, not a command-only wrapper.
- **Decisions you can now make alone:** Improve diagnostics and strict grammar fixtures. Escalate new state transitions, reopening done or automatic dispatch to their owners.
- **What you should learn from this:** Returned text, human authority and durable state are separate responsibilities.
