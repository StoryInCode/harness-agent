# 00.07 — Research Capability Policy and Acceptance

**Set:** 00-dev-loop · **Queue:** 7 · **Depends on:** 00.06
**Status:** done
**Harness primitive:** subagent consumer · **Package:** `@deepseek-ai/dsh-dev-loop-roles`

## Summary

Research assignments use an explicit deployment-owned allowlist of inspected reading capabilities. This piece validates that policy and demonstrates that excluded inherited tools cannot execute, including the child's first attempted call. It does not promise that arbitrary plugins or every operation in the child process cannot mutate files.

All fourteen pieces remain separately accepted milestones. This piece is implemented in the Roles workspace package specified by [00.06](00.06-role-delegation.md), not an empty additional package. 00.06 owns generic role dispatch, configured filter forwarding, caller identity, records, and cleanup. 00.07 owns Research-specific policy validation and deployment acceptance tests; the existing tool runtime owns enforcement. These additions have passed the frozen policy tests and parent-reported post-transfer checks below.

## Behaviour

- **Given** a valid Research allowlist **When** Roles starts a child **Then** the start request carries the filter before the provider creates the child or requests its first model response.
- **Given** an excluded inherited tool **When** the Research child's first response nevertheless calls it **Then** the executor refuses the call and its tool body never runs; the capability is also absent from the child's advertised tools.
- **Given** the tested deployment mounts inherited `read` and `read_image` capabilities **When** those names are allowed **Then** the child can read source text and an image through the actual tools.
- **Given** an additional inherited execution or delegation tool outside the allowlist **When** it is registered **Then** it remains unavailable to Research without extending a deny-name inventory.
- **Given** an invalid Research policy, unknown configured tool name, or unsupported provider **When** delegation is attempted **Then** it fails before a model request rather than silently dropping the restriction.
- **Given** Research and Implementer children of the same parent **When** their tools execute **Then** Research's additional restriction does not remove the parent's or Implementer's allowed writing capability.
- **Given** a child-local structured-result tool **When** the provider registers it **Then** it remains usable; the test must not misrepresent inherited-tool filtering as control over child-local registrations.

## Harness fit

The owning primitive is the **subagent consumer** in `@deepseek-ai/dsh-dev-loop-roles`. Its existing role configuration selects the Research filter. Its scoped `./tool` consumer supplies the model entry through `dev_loop_delegate`; this piece adds no model tool, public service method, registry, Session event, or Agent-loop behavior.

The existing public operation is `SubagentRuntime.start(providerName, request)`. Its capability check rejects unsupported `toolFilter`. In-process `startInProcessRun` owns a private Agent creation `setup` callback, which calls `applyChildComposition`; that function joins the parent's standing composition and calls `childCtx.tools.restrict` before the run starts. Roles supplies the request, not a child-context callback.

The existing production consumer `tool-subagent` already forwards its configured filter through this operation. Roles is an additional consumer. Neither consumer needs a wrapper provider or access to provider-private creation code. A post-start registration is invalid: the in-process driver starts the child's followup before returning the run to its caller.

`ToolRuntime.view` applies restrictions to inherited global and ancestor/preset tools. The child's own registrations remain visible. `resolveExecution` and `dispatchToolBody` consult the filtered view at execution, including nested PTC dispatch; removing a schema alone is not the acceptance criterion. Existing restriction registrations are effect-owned and need no duplicate disposal layer here.

## Contracts

### Research policy owned by Roles

Use `Config.roles.Research.toolFilter` from 00.06. Require an explicit `allow` list for Research, rather than accepting a deny-only policy as proof that future inherited tools are excluded. The list must be nonempty and name the reading capabilities required by the configured assignments. An optional existing `deny` field may only subtract. Configuration remains Host-owned; model arguments cannot select or override it.

The Roles configuration owner validates the Research-specific requirement at its mount and passes the typed filter through its existing dispatch path. Any helper remains private to that owner and receives its already-owned configuration. The tool consumer must not reach into the service's private configuration, and one internal helper does not justify a public policy service method.

The deployment author supplies the exact names and records the inspected implementations that justify admission. `read` and `read_image` are acceptance-fixture capabilities, not invented defaults for every deployment. The fixture also mounts representative filesystem mutation, general execution, and further-delegation tools and excludes them. Do not derive authorization from descriptions, a role label, TypeScript `readonly`, or concurrency metadata. Do not introduce another tool-classification registry.

Validate configured referents at the earliest supported point, and retain the runtime's child-scope validation at start. Do not silently intersect configured names with a global registry snapshot: inherited preset tools also matter, and misspelled names must not disappear. Unknown names and reserved PTC transport names reject through `restrict`; filter end capabilities rather than naming `run_code`.

An allowlist constrains names, not implementations. The tested deployment must inspect allowed implementations and child-local contributions. General execution and further-delegation tools stay excluded unless a separately identified, real owner bounds their effects. Adding such an exception requires new evidence and acceptance scope; this piece provides no shell-command parser or argument-aware guard escape.

### Guarantees and exclusions

The guarantee is refusal of excluded inherited capabilities through the real model/tool execution path. Allowed reading tools still operate under their own filesystem policy. This is not a security fence against trusted plugins, direct service calls, child-local tools, or filesystem effects of an allowed executable tool. Worktree allocation and filesystem/subprocess sandbox enforcement remain separate responsibilities under [00.05](00.05-worktree-assignment.md).

`ToolDefinition.isConcurrencySafe` classifies parallel versus exclusive scheduling. It does not authorize a call or enforce filesystem read-only behavior. The inspected ToolDefinition and schema sources provide no authoritative read-only/effect permission annotation.

No `agent.role`, `header.role`, or execution role field is required. Roles chooses the configured Research request, and the provider installs its filter on that actual child's scope. Scope does not exempt trusted extension code from the limitations above.

00.06 uses one-shot `start`. Its one-shot descriptor does not persist the filter for a promised cold continuation. The existing continuable manager separately persists and restores filters; that behavior belongs to the subagent owner and does not add continuation or recovery to this piece.

Source provenance requirements belong to [00.08](00.08-references-provenance.md) and claim-verification assignments to [00.13](00.13-claim-verification.md). Tool denial cannot establish that a report's citations are true. Those consumers use this Research policy without another enforcement path.

## Teach me while you build

- **What it does:** Research receives only the inherited reading capabilities its deployment explicitly selects, and an executable test proves that excluded tools cannot run even when requested first.
- **Background:** An allowlist admits named capabilities and excludes other inherited names. An agent scope holds contributions for one agent. An executor dispatches a requested tool; this is where denial must prevent its body from running.
- **How it works here:** Roles chooses its Research configuration and sends `toolFilter` to `subagents.start`. The in-process provider installs the restriction during unpublished child setup. ToolRuntime applies that restriction when advertising and dispatching inherited tools. Invalid referents reject creation rather than producing an unrestricted child.
- **Why this approach:** The public request already reaches the correct pre-execution owner. Roles selects and validates the Research policy; its Loader fixtures prove the configured policy without another enforcement mechanism.
- **Approaches considered:** Explicit allowlists through the existing request are chosen; the real `tool-subagent` consumer demonstrates the input. Deny lists remain supported by the runtime but require continually identifying new inherited mutation/delegation capabilities. Provider-local guards are real in `structured.ts`, where the provider owns creation; they suit terminal structured-output policy, not a Roles callback that does not exist. Filesystem sandboxing can provide different filesystem guarantees but does not replace capability selection. Node's process-level permission model is an external alternative for separately launched workers that need documented resource-API restrictions; it does not filter Harness tool names or automatically constrain child-local tools in a shared process. It is not an OS sandbox.
- **Prior art inspected:** The in-repository tool-subagent consumer and structured-output attachment were opened. Research, preset not recorded, opened [Node v22.19.0 permission documentation](https://github.com/nodejs/node/blob/v22.19.0/doc/api/permissions.md), Permission Model, File System Permissions and Permission Model constraints. This is documentation inspection, not implementation inspection; no external code reused.
- **What we get for free:** The subagent runtime checks capabilities; providers own creation timing; ToolRuntime owns scope inheritance, native/PTC execution checks, and effect removal. Roles owns deployment policy and its tests. No new guard registry, role metadata propagation, or session event is needed.
- **From the source documentation:** `ToolRuntime.restrict` states “Restrictions intersect; scoped registrations remain visible.” The caller must distinguish inherited capabilities from child-local machinery rather than claiming every tool is filtered. Research verified Node's separate warning: “It does not provide security guarantees in the presence of malicious code.” That warning limits Node's permission model; it is not evidence of a particular Harness bypass.
- **What to notice:** The driver installs the filter before `drivePublishedRun` submits the followup. `ToolRuntime.view` adds the child's own tools after inherited-tool filtering. These two locations determine the useful guarantee and its limit.
- **Concepts to own:** Complete mediation means testing the actual dispatch path rather than schemas alone; this piece proves it for excluded inherited tools. Least privilege means selecting only capabilities the assignment needs. Ownership separates deployment policy from runtime enforcement and filesystem isolation.
- **Interview angle:** “How do you avoid a first-call policy race?” Supply the restriction in the existing start request so the provider installs it during creation; never attach it after start returns. Follow-up: child-local tools and trusted plugin execution require separate scrutiny.
- **Decisions you can now make alone:** Adjust the explicit deployment allowlist after inspecting each admitted tool and extending policy tests. Escalate executable/delegation exceptions, child-local enforcement, sandbox changes, and continuation requirements to their respective owners.
- **What you should learn from this:** A capability filter proves a specific dispatch restriction, not that every effect in the process is read-only.
