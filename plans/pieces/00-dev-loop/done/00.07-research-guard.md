# 00.07 — Research Capability Policy and Acceptance

**Set:** 00-dev-loop · **Queue:** 7 · **Depends on:** 00.06
**Status:** done
**Harness primitive:** subagent consumer · **Package:** `@deepseek-ai/dsh-dev-loop-roles`

## Summary

Research work uses an allowlist. An allowlist is a list of tool names that are allowed. Every other inherited tool is blocked.

This piece proves two things. First, the allowlist policy works. Second, a blocked tool cannot run, even when the child model calls it first. It does not promise that every part of the child process is safe from file changes.

All fourteen pieces stay separate accepted milestones. This piece lives in the Roles package from [00.06](00.06-role-delegation.md). It is not an empty extra package. 00.06 owns generic role dispatch, filter forwarding, caller identity, records, and cleanup. 00.07 owns the Research policy validation and its acceptance tests. The existing tool runtime does the enforcement. The frozen policy tests and the parent-reported checks below have passed.

## Behaviour

- **Given** a valid Research allowlist **When** Roles starts a child **Then** the start request carries the filter before the provider creates the child or asks for its first model response.
- **Given** an excluded inherited tool **When** the Research child's first response calls it anyway **Then** the executor refuses the call and the tool body never runs. The blocked tool also does not appear in the child's advertised tools.
- **Given** the tested deployment mounts inherited `read` and `read_image` capabilities **When** those names are allowed **Then** the child can read source text and an image through the real tools.
- **Given** another inherited execution or delegation tool outside the allowlist **When** it is registered **Then** it stays unavailable to Research. No deny-name inventory is needed.
- **Given** an invalid Research policy, an unknown configured tool name, or an unsupported provider **When** delegation is attempted **Then** it fails before a model request. The restriction is never silently dropped.
- **Given** Research and Implementer children of the same parent **When** their tools execute **Then** Research's extra restriction does not remove the parent's or the Implementer's allowed writing capability.
- **Given** a child-local structured-result tool **When** the provider registers it **Then** it stays usable. The test must not claim that inherited-tool filtering controls child-local registrations.

## Harness fit

The owning primitive is the **subagent consumer** in `@deepseek-ai/dsh-dev-loop-roles`. Its existing role configuration selects the Research filter. Its scoped `./tool` consumer supplies the model entry through `dev_loop_delegate`. This piece adds no model tool, public service method, registry, Session event, or Agent-loop behavior.

The public operation is `SubagentRuntime.start(providerName, request)`. Its capability check rejects an unsupported `toolFilter`. Inside one process, `startInProcessRun` owns a private Agent creation `setup` callback. That callback calls `applyChildComposition`. That function joins the parent's standing composition and calls `childCtx.tools.restrict` before the run starts. Roles supplies the request. It does not supply a child-context callback.

The existing production consumer `tool-subagent` already forwards its configured filter through this operation. Roles is one more consumer. Neither consumer needs a wrapper provider or access to provider-private creation code. A post-start registration is invalid: the in-process driver starts the child's followup before it returns the run to its caller.

`ToolRuntime.view` applies restrictions to inherited global and ancestor/preset tools. The child's own registrations stay visible. `resolveExecution` and `dispatchToolBody` consult the filtered view at execution time, including nested PTC dispatch. Removing a schema alone is not enough to pass. Existing restriction registrations are effect-owned. They need no duplicate disposal layer here.

## Contracts

### Research policy owned by Roles

Use `Config.roles.Research.toolFilter` from 00.06. Require an explicit `allow` list for Research. A deny-only policy is not proof that future inherited tools are excluded. The list must be nonempty. It must name the reading capabilities that the configured assignments need. An optional existing `deny` field may only subtract. Configuration stays Host-owned. Model arguments cannot select or override it.

The Roles configuration owner validates the Research-specific requirement at its mount. It passes the typed filter through its existing dispatch path. Any helper stays private to that owner and receives its already-owned configuration. The tool consumer must not reach into the service's private configuration. One internal helper does not justify a public policy service method.

The deployment author supplies the exact names. The author records the inspected implementations that justify admitting each tool. `read` and `read_image` are acceptance-fixture capabilities. They are not invented defaults for every deployment. The fixture also mounts representative filesystem mutation, general execution, and further-delegation tools and excludes them. Do not derive authorization from descriptions, a role label, TypeScript `readonly`, or concurrency metadata. Do not build another tool-classification registry.

Validate configured referents at the earliest supported point. Keep the runtime's child-scope validation at start. Do not silently intersect configured names with a global registry snapshot. Inherited preset tools also matter, and misspelled names must not disappear. Unknown names and reserved PTC transport names reject through `restrict`. Filter end capabilities instead of naming `run_code`.

An allowlist constrains names, not implementations. The tested deployment must inspect the allowed implementations and child-local contributions. General execution and further-delegation tools stay excluded. Admitting them requires a separately identified, real owner that bounds their effects. Adding such an exception requires new evidence and acceptance scope. This piece provides no shell-command parser and no argument-aware guard escape.

### Guarantees and exclusions

The guarantee is refusal of excluded inherited capabilities through the real model/tool execution path. Allowed reading tools still run under their own filesystem policy. This is not a security fence. It does not stop trusted plugins, direct service calls, child-local tools, or filesystem effects of an allowed executable tool. Worktree allocation and filesystem/subprocess sandbox enforcement stay separate responsibilities under [00.05](00.05-worktree-assignment.md).

`ToolDefinition.isConcurrencySafe` classifies parallel versus exclusive scheduling. It does not authorize a call. It does not enforce read-only filesystem behavior. The inspected ToolDefinition and schema sources provide no authoritative read-only/effect permission annotation.

No `agent.role`, `header.role`, or execution role field is required. Roles chooses the configured Research request. The provider installs its filter on that actual child's scope. Scope does not exempt trusted extension code from the limits above.

00.06 uses one-shot `start`. Its one-shot descriptor does not persist the filter for a promised cold continuation. The existing continuable manager separately persists and restores filters. That behavior belongs to the subagent owner. It adds no continuation or recovery to this piece.

Source provenance requirements belong to [00.08](00.08-references-provenance.md). Claim-verification assignments belong to [00.13](00.13-claim-verification.md). Provenance means the record of who reported a finding and from where. Tool denial cannot prove that a report's citations are true. Those consumers use this Research policy. They add no other enforcement path.

## Teach me while you build

- **What it does:** Research receives only the inherited reading capabilities its deployment explicitly selects. A runnable test proves that excluded tools cannot run, even when the model calls one first.
- **Background:** An allowlist admits named capabilities and excludes other inherited names. An agent scope holds contributions for one agent. An executor dispatches a requested tool. Denial must happen there, before the tool body runs.
- **How it works here:** Roles chooses its Research configuration and sends `toolFilter` to `subagents.start`. The in-process provider installs the restriction during unpublished child setup. ToolRuntime applies that restriction when it advertises and dispatches inherited tools. Invalid referents reject creation. The result is never an unrestricted child.
- **Why this approach:** The public request already reaches the correct pre-execution owner. Roles selects and validates the Research policy. Its Loader fixtures prove the configured policy without another enforcement mechanism.
- **Approaches considered:** Explicit allowlists through the existing request are chosen. The real `tool-subagent` consumer demonstrates the input. Deny lists stay supported by the runtime but require naming each new inherited mutation/delegation capability forever. Provider-local guards are real in `structured.ts`, where the provider owns creation. They suit terminal structured-output policy, not a Roles callback that does not exist. Filesystem sandboxing gives different filesystem guarantees but does not replace capability selection. Node's process-level permission model is an external alternative for separately launched workers that need documented resource-API restrictions. It does not filter Harness tool names or automatically constrain child-local tools in a shared process. It is not an OS sandbox.
- **Prior art inspected:** The in-repository tool-subagent consumer and structured-output attachment were opened. Research, preset not recorded, opened [Node v22.19.0 permission documentation](https://github.com/nodejs/node/blob/v22.19.0/doc/api/permissions.md), Permission Model, File System Permissions and Permission Model constraints. This is documentation inspection, not implementation inspection. No external code was reused.
- **What we get for free:** The subagent runtime checks capabilities. Providers own creation timing. ToolRuntime owns scope inheritance, native/PTC execution checks, and effect removal. Roles owns deployment policy and its tests. No new guard registry, role metadata propagation, or session event is needed.
- **From the source documentation:** `ToolRuntime.restrict` states “Restrictions intersect; scoped registrations remain visible.” The caller must tell inherited capabilities apart from child-local machinery. It cannot claim every tool is filtered. Research verified Node's separate warning: “It does not provide security guarantees in the presence of malicious code.” That warning limits Node's permission model. It is not evidence of a particular Harness bypass.
- **What to notice:** The driver installs the filter before `drivePublishedRun` submits the followup. `ToolRuntime.view` adds the child's own tools after inherited-tool filtering. These two locations decide the useful guarantee and its limit.
- **Concepts to own:** Complete mediation means testing the actual dispatch path, not schemas alone. This piece proves it for excluded inherited tools. Least privilege means selecting only the capabilities the assignment needs. Ownership separates deployment policy from runtime enforcement and filesystem isolation.
- **Interview angle:** “How do you avoid a first-call policy race?” Supply the restriction in the existing start request so the provider installs it during creation. Never attach it after start returns. Follow-up: child-local tools and trusted plugin execution need separate scrutiny.
- **Decisions you can now make alone:** Adjust the explicit deployment allowlist after inspecting each admitted tool and extending policy tests. Escalate executable/delegation exceptions, child-local enforcement, sandbox changes, and continuation requirements to their respective owners.
- **What you should learn from this:** A capability filter proves one specific dispatch restriction. It does not prove that every effect in the process is read-only.
