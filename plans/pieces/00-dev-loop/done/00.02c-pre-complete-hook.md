## Summary

Let us consider the final barrier. An orchestrator requests a transition to `done`. Should we accept it? Absolutely not. Witness testimony is unreliable. We install the `piece/pre-complete` Cordis serial event hook. Any registered verification gate may cast an absolute veto by rejecting its promise before filesystem mutation or Git operations commence. There is a 100% certainty that unverified transitions must fail closed.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Serial pre-complete event hook awaiting registered policy listeners and failing closed before any disk header edit or git move.
- **Option B (Alternative)**: Direct completion without event interception, preventing verification gates from exercising mediation.

## Behaviour

- **Given** a piece in `pending` status **When** `transition(pieceId, 'pending', 'done')` is called and a registered `piece/pre-complete` listener rejects **Then** the transition aborts, status remains `pending`, disk and index are untouched, and the claim is released for retry.
- **Given** multiple serial `piece/pre-complete` listeners registered **When** `transition(pieceId, 'pending', 'done')` executes **Then** all listeners are awaited in registration order before any filesystem or Git operation begins.
- **Given** no listeners registered for `piece/pre-complete` **When** `transition(pieceId, 'pending', 'done')` is called **Then** the serial hook executes cleanly and completion proceeds to filesystem relocation.

## Harness fit

Cordis serial event hook declared on `Context` in `packages/dev-loop/lifecycle/src/index.ts` and dispatched via `ctx.serial('piece/pre-complete', event)`. Allows decoupled verification gates to veto piece completion before filesystem mutation.

## Teach me while you build

The suspect has presented an alibi. Before releasing them, we must check every forensic corroboration.

- **What it does**: Intercepts completion attempts via `piece/pre-complete` and queries registered verification gates before any mutation.
- **Background**: In Cordis, `ctx.serial` executes event listeners in registration order. Listeners return a Promise; if any listener rejects, the promise chain halts and the initiating operation fails closed.
- **How it works here**: Before rewriting headers or executing git commands in `complete()`, `DevLoopLifecycle` calls `await this.ctx.serial('piece/pre-complete', { pieceId, from: 'pending', to: 'done', signal, reason })`. If any listener rejects, the error aborts the transition before `fs.editText` or `git mv`.
- **Why this approach**: Complete mediation: the core lifecycle service does not hardcode specific gate logic (Format, RED, GREEN, Git); independent gate plugins register their own checks.
- **Approaches considered**: Hardcoded gate checks inside lifecycle (violates separation of concerns) vs Cordis serial hook (chosen: modular and fail-closed).
- **Prior art inspected**: Git pre-commit hook architecture and OS-level security reference monitors.
- **What we get for free**: Cordis event dispatcher provides execution ordering, error propagation, and automatic unregistration on plugin disposal.
- **From the docs**: `docs/cordis-primer.md`: "serial: listeners observe in registration order, awaited".
- **What to notice**: Notice how the caller's `AbortSignal` is passed to the listener so long-running gate checks can be cancelled cleanly!
- **Concepts to own**: Complete mediation: ensuring every sensitive state transition passes through authorization hooks.
- **Interview angle**: How do you implement extensible validation pipelines without coupling components? Answer: Event hooks with fail-closed serial semantics where any rejection halts execution.
- **Decisions you can now make alone**: You can attach new verification gates without altering the lifecycle service.
- **What you should learn from this**: Never trust an unverified claim of completion; require independent empirical verification before committing state.
