## Summary

Sup! Here's the nightmare scenario: an agent is in the middle of moving a completed piece to `done/`, and the server loses power or gets `kill -9`ed! Now you have a half-moved file, a desynced database, and corrupted state! Daru solves this with Write-Ahead Intent Logging (WAL). We journal our intent to the durable storage domain BEFORE touching disk or Git. If we crash, recovery replays or rolls back the intent. 100% crash-proof!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Log transition intent to durable storage domain before mutating filesystem, resolving upon success.
- **Option B (Alternative)**: Mutate filesystem first and update database second, leaving desynced state on crash.

## Behaviour

- **Given** a valid transition request with human authorization **When** beginTransition(request) is called **Then** it persists an unresolved TransitionRecord with a new TransitionId into the transitions table before any effects occur.
- **Given** an in-flight transition with an unresolved TransitionId **When** finishTransition(id, observation) is executed **Then** it atomically records the terminal outcome with observed effects and timestamp on that intent row.
- **Given** an unresolved admitted intent for a piece in durable storage **When** another beginTransition is attempted for that piece **Then** it rejects with PIECE_QUARANTINED before modifying state or storage.

## Teach me while you build

Rule number one of database engineering: write the intent before you touch the data. That's WAL.

- **What it does**: Records planned state changes in durable storage before executing file operations, enabling crash recovery.
- **Background**: Write-Ahead Logging ensures that if a system halts mid-operation, the recovery engine knows what was attempted.
- **How it works here**: Inserts an intent record with a UUID. After disk mutation succeeds, updates the row to committed. Incomplete rows signal crash recovery.
- **Why this approach**: Guarantees atomicity across heterogeneous resources (storage domain + POSIX filesystem).
- **Approaches considered**: File operations without logging (vulnerable to crash desync) vs Two-phase commit (complex) vs Write-ahead intent (chosen: lean and robust).
- **Prior art inspected**: ARIES recovery algorithm and PostgreSQL WAL.
- **What we get for free**: Storage domain single-layout mode guarantees serialization and atomic persistence across intents.
- **From the docs**: AGENTS.md: 'Public APIs are pre-stable; update every consumer. SQLite uses monotonic SCHEMA_VERSION.'
- **What to notice**: Notice how an unresolved intent immediately quarantines the piece against duplicate concurrent transitions!
- **Concepts to own**: Write-ahead logging (WAL): recording intention in durable storage prior to applying state mutations.
- **Interview angle**: How do you achieve atomic consistency between database updates and filesystem modifications? Answer: Write-ahead intent logging with startup reconciliation.
- **Decisions you can now make alone**: You can configure history limits and record byte budgets in persistence config.
- **What you should learn from this**: Log your intent before you act. Crash recovery is only possible if you leave a paper trail.
