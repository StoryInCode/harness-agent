# 00.07 — Research Subagent Read-Only Guard

**Set:** 00-dev-loop · **Queue:** 7 · **Depends on:** 00.06
**Status:** todo
**Harness primitive:** event/hook plugin · **Package:** `@deepseek-ai/dsh-dev-loop-research-guard`

## Summary

Enforces that a subagent delegated the `Research` role cannot mutate the repository. Enforcement is **scope-based, not metadata-based**: the restriction is installed on the Research child's own context, so it applies to that child and no other, and there is no role field to forge, omit, or read. 00.06 starts the child with `toolFilter: { deny: [...] }`; the subagent seam applies it as `childCtx.tools.restrict(filter)` inside the child's creation window, which removes the named tools from that child's prompt and makes them refuse to execute.

The denied set is the tools that actually exist: `write` and `edit` from `@deepseek-ai/dsh-tool-fs`, plus `bash` wherever a shell tool is mounted. It is intersected with the names the deployment really registers, because `restrict()` rejects an unknown global-tool name loudly. Where a mounted tool must stay available but not mutate, a second, argument-aware layer denies one call at a time: `childCtx.tools.guard()`, whose returned string is the denial reason. This read-only scope covers spec claim-verification assignments (00.13): a subagent checking repository facts, dependency APIs, or negative existence cannot mutate code or tests to make a claim true, and returns findings carrying exact source provenance.

## Behaviour

- **Given** a Research child started with the read-only filter **When** its tool list is built **Then** `read` and `read_image` are present and `write` and `edit` are absent from that child's prompt.
- **Given** a Research child **When** the model nonetheless calls `write` **Then** the executor reports `UNKNOWN_TOOL`, because a restricted tool is invisible to execution as well as to the prompt.
- **Given** a Research child whose deployment mounts `bash` and keeps it visible **When** the guard registered on that child's context returns a reason for the call **Then** the call settles as an error result whose message is that reason, and the tool body never runs.
- **Given** a Research subagent executing a claim-verification brief (00.13) **When** it verifies repository facts, dependency APIs, or negative existence **Then** every mutating tool remains denied and its findings carry verifiable provenance citations.
- **Given** an Implementer child started without the filter **When** it calls `write` **Then** the call executes normally, because the restriction lives on the Research child's scope and on no other.
- **Given** a deny list naming a tool this deployment does not register **When** the child is composed **Then** `restrict()` throws naming the unknown tool, so a stale deny list fails loud at delegation instead of silently protecting nothing.

## Harness fit

This is an `event/hook plugin` whose registrations are installed on the Research child's own scope, never globally.

There is no role discriminator to check. `ToolGuard = (execution: Readonly<ToolExecution>) => string | undefined` receives `callId`, `rootCallId`, `name`, `arguments`, `agent?: Agent`, `parent`, `signal` and `token` — no session, no role. A guard that branched on `session.role` would never fire. Scope is the discriminator instead, and it is the stronger one: nothing has to set, propagate, or trust a label.

Two registrations, both scoped to the child, both returning their exact disposer:

1. **`childCtx.tools.restrict({ deny })`** — declarative and durable. 00.06 passes it as `SubagentStartRequest.toolFilter`; `applyChildComposition` calls `restrict` in the creation window, and the filter is persisted in the subagent descriptor, so a cold-resumed continuation is composed with it again. `restrict()` throws on an unscoped context ("requires a scoped context (agent.ctx): a context-global restriction would mask every agent"), which is exactly the mistake this piece must not make, and it throws on an unknown global-tool name. The provider must declare `SubagentCapabilities.toolFilter`; in-process spawn and fork do, and `subagent-acp` does not, so an ACP-backed Research delegation is rejected at start rather than silently unrestricted.
2. **`childCtx.tools.guard(fn)`** — argument-aware and per-call, for a tool that must remain visible (a shell tool whose command line decides mutation). Guards run after the whole `tools/pre-execute` waterfall and compose monotonically: any guard may deny, none can force-allow what another denied, so a later listener cannot resurrect a denied dispatch. Registering a guard needs the child's creation window, which the subagent provider owns; this package therefore exports the registration as a function the delegation path calls with `childCtx`, and where no creation window is reachable the tool is denied outright in the restriction instead.

## Contracts

```typescript
import type { Context } from '@deepseek-ai/cordis'
import type { ToolRestriction } from '@deepseek-ai/dsh-tools'

/**
 * Registered model-facing tool names that mutate. These are TOOL names, not
 * `FileSystem` method names: `writeText`/`editText` are methods on the fs
 * seam and are not callable by a model.
 */
export const MUTATING_TOOL_NAMES = ['write', 'edit', 'bash'] as const

/** Every field optional so a cordis.yml row may set one and inherit the rest. */
export interface Config {
  /** Tool names denied to a Research child. Default: `MUTATING_TOOL_NAMES`. */
  denyTools?: string[]
  /**
   * Names denied by the per-call guard rather than removed, for a tool that
   * must stay visible. Default: empty.
   */
  guardTools?: string[]
}

/**
 * The start-request filter for a Research child, intersected with the tools
 * this deployment registers, because `restrict()` rejects an unknown name.
 * @param registered - global tool names currently registered.
 * @returns the filter to pass as `SubagentStartRequest.toolFilter`.
 */
export function researchToolFilter(registered: Iterable<string>): ToolRestriction

/**
 * Install the per-call denial on one Research child, inside its creation window.
 * @param childCtx - the child agent's scoped context; an unscoped context throws.
 * @returns the exact disposer that lifts the guard.
 */
export function guardResearchChild(childCtx: Context): () => void
```

A guard denial is not an exception: the executor materializes an error result whose text is `Error: <reason>`, so the child sees the refusal and can report it. A restricted tool is invisible instead, and the executor answers `UNKNOWN_TOOL`.

## Teach me while you build

- **Background**: A *scope* here is one agent's own Cordis context. Registrations made on it are visible to that agent alone and disappear when it is disposed. A *tool restriction* removes named tools from a scope; a *tool guard* is a synchronous function consulted per call that denies by returning a reason string. *Monotonic composition* means guards only ever subtract: adding one can never re-admit a call another denied.
- **How it works here**: 00.06 builds the Research child's start request and attaches `toolFilter` from `researchToolFilter(...)`. Inside the child's creation window, `applyChildComposition` (`packages/subagent/subagent/src/child-agent.ts`) calls `childCtx.tools.restrict(filter)`; the same filter is persisted in the child's descriptor, so a continuation that cold-resumes is composed with it again rather than waking up unrestricted. A call to a removed tool reports `UNKNOWN_TOOL` from the executor. For a tool that must stay visible, `guardResearchChild(childCtx)` registers the per-call check, which runs after the `tools/pre-execute` waterfall and turns a returned reason into an error result. Open `packages/dev-loop/research-guard/src/index.ts`, and read `packages/subagent/subagent-in-process-driver/src/structured.ts` for a five-line production guard on a child scope.
- **Why this approach**: Scope is a fact of the runtime; role metadata would be an assertion this piece has to keep true everywhere. The first draft of this piece tried to branch on `session.role` inside the guard — `ToolExecution` carries no session at all, so the check would have compiled only if invented and fired never. The simplest alternative is prompting ("do not modify files"), which models ignore while exploring.
- **Approaches considered**: (1) *Scoped `restrict()` at delegation, chosen* — declarative, survives cold resume through the descriptor, fails loud on an unknown name; it cannot see arguments. (2) *Scoped `guard()`* — sees `name` and `arguments`, so it can deny `bash rm -rf` while allowing `bash ls`; needs the creation window and re-registration on resume, and every command-line parser is an arms race. (3) *A global guard filtering by agent id* — one registration for all children, but `ToolRuntime.guard`'s own JSDoc says a plain-context guard applies globally, so a bug there masks every agent; rejected. (4) *Denying at the filesystem layer instead*, by starting the child under a `read-only` sandbox policy — genuinely stronger for files, since it also binds a shell tool, but it is per-session policy rather than per-role and it denies the child's own scratch writes too; the right combination is probably both, and 00.05 owns that half.
- **Prior art inspected**: None. No external project was opened for this amendment, and none is named. The in-repository precedent is `subagent-in-process-driver/src/structured.ts`, which was read.
- **What we get for free**: The subagent seam applies `toolFilter` in the creation window and persists it in the descriptor; `ToolRuntime` owns visibility collapse, `UNKNOWN_TOOL` denial, guard composition, and the disposer for every registration. We write the deny list, the intersection with registered names, and the argument-aware predicate.
- **What to notice**: `restrict()` throws on an unscoped context by design — the error text explains that a context-global restriction would mask every agent. That throw is the guardrail against the most tempting wrong implementation of this piece.
- **Lesson**: Enforce a boundary where the runtime already draws one. A check keyed on metadata is only as good as the code that remembers to set the metadata; a check keyed on scope cannot be forgotten, because the scope is what runs the call.

## Reuse capture

- **Reuse candidate**: Scope-confined read-only child · Composes a delegated child with a deny filter on its own context plus an argument-aware per-call guard, so the confinement travels with the agent rather than with a label · Used in `researchToolFilter` / `guardResearchChild` · Reusable for read-only auditor agents, dry-run modes, and any delegation that must not write · Would need the deny list and the guard predicate lifted into parameters · Evidence: `packages/dev-loop/research-guard/tests/research-guard.spec.ts` · Confidence: medium — one implementation, and the guard half depends on reaching a creation window
- **Anti-pattern worth keeping**: Enforcing a permission by reading role metadata off the execution. This piece specified `session.role === 'Research'` on an object that carries no session; the guard would have compiled only with an invented type and denied nothing at runtime. Before keying a security check on a field, open the type that is supposed to carry it.
- **Known limitations**: A denied tool is denied wholesale unless a guard inspects its arguments, and a shell-command parser is an arms race — prefer removing `bash` from a Research child to policing it. The guard half requires the child's creation window, which the subagent provider owns; a provider that exposes none leaves only the restriction. Neither layer constrains what a tool the child KEEPS may do (a read tool that follows a symlink out of the workspace is a filesystem-sandbox question, not a tool-scope one).
