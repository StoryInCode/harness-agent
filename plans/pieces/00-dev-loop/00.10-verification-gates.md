# 00.10 — Multi-Gate Verification Enforcer

**Set:** 00-dev-loop · **Queue:** 10 · **Depends on:** 00.02, 00.09
**Status:** todo
**Harness primitive:** event/hook plugin · **Package:** `@deepseek-ai/dsh-dev-loop-gates`

## Summary

Enforces four mandatory post-implementation behaviour verification gates before any piece can transition to `done`: (1) Format Gate (piece AST and axioms pass), (2) RED Gate (test suite initially failed against baseline), (3) GREEN Gate (all tests pass and test hashes remain pinned), and (4) Post-merge Gate (tests rerun successfully on master after the implementation is transferred). This behaviour verification (does the code work?) is strictly distinguished from upstream claim verification (00.13: is the spec true?), which is evaluated before test authoring begins. It hooks into the serial `piece/pre-complete` lifecycle hook, blocking completion if any behaviour verification check fails or lacks objective evidence.

## Behaviour

- **Given** a piece where all four behaviour verification gates pass **When** `piece/pre-complete` is evaluated **Then** the hook resolves cleanly and allows transition to `done`.
- **Given** a piece completing implementation **When** behaviour verification gates run **Then** the enforcer assesses post-implementation runtime evidence (test execution, hash integrity, and post-merge test results) rather than re-evaluating pre-implementation spec claims.
- **Given** a piece whose implementation modified tests **When** the GREEN gate checks test file SHA-256 hashes **Then** the hook throws `TEST_TAMPERING_DETECTED` and blocks completion.
- **Given** a piece with failing unit tests **When** the GREEN gate evaluates test results **Then** the hook throws `TEST_SUITE_FAILED` and transitions the piece to `blocked`.
- **Given** a piece whose changes were transferred to master **When** the final post-merge tests fail or lack execution evidence **Then** the hook throws `POST_MERGE_TESTS_FAILED` and does not mark the piece done.
- **Given** a piece attempting completion without proof of RED gate execution **When** evaluated **Then** the hook throws `UNPROVEN_RED_BASELINE`.

## Teach me while you build

- **Background**: Verification occurs at two distinct stages in the loop, answering two fundamentally different questions. *Claim verification* (00.13) runs upfront before any tests or code are written, asking: **is the spec true?** (checking repo symbols, pinned dependency APIs, and negative existence). *Behaviour verification* (00.10) runs at the end of implementation, asking: **does the code work?** (checking test execution, hash pinning, and post-merge results). Conflating the two creates false confidence: passing tests for an untrue spec simply codifies defects into working code.
- **How it works here**: The plugin registers `ctx.on('piece/pre-complete', async (event) => ...)`. When completion is requested, the hook sequentially evaluates 4 post-implementation behaviour gates: (1) Format Gate validates markdown AST and primitive declarations, (2) RED Gate checks for recorded initial test failure proof, (3) GREEN Gate runs the test suite and verifies test file SHA-256 hashes match the RED baseline (anti-tampering), and (4) Post-merge Gate verifies successful test execution on master after transfer. No separate Reviewer is dispatched. If any gate fails, an error (e.g. `TEST_TAMPERING_DETECTED`) is thrown, halting completion. Open `packages/dev-loop/gates/src/index.ts`.
- **Why this approach**: Serial pre-completion event interceptor. The simplest alternative is running verification checks in a post-commit hook or script, but post-commit checks cannot prevent invalid status transitions from entering the database.
- **What we get for free**: Cordis serial event dispatch stops execution on the first thrown error and aborts downstream listeners automatically.
- **What to notice**: Test file SHA-256 hash pinning prevents Implementer agents from making tests pass by deleting assertions or disabling tests, while claim verification in 00.13 ensures those tests were built on true premises.
- **Lesson**: Enforce multi-layer quality invariants at state transitions using serial event hooks that can veto invalid mutations before commit, and always separate claim truth from runtime behaviour.
