## Summary

Samples host available memory by parsing Linux `/proc/meminfo` (`MemAvailable`, `MemTotal`, `SwapTotal`, `SwapFree`) with sub-millisecond TTL memoization (`cacheTtlMs`, default 500ms) to prevent I/O thrashing during parallel tool calls. It computes memory metrics against configurable thresholds, returning structured `MemorySnapshot` records. On macOS (Darwin) and Windows, it transparently degrades to `node:os.freemem()` and `totalmem()`, populating `isDegraded: true` without throwing unhandled exceptions.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Parse kernel `/proc/meminfo` for true `MemAvailable` with a 500ms TTL cache, degrading gracefully to `node:os.freemem()` on macOS/Windows.
- **Option B (Alternative)**: Poll `node:os.freemem()` exclusively on all platforms, producing inaccurate free-memory readings on Linux that mistake reclaimable page cache for memory exhaustion.

## Behaviour

- **Given** a Linux host **When** `getMemorySnapshot()` is called **Then** it parses `/proc/meminfo` to extract true kernel `MemAvailable` (avoiding misleading `MemFree` numbers).
- **Given** repeated queries within `cacheTtlMs` (default 500ms) **When** called in rapid succession **Then** it returns the memoized snapshot without re-reading procfs.
- **Given** execution on macOS or Windows **When** snapshot is requested **Then** it degrades transparently to `node:os.freemem()`, setting `isDegraded: true` and `cgroupAvailable: false`.
- **Given** a complete OS memory query failure **When** evaluated **Then** it fails closed by reporting 0 available bytes, refusing heavy workloads to prevent host lockup.

## Harness fit

This is a `Service Provider` primitive owned by `@deepseek-ai/dsh-guard-memory-provider`. It isolates low-level OS memory metric extraction and cache invalidation. Decoupling memory metric acquisition from admission policy ensures high-performance, crash-resilient telemetry across platforms.

## Teach me while you build

Checking `os.freemem()` on Linux is a classic rookie mistake. Linux uses free RAM for buffer cache, so `freemem()` says you have 200MB left when you actually have 14GB of reclaimable memory! Daru explains how we sample memory like real system engineers.

- **What it does**: Parses Linux `/proc/meminfo` to capture true available memory and swap usage with a 500ms TTL cache, falling back to `node:os` on other platforms.
- **Background**: The Linux kernel reports `MemAvailable` in `/proc/meminfo`, estimating how much memory can be allocated without triggering swap or out-of-memory (OOM) killing.
- **How it works here**: On Linux, we read `/proc/meminfo`, parse the `MemAvailable:` and `MemTotal:` fields in kB, and convert to bytes. A 500ms memoization timer ensures high-concurrency tool spikes don't re-read procfs dozens of times per second. On macOS and Windows, it calls `os.freemem()` and flags `isDegraded: true`.
- **Why this approach**: Reading `MemAvailable` gives accurate admission headroom, preventing premature tool rejection while avoiding OOM lockup.
- **Approaches considered**: Naive `os.freemem()` everywhere (rejected: falsely triggers OOM throttles on Linux due to buffer cache) vs Shelling out to `free -b` (rejected: heavyweight subprocess per check) vs Direct `/proc/meminfo` parser with TTL cache (chosen: microsecond latency and accurate telemetry).
- **Prior art inspected**: Linux kernel `/proc/meminfo` documentation and systemd memory pressure monitoring.
- **What we get for free**: Node's built-in `node:os` provides cross-platform fallbacks without third-party native addons.
- **What to notice**: Notice the 500ms TTL cache: queries within that window return instantly from memory, eliminating procfs I/O contention.
- **Concepts to own**: Kernel memory accounting: distinguishing between unallocated memory (`MemFree`) and instantly reclaimable cache memory (`MemAvailable`).
- **Interview angle**: Why shouldn't you rely on `os.freemem()` on Linux servers? Answer: `os.freemem()` reports raw unused pages (`MemFree`), ignoring page cache and reclaimable dentries, which makes a healthy system look starved of memory.
- **Decisions you can now make alone**: You can tune `cacheTtlMs` in `MemoryProviderConfig` based on the frequency of tool admission checks.
- **Lesson**: Know what your OS abstractions actually measure before making admission decisions based on their numbers.
