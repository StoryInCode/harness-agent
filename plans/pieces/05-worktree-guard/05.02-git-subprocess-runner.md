## Summary

Provides a typed, security-hardened Git CLI invocation runner wrapping `ctx.subprocess.spawn` (`SubprocessRuntime`) for all worktree operations. It enforces discrete `argv` execution with zero shell interpretation, strips sensitive credentials via `scrubbedParentEnv()`, and forces non-interactive flags (`GIT_TERMINAL_PROMPT=0`). On Linux and Windows, it bounds Git processes inside systemd transient scopes or Job Objects to prevent orphaned lockfiles, and includes shallow repository recovery (`git fetch --unshallow`) to guarantee reachability calculations succeed.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Invoke Git via discrete `argv` argument vectors using `ctx.subprocess.spawn` with scrubbed environments (`GIT_TERMINAL_PROMPT=0`) and managed process group cancellation.
- **Option B (Alternative)**: Pass concatenated command strings through `/bin/bash -c` or `ctx.shell`, introducing shell quotation bugs, shell injection risks, and uncontrolled process leakage.

## Behaviour

- **Given** an array of Git arguments **When** `git.run(argv, options)` is executed **Then** `ctx.subprocess.spawn` executes Git directly without `/bin/bash` or shell concatenation.
- **Given** an ambient environment containing API keys (`DEEPSEEK_API_KEY`, etc.) **When** Git commands run **Then** credentials are scrubbed case-insensitively while preserving proxies, `PATH`, and non-interactive flags.
- **Given** an aborted `signal` during Git checkout **When** abort fires **Then** the process group is cleanly terminated, avoiding stale `.git/index.lock` locks.
- **Given** a Git process exiting with non-zero code **When** command fails **Then** `GitSubprocessError` is thrown containing exact exit code, stdout, and trimmed stderr.

## Contracts

```typescript
export interface GitRunOptions {
  readonly cwd: string
  readonly timeoutMs?: number | undefined
  readonly signal?: AbortSignal | undefined
  readonly env?: Record<string, string> | undefined
  readonly allowNonZeroExit?: boolean | undefined
}

export interface GitRunResult {
  readonly exitCode: number
  readonly stdout: string
  readonly stderr: string
  readonly durationMs: number
}

export class GitSubprocessError extends Error {
  constructor(
    readonly command: string,
    readonly exitCode: number,
    readonly stdout: string,
    readonly stderr: string,
  ) {
    super(`Git command failed (${exitCode}): git ${command}\n${stderr.trim()}`)
    this.name = 'GitSubprocessError'
  }
}

export interface GitRunner {
  run(argv: readonly string[], options: GitRunOptions): Promise<GitRunResult>
  runLines(argv: readonly string[], options: GitRunOptions): Promise<readonly string[]>
  isShallow(cwd: string, signal?: AbortSignal): Promise<boolean>
  deepenShallowRepo(cwd: string, signal?: AbortSignal): Promise<void>
}
```

## Teach me while you build

Yo, Daru here. Let me tell you straight: script kiddies concatenate shell strings with `exec('git ' + cmd)`. Elite hackers use discrete `argv` vectors so no weird filename or rogue parameter can ever trick the shell!

- **What it does**: Wraps Git CLI execution in a typed, hardened subprocess runner with strict environment scrubbing and process group isolation.
- **Background**: Executing Git commands via shell strings invites shell injection and leaks terminal prompts that hang background processes forever.
- **How it works here**: `packages/dev-loop/worktree/src/git.ts:39-103` passes discrete `argv` arrays directly to `ctx.subprocess.spawn` (`packages/subprocess/subprocess/src/index.ts:86-154`), wiping sensitive environment variables and setting `GIT_TERMINAL_PROMPT=0`.
- **Why this approach**: Option A eliminates shell parsing entirely and ensures clean process group cleanup on abort, whereas Option B leaves dangling lockfiles and leaked API tokens.
- **Approaches considered**: Raw shell string execution with bash -c (rejected: shell injection and quote escaping nightmares) vs Node child_process.execFile (rejected: lacks Cordis subprocess lifecycle and systemd scope binding) vs Managed `ctx.subprocess.spawn` with argv vectors (chosen).
- **Prior art inspected**: Git documentation on non-interactive environment configuration (`git(1)` man page and `GIT_TERMINAL_PROMPT` specifications).
- **What we get for free**: Automated stdio buffer bounding, process tree tracking, and systemd transient scope cleanup from `packages/subprocess/subprocess-local/src/linux-scope.ts:404-450`.
- **What to notice**: Look at how `GIT_TERMINAL_PROMPT: '0'` and `GCM_INTERACTIVE: 'Never'` prevent Git from silently waiting on an interactive credential helper prompt.
- **Concepts to own**: Discrete argument execution (preventing shell word-splitting) and synchronous process tree teardown on cancellation.
- **Interview angle**: Why should you never use `child_process.exec` for Git automation? Answer: Exec spawns a shell, exposing commands to shell injection, argument truncation, and zombie children.
- **Decisions you can now make alone**: You can safely add custom Git flags without worrying about escaping spaces or metacharacters in paths.
- **Lesson**: Keep your subprocesses on a short leash with discrete argv vectors and strict environment scrubbing, or watch your background workers lock up your repo!
