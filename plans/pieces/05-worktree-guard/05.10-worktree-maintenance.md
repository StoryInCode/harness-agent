## Summary

Maintains Git object database health and prevents filesystem performance degradation caused by pack file sprawl during intensive multi-worktree lifecycles. It monitors the count of `.pack` files under `<repoRoot>/.git/objects/pack/` against a configurable threshold (default 15). When exceeded, it triggers an asynchronous, fail-soft background `git repack -a -d --quiet` executed with low scheduling priority (`nice -n 19` on Linux) without blocking foreground agent turns.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Trigger asynchronous background repacking with low scheduling priority (`nice -n 19`) when `.pack` file count reaches threshold, coalescing concurrent runs.
- **Option B (Alternative)**: Run synchronous foreground repacks or rely on automated git gc, blocking task allocation and stalling worker subagents.

## Behaviour

- **Given** a repository with pack count below `packSprawlThreshold` **When** pack health is evaluated **Then** it records health status and takes no repack action.
- **Given** pack file count reaching or exceeding threshold (>= 15) **When** pack health check runs **Then** it triggers a background repack task.
- **Given** a Linux host **When** background repack spawns **Then** it is executed under `nice -n 19` to preserve CPU headroom for active worker subagents.
- **Given** multiple allocation cycles triggering maintenance concurrently **When** a repack is already running **Then** duplicate requests are coalesced.

## Teach me while you build

When you spawn dozens of worktrees and commit chunks of code, Git fragments objects into separate pack files. Let enough `.pack` files pile up and your filesystem crawls. Here is how we keep the repo lean in the background without stealing cycles from active compilers.

- **What it does**: Monitors `.pack` file sprawl under `.git/objects/pack/` and asynchronously triggers low-priority `git repack` when counts exceed threshold.
- **Background**: Git packs objects into compressed archive files (`.pack`). Too many pack files degrade index lookup performance and waste inode descriptors.
- **How it works here**: We count `.pack` files in `<repoRoot>/.git/objects/pack/`. If count >= 15, we spawn `git repack -a -d --quiet` under `nice -n 19` on Linux, coalescing overlapping requests into a single running job.
- **Why this approach**: Running maintenance asynchronously with reduced priority keeps Git fast without causing CPU spikes that stall worker subagent test runs.
- **Approaches considered**: Synchronous `git gc` on every allocation (rejected: introduces 2-10 second latency spikes) vs Ignoring pack sprawl entirely (rejected: leads to disk thrashing and slow git operations) vs Asynchronous fail-soft repack with nice priority (chosen: background hygiene without foreground impact).
- **Prior art inspected**: Git documentation on `git repack` and `git gc --auto`.
- **What we get for free**: Git's pack redundant object deletion (`-d`) automatically prunes unpacked duplicates during repacking.
- **What to notice**: If the background repack fails (e.g. repo lock contention), it logs a diagnostic warning fail-soft instead of crashing the orchestrator or active worktree.
- **Concepts to own**: Fail-soft background maintenance: scheduling non-critical cleanup tasks asynchronously with throttled concurrency and low priority.
- **Interview angle**: How do you maintain Git repository health in automated multi-agent environments? Answer: Monitor `.pack` file counts and trigger background `git repack` with low scheduling priority and request deduplication.
- **Decisions you can now make alone**: You can tune `packSprawlThreshold` or minimum interval between repacks in `PackMaintenanceConfig`.
- **Lesson**: Clean up your garbage in the background so your main thread never stutters.
