## Summary

Allocates an isolated Git worktree for an autonomous task from a recorded base commit. It resolves the freshest upstream ref or HEAD (`git rev-parse HEAD^{commit}`), pins the immutable 40-character base commit SHA in `WorktreeRecord`, provisions `.worktrees/<taskId>/` on dedicated branch `kanban/<taskId>`, and verifies `.worktrees/` is present in the root `.gitignore`. If worktree creation fails or is aborted, it executes an atomic rollback protocol to purge partial checkout directories, delete half-born branch refs, and prune Git admin records.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Pin an explicit immutable base commit SHA, verify `.gitignore` containment, and execute an all-or-nothing rollback protocol that purges partial checkouts and pruned metadata on failure.
- **Option B (Alternative)**: Create worktrees on dynamic floating references without rollback handling, risking stale bases, unignored worktree commits, and orphaned half-created worktree artifacts on crash or abort.

## Behaviour

- **Given** a task ID and repository root **When** `allocateWorktree` runs **Then** it queries `git rev-parse HEAD^{commit}`, pins the resulting SHA in `WorktreeRecord.baseCommit`, and creates the worktree directory.
- **Given** an allocation request with `syncBase: true` **When** remote tracking is available **Then** it checks remote upstream freshness before branching.
- **Given** an execution failure or abort signal during `git worktree add` **When** rollback triggers **Then** it removes partial files, deletes the newly created branch, runs `git worktree prune`, and throws structured `WorktreeAllocationError`.
- **Given** an allocated worktree **When** inspected **Then** `WorktreeRecord` contains the exact pinned base commit, branch name, path, and creation timestamp.

## Harness fit

This is a `workflow capability` primitive owned by `@deepseek-ai/dsh-worktree-allocator`. It encapsulates the transactional multi-step creation and rollback sequence. Separating allocation from high-level coordination guarantees atomicity and ensures that checkout errors or cancellation signals never leave orphaned branches or dirty filesystem residue.

## Contracts

```typescript
export interface WorktreeAllocator {
  allocate(options: WorktreeAllocateOptions): Promise<WorktreeRecord>
  resolveBaseCommit(repoRoot: string, baseRef?: string, signal?: AbortSignal): Promise<{ sha: CommitSha; label: string }>
  ensureGitignored(repoRoot: string, entry?: string): Promise<void>
  rollbackFailedAllocation(params: {
    repoRoot: string
    worktreePath: string
    branchName?: string | undefined
  }): Promise<void>
}

export class WorktreeAllocationError extends Error {
  constructor(
    readonly taskId: string,
    readonly worktreePath: string,
    readonly gitStderr: string,
  ) {
    super(`Failed to allocate worktree for task "${taskId}" at "${worktreePath}":\n${gitStderr.trim()}`)
    this.name = 'WorktreeAllocationError'
  }
}
```

## Teach me while you build

Yo, Daru here. If your worktree allocator doesn't clean up after itself when a subprocess crashes, congratulations: you just wrote a hard disk pollution script!

- **What it does**: Pins an immutable base commit, checks `.gitignore`, creates the isolated worktree directory, and cleans up partial residue if anything aborts.
- **Background**: If an agent starts working against a dirty or floating HEAD, any subsequent push or rebase will produce silent conflicts. Even worse, if worktree creation aborts midway, orphaned folders and dangling Git metadata will block future tasks.
- **How it works here**: In `packages/dev-loop/worktree/src/index.ts:95-140`, `allocate()` reads `main.head`, checks that `.worktrees/` is in `.gitignore` via `git check-ignore`, and creates the worktree. On failure, `rollbackFailedAllocation()` deletes the directory and prunes Git worktree refs.
- **Why this approach**: Option A guarantees atomic transactional allocation—either the worktree is completely valid and pinned, or nothing is left behind on disk. Option B leaves dirty disk residue that corrupts future builds.
- **Approaches considered**: Blind worktree creation without rollback (rejected: leaves zombie worktrees on abort) vs Floating branch checkouts (rejected: commits slip out from under running tests) vs Pinned commit allocation with atomic rollback (chosen).
- **Prior art inspected**: Git documentation on `git worktree add` flags and `git worktree prune`.
- **What we get for free**: Git's built-in reference tracking ensures that once a commit is pinned, concurrent commits on the mainline never alter the worktree's tree state.
- **What to notice**: Look at how `check-ignore` is executed before creating the directory, preventing accidental tracking of the entire `.worktrees` subtree.
- **Concepts to own**: Transactional filesystem allocation with compensating rollback actions.
- **Interview angle**: How do you implement crash-safe workspace allocation for concurrent worker threads? Answer: Pin an immutable snapshot ID up front and register an idempotent rollback handler that unwinds half-created state on failure.
- **Decisions you can now make alone**: You can change the worktree root path safely knowing the ignore check will prevent accidental commits.
- **Lesson**: If your workspace allocation can't cleanly roll back after a SIGINT, you're not writing infrastructure—you're writing a disk corrupter!
