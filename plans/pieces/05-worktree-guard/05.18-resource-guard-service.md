## Summary

Yo, Daru here. We're locking down the entire machine with the singleton `ResourceGuardService` extending Cordis `Service` on the Host Plane, injecting `['tools']` and publishing `ctx.resourceGuard` and typed events into Cordis. It defines a comprehensive Schemastery `Config` schema validating every threshold (`minAvailableMemBytes`, `headroomBytes`, `sliceCeilingBytes`, `swapCeilingBytes`, `perWorkerReservationBytes`, `cgroupPressureThrottlePercent`, `cacheTtlMs`, `heavyToolPatterns`, `heavyCommandNames`, `protectedPaths`, `mutationToolPatterns`) with fail-loud validation. It coordinates telemetry providers, admission evaluation, and monotonic tool guard lifecycle.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Deploy a unified singleton `ResourceGuardService` on the Host Plane validating thresholds through strict Schemastery schemas and coordinating memory, cgroup, and tool guards across all sessions.
- **Option B (Alternative)**: Instantiate disparate per-session guard services without centralized Schemastery validation, duplicating telemetry polling and causing inconsistent admission thresholds between parallel sessions.

## Behaviour

- **Given** Cordis initialization **When** `@deepseek-ai/dsh-guard-resource` loads **Then** `ctx.resourceGuard` is registered globally on the Host Plane with typed event definitions.
- **Given** an invalid config (e.g. `headroomBytes < minAvailableMemBytes` or negative TTL) **When** loaded **Then** it fails loudly with `ConfigurationError`.
- **Given** a query for host memory or worker admission **When** `getMemorySnapshot()` or `canAdmitWorker(count)` is invoked **Then** it coordinates provider caches and returns deterministic admission verdicts.

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'

export interface Config {
  minAvailableMemBytes?: number
  headroomBytes?: number
  sliceCeilingBytes?: number
  swapCeilingBytes?: number
  perWorkerReservationBytes?: number
  cgroupPressureThrottlePercent?: number
  meminfoPath?: string
  cgroupSlicePath?: string
  cacheTtlMs?: number
  heavyToolPatterns?: string[]
  heavyCommandNames?: string[]
  protectedPaths?: string[]
  mutationToolPatterns?: string[]
}

export const Config: z<Config> = z.object({
  minAvailableMemBytes: z.number().default(1536 * 1024 * 1024),
  headroomBytes: z.number().default(3072 * 1024 * 1024),
  sliceCeilingBytes: z.number().default(6144 * 1024 * 1024),
  swapCeilingBytes: z.number().default(512 * 1024 * 1024),
  perWorkerReservationBytes: z.number().default(768 * 1024 * 1024),
  cgroupPressureThrottlePercent: z.number().default(80),
  meminfoPath: z.string().default('/proc/meminfo'),
  cgroupSlicePath: z.string().default('/sys/fs/cgroup/hermes-work.slice'),
  cacheTtlMs: z.number().default(500),
  heavyToolPatterns: z.array(z.string()).default(['bash', 'terminal', 'execute_code', 'browser_exec', 'subagent_*']),
  heavyCommandNames: z.array(z.string()).default(['vitest', 'jest', 'webpack', 'tsc', 'make', 'cargo', 'go', 'npm', 'pnpm', 'yarn', 'bun', 'pytest']),
  protectedPaths: z.array(z.string()).default(['**/SOUL.md', '**/.hermes/SOUL.md', 'SOUL.md']),
  mutationToolPatterns: z.array(z.string()).default(['writeText', 'editText', 'write_file', 'edit_file', 'str_replace_editor', 'bash', 'terminal']),
})

export class ResourceGuardService extends Service {
  static readonly inject = ['tools']
  static readonly Config = Config
  constructor(ctx: Context, config: Config) { super(ctx, 'resourceGuard') }
  abstract getMemorySnapshot(): MemorySnapshot
  abstract checkAdmission(requestedBytes?: number): Promise<AdmissionResult>
  abstract canAdmitWorker(activeWorkerCount: number): Promise<boolean>
  abstract isPathProtected(filePath: string): boolean
  abstract getSliceMetrics(): Promise<CgroupSliceMetrics | undefined>
}

declare module '@deepseek-ai/cordis' {
  interface Context { resourceGuard: ResourceGuardService }
  interface Events {
    'resource/admission-denied'(event: { toolName: string; availableBytes: number; requiredHeadroomBytes: number }): void
    'resource/headroom-warning'(event: { availableBytes: number; headroomBytes: number; activeWorkers: number }): void
    'resource/soul-violation'(event: { toolName: string; attemptedPath: string }): void
  }
}
```

## Teach me while you build

No shortcuts when dealing with physical host limits. Here's how we wire up the host master service cleanly.

- **What it does**: Binds memory metrics, cgroup telemetry, command classification, and admission logic into a single Host Plane Cordis service.
- **Background**: Isolated components need a centralized host coordinator to mount onto Cordis, publish typed events, and expose unified APIs to task runners and Kanban.
- **How it works here**: Extends `Service(ctx, 'resourceGuard')`. Declares `inject: ['tools']`. Validates config with Schemastery. On startup, attaches telemetry providers and mounts monotonic tool guards. Emits `resource/admission-denied` and `resource/soul-violation` on breaches.
- **Why this approach**: Host Plane singleton ensures one single source of truth for machine capacity; every worker session shares the exact same memory telemetry and admission governor.
- **Approaches considered**: Per-session guard instances (rejected: causes redundant procfs polling and divergent admission decisions) vs Decentralized ad-hoc hooks (rejected: difficult to inspect or test as a unified unit) vs Centralized Host Service (chosen: single point of coordination).
- **Prior art inspected**: Systemd resource management slices and Cordis service container architecture.
- **What we get for free**: Cordis `Service` base class handles automatic lifecycle management, service registration, and dependency injection.
- **What to notice**: Notice the fail-loud Schemastery schema: an invalid threshold crashes at boot time before any worker can run into undefined behavior.
- **Concepts to own**: Host Plane singletons: services that manage machine-level hardware resources across multiple isolated agent sessions.
- **Interview angle**: How do you structure resource management across multiple isolated sandboxed agents in an extensible application? Answer: Register a host-level singleton service that owns physical machine telemetry and exposes admission checks, while worker agents receive read-only or scoped capabilities.
- **Decisions you can now make alone**: You can configure host-wide memory thresholds in configuration without modifying subagent code.
- **Lesson**: Hardware is shared. Never let individual agent sessions independently guess host resource limits. Centralize telemetry on the host!
