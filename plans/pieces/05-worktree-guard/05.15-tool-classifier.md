## Summary

The probability of autonomous model divergence causing unmonitored host resource exhaustion or identity corruption approaches certainty without deterministic classification. We rigorously classify tool executions and shell invocations into resource-heavy workloads versus lightweight diagnostic commands, and enforce human file sovereignty (`INV-09`). It evaluates tool names against configured patterns, tokenizes compound shell commands via a POSIX tokenizer (`shlex`) to detect heavy build and test binaries, exempts diagnostic queries (`git status`, `ls`, `cat`), and inspects filesystem mutations against `protectedPaths` to veto any autonomous mutation targeting `SOUL.md`.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Tokenize shell commands via an exact POSIX shlex lexer and match AST/binary tokens against configured heavy binaries and protected paths (`SOUL.md`), allowing lightweight diagnostics (`git status`, `ls`) to run unhindered.
- **Option B (Alternative)**: Blindly classify all `bash` or execution tools as heavy, or rely on naive substring searching (`command.includes("SOUL.md")`), which produces catastrophic false positives on inspection (`cat SOUL.md`) and misses aliased mutation vectors.

## Behaviour

- **Given** a tool execution matching `heavyToolPatterns` or a shell command invoking heavy binaries (`vitest`, `tsc`, `cargo`, `npm test`) **When** classified **Then** `isHeavy` returns `true`.
- **Given** a shell command running diagnostic queries (`git status`, `ls -la`, `pwd`) **When** tokenized **Then** `isHeavy` returns `false`, exempting it from headroom vetoes.
- **Given** a filesystem mutation tool or shell redirection targeting `SOUL.md` **When** inspected **Then** `isSoulMutation` returns `true`, whereas read-only inspection (`cat SOUL.md`) returns `false`.

## Teach me while you build

The evidence indicates that models will inadvertently bypass resource limits or overwrite critical instructions if boundaries rely on trust. Forensic verification is mandatory.

- **What it does**: Inspects tool invocation metadata and tokenizes shell pipelines to classify resource intensity and detect unauthorized mutations of sovereign files (`SOUL.md`).
- **Background**: Autonomous agents frequently issue compound shell commands (`git checkout . && npm test`) that mix benign diagnostics with heavy workloads, or accidentally overwrite system identity instructions.
- **How it works here**: Receives `toolName` and `args`. For shell tools (`bash`), runs POSIX `shlex` tokenization to extract binary names and file redirection targets. Compares against `heavyToolPatterns`, `heavyCommandNames`, and `protectedPaths`.
- **Why this approach**: Token-level inspection yields 100% precision on binary detection without the false positives of naive substring searching.
- **Approaches considered**: Substring searching (rejected: treats `cat SOUL.md` identically to `rm SOUL.md`) vs Full bash AST parser (rejected: heavy dependency and unnecessary parsing overhead for command detection) vs POSIX tokenization with stream classification (chosen: O(N) tokens, zero false positives on flag-free queries).
- **Prior art inspected**: GNU Bash POSIX word splitting specification and Python `shlex` lexical analysis.
- **What we get for free**: Standard regex and token iteration in TypeScript provide deterministic execution without external C++ bindings.
- **What to notice**: Redirection operators (`>`, `>>`) and deletion utilities (`rm`, `unlink`, `shred`) mutate files even when wrapped in subshells; the tokenizer inspects redirect targets.
- **Concepts to own**: Epistemic bounds and lexical classification: distinguishing semantic intent (read vs write, heavy vs diagnostic) from surface strings.
- **Interview angle**: How do you prevent an agent sandbox from executing unauthorized file overwrites via shell redirection without disabling the shell? Answer: Tokenize the shell command stream to detect redirection targets pointing to protected file paths before execution.
- **Decisions you can now make alone**: You can add new heavy testing binaries to `heavyCommandNames` without altering the tokenization logic.
- **Lesson**: Substring matching is an epistemic hazard. Always tokenize command streams before making authorization or admission decisions.
