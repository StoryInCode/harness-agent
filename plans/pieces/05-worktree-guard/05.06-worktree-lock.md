## Summary

Manages administrative Git worktree locks using `git worktree lock --reason` tagged with the host process ID and task purpose. It prevents external Git routines (`git worktree prune`) or concurrent tasks from dismantling active checkouts. It features dead-lock detection using POSIX process probing (`process.kill(pid, 0)` catching `ESRCH`), safely unlinking stale locks abandoned by crashed workers while protecting live processes from accidental interference.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Acquire administrative Git worktree locks tagged with host PID and timestamp, using POSIX signal 0 probing (`process.kill(pid, 0)`) to distinguish live worker locks from stale dead-process locks.
- **Option B (Alternative)**: Rely solely on bare file presence or untagged locks, unable to differentiate running workers from crashed orphans and risking either accidental deletion of active worktrees or permanent deadlocks.

## Behaviour

- **Given** an allocated worktree **When** `lockWorktree` executes **Then** `git worktree lock` is applied with structured reason containing host PID and timestamp.
- **Given** a locked worktree **When** `getLockInfo` runs **Then** it extracts owning PID, reason string, and lock liveness status.
- **Given** a lock held by a live process **When** liveness probe runs **Then** `isLockLive` returns `true` and prevents unforced unlocking.
- **Given** a lock held by a deceased process (`ESRCH`) **When** liveness probe runs **Then** `isLockLive` returns `false`, classifying the lock as dead and reclaimable.

## Harness fit

Centralizing lock management ensures that orphaned lock files from SIGKILL or power events are safely cleared without risking corruption of running tasks.

## Contracts

```typescript
export interface WorktreeLockInfo {
  readonly isLocked: boolean
  readonly pid?: number | undefined
  readonly reason?: string | undefined
  readonly isLive: boolean
}

export class WorktreeLockedError extends Error {
  constructor(readonly worktreePath: string, readonly lockInfo: WorktreeLockInfo) {
    super(`Worktree "${worktreePath}" is locked by PID ${lockInfo.pid ?? 'unknown'}: ${lockInfo.reason ?? 'no reason'}`)
    this.name = 'WorktreeLockedError'
  }
}

export interface WorktreeLockManager {
  lock(worktreePath: string, reason: string): Promise<void>
  unlock(worktreePath: string, forceIfDead?: boolean): Promise<void>
  getLockInfo(worktreePath: string): Promise<WorktreeLockInfo>
  isProcessLive(pid: number): boolean
}
```

## Teach me while you build

Yo, Daru here. Leaving untagged lockfiles around when an agent dies is how you get phantom locks that freeze your entire pipeline until someone manually runs `rm -rf`!

- **What it does**: Tags worktrees with administrative locks via `git worktree lock` and uses POSIX signal 0 probes to detect and clear dead-process locks.
- **Background**: If a background agent crashes or receives a SIGKILL, its worktree lock file stays on disk forever. A naive script either deadlocks forever waiting for the lock, or blindly deletes locks and corrupts a currently running worker.
- **How it works here**: In `packages/dev-loop/worktree/src/git.ts:150-165`, Git's porcelain inventory reads lock state and reason fields. In `WorktreeLockManager`, `process.kill(pid, 0)` is used to ping the PID without sending an actual signal; if it throws `ESRCH`, the process is dead and the lock is classified as dead and safe to reclaim.
- **Why this approach**: Option A inspects the PID and proves process death via POSIX signal 0 before unlocking, whereas Option B blindly deletes locks or gets stuck indefinitely.
- **Approaches considered**: Unconditional lock deletion on timeout (rejected: falsely unlocks slow but active workers) vs Permanent blocking (rejected: locks out the repo after a crash) vs PID-tagged locks with POSIX liveness verification (chosen).
- **Prior art inspected**: POSIX kill(2) specification for signal 0 process existence checks and Git `git worktree lock` documentation.
- **What we get for free**: Native Git lock files in `.git/worktrees/<id>/locked` prevent Git's own garbage collection (`git worktree prune`) from deleting the worktree.
- **What to notice**: Look at how `ESRCH` means the process does not exist, whereas `EPERM` means the process exists but is owned by another user (still alive!).
- **Concepts to own**: POSIX process liveness probing using signal 0 (`kill(pid, 0)`).
- **Interview angle**: How can a Node.js daemon detect if a process holding a file lock is still running? Answer: Call `process.kill(pid, 0)`. If it succeeds or throws `EPERM`, the process is alive; if it throws `ESRCH`, the process has terminated.
- **Decisions you can now make alone**: You can safely write automatic crash-recovery routines that sweep dead locks on daemon startup without risking running jobs.
- **Lesson**: Don't guess if a worker is alive based on a timestamp; ask the OS kernel with signal 0!
