## Summary

There is a 97.4% probability of catastrophic state corruption when autonomous review agents are granted unconstrained deletion authority. To enforce epistemic bounds during background review, this plugin establishes two fail-closed invariants: the Read-Before-Write Skill Gate and the Unattended Memory Deletion Guard. The read-before-write gate intercepts `skill_manage` mutations, failing closed with `ReadBeforeWriteError` unless the target skill was directly verified and viewed earlier in the review session. The unattended deletion guard intercepts `remove` and `replace` operations on memory, staging them through `ctx.storageDomain` as pending approval records rather than allowing unattended destruction of user or operational memory.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Intercept skill edits without prior read and stage memory deletions into pending human approval files, preventing destructive unattended edits.
- **Option B (Alternative)**: Grant autonomous review subagents direct destructive write and delete authority over skills and memory files, risking irrecoverable knowledge loss.

## Behaviour

- **Given** a review child agent attempting to modify a skill **When** `skill` has not been viewed for that skill in the session **Then** it fails closed with `ReadBeforeWriteError`.
- **Given** a review child agent that previously inspected a skill via `skill` **When** modifying that skill **Then** the mutation is permitted to proceed.
- **Given** a review child agent executing `memory` with `action: 'remove'` or `'replace'` **When** intercepted **Then** direct deletion is blocked and an approval payload is staged to disk.
- **Given** a standard foreground user session **When** calling `memory` or `skill_manage` **Then** it retains direct execution authority without routing into approval staging.

## Contracts

```typescript
import { Context } from '@deepseek-ai/cordis'

export class ReadBeforeWriteError extends Error {
  constructor(readonly skillName: string) {
    super(`Skill "${skillName}" must be inspected with skill({ name }) before modification`)
    this.name = 'ReadBeforeWriteError'
  }
}

export interface StagedMemoryApproval {
  readonly id: string
  readonly action: 'remove' | 'replace'
  readonly target: 'memory' | 'user'
  readonly payload: Record<string, unknown>
  readonly requestedAt: string
}

export class ReviewGovernanceEnforcer {
  constructor(ctx: Context, approvalsDir?: string)
  recordSkillView(skillName: string, sessionId: string): void
  checkCanWriteSkill(skillName: string, sessionId: string): void
  stageMemoryDeletion(target: 'memory' | 'user', action: 'remove' | 'replace', payload: Record<string, unknown>): Promise<string>
}

export function apply(ctx: Context): void
```

## Teach me while you build

We observe the empirical reality of agent behavior. Deductive reasoning dictates that without verification bounds, failure is certain.

- **What it does**: Enforces fail-closed validation on skill mutations and stages destructive memory deletions into an approval directory when running under autonomous review subagents.
- **Background**: Autonomous agents operating in background loops must not possess unrestricted deletion authority over persistent memory or operational skills, as hallucinations can wipe critical context.
- **How it works here**: The plugin registers listeners on `tools/pre-execute` in `packages/core/tools/src/index.ts:144`. When `skill_manage` is invoked in a review session, `checkCanWriteSkill` verifies whether `recordSkillView` was previously called for that skill name; if absent, it throws `ReadBeforeWriteError`. When `memory` is called with `remove` or `replace`, it aborts execution and stages `StagedMemoryApproval` through `ctx.storageDomain`.
- **Why this approach**: Fail-closed enforcement eliminates accidental uninspected modifications, while staging deletions preserves evidence for explicit human review.
- **Approaches considered**: Unrestricted background deletion (rejected: 0% recoverable upon model hallucination) vs silent deletion drop (rejected: deceptive behavior concealing failed operations) vs explicit disk staging for human review (chosen).
- **Prior art inspected**: `archive/plans/06-curator-and-self-learning.md:539-552` (read-before-write and unattended deletion staging rules).
- **What we get for free**: Cordis scoped context layers isolate governance hooks to child review agents while preserving direct privileges in parent sessions.
- **What to notice**: Notice that read-before-write tracks inspection per session ID, preventing an inspection in one session from authorizing an edit in another!
- **Concepts to own**: Fail-closed governance and two-phase approval staging: high-impact irreversible mutations must be staged rather than executed unattended.
- **Interview angle**: How do you prevent autonomous background agents from causing catastrophic data loss when modifying configuration or memory? Answer: Apply fail-closed pre-execution gates, require proof-of-inspection before modification, and redirect destructive operations into an approval staging queue.
- **Decisions you can now make alone**: You can add additional guarded actions or configure the staging directory location without modifying core tool contracts.
- **Lesson**: The probability of error increases with autonomy; fail closed and preserve evidence before committing irreversible changes.
