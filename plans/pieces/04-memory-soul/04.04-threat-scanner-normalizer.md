## Summary

Nya~ (=^･ω･^=)🐾 Inspector Cat's whiskers twitch whenever sneaky threats hide in text! Implements security scanning, normalization, and sanitization for memory note writes and prompt loading. It normalizes inputs using Unicode Normalization Form KC (NFKC), blocks invisible characters (zero-width spaces `\u200B`, joiners, direction isolates), and runs regex threat pattern scanning against prompt injection vectors. On write, threats abort immediately with `MemoryThreatDetectedError`; on load, compromised entries on disk are masked with `[BLOCKED: security threat detected]` placeholders while preserving raw disk content for forensics.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Normalize text with Unicode NFKC, strip invisible characters, and scan against prompt-injection regex patterns on write while masking on load.
- **Option B (Alternative)**: Rely solely on LLM self-moderation or raw string equality, leaving memory storage vulnerable to zero-width steganography and homoglyph evasion.

## Behaviour

- **Given** note text containing Unicode homoglyphs **When** scanned **Then** it normalizes characters using NFKC before threat evaluation.
- **Given** note text containing zero-width spaces (`\u200B`) or direction overrides (`\u202A`–`\u202E`) **When** scanned on write **Then** it throws `MemoryThreatDetectedError`.
- **Given** note text containing known prompt injection patterns **When** scanned on write **Then** it rejects the write with `MemoryThreatDetectedError`.
- **Given** an existing poisoned note on disk **When** loaded for prompt assembly **Then** `sanitizeNote` masks the content with `[BLOCKED: security threat detected]`.

## Teach me while you build

Purr~ Let's learn how to spot tricky disguises and invisible mouse traps! (=^･ω･^=)

- **What it does**: Normalizes text into standard Unicode characters, rejects zero-width characters and prompt injections on write, and masks toxic entries when loading.
- **Background**: Attackers use Unicode tricks (like looking like regular letters using Cyrillic homoglyphs or hiding payloads inside zero-width spaces) to bypass simple string filters.
- **How it works here**: `normalizeContent` applies `String.prototype.normalize('NFKC')` to collapse visual equivalents into standard ASCII/Unicode. `scanThreat` checks for zero-width spaces, bidirectional override characters, and known prompt injection signatures.
- **Why this approach**: Option A cleanses and checks inputs at the string level before they touch storage or prompts, defeating obfuscated injection payloads deterministically.
- **Approaches considered**: LLM-based safety classifier (rejected: high latency, token cost, and non-deterministic) vs Blacklist of ASCII words only (rejected: trivially bypassed by Unicode homoglyphs) vs Unicode NFKC normalization with regex scanning (chosen).
- **Prior art inspected**: no prior art inspected
- **What we get for free**: Native ECMAScript `String.prototype.normalize` handles full Unicode standard compatibility tables without third-party dependencies.
- **What to notice**: On write, threats are aborted immediately (`MemoryThreatDetectedError`). But on load from disk, we do not crash; we mask with `[BLOCKED: ...]` so the rest of memory remains accessible!
- **Concepts to own**: Unicode normalization forms (NFC, NFD, NFKC, NFKD), homoglyph attacks, zero-width steganography, fail-safe degradation.
- **Interview angle**: Why is NFKC preferred over NFC when sanitizing untrusted inputs for security filters? Answer: NFKC applies compatibility decomposition, converting visual lookalikes (like fullwidth characters and mathematical symbols) into canonical equivalents so filters cannot be evaded.
- **Decisions you can now make alone**: You can add new threat signature regexes without altering the normalization pipeline.
- **Lesson**: Normalize text representations before evaluating security predicates; otherwise, equivalent characters will slip right past your defenses! Nya~
