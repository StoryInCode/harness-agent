## Summary

Yo! Daru here with raw filesystem locking. Provides multi-process mutual exclusion and atomic commit mechanics for memory note files. It acquires cooperative `.lock` files with exponential backoff up to `lockTimeoutMs` (default 5,000ms), records the owning PID, and incorporates stale lock recovery (`REVIEW-lifecycle.md` Gap 6) that unlinks locks older than `lockTimeoutMs * 2` whose recorded PID is dead (`process.kill(pid, 0)` throws `ESRCH`). Writes stage to temporary files (`.mem_<uuid>`) and commit via atomic POSIX filesystem renames.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Acquire cooperative `.lock` files containing process PIDs with exponential backoff, dead PID reaping (`ESRCH`), and atomic temp-file rename swaps.
- **Option B (Alternative)**: Rely on non-atomic direct file overwrites or in-memory mutexes, causing race conditions and file truncation across multiple process instances.

## Behaviour

- **Given** a target file path **When** `withLock` executes **Then** it creates `<file>.lock` containing process PID and executes the mutation exclusively.
- **Given** two concurrent processes attempting to mutate `MEMORY.md` **When** executed **Then** the second process waits and acquires only after the first releases.
- **Given** a lock held by a live process exceeding `lockTimeoutMs` **When** timeout expires **Then** it throws `MemoryLockTimeoutError`.
- **Given** a stale `.lock` file older than `lockTimeoutMs * 2` whose recorded PID is dead (`ESRCH`) **When** lock acquisition runs **Then** it unlinks the stale lock and acquires successfully.

export class MemoryLockTimeoutError extends Error {
  constructor(readonly lockPath: string, readonly timeoutMs: number) {
    super(`Failed to acquire lock at ${lockPath} within ${timeoutMs}ms`)
    this.name = 'MemoryLockTimeoutError'
  }
}

export interface LockOptions {
  lockTimeoutMs?: number
  staleThresholdMs?: number
  backoffInitialMs?: number
  backoffMaxMs?: number
}

export class MemoryFileLock {
  constructor(readonly targetPath: string, readonly options?: LockOptions)
  withLock<T>(action: () => Promise<T>): Promise<T>

## Teach me while you build

Alright, listen up. Here is how you handle multi-process file concurrency without corrupting data like a total amateur.

- **What it does**: Prevents concurrent processes from overwriting each other's memory files by using PID-stamped lockfiles, exponential backoff, and atomic renames.
- **Background**: If two agent workers write to `MEMORY.md` at the same instant, standard file writes result in interleaved content or truncated files. In-process mutexes are useless when multiple separate OS processes run.
- **How it works here**: `withLock` attempts to create `<file>.lock` using `O_CREAT | O_EXCL`. If the file exists, it polls with exponential backoff. If the lock is older than `lockTimeoutMs * 2`, it probes the PID via `process.kill(pid, 0)`. If the OS returns `ESRCH` (no such process), the lock is orphaned and gets unlinked.
- **Why this approach**: Option A guarantees process-level mutual exclusion across workers and crash recovery without requiring an external database daemon like Redis.
- **Approaches considered**: In-memory JavaScript mutex (rejected: does not protect across OS processes) vs Advisory `flock(2)` (rejected: platform inconsistencies and NFS hazards) vs Cooperative PID lockfile with atomic rename (chosen).
- **Prior art inspected**: no prior art inspected
- **What we get for free**: POSIX atomic rename semantics (`rename(2)` / `fs.promises.rename`) ensure that reader processes never see half-written temporary files.
- **What to notice**: Look at how `process.kill(pid, 0)` is used: passing signal 0 performs error checking without actually sending a kill signal!
- **Concepts to own**: Atomic filesystem operations, test-and-set mutual exclusion, exponential backoff with jitter, zombie lock reaping.
- **Interview angle**: How do you detect if a process holding a lockfile crashed without deleting the lock? Answer: Record the PID in the lockfile; on timeout, check if the PID still exists in the OS using `kill(pid, 0)`; if `ESRCH` is returned, reap the stale lock.
- **Decisions you can now make alone**: You can tune backoff intervals and timeout thresholds for high-contention scenarios.
- **Lesson**: Never write directly to a live shared file; write to a temp file first, then atomically rename it under a cooperative lock!
