## Summary

Tut-turii~ (★^O^★) Mayuri is here to stitch all our lovely memory, soul, and curator pieces together so everyone gets along in perfect harmony! Configures host bundle wiring and agent preset compositions for memory, soul, and curator capabilities. In the host bundle (`packages/bundle/base/cordis.patch.yml`), it registers storage domain routes (`curator: sqlite`) and mounts host singleton services (`ctx.memory`, `ctx.memoryCurator`). In agent presets (`presets/dev-loop-brain/agent.cordis.yml` and `dev-loop-worker`), it mounts `@deepseek-ai/dsh-soul` (Identity Slot #1), `@deepseek-ai/dsh-tool-memory`, and (in `dev-loop-brain`) existing `@deepseek-ai/dsh-tool-session-query` without scope collisions.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Separate host-level singleton storage services into the host bundle patch and mount agent-level prompt/tool plugins into preset YAML files, respecting container lifecycle boundaries.
- **Option B (Alternative)**: Bundle host storage singletons directly into agent session presets, causing duplicate service instantiation and SQLite locking collisions on every new session.

## Behaviour

- **Given** host initialization **When** the base bundle patch loads **Then** `LocalMemoryStore` and `CuratorRuntime` mount as host singletons on the root container.
- **Given** a `dev-loop-brain` session **When** initialized **Then** it mounts `tool-memory`, `tool-session-query` (bounded to 20 hits), and renders `SOUL.md` at order 0.
- **Given** a `dev-loop-worker` session **When** initialized **Then** it mounts `tool-memory` and renders `SOUL.md` at order 0 without session query tools.
- **Given** an HMR reload of the memory bundle **When** executed **Then** prompt sections and tools unbind cleanly without memory leaks or orphan listeners.

## Harness fit

This component is a `patch layer` providing declarative Cordis configurations across host (`packages/bundle/base/cordis.patch.yml`) and agent planes (`presets/dev-loop-brain/agent.cordis.yml`, `presets/dev-loop-worker/agent.cordis.yml`), adhering strictly to host singleton and session tool composition rules (`plans/REVIEW-seams.md:105-112`).

## Teach me while you build

Tut-turii~ Everyone gather 'round! Mayuri made sure all the pieces fit snugly into their matching slots!

- **What it does**: Stitches together host distribution patches and agent session presets so identity, semantic notes, and background curation work smoothly without scope clashes.
- **Background**: Cordis maintains a two-plane hierarchy: the host plane (root container for long-lived singletons) and the agent plane (per-session isolated contexts for tools and prompts).
- **How it works here**: In `packages/bundle/base/cordis.patch.yml`, storage routes allocate SQLite backing for `curator`, mounting `LocalMemoryStore` and `CuratorRuntime`. In `presets/dev-loop-brain/agent.cordis.yml` and worker presets, `@deepseek-ai/dsh-soul` and `@deepseek-ai/dsh-tool-memory` are mounted directly in the session context, providing identity and memory tools.
- **Why this approach**: Clear separation between root singletons and session plugins prevents file lock contention and duplicate background housekeeping tasks.
- **Approaches considered**: Monolithic session mounting (rejected: spawns duplicate housekeeping timers per session) vs global tool registration (rejected: leaks specialized tools into worker agents that do not need them) vs layered host patch plus preset composition (chosen).
- **Prior art inspected**: `plans/REVIEW-seams.md:105-112` (root container multi-session singleton rules).
- **What we get for free**: Cordis loader automatically handles YAML config schema validation, dependency injection, and clean service unbinding during HMR reload.
- **What to notice**: Notice how `tool-session-query` is granted to `dev-loop-brain` but omitted from `dev-loop-worker` to keep worker context footprints small and light!
- **Concepts to own**: Plane separation in IoC containers: keeping durable stateful services in the root container and ephemeral prompt/tool bindings in leaf sessions.
- **Interview angle**: How do you architect plugin composition across shared daemon infrastructure and ephemeral worker sessions? Answer: Anchor stateful resources and cross-session daemons as host singletons, and project stateless tools and prompts into session-scoped child containers.
- **Decisions you can now make alone**: You can easily adjust housekeeping intervals or attach new agent-level tools without modifying the host storage layer.
- **Lesson**: Good architecture is like sewing a warm quilt: every patch has its place, and the seams keep everything together! Tut-turii~
