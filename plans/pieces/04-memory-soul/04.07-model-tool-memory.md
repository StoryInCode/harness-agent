## Summary

Nya~ (=^･ω･^=)🐾 Inspector Cat is checking the tool chest! We are implementing the model-facing `memory` tool registered via `ctx.tools.register()`. It exposes single actions (`add`, `replace`, `remove`) and atomic batch `operations` for managing operational memory (`target: "memory"`) and founder preferences (`target: "user"`). It validates parameter schemas, delegates mutations to host `ctx.memory`, supports deferred budget evaluation, and strictly enforces `INV-09` by rejecting any attempt to target `soul`.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Expose both single operations and atomic batch arrays with deferred schema and budget validation, allowing note removals and additions to resolve together at capacity.
- **Option B (Alternative)**: Restrict the tool to single-note mutations only, forcing multi-step round trips that fail whenever a user attempts to replace a note while at the maximum character budget limit.

## Behaviour

- **Given** a tool invocation with `action: 'add'` and `target: 'memory'` **When** executed **Then** it adds the note to `MEMORY.md` via `ctx.memory.mutate()`.
- **Given** a tool invocation with `target: 'soul'` **When** evaluated **Then** parameter schema validation rejects the invocation before execution (`INV-09`).
- **Given** a store at maximum character capacity **When** a batch operation simultaneously removes and adds notes **Then** deferred budget validation succeeds without intermediate overflow failure.

```typescript
import type { Context } from '@deepseek-ai/cordis'
import type { ParameterSchemaSpec } from '@deepseek-ai/dsh-tools'

export const name = 'tool-memory'
export const inject = ['tools', 'memory'] as const

export const memoryToolParameters = {
  action: {
    type: 'string',
    enum: ['add', 'replace', 'remove'],
    description: 'Operation to perform for a single mutation. Omit when using operations array.',
  },
  target: {
    type: 'string',
    enum: ['memory', 'user'],
    required: true,
    description: 'Target note store: "memory" for operational notes, "user" for founder preferences. SOUL.md cannot be targeted.',
  },
  content: { type: 'string', description: 'Note text for "add", or replacement text for "replace".' },
  old_text: { type: 'string', description: 'Existing text snippet to match for "replace" or "remove".' },
  new_text: { type: 'string', description: 'Replacement text for "replace" action.' },
  operations: {
    type: 'array',
    description: 'Atomic batch of operations evaluated sequentially with deferred character budget validation.',
    items: {
      type: 'object',
      additionalProperties: false,
      properties: {
        action: { type: 'string', enum: ['add', 'replace', 'remove'], required: true },
        content: { type: 'string' },
        old_text: { type: 'string' },
        new_text: { type: 'string' },
      },
    },
  },
} as const satisfies ParameterSchemaSpec

export function apply(ctx: Context): void
```

## Teach me while you build

Purr~ Let's inspect how model tools stay safe from naughty tricks! (=^･ω･^=)

- **What it does**: Exposes the `memory` tool to the LLM so it can save, update, and remove notes without ever pawing at the forbidden `SOUL.md`!
- **Background**: Language models need clear tool schemas. If the parameter schema is ambiguous, models hallucinate invalid keys and cause messy errors.
- **How it works here**: The tool parses incoming arguments against `memoryToolParameters`. If `target: 'soul'` is detected, it fails with a strict validation rejection (`INV-09`). Otherwise, it forwards the mutation to `ctx.memory.mutate()`.
- **Why this approach**: Validating parameters at the schema boundary prevents unauthorized operations before they ever touch disk or the underlying store.
- **Approaches considered**: Unchecked string arguments (rejected: too claw-ful, prone to malformed writes), separate tools for every action (`memory_add`, `memory_remove`, rejected: clutters tool list), and a single unified tool with single and batch actions (chosen).
- **Prior art inspected**: Model Context Protocol (MCP) tool schemas and JSON Schema draft 2020-12 specifications.
- **What we get for free**: `ctx.tools.register()` automatically injects the tool schema into LLM prompt assembly and cleans up on plugin disposal.
- **What to notice**: The `target` parameter strictly allows `'memory' | 'user'` and completely excludes `'soul'`, keeping core identity safe from model overwrites!
- **Concepts to own**: Schema-level access control, deferred batch validation, and fail-closed parameter parsing.
- **Interview angle**: Why enforce access boundaries like `INV-09` in the tool parameter schema rather than inside the storage layer alone? Because defense in depth rejects invalid inputs before invoking execution pipelines.
- **Decisions you can now make alone**: You can add new non-destructive memory operations without modifying the core registration framework.
- **Lesson**: Strict schema gates at the perimeter keep mischievous paws away from protected state! Nya~
