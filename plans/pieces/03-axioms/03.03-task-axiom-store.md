## Summary

Manages persistence and state transitions for card-level task axiom documents (`TaskAxiomDocument`) via `ctx.storageDomain`. Consumes the typed `task_axioms` domain (version 1) over table `documents`, providing zero disk latency synchronous in-memory reads during completion gates and sequential write chain durability. Enforces the 6-state lifecycle (`PROPOSED`, `ACTIVE`, `SATISFIED`, `VIOLATED`, `BLOCKED`, `SUPERSEDED`) with Zod schema validation, failing fast on schema version mismatches. Supersedes bespoke `~/.hermes/task-axioms/` file persistence.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Persist `TaskAxiomDocument` records via SQLite-backed `ctx.storageDomain` with monotonic schema versioning and in-memory cache for zero-latency gate checks.
- **Option B (Alternative)**: Write ad-hoc unversioned JSON files to `~/.hermes/task-axioms/`, risking concurrent write corruption and disk I/O bottlenecks during gates.

## Behaviour

- **Given** a valid `TaskAxiomDocument` **When** `saveTaskAxioms` is called **Then** the record commits to `ctx.storageDomain` atomically and updates the in-memory cache.
- **Given** an existing card row ID **When** `getTaskAxioms` is called **Then** it returns the document synchronously from memory without disk I/O.
- **Given** an active task axiom **When** status updates to `SATISFIED` **Then** the transition commits and `axioms/task-updated` fires on the host event bus.
- **Given** an incompatible storage schema version on startup **When** opening the domain **Then** it throws a version mismatch error.

## Harness fit

This component is a `Service Provider` mounted on the host plane consuming `ctx.storageDomain` (`packages/storage/storage-domain`), eliminating bespoke filesystem persistence and lock contention (`archive/plans/03-axiom-subsystem.md:81-99`).

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import { z } from 'zod'
import { defineDomain, domainTable } from '@deepseek-ai/dsh-storage-domain'
import type { TaskAxiomDocument, TaskAxiomId, TaskAxiomStatus } from '@deepseek-ai/dsh-axiom'

export const TASK_AXIOMS_DOMAIN_VERSION = 1

export const taskAxiomDocumentSchema = z.object({
  task: z.string(),
  row: z.string(),
  goal: z.string(),
  created: z.string(),
  governing: z.array(z.string()),
  axioms: z.array(z.record(z.unknown())),
  proofs: z.array(z.record(z.unknown())),
  unresolved: z.array(z.string()),
  nextAction: z.string(),
})

export const taskAxiomsDomainSpec = defineDomain({
  name: 'task_axioms',
  version: TASK_AXIOMS_DOMAIN_VERSION,
  tables: {
    documents: domainTable<string, TaskAxiomDocument>(taskAxiomDocumentSchema as any),
  },
})

declare module '@deepseek-ai/cordis' {
  interface Context {
    taskAxiomStore: TaskAxiomStore
  }
}

export abstract class TaskAxiomStore extends Service {
  constructor(ctx: Context) {
    super(ctx, 'taskAxiomStore', true)
  }
  abstract get(rowId: string): Promise<TaskAxiomDocument | undefined>
  abstract save(doc: TaskAxiomDocument): Promise<void>
  abstract updateStatus(rowId: string, axiomId: TaskAxiomId, status: TaskAxiomStatus, blocker?: string): Promise<void>
}
```

## Teach me while you build

Yo! Daru the Super Hacker here. You want state persistence? Real hackers don't spew raw unversioned JSON files all over disk like script kiddies.

- **What it does**: Manages persistent card-level task axiom state using `ctx.storageDomain`, providing instant synchronous in-memory reads and transactional SQLite writes with strict monotonic schema versioning.
- **Background**: Storage domains (`ctx.storageDomain`) are the harness's official persistence layer. They wrap SQLite tables with structured Zod validation and transparent memory caching so readers never stall waiting for disk spins.
- **How it works here**: `taskAxiomsDomainSpec` defines the `task_axioms` domain with table `documents`. Calling `save(doc)` checks the payload against `taskAxiomDocumentSchema`, appends the write sequentially, updates the in-memory cache, and emits `axioms/task-updated`. Calling `get(rowId)` hits the in-memory cache directly with zero I/O latency.
- **Why this approach**: SQLite-backed storage domain with in-memory caching gives us atomic commits and microsecond gate reads, whereas flat JSON files get toasted the instant two workers write concurrently.
- **Approaches considered**: Flat files in `~/.hermes/task-axioms/` (rejected: write collisions, corrupted JSON on hard SIGKILL, zero schema migration safety) vs Raw custom SQLite connection (rejected: reinvents domain lifecycle and misses harness-managed table isolation) vs Managed `ctx.storageDomain` (chosen: turnkey atomic writes, automatic cache hydration, monotonic version checking).
- **Prior art inspected**: SQLite Write-Ahead Logging (WAL) and `packages/storage/storage-domain/src/index.ts`.
- **What we get for free**: Storage domain gives us write serialization, typed table specs, and instant crash recovery out of the box.
- **What to notice**: Fast-fail versioning: if `TASK_AXIOMS_DOMAIN_VERSION` doesn't match what's in the database header on startup, it blows up with `DomainError('version-mismatch')` instead of corrupting data.
- **Concepts to own**: Cache-aside write-through pattern: keeping an in-memory table mirrored to an append-only persistent storage engine.
- **Interview angle**: How do you guarantee sub-millisecond status lookups for state-machine gates without sacrificing durable crash recovery? Answer: Combine an in-memory cache for synchronous reads with sequential write-through persistence to an ACID-compliant storage domain.
- **Decisions you can now make alone**: You can add new indexes or table definitions to the domain spec whenever task axiom queries expand.
- **Lesson**: Never dump mutable application state into naked JSON files on disk; use an ACID-backed storage domain so a sudden `kill -9` doesn't vaporize your savegame.
