## Summary

Registers the `resolve_candidate_axioms` tool on `ctx.tools` on the agent plane for planner and orchestrator sessions (`dev-loop-brain`). It allows the model to explicitly inspect governing prose instructions and machine-checkable constraints for candidate directory and file paths prior to drafting task DoD contracts or modifying code. It solves the planning-time visibility gap cleanly via preset composition without modifying core `agent-instructions` or inventing ad-hoc event hooks.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Expose an explicit model-facing query tool (`resolve_candidate_axioms`) in planner presets, letting models inspect targeted directory constraints on demand.
- **Option B (Alternative)**: Statically inject all repository instruction files into the initial system prompt, bloating context tokens and adding noise from irrelevant subtrees.

## Behaviour

- **Given** an orchestrator session **When** calling `resolve_candidate_axioms` with `paths: ['packages/fs/fs']` **Then** it returns rendered instructions, applicable file paths, and checkable constraints.
- **Given** candidate paths spanning multiple subtrees **When** the tool executes **Then** it aggregates constraints across all target paths with shared ancestors deduplicated.
- **Given** an agent preset lacking this tool **When** model tool definitions are assembled **Then** `resolve_candidate_axioms` is absent from available tool schemas.
- **Given** an aborted agent turn **When** the tool is resolving **Then** execution terminates immediately respecting `exec.signal`.

## Harness fit

This component is a `model-facing tool` registered into `ctx.tools` (`packages/core/tools/src/index.ts:1045-1055`) on the Agent Plane in `dev-loop-brain`, requiring no `isolate` realm.

## Teach me while you build

Tutturu~ 🌸 Mayuri is here to make sure everyone has just the right tools in their sewing basket!

- **What it does**: Registers the model-facing `resolve_candidate_axioms` tool on `ctx.tools` so planning agents can inspect directory-specific instructions and rules before drafting code changes.
- **Background**: When agents plan tasks, they often don't know what rules exist in the directories they plan to touch. Giving the planner a tool to query rules solves this planning-time visibility gap.
- **How it works here**: When mounted in the planner session preset, `resolveCandidateAxiomsTool` defines a schema expecting an array of path strings. When invoked, it calls `ctx.candidateResolver.resolveCandidateChain(paths)` and returns formatted instructions, applicable file paths, and checkable axiom counts.
- **Why this approach**: Query tool via preset composition. The simplest alternative was dumping every instruction file directly into the system prompt, but that clutters the model's context with rules for code it might never touch.
- **Approaches considered**: System prompt pre-injection (rejected: wastes token budget on unvisited subtrees) vs Implicit tool pre-execution hook (rejected: hides decision-making and lacks model intentionality) vs Explicit model query tool (chosen: gives the model control over when to deliberate on constraints).
- **Prior art inspected**: Tool definition contracts in `packages/core/tools/src/index.ts` and schema validation in `packages/core/tools/src/schema.ts`.
- **What we get for free**: Harness `defineTool` validates the input `paths` array schema, enforces JSON serialization, and binds `exec.signal` for cooperative cancellation.
- **What to notice**: Notice that this tool is only sewn into the planner preset; worker agents keep smaller toolsets to stay fast and focused!
- **Concepts to own**: Just-in-time context resolution: fetching domain-specific constraints interactively rather than statically buffering everything up front.
- **Interview angle**: Why provide a query tool for repository rules instead of appending all rules into the initial system prompt? Answer: Monorepo rules scale with directory count; static inclusion causes prompt bloat and token exhaustion, whereas an on-demand tool lets the agent inspect only the subtrees it targets.
- **Decisions you can now make alone**: You can customize tool description strings or bind additional filter options without modifying the underlying path resolver.
- **Lesson**: Keep each lab member's tool basket neat and light by letting them reach for special tools only when they need them! Tutturu~ 🌸
