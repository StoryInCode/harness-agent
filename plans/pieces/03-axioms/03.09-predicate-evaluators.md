## Summary

Deterministic evaluation engine executing the 9 declarative predicate check types defined in Spec §2.5: filesystem predicates (`path_exists`, `path_absent`, `forbidden_directory`, `forbidden_file_pattern`), content predicates (`grep_absent`, `required_symbol`, `required_reference`, `max_lines`), and import predicates (`forbidden_import` AST inspection). Returns typed `CheckResult` objects recording execution time, pass/fail state, and diagnostic error output. Replaces subjective agent claims with objective ground truth.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: In-process TypeScript AST and filesystem predicate evaluation engine returning structured `CheckResult` objects with execution timing and diagnostic details.
- **Option B (Alternative)**: Spawning shell subprocesses running ad-hoc shell commands for every check, which incurs process fork overhead and suffers from platform shell incompatibilities.

## Behaviour

- **Given** a `path_exists` check for `src/index.ts` **When** the file exists on disk **Then** it returns `passed: true` with execution timing.
- **Given** a `grep_absent` check for `eval\(` **When** matching text exists in `src/calc.ts` **Then** it returns `passed: false` with the matching line content.
- **Given** a `forbidden_import` check targeting `lodash` **When** an ES import or `require('lodash')` exists in parsed AST **Then** it fails with the import AST node detail.
- **Given** a `max_lines` check with limit 160 on a 170-line file **When** evaluated **Then** it returns `passed: false` reporting actual line count.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.predicateEvaluator`), utilizing `ctx.fs` (`packages/fs/fs/src/index.ts:24-52`) and TypeScript AST inspection for import and content verification.

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { PredicateCheck } from '@deepseek-ai/dsh-axiom'

export interface CheckResult {
  readonly check: PredicateCheck
  readonly passed: boolean
  readonly exitCode?: number | null
  readonly stdout?: string
  readonly stderr?: string
  readonly message?: string
  readonly executionTimeMs: number
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    predicateEvaluator: PredicateEvaluator
  }
}

export abstract class PredicateEvaluator extends Service {
  constructor(ctx: Context) {
    super(ctx, 'predicateEvaluator', true)
  }
  abstract evaluatePredicate(check: PredicateCheck, targetDir: string, signal?: AbortSignal): Promise<CheckResult>
  abstract evaluateBatch(checks: readonly PredicateCheck[], targetDir: string, signal?: AbortSignal): Promise<readonly CheckResult[]>
}
```

## Teach me while you build

Nya~ (=^･ω･^=)🐾 Inspector Cat is sniffing out every file! We don't trust promises; we inspect real files and AST nodes directly so sneaky mice can't hide forbidden code!

- **What it does**: Evaluates 9 deterministic declarative check types across filesystem structure, file contents, and TypeScript AST imports, returning structured `CheckResult` reports.
- **Background**: Declarative predicates are check specifications represented as data objects rather than opaque executable scripts, enabling fast, repeatable, and safe in-process verification.
- **How it works here**: `evaluatePredicate(check, targetDir)` matches `check.type`. Filesystem checks query `ctx.fs` directly; content checks scan file lines for forbidden strings or regexes; import checks parse TypeScript AST to flag forbidden imports. It measures wall-clock time and returns pass/fail with diagnostic snippets.
- **Why this approach**: Option A runs pure in-process checks using AST parsing and `ctx.fs`. It executes in microseconds without spawning shells and prevents shell injection risks.
- **Approaches considered**: Shelling out to bash scripts for every check (rejected: 20x slower and prone to shell escaping bugs) vs Generic linter execution (rejected: heavy startup overhead) vs In-process declarative AST and filesystem evaluators (chosen).
- **Prior art inspected**: ESLint rule visitors (`eslint/lib/rules`) and TypeScript AST traversal APIs for import declaration node inspection.
- **What we get for free**: Native TypeScript compiler API handles AST parsing for static and dynamic imports without external CLI tools.
- **What to notice**: Every check execution logs `executionTimeMs`, making it trivial for sweepers to detect slow checks or stalling filesystem mounts.
- **Concepts to own**: Declarative verification; Abstract Syntax Tree (AST) node matching; deterministic predicate evaluation; in-process execution.
- **Interview angle**: Why evaluate declarative predicates in-process instead of executing shell scripts? Answer: In-process checks run orders of magnitude faster, avoid platform shell differences, and prevent shell injection vulnerabilities.
- **Decisions you can now make alone**: You can easily introduce new custom AST predicates (such as checking decorator patterns) by adding a new case to the evaluator switch.
- **Lesson**: Declarative data checks are faster, safer, and cleaner than shell commands for structural code verification. Nya~!
