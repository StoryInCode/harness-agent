## Summary

Tutturu~ 🌸 Mayuri is here to organize our tool basket! We want every agent to have the exact right tools for their job without bumping into each other. We configure host bundle patch layers (`packages/bundle/base/cordis.patch.yml`) and agent-plane presets (`presets/dev-loop-brain/agent.cordis.yml` and `presets/dev-loop-worker/agent.cordis.yml`). Host services (`AxiomRegistry`, `AxiomVerifier`, and sqlite storage routes) stay on the host plane, while orchestrators get candidate resolution tools and workers get proof tools. Everything stays neat, tidy, and declarative!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Compose host services in `cordis.patch.yml` and role-scoped tools in declarative agent presets (`dev-loop-brain` and `dev-loop-worker`), keeping tool boundaries strictly auditable.
- **Option B (Alternative)**: Register all tools imperatively in TypeScript during session startup, mixing role concerns and risking orchestrator sessions invoking worker proof tools.

## Behaviour

- **Given** host container boot **When** the patch layer is applied **Then** `AxiomRegistry` and `AxiomVerifier` mount as host-plane singletons.
- **Given** a `dev-loop-brain` session boot **When** presets load **Then** `resolve_candidate_axioms` is registered in `ctx.tools` while worker proof tools are absent.
- **Given** a `dev-loop-worker` session boot **When** presets load **Then** `attach_proof` and `verify_task_axioms` are registered in `ctx.tools`.
- **Given** a preset reload event **When** plugins reload **Then** effect disposers unbind cleanly without leaking Cordis listeners.

## Harness fit

This component is a `patch layer` and agent-preset composition separating host plane singleton services from agent plane tool registrations in accordance with Cordis loader conventions.

## Contracts

```yaml
# packages/bundle/base/cordis.patch.yml (Host Plane)
'@deepseek-ai/dsh-storage-domain':
  routes:
    task_axioms: sqlite

'@deepseek-ai/dsh-axiom':
  maxBytes: 65536
  maxSourceBytes: 1048576

'@deepseek-ai/dsh-axiom-verifier':
  defaultTimeoutMs: 30000
  autoTodosDir: '~/.dsh/auto-todos'

# presets/dev-loop-brain/agent.cordis.yml (Agent Plane)
- id: tool-candidate-axioms
  name: '@deepseek-ai/dsh-tool-candidate-axioms'
  inject: ['tools', 'axioms']

# presets/dev-loop-worker/agent.cordis.yml (Agent Plane)
- id: tool-axiom
  name: '@deepseek-ai/dsh-tool-axiom'
  inject: ['tools', 'axioms', 'axiomVerifier']
  config:
    autoVerifyOnProof: false
```

## Teach me while you build

Every seamstress needs her own sewing box! You wouldn't use heavy cloth shears to trim delicate embroidery threads!

- **What it does**: Composes host singleton services and scopes agent-plane tools neatly into `dev-loop-brain` and `dev-loop-worker` presets using declarative YAML patches.
- **Background**: Cordis separates the host plane (long-running daemons and storage engines) from the agent plane (ephemeral worker sessions and LLM tools).
- **How it works here**: The host patch layer `packages/bundle/base/cordis.patch.yml` mounts host services (`AxiomRegistry`, `AxiomVerifier`) and routes storage. Presets configure tools for each role: `dev-loop-brain` receives candidate resolution tools, while `dev-loop-worker` gets proof attachment tools.
- **Why this approach**: Option A declares role boundaries in static YAML. Imperative registration in application startup code creates coupling and makes permissions hard to audit.
- **Approaches considered**: Imperative runtime tool injection (rejected: bypasses declarative configuration and complicates testing) vs Monolithic single preset (rejected: leaks worker proof tools to orchestrators) vs Declarative two-plane preset composition (chosen: clean separation of duties and auditable configs).
- **Prior art inspected**: Kubernetes Pod specs and VS Code extension contribution manifests.
- **What we get for free**: Cordis schema validation, dependency injection resolution, and disposable lifecycle tracking across HMR reloads.
- **What to notice**: Agent plane tools declare `inject: ['tools', 'axioms']` without creating separate isolate realms, binding cleanly to host services while staying role-scoped.
- **Concepts to own**: Declarative capability scoping: governing agent capabilities through immutable configuration manifests rather than dynamic imperative code.
- **Interview angle**: How do you enforce role-based access control for AI agent tools across orchestrators and workers? Answer: Segregate capabilities declaratively using preset manifests — configure orchestrators and workers with distinct tool bundles so workers cannot orchestrate and orchestrators cannot fabricate worker proofs.
- **Decisions you can now make alone**: You can introduce new agent roles (e.g. `hermes-reviewer`) by defining a new preset with its own tailored tool list.
- **Lesson**: Neat and tidy presets make sure every agent has just the tools they need to do their best work without getting confused!
