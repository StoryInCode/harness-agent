## Summary

Tutturu~ 🌸 Mayuri is here to help us talk things through! When you want to discuss a card or ask questions about a task before building it, you shouldn't feel rushed! We open a cozy discussion session right on the card so you and the Brain can share ideas, ask questions, and polish up the plan together without triggering any background worker execution!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Focused interactive discussion turn loading the target card's prompt slice and task details without triggering worker execution.
- **Option B (Alternative)**: Asynchronous append-only comment threads that lack conversational back-and-forth and cannot update task specifications on disk.

## Behaviour

- **Given** an existing card ID **When** `/kanban <card-id>` is invoked **Then** a discussion session opens loading the card's prompt slice and `tasks.md` into the Brain's focus.
- **Given** an active card discussion **When** the user asks questions or provides adjustments **Then** the Brain replies with context-specific clarifications without initiating execution.
- **Given** user-agreed changes during discussion **When** confirmed **Then** the card's prompt details and `tasks.md` are updated on disk via `tasksParser`.
- **Given** a non-existent card ID **When** discussion is invoked **Then** the session refuses to start and returns `CARD_NOT_FOUND`.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanDiscussion`) extending `@deepseek-ai/cordis.Service`. It bridges the interactive slash command runtime with the agent conversation loop.

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { CardId, SubtaskCardRecord } from '@deepseek-ai/dsh-kanban'

export interface DiscussionMessage {
  readonly sender: 'user' | 'brain'
  readonly text: string
  readonly timestamp: number
}

export interface CardDiscussionSession {
  readonly cardId: CardId
  readonly card: SubtaskCardRecord
  readonly messages: readonly DiscussionMessage[]
  readonly isOpen: boolean
}

export interface KanbanDiscussionService {
  openDiscussion(cardId: CardId): Promise<CardDiscussionSession>
  sendMessage(cardId: CardId, message: string): Promise<DiscussionMessage>
  closeDiscussion(cardId: CardId): Promise<void>
  getActiveSession(cardId: CardId): CardDiscussionSession | undefined
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanbanDiscussion: KanbanDiscussionService
  }
}
```

## Teach me while you build

Just like fitting a dress pattern before making the cuts, talking through our plan makes sure everything fits wonderfully!

- **What it does**: Opens an interactive discussion session focused on a specific card, allowing the operator to clarify requirements and amend specifications without triggering execution.
- **Background**: Requirements are often underspecified; a focused discussion turn allows human and agent to align before committing to implementation.
- **How it works here**: When `/kanban <card-id>` is invoked, `openDiscussion(cardId)` retrieves the card, loads its prompt slice and `tasks.md`, and creates a `CardDiscussionSession`. Messages sent via `sendMessage()` converse with the Brain. If requirements change, `tasksParser` writes updates back to disk.
- **Why this approach**: Focused pre-execution discussion turn. Having a dedicated conversation scoped to one card keeps context small and avoids polluting the main workspace conversation.
- **Approaches considered**: Append-only issue comments (rejected: asynchronous and lacks conversational turn-taking) vs Full-session workspace derailment (rejected: clutters the root session with subtask-level nitpicks) vs Isolated card discussion session (chosen: targeted turn loop bound to the card entity).
- **Prior art inspected**: GitHub pull request review threads and Slack thread-per-issue workflows.
- **What we get for free**: Reuses `ctx.tasksParser` for loading and serializing structured markdown updates back to disk.
- **What to notice**: The session never transitions the card to `pending` or dispatches workers; it only refines the specification and prompt context.
- **Concepts to own**: Scoped conversation context: binding an interactive conversational turn loop to an isolated entity rather than global session state.
- **Interview angle**: How do you support interactive requirement clarification in an automated kanban system? Answer: Provide a dedicated discussion mode scoped to the card entity that loads relevant slices into context, records turns, and updates disk specs without dispatching execution.
- **Decisions you can now make alone**: You can add support for multi-turn question schemas or file attachments inside `CardDiscussionSession` without modifying the lifecycle state machine.
- **Lesson**: Discuss and clarify requirements interactively on the card before triggering autonomous execution.
