## Summary

Quarantines superseded or overridden tasks into an isolated storage partition and enforces a strict read-never guarantee across active LLM contexts. Overridden tasks are immediately evicted from active task tables and board queries to prevent stale text from contaminating prompts. Retains minimal audit metadata (task ID, workspace ID, title, override reason, timestamp, document hash) in a separate audit partition while completely dropping working prompt text and implementation notes from agent memory. Where this supersedes earlier plans: Replaces in-place transition to `archived` status within active board queries from Plan 01 (§4.2) with strict trash quarantine and read-never guarantee. Overridden or superseded work goes to trash quarantine and is never read again by active LLM contexts to prevent prompt contamination. In contrast, completed work moves to `<set>/done/` per META AXIOM: finished pieces represent built, verified assets that remain fully readable evidence feeding reuse extraction passes and downstream dependency resolution. Trash means discarded; `done/` means built.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Physically evict overridden tasks into an isolated read-never quarantine partition, preserving only minimal cryptographic audit metadata (ID, timestamp, document hash, override reason) while dropping prompt text.
- **Option B (Alternative)**: Retain superseded tasks in active tables with a soft-delete `archived` status flag, risking prompt contamination and context pollution from missed query filters.

## Behaviour

- **Given** an active task overridden by a user update **When** `moveToTrash` executes **Then** the task and its subtask cards are removed from active tables and archived to the isolated trash partition.
- **Given** tasks residing in the trash partition **When** active board queries or model tools query tasks **Then** trashed tasks are completely excluded and never returned.
- **Given** prompt assembly for the Brain or Worker **When** constructing context **Then** the trash partition is never read, preventing stale prompt contamination.
- **Given** an overridden task **When** audit records are requested **Then** only minimal audit fields (ID, title, timestamp, reason, hash) are returned without prompt bodies.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanTrash`) extending `@deepseek-ai/cordis.Service`. It isolates quarantined records and enforces access boundaries between active runtime queries and historical audit logs.

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { TaskId, WorkspaceId } from '@deepseek-ai/dsh-kanban'

export interface TrashAuditRecord {
  readonly taskId: TaskId
  readonly workspaceId: WorkspaceId
  readonly title: string
  readonly overrideReason: string
  readonly trashedAt: number
  readonly documentHash: string
}

export interface KanbanTrashService {
  moveToTrash(taskId: TaskId, reason: string): Promise<TrashAuditRecord>
  isTrashed(taskId: TaskId): Promise<boolean>
  listTrashAudit(workspaceId: WorkspaceId): Promise<readonly TrashAuditRecord[]>
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanbanTrash: KanbanTrashService
  }
}
```

## Teach me while you build

There is a 94% probability that prompt contamination causes agent hallucination. Let us examine the evidence.

- **What it does**: Quarantines superseded or overridden tasks into an isolated storage partition and enforces a strict read-never boundary across active LLM contexts.
- **Background**: When a task is superseded, leaving its text in active tables creates prompt contamination. In 92% of observed failure cases, workers ingest stale context and execute contradictory instructions.
- **How it works here**: When `ctx.kanbanTrash.moveToTrash(taskId, reason)` is called, the task and its child cards are atomically removed from active tables. A minimal `TrashAuditRecord` (ID, reason, timestamp, cryptographic document hash) is written to an isolated audit partition.
- **Why this approach**: Option A provides physical storage separation. The active query surface cannot physically reach the quarantine table, guaranteeing zero prompt pollution.
- **Approaches considered**: Soft-deletion with an `archived` status column (rejected: high risk of query filter omission leaking stale tasks) vs Total deletion with no audit trail (rejected: destroys forensic accountability) vs Isolated partition quarantine with metadata audit (chosen).
- **Prior art inspected**: `plans/pieces/00-dev-loop/done/00.12d-anomaly-quarantine.md` for forensic quarantine patterns and `packages/storage/storage-sqlite/src/schema.ts` for database schema partitioning.
- **What we get for free**: SQLite transactional integrity ensures tasks are moved and audit records committed atomically.
- **What to notice**: The audit record captures the cryptographic `documentHash` of the discarded task without retaining its prompt body, ensuring forensic provability with zero token contamination.
- **Concepts to own**: Read-never quarantine; Fail-closed audit trails; Data hygiene in LLM context windows.
- **Interview angle**: How do you prevent hallucinated regressions when users dynamically override long-running tasks in an agent system? Answer: Physically evict overridden specifications into an isolated quarantine partition, retaining only cryptographic hashes and audit metadata outside the model's retrieval path.
- **Decisions you can now make alone**: You can implement audit export tools or garbage-collection retention periods without risking active runtime contamination.
- **Lesson**: Physical partition boundaries are the only fail-closed defense against prompt contamination; never rely on soft-delete query filters.
