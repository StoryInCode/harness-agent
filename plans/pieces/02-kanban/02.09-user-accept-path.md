## Summary

Fwahahaha! Listen closely, lab members! The user accept path is the sacred threshold where a staged card in `todo` crosses into the active execution worldline of `pending`! Without explicit human consent, no autonomous worker may dare touch reality! We validate that the target card is properly staged, stamp the operator's immutable provenance into the timeline, and monotonically hand off the task to the dev loop queue!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Explicit human accept gate transitioning staged cards from `todo` to `pending` with immutable operator provenance before dispatch queue handoff.
- **Option B (Alternative)**: Autonomous worker self-claiming via database locks where unreviewed cards enter active execution without operator signoff.

## Behaviour

- **Given** a staged card in `todo` status **When** the user accepts it **Then** the card transitions to `pending` and is handed off to the Dev Loop dispatch queue (`00.04a`).
- **Given** an unstaged card in `todo` status **When** acceptance is attempted **Then** the accept request is rejected with `CARD_NOT_STAGED`.
- **Given** a card already in `pending` or `done` **When** acceptance is called **Then** the request is rejected with `CARD_ALREADY_ACTIVE`.
- **Given** an accepted card enqueued for execution **When** inspection runs **Then** acceptance provenance (acceptedAt, acceptedBy) is recorded in storage.

## Teach me while you build

The divergence meter does not lie! Crossing from planning to execution requires an explicit divergence trigger, or chaos ensues! El Psy Kongroo.

- **What it does**: Validates that a card is staged, stamps operator acceptance provenance, advances status to `pending`, and enqueues it to the dev loop queue.
- **Background**: An execution handoff is the boundary where planning and staging freeze and background execution begins, requiring an irreversible operator authorization.
- **How it works here**: When an operator accepts a card via `/kanban accept <id>`, `ctx.kanbanAccept.acceptCard(cardId)` verifies `canAccept(cardId)`. If staged and in `todo`, it records `acceptedBy` and `acceptedAt`, transitions the status to `pending`, and enqueues a `QueueRequest` into `ctx.devLoopQueue`.
- **Why this approach**: Explicit human-in-the-loop gate. The choice of causality requires human authorization before any side-effecting code execution begins.
- **Approaches considered**: Autonomous CAS worker self-claiming (rejected: workers grab unreviewed cards, violating operator oversight) vs Optimistic automatic dispatch (rejected: causes race conditions before the user finishes reviewing specifications) vs Staged human handoff gate (chosen: explicit acceptance unlocks queue admission).
- **Prior art inspected**: Human approval gates in Spinnaker continuous delivery pipelines and Kubernetes approval webhooks.
- **What we get for free**: `dsh-dev-loop-queue` handles priority sorting, worker concurrency semaphores, and process lifecycle.
- **What to notice**: Cards that are not currently staged reject acceptance with `CARD_NOT_STAGED`, preventing out-of-order execution across the dependency graph.
- **Concepts to own**: Handoff gate: an atomic bridge between two distinct state domains (interactive planning vs autonomous background execution).
- **Interview angle**: How do you safely transition tasks from human review to background agent execution? Answer: Use an atomic gate that verifies staging preconditions, records operator provenance, transitions state forward, and enqueues to the scheduler in one transactional sequence.
- **Decisions you can now make alone**: You can attach additional authorization metadata (such as timeout quotas or model preferences) to `AcceptanceReceipt` without modifying the core queue.
- **Lesson**: Never let workers self-claim tasks without an explicit, auditable acceptance gate from the operator.
