# 02.09 — User Accept Path and Execution Handoff

**Set:** 02-kanban · **Queue:** 9 · **Depends on:** 02.04, 02.08
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-kanban-accept`

## Summary

Coordinates the user accept workflow that unlocks execution for staged kanban cards. When the user reviews a staged subtask card and issues acceptance (via `/kanban accept <id>` or the UI Accept button), this service validates that the card is currently staged in `todo` status, records the acceptance timestamp and user provenance, transitions the card to `pending`, and enqueues it into the Dev Loop dispatch queue (`@deepseek-ai/dsh-dev-loop-queue`).
Where this supersedes earlier plans: Replaces autonomous worker self-claiming from Plan 01 (§8.2) with explicit user accept gate prior to execution handoff.

## Behaviour

- **Given** a staged card in `todo` status **When** the user accepts it **Then** the card transitions to `pending` and is handed off to the Dev Loop dispatch queue (`00.04`).
- **Given** an unstaged card in `todo` status **When** acceptance is attempted **Then** the accept request is rejected with `CARD_NOT_STAGED`.
- **Given** a card already in `pending` or `done` **When** acceptance is called **Then** the request is rejected with `CARD_ALREADY_ACTIVE`.
- **Given** an accepted card enqueued for execution **When** inspection runs **Then** acceptance provenance (acceptedAt, acceptedBy) is recorded in storage.
- **Given** multiple staged cards **When** the user accepts one card **Then** sibling staged cards remain in `todo` until individually accepted or dispatched via automode.

## Teach me while you build

- **Background**: Execution handoff is the boundary where planning ends and background worker scheduling begins, triggered by an explicit operator consent action.
- **How it works here**: When an operator types `/kanban accept <id>` or clicks Accept in the UI, `ctx.kanbanAccept.acceptCard(cardId)` checks `canAccept(cardId)`. If the card is staged and in `todo`, it stamps user provenance (`acceptedBy`, `acceptedAt`), transitions the card to `pending` via `ctx.kanbanLifecycle`, and enqueues it to `ctx.devLoopQueue`. Open `packages/kanban/accept/src/index.ts`.
- **Why this approach**: Explicit accept gate. The simplest alternative is workers self-claiming cards via database locks, which allows workers to run without user signoff.
- **What we get for free**: `00.04` (`dsh-dev-loop-queue`) handles worker concurrency limits, backpressure, and scheduling.
- **What to notice**: Unstaged cards reject acceptance with `CARD_NOT_STAGED`, preventing accidental out-of-order execution.
- **Lesson**: Require explicit user provenance on execution handoffs so audit logs always reflect who authorized autonomous execution.
