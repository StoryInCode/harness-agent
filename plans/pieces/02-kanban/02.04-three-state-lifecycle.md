# 02.04 — Three-State Lifecycle State Machine

**Set:** 02-kanban · **Queue:** 4 · **Depends on:** 02.01
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-kanban-lifecycle`

## Summary

Enforces the strict three-state lifecycle model across all kanban tasks and subtask cards: `todo`, `pending`, and `done`. It defines unambiguous state semantics: `todo` denotes waiting or staged work with no worker assigned; `pending` denotes accepted work actively executing under worker lease or undergoing verification; `done` denotes verified completed work. It restricts state mutations to legal paths (`todo` -> `pending`, `pending` -> `todo`, `pending` -> `done`), rejecting state skips and unauthorized mutations.
Where this supersedes earlier plans: Replaces the 9-state transition matrix (`triage`, `todo`, `scheduled`, `ready`, `running`, `blocked`, `review`, `done`, `archived`) from Plan 01 (§4.2, §5.1) with the strict 3-state model.

## Behaviour

- **Given** a card in `todo` status **When** user acceptance or automode dispatch triggers **Then** the card transitions to `pending` and `kanban/card-status` is emitted.
- **Given** a card in `todo` status **When** an immediate transition to `done` is requested without execution **Then** the transition is rejected with `ILLEGAL_STATE_TRANSITION`.
- **Given** a card in `pending` status **When** worker execution fails or changes are requested **Then** the card transitions back to `todo` with execution leases released.
- **Given** a card in `pending` status **When** implementation verification passes and `kanban/pre-complete` resolves **Then** the card transitions to `done`.
- **Given** a card in `done` status **When** an arbitrary status update is attempted **Then** the transition is rejected because terminal states are immutable without explicit reopen.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanLifecycle`) extending `@deepseek-ai/cordis.Service`. It intercepts transition requests to enforce transition invariants and publishes host domain events via `ctx.emit()`.

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { CardId, TaskId, TaskStatus } from '@deepseek-ai/dsh-kanban'

export const LEGAL_TRANSITIONS: Readonly<Record<TaskStatus, readonly TaskStatus[]>> = {
  todo: ['pending'],
  pending: ['todo', 'done'],
  done: ['todo'], // explicit operator reopen only
} as const

export interface StateTransitionResult {
  readonly entityId: CardId | TaskId
  readonly from: TaskStatus
  readonly to: TaskStatus
  readonly transitionedAt: number
}

export interface KanbanLifecycleService {
  canTransition(from: TaskStatus, to: TaskStatus): boolean
  transitionCard(id: CardId, to: TaskStatus, reason?: string): Promise<StateTransitionResult>
  transitionTask(id: TaskId, to: TaskStatus, reason?: string): Promise<StateTransitionResult>
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanbanLifecycle: KanbanLifecycleService
  }
}
```

## Teach me while you build

- **Background**: A finite state machine (FSM) restricts an entity to a predefined set of states and valid transitions between them, preventing impossible or contradictory lifecycle states.
- **How it works here**: Any component requesting a status change calls `ctx.kanbanLifecycle.transitionCard(cardId, newStatus)`. The service checks `LEGAL_TRANSITIONS[currentStatus].includes(newStatus)`. If valid, it updates storage via `ctx.kanban` and fires `kanban/card-status` via `ctx.emit()`. If invalid, it throws `ILLEGAL_STATE_TRANSITION`. Open `packages/kanban/lifecycle/src/index.ts`.
- **Why this approach**: Strict 3-state vocabulary (`todo`, `pending`, `done`). The simplest alternative was the 9-state model (`triage`, `scheduled`, `ready`, etc.), but more states mean more edge cases, deadlocks, and cognitive burden for LLM agents.
- **What we get for free**: `ctx.emit()` dispatches synchronous and asynchronous listeners across all loaded Cordis plugins.
- **What to notice**: Terminal state `done` can only transition back to `todo` via explicit operator reopen, protecting completed work from accidental overwrite.
- **Lesson**: Limit lifecycle states to the minimum needed to distinguish waiting, running, and verified work.

## Reuse capture

- **Reuse candidate**: Strict 3-state transition dictionary `LEGAL_TRANSITIONS` · Constrains entity movement to verifiable workflows · Used in card and task lifecycle · Reusable in any workflow pipeline with pending execution gates · Parameterize state enum · Evidence: `packages/kanban/lifecycle/tests/lifecycle.spec.ts` · Confidence: high
- **Known limitations**: Does not model multi-branch review or staging states within the state machine itself (handled via boolean flags like `staged`).
