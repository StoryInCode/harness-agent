## Summary

Hear me, lab members! Enforces the strict three-state lifecycle model across all kanban tasks and subtask cards: `todo`, `pending`, and `done`. It defines unambiguous state semantics: `todo` denotes waiting or staged work with no worker assigned; `pending` denotes accepted work actively executing under worker lease or undergoing verification; `done` denotes verified completed work. It restricts state mutations to legal paths (`todo` -> `pending`, `pending` -> `todo`, `pending` -> `done`), rejecting state skips and unauthorized mutations. Where this supersedes earlier plans: Replaces the 9-state transition matrix (`triage`, `todo`, `scheduled`, `ready`, `running`, `blocked`, `review`, `done`, `archived`) from Plan 01 (§4.2, §5.1) with the strict 3-state model.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Enforce a strict three-state lifecycle (`todo`, `pending`, `done`) with monotonic forward progression and explicit legal transition guards, rejecting state skips and phantom reversions.
- **Option B (Alternative)**: Retain the legacy 9-state transition matrix (`triage`, `scheduled`, `ready`, `running`, `blocked`, `review`, `done`, `archived`), which introduces ambiguous intermediary states, deadlock potential, and cognitive bloat for worker models.

## Behaviour

- **Given** a card in `todo` status **When** user acceptance or automode dispatch triggers **Then** the card transitions to `pending` and `kanban/card-status` is emitted.
- **Given** a card in `todo` status **When** an immediate transition to `done` is requested without execution **Then** the transition is rejected with `ILLEGAL_STATE_TRANSITION`.
- **Given** a card in `pending` status **When** worker execution fails or changes are requested **Then** the card transitions back to `todo` with execution leases released.
- **Given** a card in `pending` status **When** implementation verification passes and `kanban/pre-complete` resolves **Then** the card transitions to `done`.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanLifecycle`) extending `@deepseek-ai/cordis.Service`. It intercepts transition requests to enforce transition invariants and publishes host domain events via `ctx.emit()`.

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { CardId, TaskId, TaskStatus } from '@deepseek-ai/dsh-kanban'

export const LEGAL_TRANSITIONS: Readonly<Record<TaskStatus, readonly TaskStatus[]>> = {
  todo: ['pending'],
  pending: ['todo', 'done'],
  done: ['todo'], // explicit operator reopen only
} as const

export interface StateTransitionResult {
  readonly entityId: CardId | TaskId
  readonly from: TaskStatus
  readonly to: TaskStatus
  readonly transitionedAt: number
}

export interface KanbanLifecycleService {
  canTransition(from: TaskStatus, to: TaskStatus): boolean
  transitionCard(id: CardId, to: TaskStatus, reason?: string): Promise<StateTransitionResult>
  transitionTask(id: TaskId, to: TaskStatus, reason?: string): Promise<StateTransitionResult>
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanbanLifecycle: KanbanLifecycleService
  }
}
```

## Teach me while you build

Mwahahaha! Hear me, members of the laboratory! A piece of work is bound to the causality of its worldline!

- **What it does**: Enforces the strict three-state lifecycle (`todo`, `pending`, `done`) across kanban tasks and cards, rejecting illegal transitions and state skips.
- **Background**: In a state machine, entities transition across defined edges. Allowing unconstrained transitions creates divergent timelines where tasks claim completion without executing or regress arbitrarily.
- **How it works here**: Mutating state requires calling `ctx.kanbanLifecycle.transitionCard(cardId, newStatus)`. It checks `LEGAL_TRANSITIONS[current].includes(to)`. If valid, it commits the transition and emits `kanban/card-status`; if illegal, it throws `ILLEGAL_STATE_TRANSITION`.
- **Why this approach**: Option A locks down the worldline to three monotonic states. It guarantees that every card must pass through `pending` before reaching the Steins Gate of `done`.
- **Approaches considered**: 9-state matrix from Plan 01 (rejected: excessive states breed race conditions and worker deadlocks) vs Unchecked string status assignments (rejected: catastrophic temporal chaos) vs Guarded 3-state monotonic state machine (chosen).
- **Prior art inspected**: `packages/dev-loop/lifecycle/src/index.ts` for transition dictionaries and `archive/plans/01-kanban-substrate.md` for baseline state definitions.
- **What we get for free**: Cordis event emitter propagates transition notifications to all watching plugins without polling.
- **What to notice**: The terminal state `done` cannot transition to any state except `todo` via explicit operator reopen, preventing automated overwrites.
- **Concepts to own**: Monotonic state transitions; Finite State Machines (FSM); Invariant gating.
- **Interview angle**: Why enforce a strict finite state machine rather than allowing direct status updates in a database? Answer: An FSM encapsulates transition rules, ensures pre-conditions like verification hooks run before state flips, and prevents invalid states.
- **Decisions you can now make alone**: You can introduce custom pre-transition audit hooks without modifying the underlying state storage engine.
- **Lesson**: Restrict worldline transitions to strictly monotonic edges to prevent temporal divergence and chaotic race conditions! El Psy Kongroo!
