## Summary

Implements the authoritative relational storage engine for `KanbanStore` using Node.js `node:sqlite`. Reuses verified Plan 01 Option (b) architectural decisions: SQLite WAL mode, `PRAGMA busy_timeout = 120000`, `PRAGMA user_version` monotonic schema validation with newer-version refusal, and `BEGIN IMMEDIATE` cross-table transactions. Persists workspace-scoped tables (`tasks`, `subtask_cards`, `task_trash_audit`), enforcing foreign keys and ACID concurrency across independent agent processes.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Implement a bespoke SQLite relational store using Node.js `node:sqlite` with WAL mode, `PRAGMA busy_timeout = 120000`, and `BEGIN IMMEDIATE` multi-row transactions to guarantee cross-process lock safety and relational queries.
- **Option B (Alternative)**: Reuse `ctx.storageDomain` key-value storage, which lacks cross-table transactions, secondary indexes, cross-process busy-wait locks, and relational join support.

## Behaviour

- **Given** a new database file **When** initialized **Then** tables are created under WAL mode and `PRAGMA user_version = 1` is stamped last.
- **Given** an existing database with `user_version > KANBAN_SQLITE_SCHEMA_VERSION` **When** opened **Then** initialization refuses to proceed and throws typed `version-mismatch`.
- **Given** competing read and write operations **When** a write transaction begins **Then** `BEGIN IMMEDIATE` acquires exclusive writer locks waiting up to 120,000ms before timeout.
- **Given** a task moved to trash **When** the transaction executes **Then** the task and its cards are removed from active tables and logged into `task_trash_audit` atomically.

## Teach me while you build

Yo, super hacker Daru here! Fluffy ORMs are for noobs; when you need real concurrent multi-process IO, you talk straight to the kernel!

- **What it does**: Implements the SQLite backend for `KanbanStore` with WAL mode, 120s busy timeouts, monotonic version validation, and `BEGIN IMMEDIATE` multi-statement transactions.
- **Background**: SQLite's default rollback journal locks the entire database file during writes, blocking readers. Write-Ahead Logging (WAL) decouples concurrent readers from writers and prevents process contention.
- **How it works here**: In `packages/storage/storage-sqlite/src/schema.ts:60-107`, `openDatabase` configures `PRAGMA foreign_keys = ON`, `PRAGMA journal_mode = WAL`, and inspects `PRAGMA user_version`. If `user_version` matches `KANBAN_SQLITE_SCHEMA_VERSION`, it proceeds; if higher, it throws `version-mismatch`. Write transactions run inside `writeTxn` using `BEGIN IMMEDIATE`.
- **Why this approach**: Dedicated SQLite store provides real relational queries, foreign key constraints, and cross-process multi-statement transactions that key-value storage (`ctx.storageDomain`) cannot support.
- **Approaches considered**: Key-Value domain storage via `ctx.storageDomain` (rejected: lacks cross-table atomic transactions, secondary indexes, and cross-process locks) vs Heavy ORM like Prisma (rejected: huge dependency footprint, sluggish startup, and hides essential SQLite pragmas) vs Bespoke SQLite engine with Node native `node:sqlite` and explicit WAL pragmas (chosen).
- **Prior art inspected**: SQLite official WAL specification and SQLite `BEGIN IMMEDIATE` concurrency guidelines.
- **What we get for free**: Native `node:sqlite` in modern Node.js runs without external C++ bindings or node-gyp build steps.
- **What to notice**: `PRAGMA busy_timeout = 120000` gives concurrent agent worker processes a full 2 minutes to wait for write locks instead of crashing immediately on `SQLITE_BUSY`.
- **Concepts to own**: Monotonic schema stamping: fresh databases stamp `PRAGMA user_version` last after all DDL statements finish, ensuring failed initializations never leave corrupt half-built schemas marked as valid.
- **Interview angle**: How do you avoid `SQLITE_BUSY` errors when multiple CLI processes access a shared SQLite database? Answer: Turn on WAL mode (`PRAGMA journal_mode = WAL`), set a generous busy timeout (`PRAGMA busy_timeout = 120000`), and start all write transactions with `BEGIN IMMEDIATE` so writers serialize immediately rather than deadlocking during upgrade.
- **Decisions you can now make alone**: You can safely add new relational index tables or audit triggers without risking lock contention.
- **Lesson**: Hardware is fast, but disk deadlocks are forever. Use WAL and `BEGIN IMMEDIATE` for multi-process SQLite.
