## Summary

Enforces strict multi-tenant workspace isolation across all kanban tasks, subtask cards, and board queries. In forensic audit terms, any un-scoped entity query is an information leak. It integrates with `ctx.workspaceRegistry` to resolve canonical `WorkspaceId` tokens from session headers and filesystem paths, rejecting cross-workspace access fail-closed with `WORKSPACE_CROSS_ACCESS_DENIED`.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Mandatory workspace binding where queries enforce `WHERE workspaceId = ?` and `assertWorkspaceAccess` throws `WORKSPACE_CROSS_ACCESS_DENIED` on foreign entities.
- **Option B (Alternative)**: Optional or client-side filtering where callers specify workspace IDs dynamically, which risks cross-project card leakage on un-scoped queries.

## Behaviour

- **Given** an active session in workspace A **When** tasks are listed for the kanban dropdown **Then** only tasks with `workspaceId === A` are returned.
- **Given** a task creation request **When** committed to storage **Then** it is permanently bound to the active session's `WorkspaceId`.
- **Given** a request to fetch or mutate cards for task T belonging to workspace A **When** invoked from workspace B **Then** the request is rejected fail-closed with `WORKSPACE_CROSS_ACCESS_DENIED`.
- **Given** an invalid or unknown `WorkspaceId` **When** validating access **Then** the service rejects with `INVALID_WORKSPACE_CONTEXT`.

## Teach me while you build

Examine the boundary conditions carefully. When evaluating multi-tenant systems, any ambient authorization without explicit scope checking is a vulnerability.

- **What it does**: Binds tasks and subtask cards to their parent workspace, preventing cross-tenant data leakage across queries and mutations.
- **Background**: Multi-tenancy isolation ensures that processes and queries executing within workspace A cannot read, mutate, or inject tasks into workspace B.
- **How it works here**: Every query in `dsh-kanban-workspace` resolves `WorkspaceId` from `ctx.workspaceRegistry` and executes queries with a strict `WHERE workspaceId = ?` constraint. Cross-workspace card access triggers an immediate fail-closed `WORKSPACE_CROSS_ACCESS_DENIED`.
- **Why this approach**: Mandatory workspace binding evaluated at the service boundary. The probability of leakage with client-driven or optional filters is unacceptably high.
- **Approaches considered**: Client-side filtering (rejected: queries return cross-workspace entities over RPC, risking forensic data leaks) vs Schema-per-workspace SQLite databases (rejected: excessive connection overhead and disk fragmentation across dozens of micro-workspaces) vs Row-level workspace tenancy constraints (chosen: single database with strict service-level and query-level tenancy keys).
- **Prior art inspected**: AWS IAM multi-tenant row-level security and PostgreSQL Row-Level Security (RLS) policies.
- **What we get for free**: Canonical path resolution and branded `WorkspaceId` typing provided by `packages/workspace/workspace/src/types.ts:16-33`.
- **What to notice**: `assertWorkspaceAccess` runs before any card mutation or read is processed, rejecting unauthorized callers prior to database lock acquisition.
- **Concepts to own**: Multi-tenant isolation, fail-closed access control, and tenant-keyed data partitioning.
- **Interview angle**: How do you prevent cross-tenant information disclosure in an agent harness that operates across multiple user directories? Answer: Bind all entity records to a canonical workspace identifier and enforce tenancy checks at the service gate.
- **Decisions you can now make alone**: You can safely add new kanban entities (such as tags or attachments) by adding mandatory `workspaceId` foreign keys and routing queries through `assertWorkspaceAccess`.
- **Lesson**: Security boundaries must be enforced at the data access layer; never trust the client or caller to self-isolate.
