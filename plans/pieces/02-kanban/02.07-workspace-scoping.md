# 02.07 — Workspace Scoping and Multi-Tenant Isolation

**Set:** 02-kanban · **Queue:** 7 · **Depends on:** 02.01
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-kanban-workspace`

## Summary

Binds all kanban tasks, subtask cards, and board queries to the active workspace. It integrates directly with `ctx.workspaceRegistry` to resolve canonical `WorkspaceId` values from session headers and filesystem paths. It guarantees that task dropdowns and card lists display only records belonging to the current workspace, preventing cards from different projects or directories from leaking or mixing into views.
Where this supersedes earlier plans: Replaces global un-scoped and optional single-tenant queries from Plan 01 (§5.2) with mandatory workspace-scoped isolation.

## Behaviour

- **Given** an active session in workspace A **When** tasks are listed for the kanban dropdown **Then** only tasks with `workspaceId === A` are returned.
- **Given** a task creation request **When** committed to storage **Then** it is permanently bound to the current session's `WorkspaceId`.
- **Given** a request to fetch subtask cards for task T belonging to workspace A **When** invoked from workspace B **Then** the request is rejected with `WORKSPACE_CROSS_ACCESS_DENIED`.
- **Given** switching workspaces in the client **When** the kanban view refreshes **Then** all previous workspace tasks and cards are cleared immediately from view.
- **Given** an invalid or unknown `WorkspaceId` **When** validating access **Then** the service rejects with `INVALID_WORKSPACE_CONTEXT`.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanWorkspace`) extending `@deepseek-ai/cordis.Service`. It injects `workspaceRegistry` (`packages/workspace/workspace/src/index.ts:66-70`) to resolve and validate canonical workspace identities.

## Teach me while you build

- **Background**: Multi-tenancy or workspace scoping isolates data belonging to different projects or directories, preventing tasks from Project A appearing in Project B.
- **How it works here**: `ctx.kanbanWorkspace` resolves the active `WorkspaceId` from `ctx.workspaceRegistry`. Every task and card query includes `WHERE workspaceId = ?`. If a request attempts to access an entity belonging to another workspace, `assertWorkspaceAccess` throws `WORKSPACE_CROSS_ACCESS_DENIED`. Open `packages/kanban/workspace/src/index.ts`.
- **Why this approach**: Mandatory workspace binding. The simplest alternative is optional filtering or client-side filtering, but client-side filtering allows data leaks if an agent makes an un-scoped API query.
- **What we get for free**: `packages/workspace/workspace` provides canonical path resolution and `WorkspaceId` validation.
- **What to notice**: The method `getActiveWorkspaceId()` returns a branded `WorkspaceId` that is passed down into all store calls.
- **Lesson**: Scope database queries by workspace identity at the service boundary rather than relying on callers to pass correct filter arguments.
