## Summary

Tutturu~ 🌸 Splits actionable task requests into discrete subtasks stored as kanban cards linked strictly to their originating parent task. When an actionable task arrives, the decomposition engine parses its `tasks.md` via `tasksParser`, extracts each subtask definition with its prompt slice and implementation notes, and creates corresponding `SubtaskCardRecord` entities within the current workspace. This establishes the authoritative 1:N hierarchy necessary for verification roll-up. Where this supersedes earlier plans: Replaces ad-hoc multi-parent DAG linking and manual cycle-checking graphs from Plan 01 (§4.3, §5.1) with parent-task-to-subtask hierarchy and decomposition.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Decompose tasks into an explicit 1:N parent-task-to-subtask hierarchy where child cards inherit the parent workspace and link strictly to a single parent TaskId.
- **Option B (Alternative)**: Support arbitrary multi-parent Directed Acyclic Graphs (DAGs), which introduces complex cycle-detection overhead and makes completion roll-up unpredictable.

## Behaviour

- **Given** an actionable task with a `tasks.md` containing 3 subtasks **When** decomposition runs **Then** exactly 3 subtask cards are created linked to the parent `TaskId`.
- **Given** decomposed subtask cards **When** inspected **Then** each card carries its prompt slice, order index, and initial status `todo`.
- **Given** an actionable task in workspace W **When** subtasks are generated **Then** every created subtask card inherits workspace W strictly.
- **Given** an existing task already decomposed **When** decomposition is called again **Then** the engine rejects with `TASK_ALREADY_DECOMPOSED` unless explicit re-split is authorized.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanDecomposition`) extending `@deepseek-ai/cordis.Service`. It composes `ctx.kanban` and `ctx.tasksParser` on the host event bus, maintaining clean separation between parsing and storage.

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { TaskId, SubtaskCardRecord } from '@deepseek-ai/dsh-kanban'

export interface DecompositionResult {
  readonly taskId: TaskId
  readonly cards: readonly SubtaskCardRecord[]
  readonly totalDecomposed: number
}

export interface KanbanDecompositionService {
  decomposeTask(taskId: TaskId): Promise<DecompositionResult>
  redecomposeTask(taskId: TaskId): Promise<DecompositionResult>
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanbanDecomposition: KanbanDecompositionService
  }
}
```

## Teach me while you build

Tutturu~ 🌸 Let's learn how to take a big task pattern and cut it into gentle, easy-to-sew cards!

- **What it does**: Decomposes top-level tasks into discrete subtask cards linked strictly to their parent `TaskId` and workspace.
- **Background**: When a task is too big, an LLM worker gets confused and drops requirements. Decomposition snips large tasks into small, comfortable subtask cards that fit neatly into a single context window.
- **How it works here**: Callers invoke `ctx.kanbanDecomposition.decomposeTask(taskId)`. It gets the task record from `ctx.kanban`, asks `ctx.tasksParser` for the parsed `tasks.md` AST, and stitches each checklist item into a `SubtaskCardRecord`.
- **Why this approach**: Option A gives a strict 1:N parent-to-subtask hierarchy. It makes roll-up and status aggregation straightforward without worrying about tangled dependency loops.
- **Approaches considered**: Arbitrary multi-parent DAG (rejected: cycles cause infinite loops and deadlock) vs Monolithic single-card execution (rejected: exceeds context limits and causes hallucinations) vs Strict 1:N tree decomposition (chosen).
- **Prior art inspected**: `archive/plans/01-kanban-substrate.md` for task linking patterns and `plans/pieces/PIECE-FORMAT.md` for micro-gate sizing.
- **What we get for free**: Cordis context injection seamlessly links `ctx.kanban` storage and `ctx.tasksParser` without custom glue code.
- **What to notice**: Notice that each decomposed card inherits the exact `workspaceId` of its parent task, ensuring isolation boundaries are maintained.
- **Concepts to own**: 1:N Tree hierarchies vs DAGs; Work decomposition; Task isolation scoping.
- **Interview angle**: Why favor a strict 1:N parent-child task structure over an arbitrary DAG in autonomous agent loops? Answer: 1:N hierarchies prevent cyclic deadlocks, keep context boundaries clear, and make progress rollup trivial to verify.
- **Decisions you can now make alone**: You can add ordering rules or priority weights to subtask cards without altering the parent task contract.
- **Lesson**: Snip complex problems into bite-sized cards before handing them to workers so everyone stays happy and productive! Tutturu~ 🌸
