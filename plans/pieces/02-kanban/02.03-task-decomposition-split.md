# 02.03 — Task-to-Subtask Split and Decomposition Engine

**Set:** 02-kanban · **Queue:** 3 · **Depends on:** 02.01, 02.02
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-kanban-decomposition`

## Summary

Splits actionable task requests into discrete subtasks stored as kanban cards linked strictly to their originating parent task. When an actionable task arrives, the decomposition engine parses its `tasks.md` via `tasksParser`, extracts each subtask definition with its prompt slice and implementation notes, and creates corresponding `SubtaskCardRecord` entities within the current workspace. This establishes the authoritative 1:N hierarchy necessary for verification roll-up.
Where this supersedes earlier plans: Replaces ad-hoc multi-parent DAG linking and manual cycle-checking graphs from Plan 01 (§4.3, §5.1) with parent-task-to-subtask hierarchy and decomposition.

## Behaviour

- **Given** an actionable task with a `tasks.md` containing 3 subtasks **When** decomposition runs **Then** exactly 3 subtask cards are created linked to the parent `TaskId`.
- **Given** decomposed subtask cards **When** inspected **Then** each card carries its prompt slice, order index, and initial status `todo`.
- **Given** an incoming actionable task request with no explicit subtasks in `tasks.md` **When** decomposition runs **Then** a single self-contained subtask card is created for the task.
- **Given** an actionable task in workspace W **When** subtasks are generated **Then** every created subtask card inherits workspace W strictly.
- **Given** an existing task already decomposed **When** decomposition is called again **Then** the engine rejects with `TASK_ALREADY_DECOMPOSED` unless explicit re-split is authorized.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanDecomposition`) extending `@deepseek-ai/cordis.Service`. It composes `ctx.kanban` and `ctx.tasksParser` on the host event bus, maintaining clean separation between parsing and storage.

## Teach me while you build

- **Background**: Task decomposition is splitting a broad objective into smaller, bounded units of work (cards) that an LLM agent can ingest and execute in a single context window.
- **How it works here**: An orchestrator or workflow calls `ctx.kanbanDecomposition.decomposeTask(taskId)`. The service fetches the task record from `ctx.kanban`, reads its `tasks.md` via `ctx.tasksParser`, converts each parsed checklist item into a `SubtaskCardRecord` linked to `taskId` and `workspaceId`, and stores them in `ctx.kanban`. Open `packages/kanban/decomposition/src/index.ts`.
- **Why this approach**: 1:N parent-task-to-subtask hierarchy. The simplest alternative was an arbitrary multi-parent Directed Acyclic Graph (DAG), but DAGs introduce cycle detection overhead and complicate completion roll-up.
- **What we get for free**: Cordis service injection provides access to `ctx.kanban` and `ctx.tasksParser` without tight coupling.
- **What to notice**: Each generated subtask card inherits the parent's `workspaceId` strictly, ensuring isolation boundaries are preserved.
- **Lesson**: A strict 1:N parent-child tree is vastly easier to reason about, schedule, and verify than an arbitrary DAG.

## Reuse capture
