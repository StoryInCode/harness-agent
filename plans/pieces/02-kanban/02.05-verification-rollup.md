# 02.05 — Verification Roll-Up and Task Completion Engine

**Set:** 02-kanban · **Queue:** 5 · **Depends on:** 02.01, 02.04
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-kanban-rollup`

## Summary

Enforces the mechanical verification roll-up rule: an originating task's completion is strictly determined by the verified completion of all its decomposed subtask cards. When any subtask card transitions to `done`, the roll-up engine queries the parent task's complete subtask set. If and only if 100% of subtasks are in `done` status, it triggers the serial `kanban/pre-complete` verification hook on the parent task and commits the parent's transition to `done`.
Where this supersedes earlier plans: Replaces manual completion of root cards and worker self-completion from Plan 01 (§8.3) with mechanical 100% subtask roll-up rule.

## Behaviour

- **Given** a task with 4 subtask cards where 3 are `done` and 1 is `pending` **When** roll-up evaluation executes **Then** the parent task remains in its current status and is not marked `done`.
- **Given** the final subtask card transitioning to `done` **When** roll-up evaluation runs **Then** it verifies all subtasks are `done`, awaits `kanban/pre-complete`, and marks the parent task `done`.
- **Given** an external tool or caller attempting to mark a parent task `done` while any subtask is in `todo` or `pending` **Then** the transition is rejected with `SUBTASKS_INCOMPLETE`.
- **Given** a subtask in a `done` task reopened to `todo` **When** roll-up re-evaluates **Then** the parent task status reverts from `done` to `pending`.
- **Given** a task with zero registered subtasks **When** completion is attempted **Then** the transition is rejected with `CANNOT_COMPLETE_EMPTY_TASK`.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanRollup`) extending `@deepseek-ai/cordis.Service`. It listens to `kanban/card-status` events and orchestrates parent roll-up transactions via `ctx.kanban` and `ctx.serial()`.

import type { TaskId, CardId, TaskRecord } from '@deepseek-ai/dsh-kanban'

export interface RollupEvaluation {
  readonly taskId: TaskId
  readonly totalSubtasks: number
  readonly completedSubtasks: number
  readonly isComplete: boolean
  readonly incompleteCardIds: readonly CardId[]

export interface KanbanRollupService {
  evaluateTask(taskId: TaskId): Promise<RollupEvaluation>
  checkAndRollup(cardId: CardId): Promise<TaskRecord | undefined>
  reconcileParentStatus(taskId: TaskId): Promise<TaskRecord>
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanbanRollup: KanbanRollupService
  }
}

## Teach me while you build

- **Background**: Roll-up is aggregating the status of child records to determine the status of their parent. A task is not done merely because an agent finished one part; all parts must be verified.
- **How it works here**: The roll-up service listens to `kanban/card-status`. When a card reaches `done`, `checkAndRollup(cardId)` queries all sibling cards under the parent `taskId`. If every card has `status === 'done'`, it executes the serial hook `kanban/pre-complete` and marks the parent task `done`. Open `packages/kanban/rollup/src/index.ts`.
- **Why this approach**: Mechanical 100% completion rule. The simplest alternative is letting a worker or user manually mark the parent done, but manual completion allows orphaned, unfinished subtasks to slip by unnoticed.
- **What we get for free**: Cordis event bus (`ctx.on('kanban/card-status')`) triggers evaluation automatically without polling loops.
- **What to notice**: If a subtask card is reopened to `todo`, `reconcileParentStatus` demotes the parent from `done` back to `pending`.
- **Lesson**: Compound task status should be computed from child facts, never manually set by the worker executing the work.
