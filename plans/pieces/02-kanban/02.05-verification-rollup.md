## Summary

Hear me, lab members! Enforces the mechanical verification roll-up rule: an originating task's completion is strictly determined by the verified completion of all its decomposed subtask cards. When any subtask card transitions to `done`, the roll-up engine queries the parent task's complete subtask set. If and only if 100% of subtasks are in `done` status, it triggers the serial `kanban/pre-complete` verification hook on the parent task and commits the parent's transition to `done`. Where this supersedes earlier plans: Replaces manual completion of root cards and worker self-completion from Plan 01 (§8.3) with mechanical 100% subtask roll-up rule.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Compute parent task completion strictly via 100% mechanical roll-up of verified child subtask cards and serial pre-complete hooks, preventing manual bypasses.
- **Option B (Alternative)**: Permit workers or operators to directly mark root tasks as completed without child verification, allowing orphaned or failing subtasks to slip into mainline.

## Behaviour

- **Given** a task with 4 subtask cards where 3 are `done` and 1 is `pending` **When** roll-up evaluation executes **Then** the parent task remains in its current status and is not marked `done`.
- **Given** the final subtask card transitioning to `done` **When** roll-up evaluation runs **Then** it verifies all subtasks are `done`, awaits `kanban/pre-complete`, and marks the parent task `done`.
- **Given** an external tool or caller attempting to mark a parent task `done` while any subtask is in `todo` or `pending` **Then** the transition is rejected with `SUBTASKS_INCOMPLETE`.
- **Given** a subtask in a `done` task reopened to `todo` **When** roll-up re-evaluates **Then** the parent task status reverts from `done` to `pending`.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanRollup`) extending `@deepseek-ai/cordis.Service`. It listens to `kanban/card-status` events and orchestrates parent roll-up transactions via `ctx.kanban` and `ctx.serial()`.

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { TaskId, CardId, TaskRecord } from '@deepseek-ai/dsh-kanban'

export interface RollupEvaluation {
  readonly taskId: TaskId
  readonly totalSubtasks: number
  readonly completedSubtasks: number
  readonly isComplete: boolean
  readonly incompleteCardIds: readonly CardId[]
}

export interface KanbanRollupService {
  evaluateTask(taskId: TaskId): Promise<RollupEvaluation>
  checkAndRollup(cardId: CardId): Promise<TaskRecord | undefined>
  reconcileParentStatus(taskId: TaskId): Promise<TaskRecord>
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanbanRollup: KanbanRollupService
  }
}
```

## Teach me while you build

Mwahahaha! Verification roll-up is the ultimate Divergence Meter that prevents corrupted timelines!

- **What it does**: Enforces mechanical 100% verification roll-up, ensuring parent tasks transition to `done` only when every child subtask card is verified.
- **Background**: In composite workflows, human workers or LLM agents often claim a master goal is complete when only half the subtasks passed. Roll-up ensures parent state is an aggregate proof, not a subjective opinion.
- **How it works here**: When a card reaches `done`, `checkAndRollup(cardId)` queries all sibling cards under the parent `taskId`. If every card has `status === 'done'`, it executes the serial hook `kanban/pre-complete` and commits the parent transition to `done`.
- **Why this approach**: Option A computes completion purely mechanically. It eliminates optimistic completion anomalies and protects mainline integrity.
- **Approaches considered**: Worker self-reporting (rejected: workers suffer from hallucinated completion) vs Polling daemon (rejected: wastes compute cycles and induces lag) vs Reactive 100% event-driven roll-up with pre-complete hook (chosen).
- **Prior art inspected**: `packages/dev-loop/lifecycle/src/types.ts` for pre-complete hook contracts and `archive/plans/01-kanban-substrate.md` for serial hook specifications.
- **What we get for free**: Cordis event emitter triggers evaluation reactively on `kanban/card-status` without background timers.
- **What to notice**: If any subtask card is reopened to `todo`, `reconcileParentStatus` immediately demotes the parent from `done` back to `pending`.
- **Concepts to own**: State roll-up aggregation; Serial verification interceptors; Monotonic completion invariants.
- **Interview angle**: How do you prevent premature task completion in multi-agent systems? Answer: Compute composite status strictly as a deterministic aggregate over child subtask states, combined with serial pre-complete interceptor hooks.
- **Decisions you can now make alone**: You can attach custom gate verifiers (e.g. format checkers, test suites) to `kanban/pre-complete` without modifying the roll-up engine.
- **Lesson**: Never trust an agent's self-declaration of completion; enforce proof mechanically through total child verification!
