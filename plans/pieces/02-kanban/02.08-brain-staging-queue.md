# 02.08 — Brain Staging Queue and Candidate Selector

**Set:** 02-kanban · **Queue:** 8 · **Depends on:** 02.01, 02.04, 02.07
**Status:** todo
**Harness primitive:** Service Provider · **Package:** `@deepseek-ai/dsh-kanban-staging`

## Summary

Implements the manual-by-default staging queue populated by the Brain orchestrator. When an actionable task is decomposed, the Brain analyzes dependency order and marks eligible, next-in-line subtask cards as `staged: true` in `todo` status. Staged cards wait in the staging queue for the user to read and accept, ensuring autonomous execution never begins unprompted.
Where this supersedes earlier plans: Replaces automatic priority dispatch from Plan 01 (§4.3) with Brain staging where next-in-line cards await user acceptance.

## Behaviour

- **Given** subtask cards in `todo` status **When** the Brain evaluates next executable steps **Then** ready-to-implement cards are marked `staged: true` and `kanban/card-staged` is emitted.
- **Given** a staged card with `staged === true` and `status === 'todo'` **When** no user accept is given **Then** no worker subagent is dispatched.
- **Given** a card whose preceding subtasks are still in `todo` or `pending` **When** staging runs **Then** the card remains unstaged (`staged: false`).
- **Given** staged cards in the current workspace **When** queried by the UI or CLI **Then** they are returned with a visible staged badge and queue order.
- **Given** an operator unstaging a card **When** `unstageCard` is called **Then** `staged` is set to `false` and the card is removed from the active staging queue.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanStaging`) extending `@deepseek-ai/cordis.Service`. It mediates between Brain planning decisions and the human approval interface, preserving human-in-the-loop control.

## Teach me while you build

- **Background**: Human-in-the-loop (HITL) means an autonomous system pauses before taking real-world actions to allow human review and approval.
- **How it works here**: After decomposition, cards sit in `todo` with `staged: false`. The Brain evaluates prerequisites and calls `stageNextCards(taskId)`. Ready cards are updated to `staged: true` and emit `kanban/card-staged`. However, the cards remain in `todo` status—they do not start executing until accepted. Open `packages/kanban/staging/src/index.ts`.
- **Why this approach**: Manual-by-default staging queue. The simplest alternative is immediate autonomous dispatch upon decomposition, but unreviewed autonomous execution can waste tokens and create unwanted changes.
- **What we get for free**: `ctx.emit('kanban/card-staged')` alerts UI badges and CLI listeners without custom polling.
- **What to notice**: A card with incomplete predecessors cannot be staged, guaranteeing ordered execution even when multiple cards exist.
- **Lesson**: Separate "planning what to do next" from "executing it" with an explicit staging gate to preserve human oversight.
