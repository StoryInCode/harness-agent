## Summary

Nya~ (=^･ω･^=)🐾 Inspector Cat is inspecting the staging queue! When tasks are decomposed into subtask cards, we sniff out all the prerequisites to make sure no card jumps ahead of the line! Ready cards get a shiny `staged: true` flag in `todo` status and wait happily in the staging queue for the human developer to accept them, ensuring autonomous execution never begins unprompted!

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Manual-by-default staging queue where ready subtasks are marked `staged: true` and await explicit human acceptance before execution dispatch.
- **Option B (Alternative)**: Immediate autonomous dispatch upon task decomposition, which risks token waste and unreviewed file modifications.

## Behaviour

- **Given** subtask cards in `todo` status **When** the Brain evaluates next executable steps **Then** ready-to-implement cards with completed prerequisites are marked `staged: true` and emit `kanban/card-staged`.
- **Given** a staged card with `staged === true` and `status === 'todo'` **When** no user accept is given **Then** no worker subagent is dispatched.
- **Given** a card whose preceding subtasks are still in `todo` or `pending` **When** staging runs **Then** the card remains unstaged (`staged: false`).
- **Given** an operator unstaging a card **When** `unstageCard` is called **Then** `staged` is set to `false` and the card is removed from the active staging queue.

## Harness fit

This component is a `Service Provider` mounted on the host plane (`ctx.kanbanStaging`) extending `@deepseek-ai/cordis.Service`. It mediates between Brain planning decisions and the human approval interface, preserving human-in-the-loop control.

## Teach me while you build

Purr~ Let's organize the queue so no mischievous paws knock over our building blocks! (=^･ω･^=)

- **What it does**: Inspects subtasks and marks ready next-in-line cards as `staged: true` so the operator can review them before execution.
- **Background**: Human-in-the-loop staging prevents autonomous agents from racing ahead and making unprompted changes without operator consent.
- **How it works here**: When a parent task decomposes, `stageNextCards(taskId)` inspects dependencies. Cards with all prerequisites satisfied get `staged: true` and emit `kanban/card-staged`. They remain in `todo` status until an explicit accept command arrives.
- **Why this approach**: Manual-by-default staging queue. Staging separates candidate selection from execution dispatch.
- **Approaches considered**: Immediate auto-dispatch (rejected: risks unreviewed code modifications and token burn) vs Client-only local staging (rejected: loses shared state across multi-session or CLI operators) vs Service-backed staging queue (chosen: centralized staging state on the host plane).
- **Prior art inspected**: Git staging index (`git add` vs `git commit`) and approval gates in GitHub Actions workflows.
- **What we get for free**: Cordis context event dispatch `ctx.emit` broadcasts staging transitions without tight coupling to UI components.
- **What to notice**: A card remains in `todo` status while staged; `staged` is a boolean readiness attribute, not a separate lifecycle status.
- **Concepts to own**: Staging buffer pattern: separating entity proposal and candidate discovery from state mutation and execution.
- **Interview angle**: How do you implement safe autonomy in an agent harness? Answer: Introduce a staging phase where candidate actions are inspected and held in a staging queue until explicitly approved.
- **Decisions you can now make alone**: You can tune candidate batch sizes in `stageNextCards` without altering the underlying lifecycle state machine.
- **Lesson**: Always separate candidate selection from execution dispatch to preserve human control.
