## Summary

Provides the browser client UI extension for the kanban board surface. It renders a workspace-scoped task dropdown listing tasks for the current workspace only. Selecting a task displays strictly that task's decomposed subtask cards distributed across 3 columns (`Todo`, `Pending`, `Done`), guaranteeing cards from different tasks are never mixed in one view. It provides staged indicators, user Accept triggers, per-task automode toggles, and direct links to card discussion.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Filter kanban boards by workspace with a task selection dropdown, displaying strictly the active task's subtask cards across 3 columns (`Todo`, `Pending`, `Done`) to prevent visual clutter and cross-task card confusion at the cost of an explicit task selection step.
- **Option B (Alternative)**: Render a global multi-task board showing all subtask cards from all tasks simultaneously, avoiding dropdown switching but mixing unrelated subtasks across workflows and overwhelming the operator.

## Behaviour

- **Given** a user viewing the kanban board in workspace W **When** the task dropdown opens **Then** only tasks belonging to workspace W are presented.
- **Given** a task selected from the dropdown **When** the board renders **Then** strictly that task's subtask cards appear across Todo, Pending, and Done columns.
- **Given** a subtask card marked `staged: true` in the Todo column **When** rendered **Then** a visible staged badge and an active Accept button triggering card acceptance are displayed.
- **Given** the per-task automode switch on the selected task **When** toggled **Then** `kanbanAutomode` updates and the UI updates the automode indicator immediately.

## Teach me while you build

Tut-turii~! Mayuri is here to help keep our workspace neat and comfy so nobody gets overwhelmed!

- **What it does**: Renders a workspace-scoped task dropdown and partitions that task's subtask cards into Todo, Pending, and Done columns with staged badges and an Accept trigger.
- **Background**: Client UI extensions mount into the browser application layout and receive workspace context and RPC subscriptions from the harness host.
- **How it works here**: In `packages/client/ui-layout`, the layout mounts views. The board view subscribes to workspace tasks via `packages/workspace/workspace/src/types.ts:31-44`, binds `selectedTaskId`, and projects cards into `Todo`, `Pending`, and `Done` columns based on status.
- **Why this approach**: Filtering strictly by workspace and selected task ensures the operator focuses on one decomposed workflow at a time without cognitive overload.
- **Approaches considered**: Global multi-task board (rejected: displays hundreds of cards simultaneously across disparate projects, causing visual chaos) vs Flat unpartitioned task list (rejected: loses the visual flow of Todo/Pending/Done column progression) vs Workspace task dropdown with isolated 3-column subtask board (chosen).
- **Prior art inspected**: Trello board filtering and GitHub Project board workspace views.
- **What we get for free**: Reactive React re-rendering and Cordis client-side state synchronization.
- **What to notice**: Staged cards in Todo highlight with a distinct badge so the operator immediately recognizes which subtasks are ready for approval.
- **Concepts to own**: Hierarchical UI state projection: scoping downstream child collections (subtasks) strictly under an active parent entity (workspace task).
- **Interview angle**: How do you prevent UI state explosion when rendering deeply nested hierarchical data across multiple workspaces? Answer: Scope the top-level selection at the workspace boundary, then lazily project only the selected task's active child records into column viewmodels.
- **Decisions you can now make alone**: You can configure custom column definitions or add additional filter badges without altering backend storage models.
- **Lesson**: Keep user cognitive load light by scoping views to the immediate operational boundary.
