## Summary

Defines the core `KanbanStore` service contract, branded identifiers (`TaskId`, `CardId`, `WorkspaceId`), and entity records for top-level tasks and decomposed subtask cards. It enforces the strict three-state lifecycle (`todo`, `pending`, `done`), automode enablement flags, staging indicators, and workspace scoping on all entities. It declares typed Cordis host events for lifecycle transitions, staging, and completion. Where this supersedes earlier plans: Replaces the 38-column 9-state schema and global DAG links from Plan 01 (§4.1, §5.1) with workspace-scoped Task and SubtaskCard records and strict 3-state vocabulary.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Define an abstract `KanbanStore` service with workspace-scoped Task and SubtaskCard entities and a strict 3-state vocabulary (`todo`, `pending`, `done`), decoupling store consumers from storage backends.
- **Option B (Alternative)**: Bind directly to a concrete storage implementation or 38-column 9-state schema with global DAG links, creating tight coupling to SQLite and complex unwieldy state transitions.

## Behaviour

- **Given** a workspace context **When** a top-level task is created with a `tasks.md` path **Then** it receives a branded `TaskId` with initial status `todo` and default manual execution (`automode: false`).
- **Given** an originating task **When** its subtasks are decomposed **Then** each child receives a branded `CardId` referencing the parent `TaskId` with status `todo` and `staged: false`.
- **Given** any task or card entity **When** its status property is read **Then** the value is strictly one of `todo`, `pending`, or `done`.
- **Given** an active card **When** its status transitions to `pending` **Then** `kanban/card-status` is published with previous and updated states.

This component is a `Service Definition` declaring the abstract `KanbanStore` class and augmenting the Cordis `Context` interface (`ctx.kanban`) following the established repository pattern (`packages/workspace/workspace/src/index.ts:66-70`).

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { WorkspaceId } from '@deepseek-ai/dsh-workspace/types'

export type TaskId = string & { readonly __brand: unique symbol }
export type CardId = string & { readonly __brand: unique symbol }
export type TaskStatus = 'todo' | 'pending' | 'done'

export interface TaskRecord {
  readonly id: TaskId
  readonly workspaceId: WorkspaceId
  readonly title: string
  readonly tasksMdPath: string
  readonly status: TaskStatus
  readonly automode: boolean
  readonly createdAt: number
  readonly completedAt: number | null
}

export interface SubtaskCardRecord {
  readonly id: CardId
  readonly taskId: TaskId
  readonly workspaceId: WorkspaceId
  readonly title: string
  readonly promptSlice: string
  readonly status: TaskStatus
  readonly staged: boolean
  readonly orderIndex: number
  readonly claimWorkerId: string | null
  readonly claimExpiresAt: number | null
  readonly createdAt: number
  readonly completedAt: number | null
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanban: KanbanStore
  }
  interface Events {
    'kanban/task-created': (task: TaskRecord) => void
    'kanban/card-staged': (card: SubtaskCardRecord) => void
    'kanban/card-status': (card: SubtaskCardRecord, from: TaskStatus, to: TaskStatus) => void
    'kanban/task-completed': (task: TaskRecord) => void
    'kanban/pre-complete': (entity: TaskRecord | SubtaskCardRecord) => Promise<void> | void
    'kanban/trash-moved': (taskId: TaskId, reason: string) => void
  }
}

export abstract class KanbanStore extends Service {
  constructor(ctx: Context) { super(ctx, 'kanban', true) }
  abstract getTask(id: TaskId): Promise<TaskRecord | undefined>
  abstract getCard(id: CardId): Promise<SubtaskCardRecord | undefined>
  abstract listTasks(workspaceId: WorkspaceId): Promise<readonly TaskRecord[]>
  abstract listCards(taskId: TaskId): Promise<readonly SubtaskCardRecord[]>
  abstract createTask(record: Omit<TaskRecord, 'id' | 'createdAt' | 'completedAt'>): Promise<TaskRecord>
  abstract createCard(record: Omit<SubtaskCardRecord, 'id' | 'createdAt' | 'completedAt'>): Promise<SubtaskCardRecord>
  abstract updateTaskStatus(id: TaskId, status: TaskStatus): Promise<TaskRecord>
  abstract updateCardStatus(id: CardId, status: TaskStatus): Promise<SubtaskCardRecord>
  abstract setCardStaged(id: CardId, staged: boolean): Promise<SubtaskCardRecord>
  abstract setTaskAutomode(id: TaskId, enabled: boolean): Promise<TaskRecord>
  abstract moveTaskToTrash(id: TaskId, reason: string): Promise<void>
}
```

## Teach me while you build

- **What it does**: Declares the abstract `KanbanStore` service class, nominal entity IDs (`TaskId`, `CardId`), and entity records for tasks and decomposed subtask cards.
- **Background**: Cordis uses an inversion-of-control container where services register onto `Context`. Without nominal typing, TypeScript treats all strings as interchangeable, allowing subtle bugs where a `CardId` is passed into a `TaskId` slot.
- **How it works here**: Plugins extend `KanbanStore` from `@deepseek-ai/cordis`. Consumers access `ctx.kanban`, which emits lifecycle events like `kanban/task-created` and `kanban/card-status` across the host bus.
- **Why this approach**: Option A gives an abstract service boundary. It lets us swap an in-memory test store with a production SQLite store without breaking consumer code.
- **Approaches considered**: Direct SQLite coupling (rejected: locks unit tests into disk I/O) vs 38-column monolithic schema from Plan 01 (rejected: bloated state) vs Abstract KanbanStore with 3-state records (chosen).
- **Prior art inspected**: `packages/workspace/workspace/src/index.ts` for Cordis service augmentation and `packages/util/brand/src/index.ts` for nominal typing patterns.
- **What we get for free**: Cordis lifecycle management, event propagation, and ambient module declaration merging.
- **What to notice**: Look at `declare module '@deepseek-ai/cordis'`: ambient module augmentation extends `Context` and `Events` without touching Cordis core packages.
- **Concepts to own**: Nominal typing vs structural typing; Service Locator pattern; Decoupled storage abstraction.
- **Interview angle**: Why use branded types in TypeScript when JavaScript has no runtime concept of brands? Answer: Branded types catch entity confusion at compile time with zero runtime overhead.
- **Decisions you can now make alone**: You can add new entity fields or lifecycle events to `Context` without modifying the core Cordis framework.
- **Lesson**: Keep domain models lean and decouple service contracts from database engines before writing a single SQL query.
