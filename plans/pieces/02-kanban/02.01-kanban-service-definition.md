# 02.01 — Kanban Service Definition and Entity Model

**Set:** 02-kanban · **Queue:** 1 · **Depends on:** none
**Status:** todo
**Harness primitive:** Service Definition · **Package:** `@deepseek-ai/dsh-kanban`

## Summary

Defines the core `KanbanStore` service contract, branded identifiers (`TaskId`, `CardId`, `WorkspaceId`), and entity records for top-level tasks and decomposed subtask cards. It enforces the strict three-state lifecycle (`todo`, `pending`, `done`), automode enablement flags, staging indicators, and workspace scoping on all entities. It declares typed Cordis host events for lifecycle transitions, staging, and completion.
Where this supersedes earlier plans: Replaces the 38-column 9-state schema and global DAG links from Plan 01 (§4.1, §5.1) with workspace-scoped Task and SubtaskCard records and strict 3-state vocabulary.

## Behaviour

- **Given** a workspace context **When** a top-level task is created with a `tasks.md` path **Then** it receives a branded `TaskId` with initial status `todo` and default manual execution (`automode: false`).
- **Given** an originating task **When** its subtasks are decomposed **Then** each child receives a branded `CardId` referencing the parent `TaskId` with status `todo` and `staged: false`.
- **Given** any task or card entity **When** its status property is read **Then** the value is strictly one of `todo`, `pending`, or `done`.
- **Given** an active card **When** its status transitions to `pending` **Then** `kanban/card-status` is published with previous and updated states.
- **Given** all subtask cards of a task reaching `done` **When** roll-up completes **Then** `kanban/task-completed` is emitted on the host bus.

## Harness fit

This component is a `Service Definition` declaring the abstract `KanbanStore` class and augmenting the Cordis `Context` interface (`ctx.kanban`) following the established repository pattern (`packages/workspace/workspace/src/index.ts:66-70`).

## Contracts

```typescript
import { Context, Service } from '@deepseek-ai/cordis'
import type { WorkspaceId } from '@deepseek-ai/dsh-workspace/types'

export type TaskId = string & { readonly __brand: unique symbol }
export type CardId = string & { readonly __brand: unique symbol }
export type TaskStatus = 'todo' | 'pending' | 'done'

export interface TaskRecord {
  readonly id: TaskId
  readonly workspaceId: WorkspaceId
  readonly title: string
  readonly tasksMdPath: string
  readonly status: TaskStatus
  readonly automode: boolean
  readonly createdAt: number
  readonly completedAt: number | null
}

export interface SubtaskCardRecord {
  readonly id: CardId
  readonly taskId: TaskId
  readonly workspaceId: WorkspaceId
  readonly title: string
  readonly promptSlice: string
  readonly status: TaskStatus
  readonly staged: boolean
  readonly orderIndex: number
  readonly claimWorkerId: string | null
  readonly claimExpiresAt: number | null
  readonly createdAt: number
  readonly completedAt: number | null
}

declare module '@deepseek-ai/cordis' {
  interface Context {
    kanban: KanbanStore
  }
  interface Events {
    'kanban/task-created': (task: TaskRecord) => void
    'kanban/card-staged': (card: SubtaskCardRecord) => void
    'kanban/card-status': (card: SubtaskCardRecord, from: TaskStatus, to: TaskStatus) => void
    'kanban/task-completed': (task: TaskRecord) => void
    'kanban/pre-complete': (entity: TaskRecord | SubtaskCardRecord) => Promise<void> | void
    'kanban/trash-moved': (taskId: TaskId, reason: string) => void
  }
}

export abstract class KanbanStore extends Service {
  constructor(ctx: Context) { super(ctx, 'kanban', true) }
  abstract getTask(id: TaskId): Promise<TaskRecord | undefined>
  abstract getCard(id: CardId): Promise<SubtaskCardRecord | undefined>
  abstract listTasks(workspaceId: WorkspaceId): Promise<readonly TaskRecord[]>
  abstract listCards(taskId: TaskId): Promise<readonly SubtaskCardRecord[]>
  abstract createTask(record: Omit<TaskRecord, 'id' | 'createdAt' | 'completedAt'>): Promise<TaskRecord>
  abstract createCard(record: Omit<SubtaskCardRecord, 'id' | 'createdAt' | 'completedAt'>): Promise<SubtaskCardRecord>
  abstract updateTaskStatus(id: TaskId, status: TaskStatus): Promise<TaskRecord>
  abstract updateCardStatus(id: CardId, status: TaskStatus): Promise<SubtaskCardRecord>
  abstract setCardStaged(id: CardId, staged: boolean): Promise<SubtaskCardRecord>
  abstract setTaskAutomode(id: TaskId, enabled: boolean): Promise<TaskRecord>
  abstract moveTaskToTrash(id: TaskId, reason: string): Promise<void>
}
```

## Teach me while you build

- **Background**: Cordis uses a dependency-injected service container. A `Service` subclass attaches to `Context` so any plugin injecting that service name gets property access (e.g. `ctx.kanban`). Nominal typing (distinguishing `TaskId` from `CardId`) does not exist natively in TypeScript, so we use branded types (`string & { readonly __brand: unique symbol }`) to prevent ID confusion at compile time.
- **How it works here**: Plugins declare `static inject = ['kanban']`. When an agent or command invokes `ctx.kanban.createTask(...)`, the concrete provider implementation runs and dispatches events via `ctx.emit()`. Open `packages/kanban/src/index.ts` to see the abstract `KanbanStore` class and event augmentations.
- **Why this approach**: Defining an abstract `KanbanStore` separates consumer contracts from storage engines. The simplest alternative is importing a direct SQLite client, which couples consumers to disk I/O and prevents easy in-memory test mocks.
- **What we get for free**: Cordis handles service registration, disposal lifecycles, and typed event propagation across plugins.
- **What to notice**: Look at `declare module '@deepseek-ai/cordis'` in `packages/kanban/src/index.ts`: ambient module augmentation extends the `Context` and `Events` maps without modifying Cordis core.
- **Lesson**: Separate domain contracts from storage backends early; abstract service definitions allow parallel consumer and backend development.

## Reuse capture

- **Reuse candidate**: Branded ID types (`TaskId`, `CardId`) · Prevents argument swapping bugs across entity boundaries · Used in Kanban entity models · Potential reuse in any domain with multiple string IDs (AxiomId, WorktreeId) · Extract as generic `type Brand<K, T> = K & { readonly __brand: T }` · Evidence: `packages/kanban/src/index.ts` · Confidence: high
- **Known limitations**: Compile-time check only; requires runtime validation at boundary inputs.
- **Failure worth keeping**: Initial draft used plain strings for all IDs; tests passed while swapping parent taskId into cardId arguments.

4. All methods enforce branded `TaskId`, `CardId`, and `WorkspaceId`.
