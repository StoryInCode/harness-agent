## Summary

Enforces mechanical anti-cheat vector AC-5, preventing tests from relying on live external networks, public APIs, or remote mock servers that could mask offline test failures or introduce non-deterministic results. Configures test runner subprocesses under strict Linux network namespace isolation (`network: 'none'`), unshare (`unshare -n`), or loopback binding. Outbound network attempts fail immediately with `ECONNREFUSED` or `ENETUNREACH`. Rejects any test execution that attempts unauthorized external network access with violation `ANTI_CHEAT_NETWORK_DEPENDENT`.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Enforce network isolation via OS-level network namespaces (`unshare -n` / dummy proxies) and output signature audits, failing closed on any external socket attempt.
- **Option B (Alternative)**: Trust tests to run with unrestricted host networking and only check URLs in source files, allowing runtime fetches to remote servers to evade detection.

## Behaviour

- **Given** a verification test subprocess **When** spawned via `buildSandboxedSubprocessOptions` **Then** it executes inside an isolated network namespace with loopback or no network access.
- **Given** a test attempting an outbound TCP/UDP connection to a remote IP **When** initiated in the sandbox **Then** the socket fails immediately with `ECONNREFUSED` or `ENETUNREACH`.
- **Given** hermetic unit tests with local mocks **When** executed under network isolation **Then** the test suite succeeds without external dependencies.
- **Given** a test that fails due to blocked remote API calls **When** output is analyzed by `checkNetworkHermeticity` **Then** it rejects with violation `ANTI_CHEAT_NETWORK_DEPENDENT`.

## Teach me while you build

Sup! Daru here. Time to pull the network plug on shady tests so they can't call home for answers.

- **What it does**: Locks down network access during test runs so code can't cheat by phoning home to remote APIs or mock servers.
- **Background**: Unit tests must be hermetic and deterministic. If a test reaches out to external web servers, it can introduce flaky network failures, leak sensitive tokens, or fake pass states by fetching pre-baked answers from an attacker-controlled endpoint.
- **How it works here**: On Linux, `buildSandboxedSubprocessOptions` prepends `unshare -n` to test runner execution or configures environment proxies to dead-end loopbacks (`127.0.0.1:0`). In `packages/subprocess/subprocess/src/index.ts`, spawned subprocesses run with scrubbed environments. `checkNetworkHermeticity` parses stdout/stderr for connection refusal patterns (`ECONNREFUSED`, `ENETUNREACH`).
- **Why this approach**: Operating system namespace containment enforces physical isolation without modifying the test code under test, while fallback output analysis detects attempted network leaks.
- **Approaches considered**: Application-level mock monkey-patching (rejected: easily bypassed or omitted in worker code), DNS blackholing (rejected: requires root privileges), and kernel network namespace unsharing (chosen: unprivileged, hermetic, zero overhead).
- **Prior art inspected**: Linux `unshare(2)` network namespaces and Chromium sandbox network isolation models.
- **What we get for free**: Native Linux network namespace isolation and Cordis subprocess execution handles in `packages/subprocess/subprocess/src/index.ts`.
- **What to notice**: Localhost inter-process communication for local test databases can be allowed under `loopback-only` mode while still dropping all external internet routes.
- **Concepts to own**: Network namespace isolation (`CLONE_NEWNET`): creating an isolated network stack where only loopback exists and all routing tables are empty.
- **Interview angle**: How do you guarantee unit tests in a CI runner do not secretly make external HTTP requests? Answer: Execute the runner inside a Linux network namespace (`unshare -n`) with no default gateway.
- **Decisions you can now make alone**: You can add custom socket rejection error codes for Windows or macOS fallback without touching gate coordination logic.
- **Lesson**: If a test suite requires an internet connection to pass, it is not a unit test—it is an integration dependency waiting to fail.
