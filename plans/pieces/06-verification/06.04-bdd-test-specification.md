## Summary

Nya~ (=^･ω･^=)🐾 Inspector Cat loves clean test specifications! You can't just throw raw text at a test writer and hope for the best — you need structured Given/When/Then scenarios that map straight to executable assertions! This micro-gate establishes formal BDD test specification contracts and AST test block extractors. It parses `describe` and `it` blocks, counts assertions to make sure tests aren't empty bluffing wrappers, and compiles expected failure signatures for the RED gate! Purr~

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Parse test files with AST inspection to verify assertion presence and map Given/When/Then clauses to `describe`/`it` blocks.
- **Option B (Alternative)**: Treat test files as unparsed text blobs and rely solely on test runner exit codes, which permits assertion-free tests to pass as false positives.

## Behaviour

- **Given** task requirements with acceptance criteria **When** `compileBddSpecification` runs **Then** structured scenarios containing Given, When, and Then clauses are generated.
- **Given** an authored test file **When** `extractTestScenarios` inspects AST nodes **Then** all `describe`, `it`, and `test` blocks are mapped to BDD scenarios.
- **Given** an authored test scenario **When** `validateScenarioStructure` evaluates AST assertions **Then** it rejects any test block lacking explicit assertions.
- **Given** a BDD specification **When** `extractExpectedFailureSignatures` runs **Then** expected missing symbols and assertion error patterns are compiled for the RED gate.

By defining formal BDD contracts and AST test scenario extractors before tests are executed, it guarantees that test authoring follows strict behavioral specifications, supplying the expected failure signatures consumed by the RED gate runner (`plans/pieces/06-verification/06.06-red-gate-evaluator.md`).

## Contracts

```typescript
export interface BddScenario {
  readonly id: string
  readonly title: string
  readonly given: string
  readonly when: string
  readonly then: string
  readonly targetUnit: string
  readonly expectedFailureType: 'assertion' | 'missing_symbol' | 'not_implemented'
  readonly expectedSymbolName?: string | undefined
}

export interface BddSpecification {
  readonly cardId: string
  readonly scenarios: readonly BddScenario[]
  readonly testGlobs: readonly string[]
  readonly runnerCommand?: string | undefined
}

export interface ExtractedTestScenario {
  readonly filePath: string
  readonly blockName: string
  readonly line: number
  readonly assertionCount: number
  readonly matchedScenarioId?: string | undefined
}

export interface BddValidationResult {
  readonly valid: boolean
  readonly errors: readonly string[]
  readonly extractedScenarios: readonly ExtractedTestScenario[]
}

/** Compiles raw requirement text and acceptance criteria into structured BDD specification. */
export function compileBddSpecification(cardId: string, rawText: string, testGlobs: readonly string[]): BddSpecification

/** Inspects test file AST, extracting describe/it/test blocks and assertion counts. */
export function extractTestScenarios(fileContent: string, filePath: string): readonly ExtractedTestScenario[]

/** Validates that authored test files satisfy the BDD specification and contain assertions. */
export function validateScenarioStructure(spec: BddSpecification, testFiles: Readonly<Record<string, string>>): BddValidationResult

/** Compiles regex and string patterns representing expected behavioral failure signatures. */
export function extractExpectedFailureSignatures(spec: BddSpecification): readonly RegExp[]
```

## Teach me while you build

Nya~ (=^･ω･^=) Let's make sure tests have real teeth and claws before we let them hunt bugs!

- **What it does**: Compiles user requirements into structured BDD scenarios, parses test ASTs to verify assertions, and extracts expected failure signatures for the RED gate.
- **Background**: Tests can pass by doing nothing if they contain no assertions. A test without assertions is just an empty bowl!
- **How it works here**: Parses requirement strings into `BddScenario` records. When tests are authored, `extractTestScenarios` traverses the AST, checking each `it` block for `expect(...)` calls and ensuring failure patterns match missing implementations.
- **Why this approach**: Verifying test structure at the AST level prevents agents from writing hollow tests that pass vacuously.
- **Approaches considered**: Pure regex search for `expect` (rejected: fooled by comments and string literals) vs Running test coverage reports (rejected: slow and doesn't verify assertion semantics) vs AST traversal of test source (chosen: fast, robust, and inspects actual assertion syntax).
- **Prior art inspected**: TypeScript compiler AST API and Vitest test block conventions in `packages/dev-loop/gates/tests/red.spec.ts`.
- **What we get for free**: Structured Given/When/Then formatting aligned with `plans/pieces/PIECE-FORMAT.md`.
- **What to notice**: Notice that `extractExpectedFailureSignatures` distinguishes expected assertion failures from accidental syntax or import errors.
- **Concepts to own**: Abstract Syntax Tree (AST) inspection, behavioral specifications, and assertion density validation.
- **Interview angle**: How can automated testing frameworks verify that AI-generated tests are meaningful before running them? Answer: Inspect the test AST to ensure each test block maps to a behavioral specification, executes non-trivial assertions, and produces predictable failure modes during the RED phase.
- **Decisions you can now make alone**: You can add new test runners or assertion libraries by updating AST visitor node matchers.
- **Lesson**: A test that doesn't assert anything is just a cat napping on the keyboard! Purr~
