## Summary

Alright, time to lay down the real plumbing! No fluffy abstractions here. This piece hooks up the verification evidence storage domain directly to `ctx.storageDomain` across three tables: `events`, `state`, and `manifests`, backed by strict Zod schema validation and monotonic `VERIFICATION_DOMAIN_VERSION = 1`. It gives us zero-latency in-memory reads and sequential write-chain durability without SQLite lock contention. Plus, it includes an automated pruner that keeps things lean by capping events per session root at 100, purging anything older than 30 days, and clamping bloated output summaries to 2,000 chars.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Use Cordis `ctx.storageDomain` with typed KV tables and schema validation, providing fast in-memory reads and sequential write durability.
- **Option B (Alternative)**: Write a bespoke SQLite table schema with manual migrations, connection pools, and raw SQL queries, adding unnecessary maintenance overhead and transaction lock risks.

## Behaviour

- **Given** a Cordis context with `storageDomain` **When** `openVerificationDomain` is called **Then** tables `events`, `state`, and `manifests` open with schema validation.
- **Given** an incompatible stored version on disk **When** opening the domain **Then** it rejects immediately with `DomainError('version-mismatch')`.
- **Given** more than 100 events recorded for a session root **When** `pruneLedger` runs **Then** events beyond the newest 100 are deleted from durable storage.
- **Given** an output summary exceeding 2,000 characters **When** prepared for insertion **Then** it is clamped to 2,000 characters with a truncation marker.

## Harness fit

This is a `Service Provider` primitive owned by `@deepseek-ai/dsh-verification-store`. It fulfills the storage requirement by reusing `ctx.storageDomain` (`packages/storage/storage-domain/src/index.ts:1-60`) instead of maintaining a bespoke SQLite database. Backed by the configured repository backend (`packages/storage/storage-sqlite`), it provides synchronous in-memory `get()` lookups for turn-stopping gates while guaranteeing sequential write-chain durability without SQLite transaction contention.

## Contracts

```typescript
import { z } from 'zod'
import { defineDomain, domainTable, type KvTable, type DomainHandle } from '@deepseek-ai/dsh-storage-domain'
import type { VerificationEvent, VerificationState, PinnedSuiteManifest } from '@deepseek-ai/dsh-verification'

export const VERIFICATION_DOMAIN_VERSION = 1

export const verificationEventSchema = z.object({
  id: z.number(),
  createdAt: z.string(),
  sessionId: z.string(),
  cwd: z.string(),
  root: z.string(),
  command: z.string(),
  canonicalCommand: z.string(),
  kind: z.enum(['test', 'typecheck', 'lint', 'build', 'format', 'red_gate', 'green_gate']),
  scope: z.enum(['workspace', 'package', 'file', 'ad_hoc']),
  status: z.enum(['passed', 'failed', 'error']),
  exitCode: z.number(),
  outputSummary: z.string(),
  metadata: z.record(z.unknown()).optional(),
})

export const verificationStateSchema = z.object({
  sessionId: z.string(),
  root: z.string(),
  lastEventId: z.number().optional(),
  lastEditAt: z.string().optional(),
  changedPaths: z.array(z.string()),
})

export const pinnedSuiteManifestSchema = z.object({
  cardId: z.string(),
  baseCommit: z.string(),
  pinnedAt: z.string(),
  aggregateHash: z.string(),
  files: z.record(z.string()),
  testRunnerConfigs: z.record(z.string()),
})

export const verificationDomainSpec = defineDomain({
  name: 'verification',
  version: VERIFICATION_DOMAIN_VERSION,
  tables: {
    events: domainTable<string, VerificationEvent>(verificationEventSchema as any),
    state: domainTable<string, VerificationState>(verificationStateSchema as any),
    manifests: domainTable<string, PinnedSuiteManifest>(pinnedSuiteManifestSchema as any),
  },
})

export interface VerificationStoreConfig {
  maxEventsPerSessionRoot: number
  maxEventAgeDays: number
  maxOutputSummaryChars: number
}

export interface VerificationDomainHandles {
  readonly domain: DomainHandle
  readonly events: KvTable<string, VerificationEvent>
  readonly state: KvTable<string, VerificationState>
  readonly manifests: KvTable<string, PinnedSuiteManifest>
}

export function clampOutputSummary(summary: string, maxChars = 2000): string
export function pruneLedger(handles: VerificationDomainHandles, config: VerificationStoreConfig): Promise<number>
export function openVerificationDomain(ctx: Context): Promise<VerificationDomainHandles>
```

## Teach me while you build

Listen up! When you're managing execution logs and gate runs, you don't mess around with flimsy in-memory arrays or unbuffered raw disk writes.

- **What it does**: Implements the durable verification storage domain using `ctx.storageDomain` with Zod validation, fast in-memory lookups, and automated ledger pruning.
- **Background**: Verification events pile up fast when agents run iterative loops. If you don't prune stale logs and clamp noisy outputs, your database bloats and slows down every subsequent query.
- **How it works here**: Registers a domain specification via `defineDomain` with `events`, `state`, and `manifests` tables. `pruneLedger` inspects record timestamps and session event counts, evicting records older than 30 days and keeping only the latest 100 per session.
- **Why this approach**: Reusing `ctx.storageDomain` gives us transactional KV guarantees and automatic change events without managing raw SQLite database files.
- **Approaches considered**: Raw SQLite file per session (rejected: file descriptor leaks and concurrent access locks) vs Plain JSON files in `.worktrees` (rejected: corrupted by crashed processes and lacks atomic updates) vs Shared `ctx.storageDomain` KV tables (chosen: zero SQLite boilerplate with synchronous in-memory read caching).
- **Prior art inspected**: `packages/storage/storage-domain/src/index.ts` and SQLite WAL mode semantics in `packages/storage/storage-sqlite`.
- **What we get for free**: Schemastery config validation, Zod runtime schema decoding, and automatic `domain/changed` event dispatch.
- **What to notice**: Notice that `clampOutputSummary` cuts off at 2,000 characters so gigantic compiler traces don't blow up memory.
- **Concepts to own**: Domain-driven KV storage, write-ahead durability, and bounded retention policies.
- **Interview angle**: How do you prevent unbounded disk growth in an autonomous agent execution log without degrading read throughput? Answer: Implement in-memory index caching backed by async write-chain durability, combined with deterministic size clamping and time-based TTL pruning during ledger append operations.
- **Decisions you can now make alone**: You can tune retention limits (`maxEventsPerSessionRoot`, `maxEventAgeDays`) without altering domain table schemas.
- **Lesson**: Keep your data bounded and let the storage subsystem handle durability while you focus on execution.
