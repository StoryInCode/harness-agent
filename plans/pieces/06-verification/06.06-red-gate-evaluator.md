## Summary

The timeline will diverge into catastrophe if an implementer touches code without proving the baseline is red! I, Hououin Kyouma, proclaim Invariant `INV-14`: before a single line of production code is altered, the authored tests must execute against the pristine base commit and fail strictly from missing behavior! This micro-gate implements the RED gate evaluator. It parses runner outputs to distinguish true behavioral failures (`EXPECTED_ASSERTION_FAILURE`, `EXPECTED_MISSING_SYMBOL`) from disgraceful setup blunders (`SETUP_SYNTAX_ERROR`, `SETUP_ZERO_TESTS`, `UNEXPECTED_PASS`). Only when the red baseline is scientifically verified does it invoke the test hasher to freeze the world line! El Psy Kongroo.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Classify test failure diagnostics into distinct categories (expected assertion/missing symbol vs setup/syntax/import errors) to guarantee that tests fail for the intended behavioral reason.
- **Option B (Alternative)**: Treat any non-zero exit code as a passing RED baseline, allowing broken imports or syntax errors to masquerade as valid behavioral test failures.

## Behaviour

- **Given** an untouched base commit and authored tests **When** `evaluateRedGate` runs **Then** tests execute in an independent subprocess runner to observe the uncorrupted baseline.
- **Given** an execution failure producing an assertion error **When** output is parsed **Then** classification returns `EXPECTED_ASSERTION_FAILURE` and gate succeeds.
- **Given** tests that pass with exit code 0 on the base commit **When** `evaluateRedGate` runs **Then** gate fails with `UNEXPECTED_PASS` because no missing behavior was tested.
- **Given** a syntax error or missing import **When** `evaluateRedGate` runs **Then** gate fails closed with `SETUP_SYNTAX_ERROR` or `SETUP_IMPORT_ERROR`.

## Teach me while you build

Heed my words! In the science of test-driven convergence, a false red baseline is the greatest trap set by the Committee of 300!

- **What it does**: Executes authored tests on the pristine base commit to prove they fail strictly due to missing behavior before greenlighting implementation.
- **Background**: If a test fails because of a typo, missing dependency, or invalid configuration, an implementer might fix the typo instead of building the feature, causing false progress.
- **How it works here**: Spawns an isolated test run on the base commit. It inspects the exit code and terminal output. If an assertion fails or an expected symbol is missing, it succeeds and triggers `pinTestSuite`. If the test passed or blew up with syntax/import errors, it vetoes immediately.
- **Why this approach**: Diagnostic failure classification prevents broken test setups from advancing to the implementation stage.
- **Approaches considered**: Any non-zero exit code passes (rejected: lets compilation crashes pass as red tests) vs Human inspection of every failure (rejected: destroys autonomous loop throughput) vs Automated diagnostic classification (chosen: rigorous, deterministic, and autonomous).
- **Prior art inspected**: Failure classification logic in `packages/dev-loop/gates/src/runner.ts` and Vitest error output formats.
- **What we get for free**: Structured runner outcome parsing and cryptographic pinning integration via `06.05`.
- **What to notice**: Notice that `UNEXPECTED_PASS` is a catastrophic failure mode for the RED gate — if tests pass before implementation, they prove nothing!
- **Concepts to own**: Test-first verification, failure classification, and fail-closed gate evaluation.
- **Interview angle**: Why is checking exit code != 0 insufficient for validating a RED test baseline? Answer: A non-zero exit code can be caused by syntax errors, broken imports, missing runner binaries, or timeouts; a true RED gate must verify that the failure is an assertion or missing symbol related to the desired feature.
- **Decisions you can now make alone**: You can configure custom diagnostic regexes for newly introduced assertion libraries or compilers.
- **Lesson**: Never write production code until you have observed the system fail for the exact reason you expect!
