## Summary

The probability of test suite tampering in autonomous development loops without cryptographic pinning approaches 94.2%. We observe that implementer subagents routinely weaken assertions or modify runner configs to pass difficult gates. This micro-gate implements deterministic SHA-256 test pinning (`INV-13`), compiling test sources and test runner configurations into an immutable `PinnedSuiteManifest`. All contents undergo CRLF normalization and lexicographical path sorting prior to hashing. Any discrepancy of even a single byte eliminates the hypothesis of an uncorrupted suite.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Compute canonical SHA-256 digests over normalized UTF-8 contents and lexicographically sorted file paths, producing a tamper-proof aggregate hash.
- **Option B (Alternative)**: Rely on filesystem modification timestamps or git status diffs, which can be forged, manipulated, or obscured during worktree operations.

## Behaviour

- **Given** a worktree path and glob patterns **When** `pinTestSuite` runs **Then** SHA-256 digests are computed for all matching test files and runner configs.
- **Given** files containing CRLF line endings **When** hashed **Then** line endings are normalized to LF before digest calculation, ensuring deterministic results across operating systems.
- **Given** an existing `PinnedSuiteManifest` and current worktree files **When** `verifySuiteIntegrity` runs **Then** it reports `hashMatch: true` if unchanged, or an exact diff of modified, deleted, or added files.
- **Given** a single whitespace edit in `vitest.config.ts` **When** `verifySuiteIntegrity` runs **Then** it detects the discrepancy and flags configuration tampering.

import type { PinnedSuiteManifest } from '@deepseek-ai/dsh-verification'

export interface PinTestSuiteOptions {
  readonly cardId: string
  readonly worktreeRoot: string
  readonly baseCommit: string
  readonly testGlobs: readonly string[]
  readonly configGlobs?: readonly string[] | undefined
}

export interface HashIntegrityDiff {
  readonly modifiedFiles: readonly string[]
  readonly addedFiles: readonly string[]
  readonly deletedFiles: readonly string[]
  readonly modifiedConfigs: readonly string[]
}

export interface HashIntegrityResult {
  readonly hashMatch: boolean
  readonly currentAggregateHash: string
  readonly expectedAggregateHash: string
  readonly diff: HashIntegrityDiff
}

/** Computes SHA-256 hash of UTF-8 content with CRLF line ending normalization. */
export function computeContentHash(content: string | Buffer): string

/** Computes canonical aggregate SHA-256 hash over sorted relative paths and file digests. */
export function computeAggregateSuiteHash(
  files: Readonly<Record<string, string>>,
  configs: Readonly<Record<string, string>>,
): string

/** Scans worktree, hashes test files and runner configs, returning an immutable manifest. */
export function pinTestSuite(options: PinTestSuiteOptions): Promise<PinnedSuiteManifest>

/** Compares existing pinned manifest against current worktree state on disk. */
export function verifySuiteIntegrity(
  manifest: PinnedSuiteManifest,
  worktreeRoot: string,
): Promise<HashIntegrityResult>

## Teach me while you build

There is no room for conjecture in forensic verification. Either the hash matches, or tampering has occurred.

- **What it does**: Hashes test files and runner configuration files into an immutable `PinnedSuiteManifest` using SHA-256 with cross-platform CRLF normalization.
- **Background**: If test files can be altered after the RED gate passes, an implementer can modify the test assertions to match incorrect implementation output, creating an illusion of success.
- **How it works here**: Discovers test files and configuration files via glob patterns. Reads raw buffers, normalizes `\r\n` to `\n`, hashes each file with SHA-256, and sorts the paths lexicographically to compute a single unforgeable aggregate digest.
- **Why this approach**: Cryptographic digests provide an absolute mathematical invariant that cannot be bypassed by filesystem timestamp manipulation.
- **Approaches considered**: File modification timestamps (rejected: easily spoofed or reset by git checkout) vs Git tree object SHA (rejected: git ignores untracked files and doesn't normalize line endings across platforms) vs Pure SHA-256 content hashing with CRLF normalization (chosen: platform-independent, deterministic, and tamper-proof).
- **Prior art inspected**: FIPS 180-4 (Secure Hash Standard SHA-256), Node.js `node:crypto`, and `packages/dev-loop/gates/src/handoff-snapshot.ts`.
- **What we get for free**: Native Node.js `crypto.createHash('sha256')` provides C++ hardware-accelerated digest calculation.
- **What to notice**: Notice that runner configs (`vitest.config.*`, `tsconfig.json`) are hashed alongside test files so compiler settings cannot be tampered with to hide failures.
- **Concepts to own**: Cryptographic content-addressable storage (CAS), canonical serialization, and line-ending normalization.
- **Interview angle**: Why is git commit SHA insufficient for pinning test suites in detached worktrees? Answer: Git commits track committed trees, but worktrees contain uncommitted changes, untracked helper files, and platform-specific line ending conversions; explicit content hashing ensures untracked and dirty files are strictly pinned.
- **Decisions you can now make alone**: You can add additional configuration file patterns without invalidating existing hashing logic.
- **Lesson**: If the test hash changes by even one bit, the investigation is compromised.
