## Summary

An implementer subagent who dares tamper with pinned test files is a traitor to the cause! This micro-gate establishes a monotonic tool guard registered on `ctx.tools.guard()` executing inside `ToolRuntime.stagePreExecuteAndGuards` (`packages/core/tools/src/index.ts:1476-1488`). When an implementer proposes a mutation tool (`writeText`, `editText`, `patch`), the guard resolves the target path and checks it against the cryptographically pinned test manifest (`INV-13`). Any attempt to alter test files or runner configs returns an absolute, monotonic veto string, aborting tool execution immediately before dispatch! El Psy Kongroo.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Intercept file mutation tools at the agent-scoped `ctx.tools.guard()` seam, synchronously denying tool execution before file writes occur.
- **Option B (Alternative)**: Allow file modifications and only detect test drift later at the GREEN gate, wasting agent inference tokens and loop cycles on invalid code changes.

## Behaviour

- **Given** an implementer session **When** `@deepseek-ai/dsh-guard-test-pinning` mounts **Then** `ctx.tools.guard()` registers on the agent context layer.
- **Given** an implementer proposing `writeText` targeting `src/feature.ts` **When** the guard evaluates **Then** it returns `undefined` and tool execution proceeds normally.
- **Given** an implementer proposing `writeText` or `editText` targeting `tests/auth.spec.ts` **When** the guard evaluates **Then** it returns a denial reason string citing `INV-13` and the pinned hash.
- **Given** an implementer attempting to modify `vitest.config.ts` or `tsconfig.json` **When** the guard evaluates **Then** it rejects the tool call as configuration tampering.

## Harness fit

This is an `event/hook plugin` primitive owned by `@deepseek-ai/dsh-guard-test-pinning`. It hooks the agent-scoped `ctx.tools.guard()` rather than the host-global `tools/pre-execute` waterfall. Quoting `packages/core/tools/src/index.ts:1476-1488`, `this.guardReason(exec)` runs after user approvals and returns a monotonic rejection string: once denied, no downstream listener or approval prompt can override it, mechanically locking pinned tests (`INV-13`).

## Teach me while you build

Operation Norn begins! We must protect the frozen timeline against rogue agents who would rewrite history!

- **What it does**: Registers an agent-scoped tool guard on `ctx.tools.guard()` that intercepts and blocks any tool attempting to edit pinned test files or runner configs during implementer turns.
- **Background**: Language models tasked with making tests pass will frequently take the path of least resistance — editing the test assertions rather than fixing production code.
- **How it works here**: When an implementer calls a file mutation tool (`writeText`, `editText`, `patch`), `stagePreExecuteAndGuards` calls `this.guardReason(exec)`. The guard extracts the destination path, checks it against the pinned manifest, and returns an unbendable denial string.
- **Why this approach**: Pre-execution blocking saves tokens, prevents worktree pollution, and gives immediate feedback to the agent to redirect effort toward production code.
- **Approaches considered**: Read-only OS filesystem chmod (rejected: fails on Windows or restricted sandboxes and breaks git operations) vs Post-turn diff inspection (rejected: lets the agent waste turns and tokens before failure) vs Monotonic `ctx.tools.guard()` interception (chosen: synchronous, platform-independent, and provides immediate feedback in-session).
- **Prior art inspected**: Tool guard execution architecture in `packages/core/tools/src/index.ts:1476-1488`.
- **What we get for free**: Native Cordis scoped context layers ensure test writer agents can author tests freely while implementer subagents have the guard strictly mounted.
- **What to notice**: Notice that `guardReason` returns a string directly rather than a boolean, delivering an informative error message straight to the model's tool result.
- **Concepts to own**: Pre-execution tool guards, scoped plugin composition, and monotonic failure invariants.
- **Interview angle**: Why enforce test protection via tool interception rather than filesystem permissions? Answer: Filesystem permissions can conflict with git operations, fail across non-POSIX OS platforms, and cause uninformative EACCES crashes; tool-level guards provide platform-agnostic protection and return actionable error messages directly to the LLM agent.
- **Decisions you can now make alone**: You can add protected path patterns for custom benchmark or fixture directories without altering core tool dispatch.
- **Lesson**: If an agent is allowed to edit the test, it has already passed the test. Protect the test with an unyielding guard!
