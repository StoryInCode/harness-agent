## Summary

Applies kernel-level filesystem write protections (`chmod 0o444` to test files and `chmod 0o555` to parent test directories) to cryptographically pinned test suites and runner configs within the worker's Git worktree. Provides defense-in-depth against direct subprocess writes, shell redirects (`> tests/unit.spec.ts`), sed/awk mutations, and non-tool filesystem edits during implementer turns. Restores permissions on session teardown or when transferring custody back to authorized test writer roles.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Lock target test files to `0o444` and test parent directories to `0o555` directly on disk via POSIX mode bits with an in-memory snapshot for atomic rollback, enforcing defense-in-depth at the OS kernel level against shell redirection and subprocess tampering at the cost of needing explicit teardown restoration.
- **Option B (Alternative)**: Rely purely on tool-level write interception guards, which leaves the disk writable and allows rogue subprocesses, shell pipes, or sed/awk commands to mutate frozen tests without triggering tool hooks.

## Behaviour

- **Given** a pinned test suite manifest **When** `lockFilesystemPermissions` runs **Then** target files receive `0o444` read-only mode and parent directories receive `0o555`.
- **Given** pinned test files with `0o444` mode **When** a shell command attempts direct redirection (`cat > tests/spec.ts`) **Then** the kernel rejects the write with `EACCES (Permission denied)`.
- **Given** locked filesystem paths **When** `unlockFilesystemPermissions` is called **Then** files restore `0o644` writable mode and directories restore `0o755`.
- **Given** a failure midway through permission locking **When** an error occurs **Then** any previously modified paths roll back to their original permission snapshots.

## Harness fit

This is a `workflow capability` primitive owned by `@deepseek-ai/dsh-verification-permissions`. While tool interception guards monitor model tool calls, autonomous agents with shell or terminal access could theoretically bypass tool guards using shell commands (`cat > tests/...`). Physical permission locking provides mechanical kernel-level defense-in-depth, strictly enforcing read-only status on disk.

## Teach me while you build

Alright, listen up. Super Hacker Daru here. When you give an autonomous agent bash access, application-level guards are cute, but the kernel is final authority.

- **What it does**: Strips write bits from test files and their directories on disk during implementer turns so no tool, bash trick, or subprocess can tamper with tests.
- **Background**: POSIX filesystems control read, write, and execute permissions via octal mode bits. A file with mode `0o444` (`r--r--r--`) forbids write operations for all users, and a directory with `0o555` (`r-xr-xr-x`) prevents creating, renaming, or deleting directory entries.
- **How it works here**: `lockFilesystemPermissions` reads worktree paths from `PinnedSuiteManifest`. It stats each path, saves original permission modes into a `FilePermissionSnapshot`, and executes `chmod` to set `0o444` on files and `0o555` on enclosing directories. When custody transfers back or the session ends, `unlockFilesystemPermissions` iterates through the snapshot in reverse order and restores original modes.
- **Why this approach**: Application-level hooks can be bypassed by subprocesses running `cat > spec.ts` or inline python scripts. Real POSIX mode bits force the Linux kernel to reject writes with `EACCES` before any byte hits the inode.
- **Approaches considered**: Inotify watcher daemon (rejected: race conditions between write and kill signal) vs Read-only bind mount (rejected: requires Linux `CAP_SYS_ADMIN` or root privileges) vs POSIX mode bits with rollback snapshot (chosen: works in standard userland containers without special capabilities).
- **Prior art inspected**: POSIX `chmod(2)` and `stat(2)` mode bit specifications, specifically `S_IWUSR`, `S_IWGRP`, and `S_IWOTH`.
- **What we get for free**: Node.js `fs/promises` `chmod` and `stat` map directly to POSIX kernel syscalls across Linux and macOS.
- **What to notice**: Notice that we lock directories to `0o555` in addition to files! If you only make `spec.ts` `0o444`, an agent can still unlink the file and recreate it if the parent directory is writable. Locking the directory blocks `unlink`.
- **Concepts to own**: Kernel-enforced defense-in-depth: never rely solely on runtime software wrappers when operating system primitives can enforce security guarantees.
- **Interview angle**: Why is making a file read-only insufficient to prevent modification on POSIX systems? Answer: Because deleting/recreating a file requires write permission on the containing directory (`unlink`/`creat`), not write permission on the file inode itself.
- **Decisions you can now make alone**: You can confidently configure which runner config files must have their parent directories protected alongside the test suite files.
- **Lesson**: Security invariants should be anchored at the lowest possible layer of the execution stack.
