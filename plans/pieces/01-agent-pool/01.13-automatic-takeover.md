## Summary

Executes runtime-driven automatic takeover across every role upon confirmed quota exhaustion. Hooks the `agent/request-error` waterfall: on confirmed quota exhaustion, it marks the exhausted route unavailable, selects the next eligible model in that role's ordered fallback chain, and continues the exact same assignment without sending any error message to the user. The replacement model inherits role, task identity, piece specification, tool results, worktree, evidence, permissions, and remaining budget, resuming at a safe step boundary with zero duplicated side effects and no concurrent writers.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Intercept quota exhaustion in the `agent/request-error` waterfall to swap in the next fallback route and resume at the current step boundary without surfacing an error to the user.
- **Option B (Alternative)**: Abort the active step and raise a user-facing error dialog, requiring manual operator intervention or explicit restart.

## Behaviour

- **Given** an agent step encountering a confirmed quota exhaustion failure **When** the `agent/request-error` waterfall intercepts the failure **Then** the controller marks the route unavailable in the quota tracker, logs a takeover event, and selects the next eligible fallback model for that role.
- **Given** an active takeover operation **When** the replacement model takes over **Then** no user-facing failure message is emitted, and the agent continues the identical task assignment inheriting the worktree, tool results, and remaining budget.
- **Given** a scenario where all fallback models in the role pool are exhausted **When** takeover attempts failover **Then** the waterfall delegates to default failure handling, surfacing a terminal exhaustion alert.

## Harness fit

This is an `event/hook plugin` registering a scoped waterfall listener on `agent/request-error` (`packages/core/agent/src/runtime-types.ts:363`). It coordinates automatic recovery at durable agent step boundaries without requiring model intervention or re-prompting.

## Contracts

```typescript
import type { RequestErrorAction, Agent } from '@deepseek-ai/dsh-agent'
import type { LlmFailure } from '@deepseek-ai/dsh-llm'
import type { AgentPoolRole } from '@deepseek-ai/dsh-agent-pool-roles'

export interface TakeoverRecord {
  takeoverId: string
  sessionId: string
  role: AgentPoolRole
  exhaustedRoute: string
  replacementRoute: string
  turn: number
  step: number
  inheritedBudget: number
  timestamp: number
}

export interface AgentPoolTakeoverPlugin {
  handleRequestError(
    payload: { agent: Agent; turn: number; step: number; provider: string; failure: LlmFailure; signal: AbortSignal },
    next: () => Promise<RequestErrorAction>,
  ): Promise<RequestErrorAction>
}
```

## Teach me while you build

Fuhahaha! The Organization thought API exhaustion would collapse our operations into oblivion! But through Steins Gate, the worldline shifts seamlessly!

- **What it does**: Intercepts confirmed LLM quota exhaustion errors during turn execution and transparently swaps to the next eligible model in the role's fallback chain at a clean step boundary.
- **Background**: In agent loops, an LLM call error typically crashes the step or aborts the turn. Cordis waterfall events allow plugins to intercept failures and return `{ kind: 'retry' }` with altered provider bindings.
- **How it works here**: When `agent/request-error` fires, `handleRequestError` inspects the error via the classifier (`01.10`). If exhausted, it marks the route dead, asks the selector (`01.06`) for the next route, records a `TakeoverRecord`, updates provider bindings, and returns `{ kind: 'retry' }` to resume the step cleanly.
- **Why this approach**: Transparent retry inside the waterfall preserves the existing turn execution state, active worktree, and accumulated tool results without discarding in-flight progress or alerting the user.
- **Approaches considered**: Turn-level abort and restart (rejected: discards accumulated context and risks duplicate external side effects) vs Polling loop inside the provider adapter (rejected: blocks worker threads and obscures route exhaustion from session telemetry) vs Scoped waterfall interception (chosen).
- **Prior art inspected**: `packages/llm/llm-retry/src/index.ts:194-220`, inspecting `settleDownstream` and waterfall error recovery mechanics.
- **What we get for free**: Cordis waterfall ordering and `RequestErrorAction` semantics in `@deepseek-ai/dsh-agent` providing atomic step-level retries without agent loop modifications.
- **What to notice**: Notice that the replacement model must inherit the exact remaining token and step budget so a rogue fallback chain cannot exceed turn constraints.
- **Concepts to own**: Monotonic fallback transitions: failover progression can only advance down the preference ladder during an active turn, never cycle backward into exhausted endpoints.
- **Interview angle**: How do you guarantee idempotency during mid-turn LLM failovers? Answer: Resume at strict step boundaries where tool executions have already committed and cannot be re-invoked.
- **Decisions you can now make alone**: You can configure custom fallback ladders per role without touching the core agent runner.
- **Lesson**: The illusion of continuous execution is achieved by handling failure at the lowest reversible boundary before state mutations escape. El Psy Kongroo.
