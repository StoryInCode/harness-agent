## Summary

Hooks the `agent/request` waterfall on the agent loop to dynamically resolve and bind the active model call configuration (`LlmCallConfig`) for every conversation step. Inspects the agent's assigned role, active manual pins, and real-time route availability to select the primary eligible model preset, resolving credential references per call through `ctx.credentials`. Ensures that calls are directed exclusively to currently usable routes adhering to role boundaries.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Dynamically intercept `agent/request` per step, binding role-specific presets and resolving credentials ephemerally per call.
- **Option B (Alternative)**: Bind static model configurations at agent creation, preventing dynamic failover when routes exhaust mid-turn.

## Behaviour

- **Given** an agent dispatching a step with an assigned role or active manual pin **When** `agent/request` executes **Then** the router resolves and binds the primary eligible `LlmCallConfig` for that role, respecting manual pin overrides.
- **Given** an agent step where the primary route is exhausted **When** `agent/request` executes **Then** the router binds the next available eligible model in the role's fallback chain.
- **Given** a preset requiring credentials **When** routing the call **Then** the router resolves the `CredentialRef` via `ctx.credentials.resolve()`, passing the live key to the adapter without persisting it.

## Harness fit

This is an `event/hook plugin` registering a scoped listener on the `agent/request` waterfall (`packages/core/agent/src/runtime-types.ts:347`). It replaces static `LlmCallConfig` generation with role-pool-aware resolution before model execution occurs.

## Teach me while you build

Tutturu~ Every little helper in our lab has a special role to play! When an agent steps forward to work, Mayuri makes sure it receives just the right model preset and credentials for its outfit, without any secret keys leaking!

- **What it does**: Intercepts the agent loop's request waterfall to dress each agent step in the proper model configuration and credentials for its assigned role.
- **Background**: Agents in a team take on different roles (like Test Writer, Implementer, or Inspector). Rather than fixing a single model at agent boot, dynamic routing assigns the best available model for each turn.
- **How it works here**: An event/hook plugin attaches to the `agent/request` waterfall. For each step, it checks the agent's role and pins. It asks the selector for the best preset, resolves the credential reference with `ctx.credentials.resolve()`, and returns a tailored `LlmCallConfig`.
- **Why this approach**: Step-by-step waterfall interception ensures that if a model quota runs out mid-session, the next step seamlessly picks up an eligible fallback model without restarting the session.
- **Approaches considered**: Static model binding at session initialization (rejected: cannot adapt when routes exhaust during multi-turn workflows) vs Wrapping the LLM adapter with client proxies (rejected: bypasses Cordis waterfall semantics and loop logging) vs Dynamic `agent/request` waterfall hook (chosen).
- **Prior art inspected**: Express/Koa middleware pipelines and Cordis waterfall hook handlers.
- **What we get for free**: Ephemeral credential resolution via `packages/credentials/credentials/src/index.ts:183` and `LlmCallConfig` comparison helpers from `packages/llm/llm/src/call-config.ts:23-50`.
- **What to notice**: Notice that credentials are never stored in `LlmCallConfig` or persisted in session logs; they are passed only to the ephemeral adapter invocation.
- **Concepts to own**: Dynamic late-binding: deferring the selection and credential binding of a resource until the exact moment of execution.
- **Interview angle**: How do you implement dynamic model routing without leaking credentials into request history logs? Answer: Hook the request waterfall to inject credentials ephemerally at call dispatch and ensure config comparison objects only retain non-sensitive route metadata.
- **Decisions you can now make alone**: You can add custom temperature or sampling parameters per role without changing the underlying credential or selector logic.
- **Lesson**: When everyone has the right role and outfit, the whole lab works together happily and safely!
