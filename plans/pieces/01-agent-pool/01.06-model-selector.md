## Summary

Selects eligible agent presets for a requested role and job specification, evaluating candidates against quality floors, tool requirements, context bounds, spending limits, data policies, and real-time availability. Produces an ordered selection chain honoring established user preferences: Claude is the initial Brain, with OpenAI, Muse via Go, and GLM via subscription as the preferred fallback order; DeepSeek V4.1 via Go is the preferred candidate for Implementer. Dynamically filters out exhausted, degraded, or excluded presets.

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Ordered fallback candidate chain dynamically filtered by real-time availability, quality floors, context capacity, and user priority preferences.
- **Option B (Alternative)**: Static single-model binding that halts execution immediately on provider quota exhaustion without automatic failover to equivalent candidates.

## Behaviour

- **Given** a request to select a preset for `Brain` **When** evaluation executes **Then** Claude is selected as primary, followed in exact fallback order by OpenAI, Muse via Go, and GLM via subscription.
- **Given** a request to select an `Implementer` **When** evaluation executes **Then** DeepSeek V4.1 via Go is evaluated first and selected if available, adhering to Go access restrictions.
- **Given** a candidate preset that fails the role's quality floor or context requirement **When** filtering executes **Then** the candidate is marked ineligible and omitted from the chain.
- **Given** an active route whose status is `exhausted` **When** selection runs **Then** the selector skips it and promotes the next eligible fallback model in the chain.

## Harness fit

This is a `Service Provider` mounted on the host plane (`ctx.agentPoolSelector`) extending `@deepseek-ai/cordis.Service`. It replaces static model resolution with dynamic role-based candidate chains, interfacing with `ctx.agentDefaultModel` (`packages/core/agent-default-model/src/index.ts:16-73`).

## Contracts

```typescript
import type { AgentPoolRole } from '@deepseek-ai/dsh-agent-pool-roles'
import type { AgentPresetRecord } from '@deepseek-ai/dsh-agent-pool-store'

export interface JobRequirements {
  role: AgentPoolRole
  requiredTools?: readonly string[]
  minimumContext?: number
  allowPaidRoutes?: boolean
  maxCostPerToken?: number
}

export interface SelectionResult {
  primary: AgentPresetRecord
  fallbackChain: readonly AgentPresetRecord[]
  role: AgentPoolRole
  evaluatedCount: number
}

export interface AgentPoolSelectorService {
  selectForRole(requirements: JobRequirements): Promise<SelectionResult>
  getOrderedChain(role: AgentPoolRole): Promise<readonly AgentPresetRecord[]>
}
```

## Teach me while you build

The convergence of world lines is at hand! Even when a provider route crumbles under quota exhaustion, the ultimate model chain shall not falter!

- **What it does**: Dynamically resolves an ordered fallback chain of admissible models for any role and task requirements, bypassing exhausted endpoints.
- **Background**: If a primary LLM endpoint hits rate limits or token exhaustion mid-operation, the agent loop risks catastrophic failure unless an equivalent fallback can take over immediately.
- **How it works here**: The selector queries candidate presets from `01.04` and `01.05`, verifies quality floors and context tokens against `packages/llm/llm/src/types.ts:308-327`, and assembles an ordered chain.
- **Why this approach**: Pre-computing an ordered fallback chain allows instant zero-latency failover without repeatedly re-querying the whole catalog.
- **Approaches considered**: Hardcoded static model strings (rejected: fails on quota exhaustion) vs Random round-robin (rejected: ignores capability disparities and user preference order) vs Priority fallback chains with quality gates (chosen: resilient and policy-compliant).
- **Prior art inspected**: DNS MX record preference ordering and RFC 3484 default address selection algorithm.
- **What we get for free**: `ctx.agentDefaultModel` integration provides a unified fallback interface across the entire Cordis runtime.
- **What to notice**: Notice that exhausted models are skipped dynamically without mutating the underlying durable preset configuration.
- **Concepts to own**: Fault-Tolerant Failover: maintaining operational continuity across distributed provider failures through pre-sorted fallback hierarchies.
- **Interview angle**: How do you maintain high availability for LLM-powered systems when individual model providers experience transient 429 quota exhaustion? Answer: Maintain capability-tiered fallback chains sorted by quality floor and real-time availability.
- **Decisions you can now make alone**: You can customize fallback priority rankings for individual roles without risking quality degradation.
- **Lesson**: World lines may collapse when a provider quota runs dry, but our Reading Steiner guarantees seamless transition to the designated fallback world line! El Psy Kongroo!
