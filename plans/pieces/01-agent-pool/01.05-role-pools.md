## Summary

Defines the five functional role pools—Brain, Test Writer, Implementer, Reviewer, and Research/Utility—and enforces distinct accountability constraints, tool access, context thresholds, and quality floors for each. A single model may participate in multiple pools under role-tailored system instructions and tool permissions. Strictly bars unscored, unverified, or low-confidence models from automatic adoption into critical roles (Brain and Implementer).

### Human Decision Point: Option A vs Option B
- **Option A (Active)**: Dedicated role pools enforcing distinct quality floors, context token minimums, and strict tool permissions per execution dispatch.
- **Option B (Alternative)**: Flat single-pool model allocation where any discovered model can be assigned arbitrarily to critical roles without tool or quality gating.

## Behaviour

- **Given** an unscored candidate model **When** pool assignment runs **Then** the model is admitted only to Research/Utility and barred from Brain or Implementer with `UNSCORED_CRITICAL_ROLE_BLOCKED`.
- **Given** a preset configured for `Test Writer` **When** dispatched **Then** it receives test authoring tools and is barred from mutating production source files outside test suites.
- **Given** a preset configured for `Reviewer` **When** dispatched **Then** it is strictly restricted to read-only diff inspection tools without file edit capabilities.
- **Given** a single model assigned to both `Implementer` and `Reviewer` **When** dispatched for Reviewer **Then** it executes under the Reviewer's read-only permissions and distinct critique prompt.

## Harness fit

This is a `Service Provider` mounted on the host plane (`ctx.agentPoolRoles`) extending `@deepseek-ai/cordis.Service`. It maps role specifications to runtime subagent options and tool restrictions (`packages/core/agent/src/runtime-types.ts:26-36`), integrating with `@deepseek-ai/dsh-dev-loop-roles`.

## Contracts

```typescript
export type AgentPoolRole =
  | 'Brain'
  | 'Test Writer'
  | 'Implementer'
  | 'Reviewer'
  | 'Research/Utility'

export interface RoleRequirements {
  role: AgentPoolRole
  qualityFloor: number
  minimumContextTokens: number
  permittedTools: readonly string[]
  prohibitedTools: readonly string[]
  isCritical: boolean
  accountability: string
}

export interface RolePoolRoster {
  role: AgentPoolRole
  requirements: RoleRequirements
  presets: readonly string[]
}

export interface AgentPoolRolesService {
  getRequirements(role: AgentPoolRole): RoleRequirements
  getRoster(role: AgentPoolRole): Promise<RolePoolRoster>
  validatePresetForRole(presetId: string, role: AgentPoolRole): Promise<boolean>
}
```

## Teach me while you build

Tut-turii~! Welcome to the workshop! Making sure everyone has the right sewing needle for their cloth keeps our work beautiful and happy!

- **What it does**: Organizes models into five specialized role pools and ensures each role receives only appropriate tools and minimum context capabilities.
- **Background**: Models have different strengths. Putting an underpowered or unscored model in charge of planning or production code invites chaos for the team.
- **How it works here**: The service evaluates model metrics against `RoleRequirements` in `packages/core/agent/src/runtime-types.ts:26-36`, gating Brain and Implementer roles behind quality floors.
- **Why this approach**: Explicit role separation allows one versatile model to act as Implementer or Reviewer while strictly swapping its available tool set.
- **Approaches considered**: Unrestricted global model pool (rejected: risks allocating weak models to architecture or review) vs Hardcoded model-to-role bindings (rejected: inflexible when models update) vs Dynamic role rosters with accountability guards (chosen: flexible and safe).
- **Prior art inspected**: Role-Based Access Control (NIST RBAC model) and actor-model role specialization patterns.
- **What we get for free**: Subagent option filters and tool whitelists in Cordis agent runtime handle runtime permission enforcement.
- **What to notice**: Notice that Reviewer agents are denied edit tools completely; they can only observe and critique, protecting the mainline.
- **Concepts to own**: Role-Based Tool Scoping: granting tools based on the active role rather than the underlying model identity.
- **Interview angle**: How do you maintain safety when allowing one LLM to both write code and review pull requests? Answer: Partition execution contexts with distinct system prompts and enforce read-only tool sets during review passes.
- **Decisions you can now make alone**: You can tune the minimum quality floor or context token threshold for a role without rewriting agent prompts.
- **Lesson**: Tut-turii~! When every agent has a role suited to its talents and safe boundaries, the whole team works together in harmony!
